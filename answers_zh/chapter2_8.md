# 2.8 上下文加载与去重 — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 2 章：提示与上下文工程（Prompt & Context Engineering） · 共 20 题

**1. 上下文（Context）在 LLM 中的作用？**

<details>
<summary>💡 查看答案</summary>

上下文是每次向 LLM 发送请求时附带的所有文本内容，是模型"感知世界"的唯一信息来源。具体而言，上下文通常由以下几个部分构成：

- **System Prompt**：定义模型的角色、行为准则、输出格式等全局指令
- **历史对话**：多轮对话中已发生的 user/assistant 消息序列
- **检索文档**：通过 RAG 等机制动态注入的外部知识片段
- **工具定义**：描述模型可调用工具的 schema（函数名、参数、返回值格式）
- **结构化状态**：Agent 场景中的任务状态、中间结果等

模型在生成每一个 token 时，都基于整个上下文进行注意力计算，因此上下文的质量直接决定输出质量。上下文工程（Context Engineering）的核心目标是：**在有限的 token 预算内，最大化上下文的信息密度和相关性**。

一个常见的误区是"上下文越长越好"。实际上，冗余、无关的上下文不仅浪费 token 预算，还会分散模型注意力，导致关键信息被"稀释"，反而降低输出质量。因此，如何精心设计、动态裁剪上下文，是构建高质量 LLM 应用的核心工程挑战。

</details>

**2. 什么是 JIT（Just-In-Time）上下文加载？**

<details>
<summary>💡 查看答案</summary>

JIT 上下文加载（Just-In-Time Context Loading）是一种"按需、即时"地将信息注入上下文的策略，而非在请求开始前将所有可能用到的信息预先全部加载进 prompt。

这一概念类比于软件工程中的**懒加载（Lazy Loading）**：不在初始化时加载所有资源，而是在真正需要某段资源时才将其引入。具体到 LLM 场景：

- **传统预加载**：将完整的产品手册、用户历史、知识库全部塞入 prompt，不管当前 query 是否用得上
- **JIT 加载**：先理解用户意图，再精准检索当前 query 所需的那几段内容，只注入这些内容

JIT 的核心思想是：**信息在被需要的那一刻才出现在上下文中**。这样既节省了 token，又避免了无关信息对模型的干扰，是构建大规模、高效 LLM 应用的重要工程范式。



![MMR (最大边界相关性) 检索重排机制示意图](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter2/fig_mmr_concept.png)

</details>

**3. JIT 上下文加载和预加载（Eager Loading）各有什么优缺点？**

<details>
<summary>💡 查看答案</summary>

\begin{table}[h]



| **方式** | **优点** | **缺点** \\ \hline |
| --- | --- | --- |
| 预加载 | 实现简单，延迟低 | token 浪费，无关信息干扰模型 \\ \hline |
| JIT 加载 | token 高效，减少干扰 | 实现复杂，可能引入检索延迟 \\ \hline |


\end{table}

具体展开：

#### 预加载的适用场景与局限
预加载适合知识库小且内容固定的场景（如只有几十条 FAQ），此时将全部内容注入 prompt 代价可接受，且避免了检索环节可能出错的风险。但当知识库规模扩大到数万乃至数百万条时，预加载变得不可行——不仅 token 成本爆炸，模型在海量无关内容中提取关键信息的能力也会显著下降（即"Lost in the Middle"问题）。

#### JIT 加载的核心收益
JIT 方案在大规模场景下优势明显：每次请求只注入与当前 query 高度相关的少量片段（通常 Top-3 至 Top-10），既降低了 token 消耗，又让模型的注意力高度集中于相关内容。代价是需要引入检索模块（向量数据库、BM25 索引等），并承担额外的检索延迟（通常 50--300ms）。

对于知识库超大、但每次只需少量信息的场景（如企业知识库问答、客服机器人），JIT 明显优于预加载。

</details>

**4. JIT 上下文加载有哪些常见实现方式？**

<details>
<summary>💡 查看答案</summary>

1. **RAG（检索增强生成）**：最主流的 JIT 实现方式。对用户 query 做向量检索（或混合检索），从知识库中取 Top-K 相关片段注入上下文。检索质量直接决定 JIT 效果，因此 embedding 模型的选择和索引构建至关重要。

2. **Tool Call 按需拉取**：让模型通过工具调用主动请求信息（如查数据库、读文件、调 API）。模型自己决定需要哪些信息、何时获取，灵活性最高，但依赖模型的工具调用能力，且每次工具调用引入一次额外的网络/计算延迟。

3. **意图路由（Intent Routing）**：根据对用户意图的分类，动态决定注入哪个 system prompt 模块。例如，识别出用户问题属于"退款问题"时，才将退款政策模块注入 prompt；若属于"物流查询"，则注入物流模块。避免了将所有业务规则全量注入的浪费。

4. **延迟加载文档（Lazy Document Loading）**：将长文档拆分为固定大小的块（chunk），建立索引。检索时只召回命中的块，而非注入整篇文档。这是处理超长文档（如技术手册、合同文本）时的标准做法。

以上方式可以组合使用。例如，一个成熟的 Agent 系统可能同时使用 RAG 做知识检索、意图路由做 system prompt 动态组装、tool call 做实时数据拉取。

</details>

**5. 什么是上下文去重（Context Deduplication）？为什么需要它？**

<details>
<summary>💡 查看答案</summary>

上下文去重是指在构建 prompt 时，检测并移除重复或高度相似的内容片段，确保注入模型的每一段内容都提供增量信息价值。

#### 为什么需要去重？

- **RAG 场景下的多次命中**：同一段文本可能被多个不同 query 同时检索到（如一段核心政策描述在多个问题下都高度相关），不去重会导致该片段在上下文中重复出现。

- **多轮对话中的内容累积**：assistant 在上一轮的回复内容，有时会被下一轮重新注入（如某些框架将全部历史消息序列化后重新传入），导致相同信息反复出现。

- **Token 浪费**：重复内容直接占用宝贵的 token 预算，但不提供任何额外信息。在 128k token 的上下文窗口中，10% 的重复即意味着浪费约 12k token。

- **模型注意力偏差**：Transformer 的注意力机制对频繁出现的内容会分配更高权重。重复内容会人为放大该部分的影响，使模型输出向重复内容偏移，破坏生成的平衡性。

</details>

**6. 上下文去重有哪些常见策略？**

<details>
<summary>💡 查看答案</summary>

1. **精确去重（哈希匹配）**：对每个文本片段计算 MD5 或 SHA-256 哈希值，维护一个已有片段的哈希集合。每次加入新片段前查集合，若命中则直接丢弃。计算成本极低（O(1) 查找），适合处理完全相同的重复片段（如同一篇文档被检索两次）。

2. **语义去重（向量相似度）**：对片段计算 embedding 向量，通过余弦相似度判断语义相似程度。相似度超过阈值（如 0.95）的片段视为语义重复，保留相关性更高的一个。能处理"表述不同但含义相同"的情况，但计算成本高于哈希去重。

3. **段落合并**：对来自同一文档的相邻片段，检测其是否在原文中连续（通过位置索引判断），若连续则合并为一个完整段落，避免碎片化重复和边界信息丢失。

4. **对话级去重**：在多轮对话场景中，检测当前轮次注入的内容是否与历史消息高度重叠。例如，若用户在新消息中引用了 assistant 上一轮的完整回复，则无需再次注入该历史消息。

实践中，通常将精确去重作为第一道过滤（成本低、效果好），再对剩余片段做语义去重，形成两级去重流水线。

</details>

**7. RAG 中如何判断两个检索片段是否"语义重复"？**

<details>
<summary>💡 查看答案</summary>

语义重复判断的核心是向量相似度计算。实践中采用**贪心去重**流程：

\begin{lstlisting}[style=promptstyle]
	from sklearn.metrics.pairwise import cosine_similarity

	def is_duplicate(emb1, emb2, threshold=0.95):
	sim = cosine_similarity([emb1], [emb2])[0][0]
	return sim > threshold

	def greedy_dedup(chunks, embeddings, threshold=0.95):
	selected = []
	selected_embs = []
	for chunk, emb in zip(chunks, embeddings):
	if all(not is_duplicate(emb, s_emb, threshold)
	for s_emb in selected_embs):
	selected.append(chunk)
	selected_embs.append(emb)
	return selected
\end{lstlisting}

具体流程：将检索结果按相关性得分降序排列，依次遍历每个片段，加入前检查它与已选集合中所有片段的最大余弦相似度，超过阈值则跳过。这保证了最终选入上下文的片段集合中，任意两个片段之间的语义相似度均低于阈值。

阈值的选择需根据场景调整：
- **0.95 以上**：只去除几乎完全相同的片段，保留细微差异
- **0.85--0.95**：去除高度相似的片段，适合一般 RAG 场景
- **0.85 以下**：激进去重，可能损失有价值的补充信息，慎用

</details>

**8. MMR（Maximal Marginal Relevance）是什么？它如何解决去重问题？**

<details>
<summary>💡 查看答案</summary>

MMR 是一种在检索结果中同时平衡"相关性"和"多样性"的经典算法，每次从候选集中选取得分最高的片段加入结果集：

\begin{lstlisting}[style=promptstyle]
	MMR(d) = λ · sim(d, query) - (1-λ) · max sim(d, already_selected)
\end{lstlisting}

- **第一项** $\lambda \cdot sim(d, query)$：片段与原始 query 的相关性，越高越好
- **第二项** $(1-\lambda) \cdot \max sim(d, already_selected)$：片段与已选集合中最相似片段的相似度，作为惩罚项，越高代表越重复，得分越低
- **$\lambda$ 参数**：控制两者权重的平衡旋钮。$\lambda=1$ 退化为纯相关性排序（不去重）；$\lambda=0$ 退化为纯多样性选择（不考虑相关性）；实践中通常取 $\lambda \in [0.5, 0.7]$

相较于简单的贪心去重，MMR 的优势在于：去重的同时保留了多样性——不是简单丢弃相似片段，而是通过得分权衡，在相关性损失最小的前提下最大化内容多样性。例如，同一话题的两篇文章，如果一篇侧重优点、一篇侧重缺点，MMR 会倾向于同时保留两者，而非仅因相似度高就丢弃其中一篇。

</details>

**9. JIT 加载中，如何决定"什么时候"触发上下文加载？**

<details>
<summary>💡 查看答案</summary>

触发时机的选择直接影响系统的延迟和检索质量，常见策略如下：

- **每次请求前触发**：最简单直接的策略，每轮对话开始时都执行一次检索，将结果注入本轮上下文。实现无状态、易于维护，适合信息更新频繁或 query 变化大的场景。缺点是每轮都有检索开销。

- **意图变化时触发**：通过意图分类器或话题相似度检测，判断用户当前 query 的话题是否相对上一轮发生了显著变化。若话题连贯（如连续追问同一问题），则复用上一轮的检索结果；若话题切换，才重新触发检索。能有效减少重复检索开销。

- **模型主动触发（Tool Call）**：将检索能力封装为工具，让模型在生成过程中自主判断何时需要补充信息，通过工具调用主动拉取。灵活性最高，但对模型的工具调用能力要求较高，且可能引入多轮工具调用的累积延迟。

- **置信度触发**：对模型输出进行置信度评估（如通过自我评分或不确定性检测），若模型判断自身知识不足以回答当前问题，则触发补充检索并重新生成。适合对准确性要求极高的场景（如医疗、法律），但实现复杂且会增加整体响应时间。

生产中最常用的是"每次请求前 RAG 检索"，结合**查询缓存**（对相同或相似 query 的检索结果缓存一定时间）来避免重复检索，兼顾实时性和效率。

</details>

**10. 上下文去重后，如何处理被去除片段中可能包含的独特信息？**

<details>
<summary>💡 查看答案</summary>

去重并非简单地"丢弃相似内容"，需要防止有价值的独特信息随之流失：

1. **信息差异提取**：在判定两个片段为重复后，不直接丢弃，而是对比两者内容，提取差异部分（如不同的数据、不同的日期、补充的细节），将差异内容以简洁形式追加到保留片段之后。

2. **元数据独立保留**：即使两个片段正文内容高度相似，其元数据（来源、作者、发布时间、版本号）可能不同且有价值。去重时保留所有来源的元数据引用，使模型可以感知信息的多源性。

3. **场景自适应阈值**：对高风险场景（医疗诊断、法律条款、金融合规）将相似度阈值调高至 0.99，只去除几乎完全相同的内容，最大限度保留可能存在细微差异的片段；对低风险场景（通用知识问答）可使用较低阈值（0.85--0.90）以节省 token。

4. **软去重（降权而非丢弃）**：不完全丢弃高相似度片段，而是降低其在排序中的权重，使其在预算充足时仍能被纳入上下文，预算不足时才被优先裁剪。这是一种更温和的去重策略，在信息完整性和 token 效率之间取得平衡。

</details>

**11. 在 Agent 场景中，JIT 上下文加载如何与工具调用结合？**

<details>
<summary>💡 查看答案</summary>

在 Agent 架构中，工具调用天然是 JIT 加载的最佳载体——模型在推理过程中动态决定需要哪些信息，并主动发起工具调用来获取：

\begin{lstlisting}[style=promptstyle]
	User: 帮我分析最近三个月的销售数据，找出下滑最快的品类

	Agent Thought: 需要先获取销售数据，再进行统计分析
	Action: query_database(table="sales", date_range="last_3_months",
	group_by="category")
	Observation: [返回各品类销售数据]

	Agent Thought: 需要计算各品类环比变化率
	Action: calculate_trend(data=..., metric="mom_growth_rate")
	Observation: [返回趋势分析结果]

	Agent Final Answer: 根据数据，下滑最快的品类是...
\end{lstlisting}

这一模式的核心优势在于：
- **精准按需**：模型只拉取当前推理步骤真正需要的数据，而非预先加载整个数据库
- **动态上下文构建**：每次工具调用的返回结果动态追加到上下文，形成推理链，支持多步骤复杂任务
- **外部系统集成**：通过工具调用，JIT 加载的信息来源可以扩展到任意外部系统（数据库、API、文件系统），而不局限于预构建的向量索引

工程实现时需注意：多次工具调用的累积延迟可能显著，应对频繁访问的工具结果做本地缓存，并设置最大工具调用次数限制，防止推理陷入无限循环。

</details>

**12. 如何衡量 JIT 加载的效果？**

<details>
<summary>💡 查看答案</summary>

完整的 JIT 效果评估体系应涵盖效率、质量、可靠性三个维度：

- **Token 节省率**：$\frac{预加载 token 数 - JIT token 数}{预加载 token 数}$，直接衡量 JIT 的资源效率，通常期望达到 50%--80%

- **检索延迟**：JIT 引入的额外检索时间，关注 P50（中位数延迟）和 P95（长尾延迟）。P95 延迟过高会影响用户体验，通常期望 P95 < 500ms

- **任务准确率**：与预加载方案对比，在相同测试集上的回答准确率。JIT 方案的准确率不应显著低于预加载（通常允许 ±2% 以内的波动）

- **召回率（Recall）**：JIT 方案是否遗漏了任务所需的关键信息。可通过构造"关键信息必须来自特定文档"的测试案例，检验检索模块是否成功召回

- **上下文利用率**：注入的上下文中，实际被模型引用（可通过引用来源追踪或注意力权重分析）的比例。利用率低说明检索精度不足，注入了过多无关内容

</details>

**13. 上下文窗口利用率低是什么原因？如何通过 JIT 和去重解决？**

<details>
<summary>💡 查看答案</summary>

#### 低利用率的根本原因
- **无关内容注入**：检索精度不足，召回了大量与 query 相关性低的文档片段
- **重复内容堆积**：多次检索命中同一片段，或历史对话中相同信息反复出现
- **System Prompt 臃肿**：将所有业务规则、边界情况都写入静态 system prompt，而大多数规则在当前 query 下并不需要
- **粗粒度文档切分**：检索单元（chunk）过大，命中一个 chunk 但只有其中一小段与 query 相关，其余内容都是"搭便车"的冗余

#### 解决方案
- **JIT 精准检索**：优化 embedding 模型和检索策略，提高召回片段的相关性，从根源减少无关内容注入

- **去重流水线**：引入哈希去重 + 语义去重两级过滤，清除冗余内容，让每个 token 都承载独特信息

- **模块化 System Prompt**：将 system prompt 拆分为多个功能模块，根据意图路由动态组装，每次只注入当前 query 需要的模块

- **内容压缩**：对长文档先做摘要，用摘要替代原始全文注入。若模型判断摘要信息不够，再通过 tool call 拉取原文特定段落

- **细粒度切分**：将文档切分粒度调小（如 256 token 每块），配合句子级别的 embedding，提高检索的精准度，减少"搭便车"内容

</details>

**14. 如何防止 JIT 检索引入的上下文与对话历史产生矛盾？**

<details>
<summary>💡 查看答案</summary>

JIT 检索可能引入过时或与用户陈述不一致的文档，需要系统性的矛盾预防和处理机制：

1. **文档时效过滤**：在检索阶段加入时间维度的过滤条件，优先召回最新版本的文档（如"只检索 30 天内更新的内容"），从源头避免过时信息进入上下文。

2. **优先级声明**：在 system prompt 中明确信息优先级规则，例如："若检索到的参考文档与用户在本次对话中明确陈述的事实存在冲突，以用户陈述为准；若文档内部存在版本冲突，以发布时间最新的为准。"

3. **显式来源标注**：在注入每个检索片段时，附带来源信息和更新时间（如"[来源：产品手册 v2.3，更新于 2024-11]"），让模型在生成时能感知信息的时效性，并在必要时向用户说明文档可能过时。

4. **注入前一致性校验**：在将检索结果注入上下文前，通过规则或轻量级模型快速检查其与当前对话历史是否存在明显矛盾（如数值冲突、事实对立）。若检测到矛盾，优先提示用户确认，而非直接注入可能误导模型的冲突信息。

</details>

**15. 大规模 RAG 系统中，上下文去重的性能瓶颈在哪里？如何优化？**

<details>
<summary>💡 查看答案</summary>

#### 性能瓶颈
语义去重的核心瓶颈在于相似度计算的复杂度：对 $n$ 个候选片段做两两相似度比较，复杂度为 $O(n^2)$。当每次请求的候选片段数较少（如 Top-20）时影响不大，但在离线去重整个语料库（数百万片段）时，$O(n^2)$ 复杂度完全不可行。此外，为每个片段计算 embedding 本身也有一定的推理成本。

#### 优化方案

- **局部敏感哈希（LSH，Locality Sensitive Hashing）**：将高维 embedding 向量通过哈希函数映射到低维桶（bucket），相似向量大概率落入同一桶。只对同桶内的片段做精确相似度计算，将整体复杂度从 $O(n^2)$ 降至接近 $O(n)$，以少量精度损失换取数量级的性能提升。

- **离线预聚类去重**：在构建知识库时（离线阶段）对全量语料做聚类，将语义相近的文档归入同一簇，并在簇内提前完成去重。在线检索时，直接从已去重的语料库中召回结果，无需在线去重，彻底消除在线去重开销。

- **两级过滤流水线**：先用哈希精确去重（$O(1)$ 查找，成本极低）处理完全相同的片段，再对通过精确去重的片段子集做语义去重。由于精确重复通常占比较高，第二级语义去重的候选集规模大幅缩小，整体耗时显著降低。

- **在线去重候选集限制**：在实时 RAG 请求中，只对 Top-K 检索结果（如 Top-20）做语义去重，而不是对全量索引做去重。Top-20 的两两比较只有 190 次，完全可以在毫秒级完成，不会成为性能瓶颈。

</details>

**16. JIT 加载失败（检索到无关内容）时，模型应该如何表现？如何设计兜底机制？**

<details>
<summary>💡 查看答案</summary>

#### 失败场景的识别
检索失败通常表现为：向量检索返回的 Top-K 结果与 query 的相关性得分均低于预设阈值（如余弦相似度 < 0.6），说明知识库中不存在与当前 query 匹配的内容。

#### 兜底机制设计
1. **相关性阈值过滤**：为每个检索片段设定最低相关性准入门槛，低于阈值的片段一律不注入上下文，宁缺毋滥。这避免了"注入无关内容反而误导模型"的情况，比强行注入低质量内容更好。

2. **模型行为显式声明**：在 system prompt 中预先声明检索失败时的行为准则，例如："若提供的参考资料不足以支撑回答，请直接告知用户'暂无相关资料'，不要基于参考资料之外的内容编造答案。"这将兜底行为内化为模型的指令遵循，而非依赖模型自发判断。

3. **多路检索提升召回**：同时使用**关键词检索（BM25）**和**向量语义检索**两条并行检索通道，取两者结果的并集后再做去重和相关性过滤。两者互补：BM25 擅长精确关键词匹配（应对专有名词、代码等），向量检索擅长语义理解（应对同义词、泛化表达），混合召回能显著降低检索失败率。

4. **优雅降级策略**：当检索确实失败且无法召回有效内容时，系统回退到模型自身参数知识进行回答，并在回复中明确标注："未找到相关文档，以下回答基于模型通用知识，请注意核实。"这保证了系统在知识库缺失的边界情况下仍能提供有价值的响应，而不是直接报错或返回空回复。

</details>

**17. 如何设计一个"上下文预算分配"系统，合理分配 JIT 加载的 token 配额？**

<details>
<summary>💡 查看答案</summary>

上下文预算分配是将有限的 token 窗口按优先级和用途进行精细化管理的工程系统。以 128k token 窗口为例：

\begin{lstlisting}[style=promptstyle]
	总预算：128k tokens
	├── System Prompt：固定 2k（角色定义、行为准则、格式规范）
	├── 对话历史：动态，最多 20k（滚动摘要管理，超出时压缩早期历史）
	├── 检索文档：动态，最多 60k（JIT 分配）
	│   ├── 核心相关片段：40k（高优先级，直接回答 query 所需）
	│   └── 补充上下文：20k（低优先级，背景知识，预算不足时舍弃）
	├── 结构化状态：固定 1k（Agent 任务状态、变量等）
	└── 输出预留：45k（为模型生成留足空间）
\end{lstlisting}

#### 实现要点

- **优先级顺序填充**：按 System Prompt $\to$ 结构化状态 $\to$ 对话历史 $\to$ 核心检索片段 $\to$ 补充上下文的顺序依次填充，超出总预算时从最低优先级开始裁剪

- **对话历史滚动压缩**：当历史消息超出分配配额时，对早期历史做递进式摘要（Progressive Summarization）：先将最早的 N 轮压缩为一段摘要，释放 token 空间用于新消息

- **动态预算调整**：根据任务类型动态调整各模块配额。例如，分析型任务需要更多检索文档空间；创作型任务输出更长，需要为生成预留更多 token

- **预算感知检索**：在 JIT 检索阶段即感知当前剩余预算，动态调整召回片段数量（如当前可用 token 为 30k 时，只召回约 30k token 的内容，而非固定 Top-K 再截断）

</details>

**18. 上下文去重与信息多样性之间如何平衡？**

<details>
<summary>💡 查看答案</summary>

去重过激会损失多角度信息，去重不足则浪费 token，平衡两者需要细粒度的策略设计：

- **分层去重策略**：对**同一来源**的内容使用严格阈值（如 0.90），重点避免同一文档被多次注入；对**不同来源**的内容使用宽松阈值（如 0.97），保留不同作者、不同机构对同一话题的差异视角。

- **观点多样性保护**：对于意见类、评价类内容，在相似度计算之外引入情感/立场分析。即使两篇文章文本相似度较高（如都在讨论某项政策），若情感倾向或核心立场不同（一篇支持、一篇反对），则强制保留两者，不触发去重。

- **主题覆盖完整性校验**：去重完成后，对最终入选片段做主题覆盖检查——提取原始 Top-K 结果的主要话题簇，验证去重后的结果集是否仍覆盖所有话题簇。若某个话题簇的内容被全部去重移除，则从该簇中强制保留相关性最高的一个片段。

- **用户可控去重强度**：对外暴露 `dedup_threshold` 参数，允许调用方根据具体业务场景调整去重激进程度。高准确性场景（如医疗、法律）可设置较高阈值（保留更多内容），高效率场景（如通用问答）可设置较低阈值（激进去重）。

</details>

**19. 流式输出（Streaming）场景下，JIT 上下文加载如何处理？**

<details>
<summary>💡 查看答案</summary>

流式输出要求第一个 token 尽快出现（低首字节延迟），而 JIT 检索需要在生成前完成，两者存在天然的延迟矛盾。主要解决方案：

- **并行预检索**：当用户正在输入时（检测到用户停止打字的瞬间），立即触发基于当前输入的预检索，与用户的"提交思考时间"并行执行。用户点击发送时，检索结果可能已经就绪，从而将检索延迟隐藏在用户交互延迟内。

- **投机性预加载（Speculative Loading）**：基于对话历史预测用户最可能的下一个话题或 query，提前触发相关内容的检索并缓存结果。若预测命中，用户提问时可直接使用缓存的检索结果，检索延迟为零。

- **分阶段生成**：将生成过程拆分为两个阶段——第一阶段基于模型自身参数知识快速生成初步回答（极低延迟，立即开始流式输出）；第二阶段检索完成后，生成引用注解和来源标注，以增量方式追加到第一阶段输出后面。适合对首字节延迟极度敏感的场景。

- **流式检索与增量生成**：检索系统返回第一个高置信度片段时即开始生成，后续检索到的片段动态追加到上下文中，影响后续 token 的生成。这需要特殊的推理框架支持增量上下文更新，实现复杂度较高，但能同时兼顾低延迟和高质量。

</details>

**20. 在多模态场景（图文混合）中，JIT 上下文加载和去重有哪些特殊挑战？**

<details>
<summary>💡 查看答案</summary>

多模态场景在 JIT 加载和去重上面临文本场景所没有的特殊困难：

#### 主要挑战
- **图片 token 消耗高**：一张中等分辨率图片可能占用 1000--2000 tokens（取决于模型的视觉编码策略），是文本片段的数倍乃至数十倍。若预加载所有相关图片，token 预算会被迅速耗尽，JIT 加载在多模态场景下尤为关键。

- **跨模态语义去重困难**：一张产品图和一段描述该产品的文字，语义高度重叠，但无法用文本哈希或纯文本 embedding 检测到这种重叠。需要跨模态 embedding 模型（如 CLIP）将图文映射到统一向量空间，才能进行跨模态相似度计算。

- **检索粒度不对等**：文本可以按句子、段落做细粒度切分，但图片是不可分割的整体。文本可以只注入一个段落，图片只能全量注入，导致检索粒度存在根本性不对等。

- **多模态相关性判断复杂**：当用户 query 本身是图文混合时（如上传一张图并附文字说明），相关性判断需要理解图文联合语义，单模态检索模型无法胜任，需要多模态检索模型。

#### 解决思路
- **图片文本化代理检索**：为每张图片生成高质量文本描述（caption 或 alt text），用文本描述建立检索索引。JIT 检索时先通过文本索引定位相关图片，确认相关后再将原图注入上下文。这将多模态检索问题转化为文本检索问题，复用成熟的文本 JIT 基础设施。

- **统一多模态向量空间**：使用 CLIP 或类似的多模态 embedding 模型，将图片和文本映射到同一向量空间，支持"文字 query 检索图片"和"跨模态去重"（检测图片与描述它的文字之间的语义重叠），从根本上解决跨模态相似度计算问题。

</details>
