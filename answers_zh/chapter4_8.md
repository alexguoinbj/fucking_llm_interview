# 4.8 SFT 微调实践 — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 4 章：微调（Fine-Tuning） · 共 12 题

**1. SFT Packing 是什么？**

<details>
<summary>💡 查看答案</summary>

SFT Packing（Supervised Fine-Tuning Packing）是一种在监督微调阶段高效利用计算资源的技术，其核心思想是通过将多个训练样本（尤其是短文本）拼接（pack）成一个连续的序列，从而减少传统填充（padding）带来的计算浪费。

**直接拼接**：将多个样本直接连接，中间添加分隔符（如 `<eos>`），例如样本 A（“Hello”）和样本 B（“How are you?”）拼接为 `Hello<eos>How are you?<eos>`。

**优点**：计算零浪费，无 padding，所有 token 均有效；与预训练一致性，预训练时模型通常也处理连续文本。

**潜在噪声**：模型可能学到样本间的虚假关联，但实际影响较小。

![SFT 数据处理中 Padding 填充与 Packing 打包技术对比](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter4/fig_padding_vs_packing.png)

</details>

**2. SFT Packing 对 SFT 训练的影响是什么？**

<details>
<summary>💡 查看答案</summary>

通过打包技术，训练效率得以提升。该技术可将若干较短的训练样本整合至单一序列中，优化 GPU 使用效率，减少 padding 浪费。但也可能引发潜在的注意力交互问题，例如不同样本之间可能出现意外的注意力交互，尤其在注意力掩码未正确设置时可能导致信息泄露。

实验发现：当数据量较少或面对特定复杂任务时，SFT packing 会对泛化能力产生负面影响；而在大规模数据场景下则不会造成损害。

</details>

**3. 为什么 SFT 之后感觉 LLM 变"傻"了？**

<details>
<summary>💡 查看答案</summary>

在进行监督微调（SFT）后，有时会发现语言模型的性能下降或出现"傻"的行为，原因可能包括：
1. **数据偏差**：SFT 使用的数据集可能与模型预训练阶段的数据分布不同，如果两者差异较大，模型在新任务上可能表现不佳。
2. **标注错误**：微调数据集的标注可能存在错误或不准确，这会对模型性能产生负面影响。
3. **过拟合**：如果微调数据集较小，或者模型参数过多，模型可能会过拟合，导致在新输入上表现不佳。
4. **数据缺乏多样性**：微调数据集可能无法涵盖模型在新任务中可能遇到的各种输入情况。

</details>

**4. 微调大型模型时应该选择和优化哪些超参？**

<details>
<summary>💡 查看答案</summary>

在对大型模型进行调整时，通常不需要对超参数进行大幅度的调整：
- 显存大小是决定 batch size 的关键因素，context length 一般建议设置为 2048 或更高；
- 学习率一般推荐采用 cosine 退火策略，并根据 batch size 进行适当调整；
- 对梯度进行裁剪时，通常将阈值设置在 0.3 左右，weight decay 的值可以选择 0.1 或 0；
- 除上述参数外，其他参数一般无需进行调整。

</details>

**5. 微调大模型时，如果 batch size 设置太小会出现什么问题？**

<details>
<summary>💡 查看答案</summary>

当 batch size 较小时，梯度更新的方向会具有较高的方差，导致更新主要由噪声驱动。虽然经过多次更新后，方差会相互抵消，推动模型朝着正确方向前进，但个别更新可能无效。相比之下，使用更大的 batch size 可以更有效地进行更新。

</details>

**6. 微调大模型时，如果 batch size 设置太大会出现什么问题？**

<details>
<summary>💡 查看答案</summary>

当 batch size 非常大时，从训练数据中抽取的任何两组数据会非常相似，因为它们几乎完全匹配真实梯度。在这种情况下，增加 batch size 几乎不会改善性能。此外，虽然使用更大的 batch size 可以减少训练步数，但总体训练时间几乎没有改善，同时计算资源的消耗会显著增加。Google 的研究表明，在固定的 epoch 预算下，当 batch size 超过某个临界值时，模型性能会随着 batch size 的增加而下降。

</details>

**7. 微调大模型时，优化器如何选择？**

<details>
<summary>💡 查看答案</summary>

除了常用的 Adam 和 AdamW，其他优化器如 Sophia 也值得研究。Sophia 使用梯度曲率而非方差进行归一化，可能提高训练效率和模型性能。

</details>

**8. 微调大模型的一些实验设置？**

<details>
<summary>💡 查看答案</summary>

- **模型结构**：采用 Causal Decoder + LM，具有良好的 zero-shot 和 few-shot 能力，能产生涌现效应。
- **Layer normalization**：使用 Pre RMS Norm。
- **激活函数**：推荐使用 GeGLU 或 SwiGLU。
- **Embedding 层**：Embedding 层后不添加 Layer Normalization，以免影响 LLM 性能。
- **位置编码**：使用 ROPE 或 ALiBi，其中 ROPE 更为广泛。

</details>

**9. 微调过程中 loss 异常升高如何解决？**

<details>
<summary>💡 查看答案</summary>

在预训练过程中，loss 的异常升高往往难以直接定位原因，可能需要通过调整学习率或引入正则化项来解决。微调阶段如果遇到 loss 异常升高，可能是由于数据量不足导致的，建议采用成熟的框架，并对学习率和梯度裁剪值进行适当调整。

</details>

**10. 如何预防或减轻微调过程中的过拟合现象？**

<details>
<summary>💡 查看答案</summary>

为预防或减轻过拟合，建议在数据去重后选择大型模型，并仅训练一个 epoch。对于大型模型而言，通常不需要担心过拟合问题，如果出现过拟合，可以尝试使用不同的数据格式或增加更多高质量数据。

</details>

**11. 长文本微调需要注意哪些问题？**

<details>
<summary>💡 查看答案</summary>

长文本微调需要注意以下问题：

**1. 显存与计算开销**：Attention 计算复杂度随序列长度呈平方级增长，需要结合激活重计算（gradient checkpointing）、FlashAttention 等高效 Attention 实现。

**2. 位置编码的外推问题**：模型在预训练阶段通常在固定的最大长度下训练，如果微调时需要处理超出预训练长度的序列，位置编码可能表现下降。常见解决方法包括位置编码插值（Position Interpolation）和调整 RoPE 的 base 频率参数（NTK-aware scaling、YaRN 等）。

**3. 训练数据的长度分布**：微调数据中需要包含足够数量和比例的长文本样本；注意避免大量 padding 造成计算浪费。

**4. "大海捞针"（Needle in a Haystack）类能力**：微调数据设计中可以有意识地构造"关键信息分布在文本不同位置"的样本，提升模型对长文本各位置信息的均衡利用能力。

</details>

**12. 在 Llama-3 70B 开源模型基础上，如何微调模型以使其输出风格更简洁、更像微信聊天，并保证输出的内容符合中国的大模型安全要求？**

<details>
<summary>💡 查看答案</summary>

这是一个"风格迁移 + 安全合规"的双重目标微调任务：

**1. 数据构建**：

*风格数据*：收集符合"微信聊天"风格的对话样本（短句、口语化、分段发送），通过 LLM 将现有长回复风格改写为简洁口语化版本。

*安全合规数据*：构建覆盖各类敏感话题的拒绝/正确引导样本（政治敏感、暴力、色情、违法犯罪等），覆盖直接请求和"伪装/绕过"式请求。

**2. 训练策略**：将"风格化的常规任务数据"和"安全合规数据"按一定比例混合进行 SFT；使用 QLoRA 等方法在可接受的硬件资源下完成微调；注意不要因为风格数据中包含大量"随意"的聊天内容而削弱模型对敏感请求的拒绝倾向。

**3. 评估**：风格评估（平均回复长度、句子数量分布、LLM-as-Judge）；安全评估（中文安全评测集 + 越狱测试）。

</details>
