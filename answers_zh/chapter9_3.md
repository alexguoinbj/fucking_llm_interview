# 9.3 AI Coding 的 Agent 设计 — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 9 章：AI Coding · 共 25 题

**1. AI Coding 场景下的 Agent 应该如何设计？**

<details>
<summary>💡 查看答案</summary>

通常以"理解任务—探索代码库—制定修改计划—执行修改—运行测试验证—根据结果迭代"的循环为核心，关键在于能够利用真实的执行反馈（编译/测试结果）作为修正依据。

</details>

**2. Agent 的工具调用（Tool Use）接口应该如何设计？**

<details>
<summary>💡 查看答案</summary>

工具接口应该职责单一、语义清晰（如"读文件""写文件""运行命令""搜索代码"分别独立），并提供结构化的返回结果（而非纯文本）便于模型稳定解析，同时要为每个工具设计合理的错误反馈格式，让模型能根据失败原因调整下一步行动。

</details>

**3. Agent 如何判断一个任务已经完成？**

<details>
<summary>💡 查看答案</summary>

通常依赖客观可验证的信号（如相关测试全部通过、编译无报错）而非模型主观判断"感觉做完了"，对于缺乏自动化验证手段的任务，可以要求模型显式列出验收标准并逐项自查，或引入人工确认作为最终判定环节。

</details>

**4. Agent 如何避免陷入"死循环"（反复修改又反复出错）？**

<details>
<summary>💡 查看答案</summary>

需要设置最大迭代次数或时间预算的硬性上限，并在每次修改后检测状态是否相比上一轮有实质性改善（如失败的测试数量是否减少），如果连续多轮没有改善或出现反复横跳（改了又改回去），应主动中止并转交人工介入而非无限重试。

</details>

**5. 如何为 Agent 设计合理的"停止条件"，避免过度修改？**

<details>
<summary>💡 查看答案</summary>

停止条件应该同时包含"正向完成信号"（任务目标达成、测试通过）和"负向保护信号"（修改范围超出预期文件数、连续多轮无进展），二者缺一不可——只有完成信号容易导致 Agent 在无法达成目标时无限尝试，只有保护信号则可能过早中止本可完成的任务。

</details>

**6. Agent 执行失败后应该如何重试或降级？**

<details>
<summary>💡 查看答案</summary>

应先分析失败原因（环境问题、理解偏差、任务本身超出能力范围）再决定策略：环境类问题可以直接重试；理解偏差应该重新规划而非简单重复上一次的操作；确认超出当前能力范围时应该主动降级为"给出建议但不自动执行"，交还决策权给人。

</details>

**7. Agent 的错误处理和异常捕获机制应该如何设计？**

<details>
<summary>💡 查看答案</summary>

需要区分"预期内的失败"（如测试未通过，属于正常迭代信号）和"意外的系统性错误"（如工具调用崩溃、权限不足），前者应作为反馈继续驱动 Agent 迭代，后者应该立即中止当前任务并明确报告给用户，避免 Agent 在异常状态下继续做出不可预期的操作。

</details>

**8. AI Coding 场景下 Memory 应该如何设计？**

<details>
<summary>💡 查看答案</summary>

记忆应包括：项目的架构约定和编码规范、历史修改记录及其原因、之前遇到的坑和解决方案，便于在后续任务中复用这些项目特定知识。

</details>

**9. Agent 的记忆机制如何处理更新和过期问题？**

<details>
<summary>💡 查看答案</summary>

项目规范和最佳实践会随时间演变，过时的记忆如果不及时修正反而会误导后续任务的执行，因此需要为记忆条目附加时间戳或版本标记，并在检测到相关代码/规范已发生变化时主动标记旧记忆失效或触发重新总结，而非让记忆无限期累积。

</details>

**10. Agent 的记忆应该分为短期记忆和长期记忆吗，分别如何管理？**

<details>
<summary>💡 查看答案</summary>

短期记忆对应单次任务执行过程中的中间状态（已探索的文件、已尝试的方案），任务结束后可以清空或归档；长期记忆对应跨任务持久保留的项目知识（架构约定、历史踩坑经验），需要单独存储并在新任务开始时按需检索加载，两者的更新频率和生命周期完全不同，不能混为一谈。

</details>

**11. 长时间运行任务中，如何管理和压缩中间状态/上下文？**

<details>
<summary>💡 查看答案</summary>

可以周期性地对已完成步骤的详细过程做摘要压缩，只保留结论性信息（做了什么改动、验证结果如何）而丢弃过程细节，避免上下文随着任务推进无限膨胀直至超出窗口限制，同时摘要机制本身要注意不能丢失后续步骤依赖的关键信息。

</details>

**12. Agent 自主运行时间过长会带来哪些风险？**

<details>
<summary>💡 查看答案</summary>

包括错误累积和放大（早期一个小的理解偏差可能在后续步骤中被不断放大）、修改范围失控（偏离最初任务意图）、以及资源和成本消耗过高，这也是为什么长时间自主运行的任务通常需要设置阶段性检查点而非完全放手不管。

</details>

**13. AI Coding 中的规划应该如何做？**

<details>
<summary>💡 查看答案</summary>

规划应基于对代码库现状的探索结果（而非凭空假设），明确需要修改/新增哪些文件、修改的大致内容和顺序，并考虑修改对其他模块的潜在影响。

</details>

**14. Agent 如何平衡探索成本（读取过多文件）和执行效率？**

<details>
<summary>💡 查看答案</summary>

可以采用"渐进式探索"策略——先基于任务描述做粗粒度的相关性判断，只深入读取高相关度的文件，执行过程中如果发现信息不足再按需补充探索，而不是一次性读取整个代码库；同时可以复用之前任务积累的仓库结构认知，减少重复探索的开销。

</details>

**15. Sub-agent/子任务拆分的粒度应该如何把握？**

<details>
<summary>💡 查看答案</summary>

拆分粒度应该以"可独立验证"为标准——每个子任务最好对应一个可以单独测试或检查结果的最小单元，粒度过粗会导致子任务内部依然存在复杂的多步决策难以把控，粒度过细则会引入过多的协调开销和上下文传递成本。

</details>

**16. 多 Agent 协作模式（Orchestrator + Worker）在编码场景下如何拆分职责？**

<details>
<summary>💡 查看答案</summary>

Orchestrator 负责理解整体任务、拆分子任务并汇总各 Worker 的执行结果，Worker 负责具体执行某个边界清晰的子任务（如"实现某个函数""修复某个测试失败"），这种分工使得复杂任务的规划能力和具体执行能力可以分别优化，但也需要设计好子任务间的依赖顺序和结果整合机制。

</details>

**17. AI 如何处理跨多文件的代码修改？**

<details>
<summary>💡 查看答案</summary>

需要先识别出本次修改涉及的所有相关文件及其依赖关系，规划修改顺序（如先改接口定义再改调用处），并在修改后检查各文件间的一致性。

</details>

**18. AI Coding 中 Agent 如何理解并遵循项目特定的编码规范（如 Linter 规则）？**

<details>
<summary>💡 查看答案</summary>

可以在任务执行前主动读取项目中的规范配置文件（如 ESLint、Prettier 配置）和已有代码的风格特征作为约束条件，并在生成修改后调用对应的静态检查工具做验证，将规范检查作为执行反馈闭环的一部分而非仅依赖模型"记住"规范。

</details>

**19. AI Coding 中如何做版本管理？**

<details>
<summary>💡 查看答案</summary>

AI 的修改应遵循正常的版本控制流程（分支、提交、PR），每次修改对应清晰的提交记录和说明，便于追溯和必要时的回滚。

</details>

**20. AI Coding 中如何实现修改的回滚？**

<details>
<summary>💡 查看答案</summary>

依赖版本控制系统（如 Git）作为天然的回滚机制——每次 AI 修改前确保有清晰的版本快照，修改出现问题时可以方便地回退到之前的提交。

</details>

**21. 多步骤任务中，Agent 如何做检查点（Checkpoint）恢复？**

<details>
<summary>💡 查看答案</summary>

可以在每个关键步骤完成后保存当前的代码状态和任务进度快照，当后续步骤出现问题或需要中断恢复时，可以从最近一个稳定的检查点重新开始，而不必从头重新执行整个任务，既节省成本也降低了因中途失败导致状态混乱的风险。

</details>

**22. 哪些操作必须引入人工确认（Human-in-the-Loop）？**

<details>
<summary>💡 查看答案</summary>

通常是不可逆或影响范围大的操作，例如删除文件、修改数据库 schema、直接推送到主分支、涉及权限或安全配置的改动，这类操作即使 Agent 有能力自主完成，也应该在执行前暂停并等待人工明确批准。

</details>

**23. Agent 执行代码时的沙箱隔离与权限控制如何设计？**

<details>
<summary>💡 查看答案</summary>

应该让 Agent 在与生产环境隔离的沙箱/容器中执行命令和测试，限制其网络访问和文件系统权限范围（如仅能读写指定项目目录），避免因模型的意外行为（如误删文件、执行危险命令）对真实环境造成不可恢复的影响。

</details>

**24. Agent 在执行破坏性操作（如删除文件）前应该如何设计保护机制？**

<details>
<summary>💡 查看答案</summary>

除了前置的人工确认外，还可以结合版本控制自动创建快照、对高风险操作设置白名单/黑名单规则、以及要求 Agent 在执行前显式说明操作的影响范围，多层防护共同降低破坏性操作造成不可逆损失的概率。

</details>

**25. Agent 如何与人类协作完成一个复杂需求（而非全自动）？**

<details>
<summary>💡 查看答案</summary>

可以将任务拆解为"Agent 提议方案—人工审阅调整—Agent 执行—人工验收"的迭代循环，在关键决策节点（如架构选型、影响范围较大的改动）保留人工判断，而把机械性、可验证的执行环节交给 Agent 自主完成，兼顾效率和可控性。

</details>
