# 7.9 RAG 评估（RAGAS、忠实度、相关性） — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 7 章：RAG（检索增强生成） · 共 19 题

**1. 用于评估 RAG 系统的指标有哪些？**

<details>
<summary>💡 查看答案</summary>

RAG 系统的评估需要覆盖检索、生成和系统三个层面，单一指标无法全面衡量系统质量：

**检索层指标**（衡量"找得对不对、全不全"）：
- **Hit Rate@k**：top-k 结果中至少有一个正确文档的查询比例，是最基础的召回指标；
- **MRR（Mean Reciprocal Rank）**：第一个正确文档在排名中倒数的均值，衡量精确排序能力；
- **NDCG@k**：综合考虑相关性等级和排名的标准化折现累积增益，最全面的检索质量指标；
- **Context Precision / Context Recall**：RAGAS 框架中的检索精确率和召回率，无需人工标注正确文档即可自动计算。

**生成层指标**（衡量"答案准不准、可不可信"）：
- **Faithfulness（忠实度）**：答案中的陈述是否都有检索文档支撑，衡量幻觉程度；
- **Answer Relevancy（答案相关性）**：答案是否真正回答了用户提问；
- **Answer Correctness**：与人工标注标准答案的一致性；
- **BLEU/ROUGE**：与参考答案的 n-gram 重叠率，适合有标准答案的评测场景（但对同义表达不友好）。

**系统层指标**（衡量"工程质量"）：
- **端到端延迟**（P50/P99）：用户感知的响应速度；
- **每次查询成本**：Embedding + 向量检索 + LLM API 的综合成本；
- **系统可用性**（SLA）：服务稳定性指标；
- **用户满意度**（CSAT）：最终业务指标，是所有技术指标的综合体现。

推荐工具：RAGAS 框架可自动计算 Faithfulness、Answer Relevancy、Context Precision、Context Recall 四个核心指标，是目前最流行的 RAG 评估工具。

</details>

**2. RAG 系统的主要性能指标有哪些？**

<details>
<summary>💡 查看答案</summary>

**检索阶段指标**：
1. Context Precision（上下文精确率）：检索到的文档中真正相关的比例；
2. Context Recall（上下文召回率）：应该检索到的相关文档有多少比例被检索到了；
3. MRR（Mean Reciprocal Rank）：最相关文档排名的倒数均值。

**生成阶段指标**：
1. Faithfulness（忠实度）：答案是否完全基于检索文档，无凭空添加；
2. Answer Relevancy（答案相关性）：答案是否真正回答了用户问题；
3. Answer Correctness：与标准答案的一致性。

**系统整体指标**：
1. 端到端延迟；
2. 每次查询成本（token + 向量检索）；
3. 用户满意度。

</details>

**3. 如何独立评估检索组件？**

<details>
<summary>💡 查看答案</summary>

独立评估检索组件（与生成阶段解耦），可以准确判断系统问题是出在检索还是生成，避免两个组件互相干扰导致诊断困难。评估方法如下：

**构建检索评估集**：
- 准备若干测试 query，每个 query 人工标注其对应的"正确文档"（golden documents）——即包含回答该问题所需信息的文档 ID 列表；
- 标注可以是精确相关（只有这几个文档）或分级相关（高度相关/部分相关/不相关）。

**核心评估指标**：
1. **Hit Rate@k（命中率）**：在 top-k 检索结果中，至少包含一个 golden document 的 query 比例。简单直观，是最常用的基础指标。常见取值：Hit Rate@1、@5、@10；
2. **MRR（Mean Reciprocal Rank，平均倒数排名）**：第一个 golden document 出现在检索结果中排名的倒数，再对所有 query 取均值。衡量系统能多快地将正确文档排到前面；
3. **NDCG@k（标准化折现累积增益）**：同时考虑相关性等级（不同文档的相关程度）和排名（排名越靠前权重越高）的综合指标，是最全面但最复杂的检索评估指标；
4. **Recall@k**：top-k 中召回的 golden documents 占全部 golden documents 的比例，衡量不遗漏关键文档的能力（尤其在需要综合多文档回答时重要）；
5. **Precision@k**：top-k 中相关文档的比例，衡量检索结果的"纯度"，即噪声比例。

**评估流程**：在评估集上运行检索系统，获取每个 query 的 top-k 结果，对照 golden documents 计算上述指标，与基线方法（BM25、不同 Embedding 模型）对比，评估各优化手段（Reranking、混合检索）的实际提升效果。

</details>

**4. 什么是 RAGAS 框架？它包含哪些评估指标？**

<details>
<summary>💡 查看答案</summary>

![RAGAS 评估指标体系图](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter7/fig_ragas_metrics.png)

RAGAS（Retrieval Augmented Generation Assessment）是专门评估 RAG 系统质量的自动化评估框架，使用 LLM-as-judge 对各维度打分。核心指标：
1. **Faithfulness（忠实度）**：生成答案的每个陈述是否都有检索上下文支持（无幻觉）；
2. **Answer Relevancy（答案相关性）**：答案是否真正回答了用户提问；
3. **Context Precision（上下文精确率）**：检索到的上下文中，有多少比例对生成答案有贡献；
4. **Context Recall（上下文召回率）**：生成正确答案所需的信息，有多少在检索到的上下文中；
5. **Answer Correctness**（可选）：生成答案与标准答案的相似度。
RAGAS 无需人工标注，可大规模自动运行，是当前最流行的 RAG 评估框架之一。

</details>

**5. Faithfulness（忠实度）和 Answer Relevancy（答案相关性）分别衡量什么？**

<details>
<summary>💡 查看答案</summary>

**Faithfulness（忠实度）**：衡量生成答案中的每个事实性陈述是否都可以在检索到的上下文中找到依据，衡量的是"答案是否凭空捏造"。评分方式：将答案分解为若干陈述，判断每个陈述是否有上下文支持，支持比例即忠实度分数。低分说明：LLM 在检索内容之外添加了幻觉内容。

**Answer Relevancy（答案相关性）**：衡量生成的答案是否真正回答了用户的问题，而不是答非所问或只回答了问题的一部分。评分方式：基于答案反向生成可能的问题，计算这些反向问题与原始问题的语义相似度。低分说明：检索到的文档与问题不直接相关，或 LLM 用相关但不精确的信息回答。

</details>

**6. Context Precision 和 Context Recall 有什么区别？**

<details>
<summary>💡 查看答案</summary>

**Context Precision（上下文精确率）**：在检索到的所有上下文（chunk）中，对生成正确答案有实际贡献的比例。衡量的是"检索到的内容有多少是有用的"，即噪声比例。低分说明：检索召回了太多不相关的 chunk，给 LLM 引入了干扰。

**Context Recall（上下文召回率）**：生成正确答案所需的全部信息，有多少比例出现在检索到的上下文中。衡量的是"有多少必要信息被检索到了"。低分说明：检索遗漏了关键信息，答案不完整。

两者的权衡：提高 k 值通常提升 Recall 但降低 Precision（引入更多不相关内容），Reranking 可以同时提升两者。

</details>

**7. 如何全面地评估一个 RAG 系统的性能？请分别从检索和生成两个阶段提出评估指标。**

<details>
<summary>💡 查看答案</summary>

全面地评估一个 RAG 系统，必须将其拆分为检索阶段和生成阶段两个独立但又相互关联的部分进行评估。

**第一阶段：检索性能评估**，评估检索器能否"找得对、找得全"：
1. **上下文精确率（Context Precision）**：衡量检索到的文档中有多少是真正与问题相关的，反映检索结果的信噪比。
2. **上下文召回率（Context Recall）**：衡量所有相关的文档中，有多少被检索器成功找回来了，反映信息查找的全面性。
3. **Hit Rate**：检索到的文档中是否至少包含一个相关文档，是一个基础的"及格线"指标。
4. **MRR（Mean Reciprocal Rank）**：第一个相关文档排名的倒数的平均值，衡量找到第一个正确答案的速度。
5. **nDCG@k（Normalized Discounted Cumulative Gain）**：最全面和常用的指标之一，同时考虑了检索结果的相关性等级和它们在结果列表中的排名。

**第二阶段：生成性能评估**，评估 LLM 在给定上下文后，能否生成"忠实、准确、有用"的答案：
1. **忠实度/可溯源性（Faithfulness/Groundedness）**：生成的答案是否完全基于所提供的上下文？是否存在捏造或幻觉？
2. **答案相关性（Answer Relevancy）**：生成的答案是否直接、清晰地回答了用户的原始问题？
3. **答案正确性（Answer Correctness）**：答案中的信息是否事实准确（与"黄金标准"答案对比，或由领域专家进行事实核查）？
自动化评估框架：RAGAS、ARES、TruLens 等框架使用 LLM-as-a-Judge 的思想，将上述指标自动化计算出来，极大地提高了评估效率。

</details>

**8. 如何构建 RAG 系统的评估数据集（golden dataset）？**

<details>
<summary>💡 查看答案</summary>

1. **从用户日志提取**：收集真实用户 query，对高频和代表性的 query 进行人工标注（正确答案 + 答案所在文档）；
2. **专家出题**：邀请领域专家针对知识库内容设计问题，涵盖不同难度和类型（事实性/推理性/综合性）；
3. **合成生成**：用 LLM 对知识库文档生成问答对，再人工抽样验证质量；
4. **边界 case 设计**：专门构建知识库无法回答的问题、需要多跳推理的问题、模糊问题等；
5. **标注内容**：每个测试用例包含：query、标准答案、答案来源文档 ID（用于评估 Context Recall）；
6. **规模建议**：最小可用规模 100 条，覆盖主要 query 类型；生产级评估集 500+ 条；
7. **定期更新**：随知识库和用户需求变化定期扩充测试集。

</details>

**9. 如何用 LLM-as-judge 评估 RAG 输出的质量？**

<details>
<summary>💡 查看答案</summary>

1. **评估维度**：忠实度、相关性、完整性、简洁性，可用 RAGAS 框架或自定义 prompt；
2. **评估 prompt 设计**：提供评分标准（1–5 分）和参考示例，让 LLM 对每个维度打分并给出理由；
3. **参考答案对比**（有 ground truth 时）：让 LLM 对比生成答案与标准答案的一致性；
4. **多次采样**：同一输入运行 3–5 次，取平均分减少随机性；
5. **偏见控制**：随机化答案展示顺序，防止位置偏见；使用不同的评审 LLM 对比，防止自我偏见；
6. **人工校准**：定期抽取样本与人工评分对比，验证 LLM judge 的一致性（相关系数 > 0.8 认为可靠）；
7. **成本控制**：非每次都全量评估，采用分层抽样。

</details>

**10. 如何对 RAG 系统进行整体效果评测？**

<details>
<summary>💡 查看答案</summary>

可以分层评测：检索层（召回率、准确率、MRR 等指标）、生成层（基于检索内容的答案准确性、忠实度）、端到端层（用户满意度、任务完成率），并构建带标注答案的评测集。完整评测体系如下：

**第一层：检索质量评测**（离线评测，需要标注数据）：
- **Hit Rate@k**：top-k 检索结果中包含正确答案来源文档的比例，衡量召回是否足够；
- **MRR（Mean Reciprocal Rank）**：正确文档在排名中的倒数均值，衡量精确排序质量；
- **NDCG@k**：综合考虑相关性等级和排名的全面指标；
- **Context Precision / Context Recall**（RAGAS 指标）：检索内容的精确率和召回率。

**第二层：生成质量评测**（可用 LLM-as-judge 自动化）：
- **Faithfulness**：答案是否忠实于检索内容，无幻觉；
- **Answer Relevancy**：答案是否真正回答了问题；
- **Answer Correctness**：与标准答案的一致性（需要人工标注标准答案）。

**第三层：端到端业务评测**（最终指标）：
- 用户满意度（CSAT 评分、点赞率）；
- 任务完成率（用户问题是否得到满意解决）；
- 人工接管率（系统无法处理转人工的比例）；
- A/B 测试（与旧版本或竞品对比的直接业务指标）。

**实施工具**：RAGAS 框架可以自动化计算第一、二层大部分指标，无需大量人工标注，是当前最推荐的 RAG 评测工具。

</details>

**11. RAG 系统中检索阶段和生成阶段的问题如何分别定位？**

<details>
<summary>💡 查看答案</summary>

**检索阶段问题定位**：
1. 查看 Context Recall：是否检索到了所有必要信息？低分→检索策略问题；
2. 查看 Context Precision：是否引入了大量不相关内容？低分→召回噪声问题；
3. 直接检查 top-k 结果：人工审查检索到的 chunk 是否相关；
4. 分析 query 类型：哪类 query 的检索效果差（多跳/稀有词汇/长 query）？

**生成阶段问题定位**：
1. 查看 Faithfulness：答案是否超出检索内容？低分→生成幻觉问题；
2. 查看 Answer Relevancy：答案是否答非所问？低分→prompt 问题；
3. 固定检索结果，测试不同 LLM 的生成质量，排除检索干扰；
4. 分析长答案 vs. 短答案的质量差异，判断是否为 lost in the middle 问题。

</details>

**12. 如何系统性地排查"检索到了正确文档但答案仍然错误"的问题？**

<details>
<summary>💡 查看答案</summary>

1. **Faithfulness 检查**：答案中的错误信息是否在检索文档中？如果有，说明 LLM 对文档产生了误读；如果没有，说明 LLM 在文档之外添加了幻觉；
2. **上下文位置问题**：正确文档是否在传入 LLM 的上下文中排名靠后（Lost in the Middle）？尝试将正确文档移到前面；
3. **文档质量问题**：检索到的文档格式复杂（表格、代码嵌套）导致 LLM 解析错误？尝试对该类文档做预处理；
4. **上下文矛盾**：传入的多个文档有相互矛盾的信息，LLM 选择了错误的来源？检查是否存在矛盾文档；
5. **Prompt 问题**：Prompt 的指令是否足够清晰？是否明确要求"只基于提供的文档回答"？
6. **模型能力限制**：问题是否需要超出当前 LLM 的推理能力（复杂数值计算、多步逻辑推理）？

</details>

**13. RAG 系统出现问题时应该如何 Debug？**

<details>
<summary>💡 查看答案</summary>

![RAG 系统错误归因与调试决策树](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter7/fig_rag_debug_decision_tree.png)

分步排查：先检查原始文档解析和切片是否正确 → 检查检索结果是否包含正确答案所在片段 → 检查送入模型的最终 Prompt → 检查模型基于该 Prompt 的生成结果，逐层定位问题环节。完整的 Debug 流程：

1. **Step 1：文档处理层检查**
    - 原始文档是否被正确解析？（检查 PDF 文本提取是否有乱码、格式错误）
    - 分块是否合理？（检查关键信息有没有被切断在两个 chunk 的边界处）
    - Embedding 是否成功生成？（检查向量维度、是否有异常值）
2. **Step 2：检索层检查**
    - 直接查询向量数据库，查看 top-k 结果——正确答案所在的 chunk 是否在 top-k 内？如果不在，问题在检索；
    - 检查相似度分数分布——top-1 和 top-5 的分数差异是否合理？
    - 尝试不同措辞的 query，观察检索结果是否稳定。
3. **Step 3：上下文构建层检查**
    - 查看实际传给 LLM 的完整 Prompt（建议开启 Prompt 日志）；
    - 检查 Reranking 后的排序是否将最相关 chunk 排在前面；
    - 检查 Contextual Compression 是否误删了关键信息。
4. **Step 4：生成层检查**
    - 将包含正确答案的 chunk 作为理想上下文直接传给 LLM，观察生成结果——如果仍然错误，问题在 Prompt 设计或 LLM 能力；
    - 检查 LLM 是否在系统 Prompt 约束下正确工作；
    - 对比不同 LLM（GPT-4 vs Claude）的表现，判断是否为模型能力问题。
5. **工具辅助**：使用 Langfuse、LangSmith 等可观测性工具记录每次请求的完整链路（检索结果、Prompt、输出），支持历史 case 的离线 Debug，大幅提升排查效率。

</details>

**14. 如何系统性地定位 RAG 中的问题根因？**

<details>
<summary>💡 查看答案</summary>

建立可复现的 Case 集合，对每个失败 Case 记录"检索结果""最终 Prompt""模型输出"三元组，分类统计问题主要分布在检索缺失、检索噪声还是生成误用三类原因中的哪一类。系统性的根因定位流程：

1. **建立失败 Case 库**：从生产日志或测试评估中收集失败 case，每个 case 记录：用户 query、检索到的 top-k chunk（含相似度分数）、最终传给 LLM 的完整 Prompt、LLM 的输出、期望的正确答案。
2. **三层分类诊断**：
    - **检索缺失**（Retrieval Miss）：top-k 中没有包含正确答案所需信息 → 问题在检索侧（分块、Embedding 模型、k 值）；
    - **检索噪声**（Retrieval Noise）：top-k 中有正确信息，但也有大量无关内容 → 问题在 Reranking 或 k 值过大；
    - **生成误用**（Generation Failure）：top-k 中有正确信息，但 LLM 的答案不正确 → 问题在 Prompt 设计、Lost in the Middle 或 LLM 能力。
3. **量化分布**：统计三类根因在失败 case 中的比例，优先解决占比最高的类型。
4. **子原因细分**：对每类根因进一步细分（检索缺失 → 分块粒度问题/Embedding 不适配/k 值过小/查询措辞不当；生成误用 → Lost in the Middle/Prompt 指令不够强/上下文矛盾/LLM 能力限制）。
5. **控制变量验证**：对诊断出的根因，用控制变量法验证（只改变一个因素，其他保持不变，观察失败 case 的修复情况）。
6. **建立监控仪表盘**：生产环境持续追踪三类根因的发生频率，及时发现新的问题模式。

</details>

**15. RAG 效果不佳，问题更多出在检索还是生成环节？**

<details>
<summary>💡 查看答案</summary>

两者都需要排查，但建议先做"分而治之"的诊断：固定检索结果手动检查生成质量，固定理想上下文检查生成是否正确，从而定位问题主要出在哪一环。以下是系统性诊断框架：

**Step 1：隔离检索问题**
- 对一批失败 case，手动查看检索到的 top-k chunk——是否包含回答该问题所需的信息？
- 如果大量 case 的 top-k 中都没有正确信息 → **问题在检索**，需要优化分块策略、Embedding 模型、混合检索或 Reranking；
- 如果 top-k 中已有正确信息但答案仍错误 → 问题可能在生成。

**Step 2：隔离生成问题**
- 将包含正确答案的 chunk 作为"理想上下文"直接传给 LLM，检查生成质量；
- 如果理想上下文下仍然答错 → **问题在 Prompt 设计或 LLM 能力**，需要优化 prompt 或换更强的模型；
- 如果理想上下文下答对、检索上下文下答错 → **问题在上下文质量**（噪声过多、位置问题、压缩丢失信息等）。

**经验分布**：工程实践中，约 40% 的 RAG 问题来自检索侧（分块差、Embedding 不适配、召回不足），约 30% 来自上下文质量（噪声多、排序差），约 30% 来自生成侧（Prompt 不当、幻觉、LLM 能力限制）。不存在"只是一个环节的问题"的情况，系统性排查比主观猜测更高效。

</details>

**16. 如何设计 RAG 系统的 A/B 测试框架？**

<details>
<summary>💡 查看答案</summary>

1. **实验设计**：明确对比的变量，每次只改变一个变量；
2. **流量分割**：按用户 ID 或 session ID 哈希，将流量随机分为两组，各组使用不同 RAG 配置；
3. **指标定义**：主要指标（用户满意度、任务完成率）+ 辅助指标（检索精度、Faithfulness、延迟、成本）；
4. **样本量计算**：根据预期效果大小（MDE）和显著性要求（p<0.05, power=80%）计算最小样本量；
5. **实验隔离**：确保两组用户的其他体验完全相同；
6. **结果分析**：达到样本量后，用统计检验（t-test/bootstrap）判断差异显著性；
7. **决策规则**：显著提升 → 全量推新配置；无显著差异 → 选成本更低的；显著下降 → 回滚。

</details>

**17. 如何在生产环境中持续监控 RAG 系统的质量？**

<details>
<summary>💡 查看答案</summary>

1. **实时指标监控**：检索耗时、生成耗时、端到端延迟（P50/P99）、检索无结果率、系统错误率；
2. **质量抽样评估**：每天从生产流量中随机抽样 50–100 条，用 RAGAS 自动评分，追踪质量趋势；
3. **用户反馈信号**：采集用户点赞/踩、满意度评分等反馈，作为质量代理指标；
4. **知识库覆盖率监控**：追踪"检索无结果"的 query 比例，发现知识覆盖缺口；
5. **异常检测**：质量指标突降时自动告警；
6. **版本跟踪**：记录每次变更与质量指标变化的关联；
7. **Dashboard**：可视化上述指标，供团队实时查看。

</details>

**18. 通常用于训练和评估 RAG 系统的数据集有哪些？**

<details>
<summary>💡 查看答案</summary>

**检索模型训练与评估数据集**：
- **MS MARCO**（Microsoft Machine Reading Comprehension）：大规模段落检索数据集，100 万+ 真实必应搜索查询 + 相关段落标注，是检索模型微调和 NDCG 评估的最主要基准；
- **BEIR**（Benchmarking Information Retrieval）：异构检索基准，涵盖 18 个不同领域和任务的检索数据集（科学文献、新闻、医疗等），用于评估检索模型的域外泛化能力；
- **MTEB**（Massive Text Embedding Benchmark）：评估 Embedding 模型在检索、分类、聚类、语义相似度等 56 个任务上的综合能力，是当前最权威的 Embedding 模型排行榜。

**端到端问答评估数据集**：
- **Natural Questions（NQ）**：Google 真实搜索查询 + 维基百科段落答案，是开放域问答的核心基准；
- **TriviaQA**：大规模知识密集型问答，包含从 Wikipedia 和网络收集的证据文档，测试模型的知识检索和推理能力；
- **SQuAD 2.0**：斯坦福阅读理解数据集，包含段落级上下文问答（含"无答案"问题），评估模型在有限上下文内的精确答案提取能力；
- **HotpotQA**：多跳推理问答数据集，答案需要综合 2 个以上维基百科段落，专门评估 RAG 系统的多跳推理能力；
- **KILT**（Knowledge Intensive Language Tasks）：知识密集型任务基准，统一评估事实核查、问答、对话、关系抽取等多种任务。

**中文数据集**：
- **CMRC 2018**：中文机器阅读理解竞赛数据集；
- **DRCD**：台湾中文阅读理解数据集；
- **C-MTEB**：中文版 MTEB，专门评估中文 Embedding 模型。

</details>

**19. 微调 RAG 模型时面临哪些挑战？**

<details>
<summary>💡 查看答案</summary>

RAG 系统涉及多个可微调组件（Embedding 模型、Reranker、生成 LLM），每个组件的微调都有其特有挑战：

**Embedding 模型微调的挑战**：
1. **训练数据构建成本高**：需要大量问题-相关文档对（正样本）和问题-不相关文档对（负样本），人工标注成本极高；自动化生成的负样本（如 BM25 Hard Negatives）质量参差不齐；
2. **负样本质量关键**：对比学习中"难负样本"（看起来相关但实际上不相关的文档）的质量对模型性能影响极大，但难负样本的挖掘本身就很困难；
3. **过拟合风险**：领域数据量少时模型容易过拟合，在领域内效果提升，但泛化能力下降。

**生成 LLM 微调的挑战**：
1. **忠实度与流畅性的平衡**：微调目标是让模型"更忠实于检索内容"，但过度约束可能导致输出过于机械、缺乏自然语言流畅性；
2. **灾难性遗忘**：在领域数据上微调可能破坏模型原有的通用能力（如推理、格式遵循），需要谨慎平衡；
3. **计算成本高**：大型 LLM（70B+）的全量微调需要数十个高端 GPU，成本动辄数万美元；LoRA 等参数高效微调可以降低成本，但效果有折扣；
4. **对齐评估困难**：如何评估微调后的模型在 RAG 场景下的综合表现（检索利用率、忠实度、回答质量）没有统一标准，需要构建专属评估集。

**联合端到端微调的挑战**：将检索器和生成器联合训练（如 REALM、RAG 原始论文的方式），面临梯度传播和训练稳定性的巨大挑战，工程复杂度极高，目前主流实践仍是分别优化各组件。
