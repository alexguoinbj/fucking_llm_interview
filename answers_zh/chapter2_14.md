# 2.14 Prompt Engineering 进阶技巧 — 题目与答案

**1. 什么是 Prompt Decomposition？它与 Prompt Chaining 有什么区别？**

<details>
<summary>💡 查看答案</summary>

**Prompt Decomposition**：将一个复杂 prompt 在设计阶段拆分为结构更清晰的子部分（角色设定、上下文、指令、格式要求），每个部分的职责单一，整体仍然是一次 LLM 调用。**Prompt Chaining**：将复杂任务拆分为多个顺序的 LLM 调用，每次调用是一个独立步骤，前一步输出传入下一步。区别：\begin{enumerate}
- Decomposition 是 prompt 的结构优化，仍是单次调用；Chaining 是执行流程的分解，是多次调用；\item  Decomposition 解决"一个 prompt 太复杂"的问题；Chaining 解决"一次调用完成不了"的问题；\item  两者可以结合：每个 chain 节点内的 prompt 可以是经过 decomposition 设计的结构化 prompt。

</details>

**2. 什么是"反事实提示"（Counterfactual Prompting）？有哪些应用场景？**

<details>
<summary>💡 查看答案</summary>

反事实提示：要求模型分析"如果某个条件不同，结果会如何变化"，通过假设性情景激活深层推理。应用场景：
1. **因果分析**："如果这家公司没有在 2020 年转型，会发生什么"；
2. **方案评估**："如果不采用方案 A，还有哪些替代路径"；
3. **风险预测**："如果这个假设是错的，会有什么后果"；
4. **代码调试**："如果去掉这一行代码，程序行为会如何改变"；
5. **历史分析**："如果这项技术早 10 年出现，会对行业产生什么影响"；
6. **决策支持**："在[不同条件]下，最优决策会有什么变化"。
优势：帮助模型跳出表面答案，探索深层逻辑关系。

</details>

**3. 什么是 Emotional Prompting（情感提示）？它对模型输出有影响吗？**

<details>
<summary>💡 查看答案</summary>

情感提示是在 prompt 中加入情感性语言，如"这对我非常重要"、"请尽你所能帮助我"、"这是紧急任务"。研究发现（Li et al. 2023）：情感提示在某些任务上确实提升了 LLM 的输出质量（约 5–10%），可能原因是这类短语在训练数据中与高质量、认真回答的内容高度相关。实践应用：
1. **正面情感**："这个分析对我的论文非常关键，请仔细思考"——可能提升回答质量；
2. **截止压力**："我明天就要用到这份报告"——可能提升响应的完整性；
3. 注意：效果不稳定，不同模型差异很大；不应该作为主要优化手段，只是轻量级的辅助技巧；
4. 与 role prompting 结合使用效果更稳定。

</details>

**4. 如何设计 Prompt 引导模型进行自我批评和修正（Self-Critique）？**

<details>
<summary>💡 查看答案</summary>

1. **两步法**：第一步生成初稿，第二步让模型评审自己的输出（在同一 prompt 或 chain 中）；
2. **批评者角色**："审视以上回答，指出其中的问题、遗漏或可以改进的地方"；
3. **对照标准批评**："对照以下标准检查你的回答：[标准1]、[标准2]……"；
4. **修订迭代**："基于你的批评，生成改进版本"；
5. **三步 Refine**：初稿 → 批评 → 改进版，可以迭代多轮；
6. **具体批评维度**："检查：是否有幻觉？逻辑是否连贯？是否遗漏了重要信息？"；
7. 应用场景：代码审查、文章校对、计划评估等质量要求高的任务。

</details>

**5. 什么是 Generated Knowledge Prompting？它如何提升事实性回答的质量？**

<details>
<summary>💡 查看答案</summary>

Generated Knowledge Prompting（Liu et al. 2021）：在回答问题之前，先让 LLM 生成与该问题相关的背景知识，再基于这些自生成的知识来回答问题。两步实现：
1. Step 1："关于[主题]，列出你所知道的相关知识"；
2. Step 2："基于以上知识，回答：[原始问题]"。
提升质量的原因：
1. 第一步强制模型把相关知识"激活"到上下文，减少遗漏；
2. 生成的知识充当"工作记忆"，让回答更有依据；
3. 知识生成步骤可以被检验，发现错误后可以在第二步中修正。
适合场景：需要综合多个知识点的复杂问答；知识密集型任务。局限：如果第一步生成的知识有误，会污染第二步的回答。

</details>

**6. 什么是 Directional Stimulus Prompting？它如何精细控制输出方向？**

<details>
<summary>💡 查看答案</summary>

Directional Stimulus Prompting（DSP，Li et al. 2023）：在 prompt 中加入"提示"（hint）或"方向性信号"，引导模型的生成方向，而不是直接给出答案或规定格式。工作方式：提示是比答案更抽象的方向指示，如关键词、方向描述、主题词。示例：任务"写一篇关于气候变化的短文"，加入 hint"请在文章中涉及：科学证据、经济影响、解决方案"。应用场景：
1. **摘要生成**：用关键词提示引导摘要内容；
2. **创意写作**：用主题词、情感方向提示引导写作；
3. **对话系统**：引导对话朝特定方向发展；
4. 与 ICL 结合：hint 可以从候选池中动态检索。

</details>

**7. 什么是 Maieutic Prompting（苏格拉底式提示）？它适合什么场景？**

<details>
<summary>💡 查看答案</summary>

Maieutic Prompting（Jung et al. 2022）：通过不断追问"为什么"，让模型对自己的推理进行层层拆解，直到找到基本真理或发现推理中的矛盾。实现方式：
1. 让模型给出初步答案；
2. 对每个关键论点追问"为什么你认为这是对的？"；
3. 继续追问，直到推理变得自洽或发现矛盾；
4. 根据拆解结果验证或修正初始答案。
适合场景：
1. **复杂推理验证**：检验推理链是否真正成立；
2. **假设检验**：发现"听起来合理但实际错误"的推断；
3. **教育场景**：引导学生深入思考问题；
4. **决策分析**：拆解决策背后的假设，识别薄弱环节。

</details>

**8. 如何通过 Prompt 实现"多角度分析"？**

<details>
<summary>💡 查看答案</summary>

1. **视角枚举**："从以下三个角度分析这个问题：[用户视角]、[开发者视角]、[商业视角]"；
2. **利益相关者分析**："列出所有相关方，对每个相关方分析这个决策的影响"；
3. **正反辩论**："先给出支持这个观点的最强论据，再给出反对的最强论据，最后综合评估"；
4. **时间维度**："分析这个方案的短期效果（1年内）、中期效果（3年）和长期效果（5年+）"；
5. **SWOT 框架**："从优势、劣势、机会、威胁四个角度分析"；
6. **专家角色轮换**："分别以数据科学家、业务经理、合规专员的视角给出意见"；
7. 格式化输出：为每个角度分配结构，便于对比。

</details>

**9. 什么是 Skeleton-of-Thought Prompting？它如何提升生成速度？**

<details>
<summary>💡 查看答案</summary>

Skeleton-of-Thought（Ning et al. 2023）：将生成过程分为两步：
1. 先让 LLM 快速生成答案的"骨架"（outline/要点列表）；
2. 再对每个要点并行扩展详细内容。
提升速度的原理：传统自回归生成是串行的（token by token），Skeleton 方法将扩展步骤并行化——多个要点的扩展可以同时进行（通过并行 API 调用）。速度提升：对于长文本生成，理论上速度可提升与要点数量成比例（N 个要点→N 并行调用）。代价：需要多次 API 调用；并行调用的协调复杂度增加；最终整合需要额外步骤。适合场景：长文章、详细报告、多章节内容的快速生成。

</details>

**10. 如何设计 Prompt 使模型区分"事实"和"观点"？**

<details>
<summary>💡 查看答案</summary>

1. **显式分类要求**："在回答中，用[事实]标注有证据支持的陈述，用[观点]标注主观判断或推断"；
2. **格式化输出**：`{"facts": ["..."], "opinions": ["..."]}`；
3. **来源要求**："对标注为事实的内容，说明其依据（统计数据/研究结论/普遍共识）"；
4. **示例引导**：提供一个正确区分事实和观点的示例；
5. **对立观点**："如果这是一个有争议的话题，列出不同立场的观点，不要只呈现一种观点"；
6. **确定性语言**："使用'研究表明'表示事实，使用'我认为/可能/据估计'表示观点"；
7. 应用场景：新闻分析、研究报告、法律文件等需要严格区分事实与观点的领域。

</details>

**11. 什么是 Dual Prompt（正反双提示）？有哪些应用场景？**

<details>
<summary>💡 查看答案</summary>

Dual Prompt 是用两个对立的 prompt 分别生成正反两方面的内容，再综合两方面生成平衡的最终输出。实现方式：
1. 正面 prompt：生成支持某立场的论据；
2. 反面 prompt：生成反对该立场的论据；
3. 综合 prompt：基于两方面内容生成综合分析。
应用场景：
1. **辩论准备**：生成辩题的正反论据；
2. **产品评估**：分别生成优势和劣势；
3. **决策分析**：列出支持和反对某决策的理由；
4. **风险评估**：分析最好情况和最坏情况；
5. **学术写作**：呈现多方观点，避免单方立场偏差；
6. **用户调研**：模拟用户的正面和负面反馈。
优势：避免模型因倾向性而只生成一方论据。

</details>

**12. 如何通过 Prompt 引导模型做决策树分析？**

<details>
<summary>💡 查看答案</summary>

1. **显式决策树结构**："用决策树格式分析这个问题：每个节点是一个判断条件，每条分支是对应的结果"；
2. **IF-THEN 格式**："列出所有关键判断条件，用'如果[条件]，则[结论/下一步]'格式"；
3. **场景穷举**："枚举所有可能的情况（A/B/C），对每种情况说明最优处理方式"；
4. **优先级排序**："按照判断条件的重要性排序，先判断最关键的条件"；
5. **图形化输出**：要求用缩进文本或 Mermaid 格式输出决策树；
6. **边界条件**："对每个分支明确说明适用条件的边界"。
适合场景：故障排查、客服路由、复杂业务规则梳理。

</details>

**13. 什么是 Persona Prompting？如何设计高质量的 Persona？**

<details>
<summary>💡 查看答案</summary>

Persona Prompting 是为 LLM 设定具体、详细的虚构人物角色，使其以该角色的知识、经验和个性回答。高质量 Persona 设计原则：
1. **专业背景**：明确角色的专业领域和经验年限（"10年经验的全栈工程师"）；
2. **性格特征**：定义沟通风格（"直接、不废话、注重实践"）；
3. **知识边界**：说明角色擅长什么、不擅长什么；
4. **价值观**：定义角色在分歧点上的立场（"倾向于简单可维护的方案而非过度设计"）；
5. **语气**：正式/非正式、专业术语/通俗语言；
6. **受众意识**：角色与不同受众交流时的适应方式；
7. **一致性约束**："保持角色一致，即使用户试图改变你的角色设定"。

</details>

**14. 如何通过 Prompt 设计让模型输出更具可操作性的建议？**

<details>
<summary>💡 查看答案</summary>

1. **"可操作性"显式要求**："给出具体的、可以立即执行的建议，不要给出模糊的方向性建议"；
2. **格式约束**："每条建议格式：[行动] + [具体步骤] + [预期结果]"；
3. **受众定义**："假设读者是[角色]，具体说明他们应该采取的下一步行动"；
4. **时间框架**："给出在[时间范围]内可以完成的建议"；
5. **资源约束**："考虑到[资源限制]，给出切实可行的建议"；
6. **优先级排序**："按影响力从高到低排列建议，最先执行收益最大的"；
7. **反例过滤**："不要给出需要专业技能或大量资源才能执行的建议，除非这是必要的"；
8. **示例验证**：提供一个"可操作建议"vs"模糊建议"的对比示例。

</details>

**15. 什么是 ReAct Prompting？它如何将推理与行动结合？**

<details>
<summary>💡 查看答案</summary>

ReAct（Reasoning + Acting，Yao et al. 2022）是一种让大语言模型交替输出**思考（Thought）**与**行动（Action）**的 Prompting 框架，并通过观察行动结果（Observation）持续修正推理路径。

#### Prompt 结构示例

\begin{lstlisting}[style=promptstyle]
	Thought: 我需要查询X来回答这个问题
	Action: search[X]
	Observation: [搜索结果]
	Thought: 根据结果，我还需要了解Y
	Action: lookup[Y]
	Observation: [查找结果]
	Thought: 现在信息已经足够，可以得出结论
	Final Answer: [最终答案]
\end{lstlisting}

#### 核心优势
- **推理过程可见**：Thought 步骤将模型的内部推理外显化，便于开发者调试与审查。
- **中间步骤可验证**：每一个 Action 与 Observation 都是显式记录，可逐步检验逻辑链条的正确性。
- **行前先想清楚**：Thought 促使模型在执行动作前完成预判，减少盲目调用工具的情况。
- **基于真实反馈调整**：Observation 引入外部世界的真实信息，使推理能够动态修正，而非依赖模型的静态知识。

#### 与纯 Chain-of-Thought（CoT）的本质区别

纯 CoT 只在模型内部进行推理链展开，没有任何与外部环境的交互；而 ReAct 引入了真实的外部工具调用（如搜索引擎、数据库、API）和来自环境的观察反馈，使模型能够获取实时、准确的外部信息来辅助推理。ReAct 因此成为构建 **LLM Agent** 的基础 Prompting 框架——它定义了 Agent 感知、思考、行动的基本循环。

</details>

**16. Prompt 设计如何支持多 Agent 系统？**

<details>
<summary>💡 查看答案</summary>

在多 Agent 系统中，Prompt 设计需要解决**角色分工**与**协作通信**两个核心问题。

#### 明确每个 Agent 的职责边界

每个 Agent 的 System Prompt 应精确描述其角色定位、能力范围与禁止越界的行为，避免多个 Agent 在同一职责域上产生重叠与冲突。例如：

\begin{lstlisting}[style=promptstyle]
	# 角色：数据分析 Agent
	你只负责对结构化数据进行统计分析并输出分析报告。
	你不负责数据采集、可视化渲染或最终决策。
	当需要可视化时，将任务转交 Visualization Agent。
\end{lstlisting}

#### 标准化 Agent 间通信格式

Agent 之间传递消息的 Prompt 应规定统一的结构（如 JSON Schema 或固定 Markdown 模板），确保接收方能可靠解析。例如：

\begin{lstlisting}[style=promptstyle]
	{
		"from": "ResearchAgent",
		"to": "SummaryAgent",
		"task": "summarize",
		"payload": {
			"content": "...",
			"max_length": 200,
			"language": "zh-CN"
		}
	}
\end{lstlisting}

#### 关键设计原则
- **单一职责**：每个 Agent 的 Prompt 聚焦于一类任务，减少歧义。
- **显式交接协议**：在 Prompt 中定义何时、如何将任务移交给其他 Agent。
- **错误处理约定**：在消息格式中预留错误码与异常描述字段，使 Agent 能够优雅降级。

</details>

**17. Prompt 设计如何支持 Workflow 系统？**

<details>
<summary>💡 查看答案</summary>

Workflow 系统将复杂任务拆解为有序的节点序列（或有向无环图），每个节点的 Prompt 设计需与整体流程的状态机结构严格对齐。

#### 节点级 Prompt 设计规范

每个 Workflow 节点的 Prompt 应明确声明三要素：

\begin{lstlisting}[style=promptstyle]
	## 节点：信息提取节点

	### 输入来源
	- 上游节点：文档预处理节点
	- 输入变量：{{raw_text}}（经清洗的纯文本）

	### 处理逻辑
	从输入文本中提取以下字段：
	- 实体名称（人名、地名、机构名）
	- 时间信息
	- 核心事件

	### 输出格式
	严格输出 JSON，结构如下：
	{"entities": [...], "time": "...", "event": "..."}
	不要输出任何额外文字或 Markdown 标记。
\end{lstlisting}

#### 与 Workflow 状态机对齐的设计要点
- **输入显式声明**：Prompt 中通过变量占位符（如 `\{\{variable\}\}`）明确标注哪些信息来自上游节点，避免隐式依赖。
- **输出格式严格约束**：节点输出必须是下游节点可直接消费的格式，减少解析层的额外处理。
- **条件分支支持**：对于需要条件跳转的节点，在 Prompt 中定义分支标识输出，供 Workflow 引擎路由决策。
- **幂等性设计**：节点 Prompt 应设计为对相同输入产生稳定输出，便于 Workflow 的重试与断点续跑。

</details>

**18. 企业级 Prompt 体系应该如何构建？**

<details>
<summary>💡 查看答案</summary>

企业级 Prompt 体系需要从**标准化、版本管理、可复用性**和**质量保障**四个维度系统性建设。

#### 标准化 Prompt 模板库

按业务场景对 Prompt 进行分类归档，建立统一的模板目录结构：

\begin{lstlisting}[style=promptstyle]
	prompt-library/
	customer-service/     # 客服场景
	intent-detection.txt
	reply-generation.txt
	content-creation/     # 内容创作场景
	blog-writing.txt
	summary.txt
	data-analysis/        # 数据分析场景
	sql-generation.txt
	report-writing.txt
\end{lstlisting}

#### 版本管理机制

参照代码版本管理思路，对 Prompt 进行 Git 托管，每次变更记录：变更内容、变更原因、效果对比数据。Prompt 头部应包含元数据：

\begin{lstlisting}[style=promptstyle]
	---
	prompt_id: customer-service/intent-detection
	version: 2.3.1
	author: prompt-engineering-team
	last_updated: 2025-06-01
	model_target: claude-sonnet-4-6
	---
\end{lstlisting}

#### 统一变量注入规范

制定全企业统一的变量命名与注入规范，避免不同团队使用不兼容的占位符格式：

\begin{lstlisting}[style=promptstyle]
	# 规范：使用双花括号，snake_case 命名
	用户姓名：{{user_name}}
	历史对话：{{chat_history}}
	当前时间：{{current_datetime}}
\end{lstlisting}

#### 评测与监控体系
- **自动化评测集**：为每类 Prompt 建立黄金测试用例集，每次版本更新后自动回归。
- **线上效果监控**：追踪关键指标（任务完成率、用户满意度、输出合规率），设置异常告警。
- **A/B 测试机制**：支持多版本 Prompt 并行灰度，依据数据驱动版本晋升决策。

</details>

**19. Prompt 优化的真正瓶颈是什么？**

<details>
<summary>💡 查看答案</summary>

Prompt 优化的瓶颈**并非措辞技巧本身**，而集中在以下三个更深层的维度：

#### 1. 对任务本质的理解深度

很多 Prompt 效果不佳，根本原因是设计者对所要解决的任务理解不够透彻——不清楚任务的边界条件、失败模式和成功标准。Prompt 的语言表达是最后一步，前提是对任务有清晰的建模。

#### 2. 上下文信息的组织质量

模型的输出质量高度依赖输入信息的完整性与结构化程度。上下文中缺少关键信息、信息顺序混乱、相关与不相关信息混杂，都会严重影响输出质量，这是比"换一个词"更根本的问题。

#### 3. 评测体系的完善程度

**没有评测的 Prompt 调优是盲目的。**如果缺少量化评测指标和标准测试集，开发者无法区分"这次改动真的有效"与"这次输出碰巧更好"。真正的瓶颈在于：
- 是否建立了覆盖典型场景与边界情况的测试集；
- 是否有客观的自动化评分机制（而非仅靠人工感觉）；
- 是否能追踪每次修改对整体效果分布的影响，而非只看少数样本。

</details>

**20. 应该选择 Prompt 调优还是模型微调来解决问题？**

<details>
<summary>💡 查看答案</summary>

#### 决策原则：优先 Prompt，按需微调

- **首选 Prompt 调优**：成本极低（无需 GPU 资源）、迭代极快（分钟级），适合绝大多数任务的初期探索与持续优化。
- **考虑微调的条件**：
    - 任务涉及模型对**特定领域知识**的根本性掌握不足（如高度专业的法律术语体系、罕见语言方言）；
    - 任务对**输出格式**有极严格要求，Prompt 难以稳定约束（如复杂嵌套 JSON Schema）；
    - Prompt 调优已反复尝试并到达**明确瓶颈**，效果提升空间已极度有限；
    - 有**足够高质量的标注数据**（数百至数千条）支撑微调。

#### 实践建议

两种方案并非互斥——微调后的模型同样需要精心设计的 Prompt 来发挥最佳效果。正确路径是：先用 Prompt 调优明确任务边界与失败模式，积累高质量样本，再以这些样本驱动微调，最后在微调模型上继续 Prompt 优化。

</details>

**21. 应该选择 Prompt 还是 RAG 来解决知识相关问题？**

<details>
<summary>💡 查看答案</summary>

#### 选择依据：知识的量级与动态性

- **直接放入 Prompt（In-Context Knowledge）适用场景**：
    - 所需知识量较小，能在上下文窗口内容纳；
    - 知识相对稳定，不需要频繁更新；
    - 需要模型在推理过程中整体理解并综合运用这些知识。
- **RAG（检索增强生成）适用场景**：
    - 知识库体量庞大（数万至数百万文档），无法全量放入上下文；
    - 知识更新频繁，需要实时反映最新内容（如产品文档、政策法规）；
    - 只需按需检索与当前问题强相关的片段，而非全量知识。

#### 两者结合使用

实践中两种方案常常协同：RAG 负责从大规模知识库中检索最相关的文档片段，再将这些片段注入精心设计的 Prompt 中，由模型综合推理生成最终答案。Prompt 的质量决定了模型如何利用检索结果，RAG 的检索质量决定了模型能获得哪些信息，二者共同决定最终效果。

</details>

**22. 应该选择 Prompt 还是 Memory 来管理用户相关信息？**

<details>
<summary>💡 查看答案</summary>

#### 核心区分维度：时效性与持久性

- **直接放入 Prompt 适用于**：
    - 当次对话内的**临时偏好**（如"这次帮我用正式语气回复"）；
    - 用户在本次会话开头明确声明的上下文信息；
    - 不需要跨会话保留的一次性指令。
- **Memory 系统适用于**：
    - 需要**跨会话持久化**的用户信息（如职业背景、语言偏好、历史决策习惯）；
    - 需要**长期积累与更新**的用户画像（随着每次对话不断丰富）；
    - 信息量已超出单次 Prompt 的合理承载范围。

#### 协作模式

Memory 系统与 Prompt 并非竞争关系，而是上下游关系：Memory 系统负责持久化存储与智能检索，在每次对话开始时将与当前任务最相关的用户记忆片段**动态注入 Prompt**，实现个性化体验的同时控制上下文长度。设计要点在于：检索策略决定注入哪些记忆，Prompt 模板决定如何呈现这些记忆，两者共同决定个性化效果的上限。

</details>
