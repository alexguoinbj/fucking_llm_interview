# 2.1 高质量提示设计基础 — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 2 章：提示与上下文工程（Prompt & Context Engineering） · 共 16 题

**1. 如何写出高质量的提示？**

<details>
<summary>💡 查看答案</summary>

高质量的 Prompt 是与大语言模型高效协作的核心。其本质是将人类的模糊意图转化为模型可准确执行的结构化指令。以下从多个维度系统阐述编写高质量 Prompt 的方法论。

#### 1. 提供具体明确的指令

模糊的指令是低质量输出的首要原因。模型无法猜测用户的真实意图，因此指令必须做到无歧义、可执行。

- **避免抽象描述，转用可操作指令**：
    - *低质量*："写一篇关于气候变化的文章。"
    - *高质量*："写一篇800字的说明性文章，面向高中生读者，介绍气候变化的三个主要成因，每个成因配一个现实案例，结尾给出个人可采取的两项行动建议。"
- **量化所有可量化的要素**：字数、段落数、列表项数、时间范围、精度要求等，均应以数字明确给出。
- **区分必须与可选**：在指令中标注哪些要求是硬性约束，哪些是偏好，避免模型在取舍时出错。

#### 2. 提供充分的上下文

上下文是模型准确理解任务意图的基础。缺乏上下文的指令会迫使模型做出大量假设，从而增加偏差风险。

\subparagraph{2.1 背景信息（Background）}

说明任务所处的情境，帮助模型校准知识范围和表达风格：

- 任务的使用场景：内部汇报、客户沟通、学术写作、产品文案等。
- 相关领域或行业背景：如"本产品面向医疗器械监管领域"。
- 已有工作基础：如"以下是已完成的初稿，请在此基础上修改"。

\subparagraph{2.2 受众信息（Audience）}

明确目标读者决定了输出的语言难度、术语密度和表达风格：

- *示例*："读者为无技术背景的企业高管，请避免使用编程术语，所有技术概念须用商业语言类比解释。"

\subparagraph{2.3 角色设定（Persona）}

为模型赋予特定角色，可激活相关领域的知识模式并稳定输出风格：

- *示例*："你是一位拥有15年经验的资深产品经理，擅长将技术需求转化为用户故事。"
- *示例*："你是一位苏格拉底式的哲学导师，习惯通过反问引导学生自主思考，而非直接给出答案。"

角色设定不仅影响内容，还会影响模型的推理路径和回应态度。

#### 3. 使用强有力的动词引导响应

指令的起始动词直接决定模型的行为模式。应根据任务类型选择精准的动词：

\begin{table}[h]



| **任务类型** | **推荐动词** | **应避免的模糊动词** |
| --- | --- | --- |
| 内容生成 | 撰写、起草、生成、创作 | 做、弄、写一下 |
| 信息提取 | 列举、提取、识别、定位 | 找找、看看有没有 |
| 分析评估 | 分析、评估、对比、诊断 | 说说、聊聊 |
| 转化改写 | 翻译、改写、压缩、扩展、转换 | 处理、改一改 |
| 结构整理 | 分类、归纳、排序、汇总 | 整理一下 |
| 推理决策 | 推断、论证、建议、预测 | 想想、猜猜 |


	\caption{任务类型与推荐动词对照表}
\end{table}

此外，在需要模型展示推理过程时，可使用"逐步"、"分阶段"等副词修饰动词，如"逐步分析"、"分阶段规划"。

#### 4. 保持简洁，避免信息过载

冗长或重复的 Prompt 会稀释关键指令的权重，使模型难以判断优先级。简洁的核心原则是：

- **一次只做一件事**：若任务复杂，拆分为多轮对话或多个独立 Prompt，而非将所有要求堆砌在一次请求中。
- **删除冗余修饰**：避免"请尽可能地"、"如果方便的话"等软化语言，这类表达会降低指令的执行力度。
- **避免重复声明**：同一约束只需声明一次，重复声明不会强化效果，反而增加干扰。
- **结构优于堆砌**：使用编号列表、分段或标签（如`[任务]`、`[约束]`、`[示例]`）组织信息，而非将所有内容写成一段连续文字。

#### 5. 善用示例（Few-Shot Prompting）

示例是传递意图最高效的方式之一，尤其适用于格式复杂或风格特殊的任务：

- **正例**：展示期望的输出格式与内容风格。
- **负例**：明确指出不希望出现的输出形式，帮助模型排除歧义。
- **示例数量**：通常1至3个示例即可，过多示例会压缩模型对实际任务的处理空间。

*示例结构参考*：
\begin{quote}
	**[任务]**：将以下产品描述改写为一句话广告语，风格简洁有力，突出核心卖点。\\
	**[示例输入]**：这款耳机采用主动降噪技术，续航40小时，重量仅180克。\\
	**[示例输出]**：40小时静音，轻如无物——专注，从不中断。\\
	**[实际输入]**：这款空气净化器覆盖面积120平方米，三重过滤系统，噪音低于30分贝。
\end{quote}

#### 6. 引导模型展示推理过程

对于需要准确性的复杂任务，指示模型"先思考后输出"可显著提升结果质量：

- *示例*："在给出最终答案之前，请先列出你的推理步骤。"
- *示例*："请先分析该问题的各个子问题，再逐一解答，最后给出综合结论。"

这一技术（即 Chain-of-Thought Prompting）在数学推理、逻辑判断和多步骤规划类任务中效果尤为显著。

#### 7. 迭代优化而非一次成型

高质量 Prompt 通常经过多轮打磨。建议遵循以下迭代流程：

1. **初稿**：按任务核心需求写出基础版本。
2. **测试**：以多样化输入验证输出是否符合预期。
3. **归因**：对不符合预期的输出分析根因（指令歧义、约束缺失、示例不足等）。
4. **修订**：针对性地补充或修改对应模块。
5. **回归**：修改后重新测试全部历史用例，确保未引入新问题。

将每次迭代的修改记录存档，有助于积累组织内部的 Prompt 工程经验库。

**2. 提示工程如何影响 LLM 输出？**

<details>
<summary>💡 查看答案</summary>

提示工程是设计清晰、具体和目标导向的输入提示的过程，以引导大型语言模型（LLM）获得期望的结果。它在最大化 LLM 性能方面至关重要，特别是在以下场景中：
- **零样本学习**：模型在没有先例的情况下执行任务，依赖于提示的清晰度来推断意图。
- **少样本学习**：在提示中提供少量示例以指导模型。

**有效的提示工程**：
- 提供上下文以减少歧义。
- 使用结构化指令强调任务的要求。
- 利用如思维链（CoT）提示等策略来引出逻辑推理。

**示例**：将“Summarize this text”重新表述为“Provide a 3-sentence summary focusing on the main theme”可以提高输出的精确性。

</details>

**3. 什么是 System Prompt？它与 User Message 有什么区别？**

<details>
<summary>💡 查看答案</summary>

System Prompt 是在对话开始前由开发者或系统设定的全局指令，用于规定模型的身份、行为准则、输出格式、知识范围及限制条件。它在整个对话生命周期内持续生效，对所有后续交互起约束作用。User Message 则是用户在对话中逐轮输入的具体请求或问题，属于动态的、即时的交互内容。

两者的主要区别体现在以下几个维度：

**作用层级：**System Prompt 处于更高的优先级，定义模型的"元行为"；User Message 在此框架内被处理，受 System Prompt 的约束。

**持久性：**System Prompt 在整个会话中保持不变；User Message 随每轮对话更新，具有时效性。

**编写者：**System Prompt 通常由产品开发者或运营方编写，用户不可见；User Message 由终端用户实时输入。

**典型内容：**System Prompt 常包含角色设定（"你是一名专业的法律顾问"）、输出格式要求、禁止事项、语言风格等；User Message 则包含具体任务、问题或上下文补充。

**安全边界：**System Prompt 是实施安全策略、防止 Prompt 注入攻击的主要屏障，其权威性高于 User Message。

</details>

**4. 什么是 Role Prompting（角色提示）？它对输出质量有什么影响？**

<details>
<summary>💡 查看答案</summary>

Role Prompting 是指在 Prompt 中为模型赋予一个明确的身份或角色（如"你是一名资深数据科学家"、"你是一名苏格拉底式的哲学教师"），从而引导模型以该角色的知识储备、思维方式和表达风格生成回答。

**对输出质量的影响：**
- **提升专业深度**：赋予专家角色后，模型倾向于使用领域术语、引用行业惯例，输出更具专业性和权威感。
- **统一语气与风格**：角色设定锚定了模型的表达基调（严谨、幽默、简洁等），使多轮对话风格保持一致。
- **激活相关知识**：角色的认知框架会引导模型优先调用与该角色相关的知识路径，提高回答的针对性。
- **潜在风险**：若角色设定过于宽泛或与任务不匹配，可能引入不必要的偏见或限制模型的灵活性；过度强化某一角色也可能导致模型拒绝超出该角色范畴的合理请求。

最佳实践是将角色设定与具体任务目标结合，例如："你是一名面向初学者的 Python 讲师，请用类比和简单示例解释以下概念。"

</details>

**5. 什么是正面指令和负面指令？各自在什么场景下更有效？**

<details>
<summary>💡 查看答案</summary>

**正面指令（Positive Instructions）**明确告诉模型"应该做什么"，例如"用简洁的中文回答"、"列出三个要点"。**负面指令（Negative Instructions）**则明确告诉模型"不应该做什么"，例如"不要使用专业术语"、"不要重复问题"。

**正面指令更有效的场景：**
- 需要引导模型向特定方向输出时，正面指令提供明确的行为目标，认知负担低，执行一致性更高。
- 定义输出格式、长度、语言风格等结构性要求时，正面指令更直接。
- 一般情况下，正面指令应作为首选，因为模型对"做什么"的理解优于对"不做什么"的理解。

**负面指令更有效的场景：**
- 需要排除已知的高频错误行为时，例如模型习惯性地添加免责声明，可用"不要添加免责声明"直接抑制。
- 安全与合规约束场景，明确禁止特定内容（如"不得透露用户隐私数据"）比正面描述更清晰。
- 与正面指令配合使用效果最佳：先用正面指令定义期望行为，再用负面指令排除边界外的干扰行为。

</details>

**6. 为什么说"展示"（show）比"描述"（tell）更有效？**

<details>
<summary>💡 查看答案</summary>

"描述"（tell）指用抽象语言说明期望的输出特征，如"请写得简洁"、"请保持专业"；"展示"（show）则是直接提供具体示例，让模型通过示例推断期望的模式。

"展示"更有效的原因体现在以下几个方面：

- **消除歧义**：抽象描述因人而异，"简洁"对不同用户意味着不同字数；具体示例则明确锚定了期望的输出形式，消除主观解读空间。
- **降低指令复杂度**：有时用语言精确描述一种输出格式需要大量文字，而一个示例可以立即传达同等信息量。
- **激活模式匹配能力**：LLM 在预训练阶段积累了强大的模式识别能力，Few-Shot 示例直接触发这一能力，使模型能够快速归纳并迁移示例中的隐含规律。
- **格式与风格的精确复现**：对于特定的输出结构（如表格、代码注释风格、JSON 模板），示例比文字描述更能确保模型精确复现。

实践建议：在 Prompt 中同时使用"描述"确立原则，用"展示"提供锚点，两者结合可达到最佳效果。

</details>

**7. Prompt 的长度和质量之间有什么关系？越长越好吗？**

<details>
<summary>💡 查看答案</summary>

Prompt 的长度与质量之间并非正相关关系，有效信息密度才是决定输出质量的核心因素。

**适当增加长度有益的情形：**
- 提供必要的背景信息、约束条件和示例，有助于模型准确理解任务意图。
- 复杂任务需要分步指令时，详细的步骤描述可防止模型跳步或遗漏。
- 提供参考文档或上下文数据时，内容越完整，生成质量越高。

**过长 Prompt 带来的问题：**
- **"迷失在中间"（Lost in the Middle）现象**：研究表明，模型对超长上下文中间部分的关注度显著下降，关键指令若置于中段可能被忽视。
- **指令冲突风险**：内容越多，前后矛盾的概率越高，模型可能在冲突指令间产生不确定行为。
- **Token 成本上升**：在 API 调用场景中，冗长 Prompt 直接增加推理成本与延迟。
- **注意力稀释**：核心指令被大量无关内容包围时，模型对关键要求的遵从率下降。

最佳实践是：以"最小充分原则"设计 Prompt——包含完成任务所必需的全部信息，去除一切冗余描述，将最关键的指令置于开头或结尾。

</details>

**8. 什么是 Prompt 的"歧义"问题？如何避免？**

<details>
<summary>💡 查看答案</summary>

Prompt 歧义是指指令的表述存在多种合理解读，导致模型输出偏离用户真实意图的现象。歧义可分为语义歧义（词语含义不明确）、范围歧义（任务边界不清晰）和格式歧义（输出结构未定义）三类。

**常见歧义示例：**"帮我总结这篇文章"——模型无法判断目标长度、受众、摘要粒度及是否保留原文结构。

**避免歧义的策略：**
- **明确任务目标与受众**：说明输出的使用场景和目标读者，例如"为没有技术背景的高管撰写一份 200 字以内的执行摘要"。
- **定义输出格式**：用结构性语言或示例明确期望的输出形式，如"以 Markdown 列表格式输出，每条不超过 20 字"。
- **限定范围与约束**：明确任务的边界条件，如"仅基于以下文档内容作答，不引入外部信息"。
- **使用分隔符隔离内容**：通过 XML 标签、三引号等将指令与数据清晰分离，避免模型混淆任务说明与待处理内容。
- **要求模型复述任务**：在复杂场景中，先让模型用自己的话重述对任务的理解，再开始执行，以提前发现歧义。

</details>

**9. 如何通过 Prompt 控制模型输出的语气和风格？**

<details>
<summary>💡 查看答案</summary>

语气与风格的控制是 Prompt 工程的重要维度，可通过以下方法实现：

- **直接描述风格属性**：在 Prompt 中明确指定目标风格，如"用正式、客观的学术语气"、"用轻松幽默的对话风格"、"避免使用被动语态"。
- **角色设定锚定风格**：通过 Role Prompting 间接定义风格，如"你是一名《经济学人》专栏作者"，模型会自动调用该角色对应的写作惯例。
- **提供风格示例（Few-Shot）**：给出目标风格的典型段落，让模型通过模仿示例复现风格，比抽象描述更精确。
- **指定受众**：受众定义会自然约束词汇选择和句式复杂度，如"面向 10 岁儿童解释"与"面向博士研究生解释"会产生截然不同的输出。
- **细化语言参数**：可具体要求句子长度（"使用短句，每句不超过 15 字"）、词汇层级（"避免行话，使用日常用语"）、情感基调（"保持中立，不带感情色彩"）等。
- **迭代校正**：在初稿基础上追加指令进行微调，如"上述回答过于正式，请改写得更加口语化"，逐步逼近目标风格。

</details>

**10. 什么是 Delimiters（分隔符）？在 Prompt 中有什么作用？**

<details>
<summary>💡 查看答案</summary>

Delimiters（分隔符）是在 Prompt 中用于区分不同内容区块的标记符号，常见形式包括三引号（`"""`）、XML 标签（`<text></text>`）、Markdown 代码块（““`）、方括号（`[]`）、破折号分隔线（`---`）等。

**分隔符的主要作用：**
- **防止 Prompt 注入**：将用户输入的数据与系统指令清晰隔离，避免恶意用户通过在数据中嵌入伪造指令来劫持模型行为。例如，将用户提交的文本置于 `<user_input></user_input>` 标签内，模型可明确识别其为"待处理内容"而非"执行指令"。
- **明确内容边界**：在多段内容并存的 Prompt 中（指令、示例、参考文档、待处理文本），分隔符帮助模型精确识别每个区块的语义角色。
- **提升解析准确性**：结构化的分隔使模型更容易定位关键信息，减少因内容混淆导致的错误理解。
- **支持复杂任务编排**：在多步骤任务中，可用分隔符标记不同阶段的输入输出，引导模型按顺序处理各个子任务。

</details>

**11. 如何在 Prompt 中有效地使用 XML 标签或 Markdown 结构？**

<details>
<summary>💡 查看答案</summary>

XML 标签和 Markdown 结构是在 Prompt 中组织复杂内容的两类主要工具，各有其适用场景和使用规范。

**XML 标签的有效使用：**
- **语义化命名**：标签名应清晰表达其内容的语义角色，如 `<instructions>`、`<context>`、`<examples>`、`<output_format>`，便于模型理解各区块的功能。
- **嵌套结构表达层级关系**：可用嵌套标签表达主从关系，如将多个 `<example>` 嵌套在 `<examples>` 内。
- **隔离用户输入**：将动态插入的用户数据包裹在专用标签内，防止其被模型误解为指令。
- **引导结构化输出**：可要求模型在特定标签内输出答案，如"请将你的推理过程放在 `<reasoning>` 标签内，最终答案放在 `<answer>` 标签内"。

**Markdown 结构的有效使用：**
- **层级标题组织长 Prompt**：对于包含多个模块的复杂 Prompt，使用 `#`、`##` 等标题划分区块，提升可读性与模型的结构感知能力。
- **代码块隔离代码内容**：用反引号代码块包裹代码片段或格式化数据，防止特殊字符被错误解析。
- **列表明确枚举要求**：使用有序或无序列表列出多条并列指令，比连续段落更易于模型逐条遵循。
- **环境适配**：需注意并非所有模型 API 都对 Markdown 有相同的渲染支持，在纯文本环境中应优先选用 XML 标签。

</details>

**12. 如何通过 Prompt 控制模型输出的长度？**

<details>
<summary>💡 查看答案</summary>

- **直接指定字数或字符数**：如"请用 150 字以内回答"、"请提供不超过 500 词的摘要"，给出明确的数量上限。
- **指定输出单元数量**：如"列出 5 个要点"、"提供 3 个示例"，通过限定条目数量间接控制长度。
- **定义输出结构**：要求模型输出固定格式（如单段摘要、一句话结论、三列表格），结构本身即约束了长度范围。
- **明确禁止冗余内容**：如"不要重复问题"、"不要添加总结段落"、"不要解释你的推理过程，只给出结论"，通过排除法压缩输出。
- **分级控制详略**：对不同部分设定不同详细程度，如"用一句话概括背景，用三段详细阐述方案"。
- **注意模型的固有倾向**：当前主流 LLM 存在过度生成的倾向，长度控制指令需置于 Prompt 的显著位置（开头或结尾），并可在 System Prompt 中全局设定，以提高遵从率。

</details>

**13. 如何设计 Prompt 使模型处理多步骤任务时不跳步？**

<details>
<summary>💡 查看答案</summary>

- **显式枚举步骤**：将任务分解为有序的编号步骤，并明确要求模型"按照以下步骤依次执行，不得跳过任何一步"。
- **要求输出每步结果**：在每个步骤后要求模型输出该步骤的中间结果，使跳步行为在输出中可见，便于检查与纠错。
- **设置步骤间依赖**：明确声明后续步骤以前一步骤的输出为输入，如"第三步：基于第二步得出的结论，进一步分析……"，强化步骤间的逻辑锁链。
- **使用思维链提示（CoT）**：在 Prompt 中添加"请一步一步地思考"或提供包含完整推理链的 Few-Shot 示例，激活模型的逐步推理模式。
- **分轮执行复杂任务**：对于步骤间依赖性强的任务，可拆分为多轮对话，每轮只执行一个步骤，以上一轮输出作为下一轮输入，从根本上消除跳步空间。
- **验证与回溯指令**：要求模型在完成所有步骤后，自我检查是否每一步均已完成，若发现遗漏则补充执行。

</details>

**14. Prompt 迭代优化的基本流程是什么？**

<details>
<summary>💡 查看答案</summary>

Prompt 迭代优化是一个系统性的工程过程，其基本流程如下：

- **第一步：明确目标与评估标准**：在开始优化前，清晰定义"好的输出"的评判维度（准确性、格式、风格、长度等），并准备一批覆盖典型场景和边界情况的测试用例。
- **第二步：撰写基线 Prompt**：基于对任务的初步理解，编写一个最简单直接的版本，作为后续迭代的对照基准。
- **第三步：执行测试与收集输出**：在测试集上运行基线 Prompt，系统性地收集模型输出，避免仅凭单次感官判断。
- **第四步：诊断失败模式**：分析不符合预期的输出，归纳失败的根本原因（指令歧义、缺少示例、格式未定义、上下文不足等）。
- **第五步：针对性修改**：每次迭代只修改一个变量（如增加一个示例、修改角色设定、调整指令顺序），以便精确定位改动效果。
- **第六步：对比评估**：将修改后的输出与上一版本在同一测试集上对比，使用量化指标（如通过率、人工评分）判断是否有所改善。
- **第七步：固化与文档化**：将验证有效的改动纳入正式 Prompt，并记录每次迭代的修改原因与效果，积累 Prompt 工程知识库。
- **持续监控**：在生产环境中持续收集真实用户案例，定期触发新一轮优化迭代。

</details>

**15. 什么是"过度指令"（Over-specification）？它会带来什么问题？**

<details>
<summary>💡 查看答案</summary>

过度指令是指 Prompt 中包含了超出完成任务实际需要的冗余约束、重复说明或相互矛盾的细节规定，导致指令密度过高的现象。

**过度指令带来的主要问题：**
- **注意力稀释**：模型的有效注意力有限，过多指令会导致关键约束被淹没，核心要求的遵从率反而下降。
- **指令冲突**：约束条件越多，前后矛盾的概率越高，模型面对冲突时会产生不确定行为，输出不稳定。
- **创造力受限**：在需要模型发挥灵活性或创造性的任务中，过于细密的约束会压缩模型的解空间，导致输出刻板、缺乏生气。
- **维护成本增加**：冗长复杂的 Prompt 难以维护和调试，修改一处约束可能引发连锁冲突，迭代效率低下。
- **Token 浪费**：冗余内容直接增加推理成本，在高并发 API 场景中尤为明显。

应对策略是定期审视 Prompt，识别并删除对输出质量无实质贡献的冗余指令，遵循"最小充分原则"。

</details>

**16. 什么是"指令不足"（Under-specification）？它会带来什么问题？**

<details>
<summary>💡 查看答案</summary>

指令不足是指 Prompt 未能提供完成任务所必需的关键信息、约束或示例，导致模型不得不依赖自身默认假设进行补全的现象。

**指令不足带来的主要问题：**
- **输出不可预测**：模型在信息缺失时会依赖训练数据中的统计偏好进行补全，不同运行之间输出差异显著，一致性差。
- **默认假设偏差**：模型的默认假设可能与用户真实意图存在偏差，例如对"总结"的默认长度、对"专业"的默认定义，均因任务和用户而异。
- **幻觉风险上升**：当任务需要特定事实或格式但 Prompt 未提供时，模型更容易凭空生成看似合理但实际错误的内容。
- **错误难以定位**：指令不足导致的输出偏差往往难以追溯，因为模型"遵守了指令"，只是指令本身不够完整。
- **用户体验下降**：在产品场景中，不稳定的输出会降低用户信任，增加人工审核负担。

应对策略是在设计 Prompt 时主动预判模型可能产生歧义或需要假设的环节，并在这些关键节点补充明确的约束或示例。

</details>
