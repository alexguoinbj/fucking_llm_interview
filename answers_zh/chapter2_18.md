# 2.18 综合开放题：系统设计与工程权衡 — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 2 章：提示与上下文工程（Prompt & Context Engineering） · 共 17 题

**1. 你会如何从零设计一个复杂 AI 产品的 System Prompt？描述你的设计流程。**

<details>
<summary>💡 查看答案</summary>

**设计流程**：\begin{enumerate}
- **需求分析**：明确产品的核心功能、目标用户、使用场景、安全边界；\item  **角色设计**：定义 AI 的角色、专业背景、性格特征、沟通风格；\item  **能力范围**：明确 AI 可以做什么，不能做什么；\item  **安全规则**：定义拒绝条件、数据处理规范、隐私保护要求；\item  **输出规范**：定义语言风格、格式偏好、长度范围；\item  **边界情况处理**：定义超出范围的请求如何处理；\item  **初稿测试**：用 50+ 个典型和边界场景测试，记录失败模式；\item  **迭代优化**：针对失败模式修改，每次只改一个变量；\item  **红队测试**：专门测试安全边界；\item  **上线监控**：建立持续评估机制，发现新问题及时迭代。关键原则：先简后繁，从最小可用版本开始，根据实际问题逐步完善。

</details>

**2. Prompt Engineering 和 Fine-tuning 的边界在哪里？什么时候该从 Prompt 切换到微调？**

<details>
<summary>💡 查看答案</summary>

应该切换到 Fine-tuning 的信号：\begin{enumerate}
- **性能天花板**：Prompt Engineering 已经充分优化，但任务性能仍无法满足要求（如准确率 <80% 而目标是 95%）；\item  **一致性要求**：需要极高的输出一致性（同一输入 100 次必须相同格式），prompt 的随机性无法满足；\item  **成本**：任务高频使用，每次传入大量 few-shot 示例的 token 成本超过微调成本；\item  **延迟**：长 prompt 导致 TTFT 不可接受，微调后 prompt 更短；\item  **专业知识注入**：需要大量私有领域知识内化到模型，RAG 也无法覆盖；\item  **数据充足**：有 1000+ 高质量标注样本；\item  持续适用场景：数据量少、任务频繁变化、多任务场景优先 Prompt。

</details>

**3. 随着模型能力越来越强，Prompt Engineering 会变得不重要吗？为什么？**

<details>
<summary>💡 查看答案</summary>

不会，但会演变。原因：\begin{enumerate}
- **任务边界上移**：模型越强，用户使用的任务越复杂，prompt 工程的难度同步上升；\item  **精确控制需求不减**：越来越多的关键业务系统依赖 LLM，对输出的精确控制要求只增不减；\item  **安全需求增加**：更强的模型能力也带来更大的风险，prompt 层的安全设计更重要；\item  **成本优化**：如何用最少的 token 获得最好的输出，永远是工程问题；\item  **多模态和 Agent 场景**：新能力带来新的 prompt 设计挑战，并非消失而是复杂化；\item  **会演变的地方**：简单格式控制类的工程技巧会被 API 特性（Structured Outputs）替代；高层次的任务分解、上下文设计和安全设计会更重要；Prompt Engineering 会从"让模型明白我说什么"演变为"让模型以正确方式处理复杂任务"。

</details>

**4. 如何建立一套企业级的 Prompt 版本管理和发布体系？**

<details>
<summary>💡 查看答案</summary>

**体系设计**：\begin{enumerate}
- **版本控制**：所有 prompt 纳入 Git，commit message 包含：变更内容、变更原因、影响范围；\item  **参数化模板**：prompt 用 Jinja2 等模板化，变量与内容分离，支持多环境（dev/staging/prod）；\item  **语义版本**：major（不兼容变更）.minor（新增功能）.patch（bug 修复）；\item  **评估套件绑定**：每个 prompt 绑定对应的测试集，变更触发自动评估；\item  **发布流程**：开发 → 自动测试 → 代码审查 → 灰度（5%流量）→ 监控 → 全量；\item  **Feature Flags**：支持不重启服务切换 prompt 版本；\item  **回滚机制**：一键回滚到任意历史版本；\item  **变更通知**：prompt 变更通知所有依赖方；\item  **审计日志**：记录每次变更的执行人、时间和原因。

</details>

**5. 你认为 Prompt Engineering 领域目前最重要的未解决问题是什么？**

<details>
<summary>💡 查看答案</summary>

（开放题）\begin{enumerate}
- **可解释性**：为什么某些 prompt 有效而其他无效，缺乏理论解释，工程优化主要靠经验试错；\item  **跨模型可迁移性**：在一个模型上优化的 prompt 换到另一个模型往往需要重新优化，缺乏通用 prompt 优化方法；\item  **自动化优化的可靠性**：APE/DSPy 等自动优化方法在简单任务上有效，但在复杂任务上泛化性不足；\item  **安全与能力的权衡**：如何在不大幅牺牲能力的前提下，通过 prompt 实现可靠的安全约束，目前主要是一门艺术；\item  **长上下文 prompt 的质量保证**：随着 context window 扩展到百万 token，如何保证 LLM 对所有内容都有效利用。面试中选 1–2 点展开并说明自己的改进想法，展示深度思考。

</details>

**6. 一个客服 Agent 需要同时访问：用户档案、订单历史、产品知识库、当前对话，请设计这个系统的上下文组织方案。**

<details>
<summary>💡 查看答案</summary>

**上下文结构（从前到后）**：
1. **System Prompt**（固定，可缓存）：客服角色定义、语气规范、安全约束、能处理的问题范围；
2. **工具定义**（固定，可缓存）：查询订单、查询产品信息、创建工单等工具的 schema；
3. **用户档案摘要**（中等稳定）：用户基本信息、VIP等级、近期重要事项（精简为100-200 token的结构化摘要，而非完整档案）；
4. **当前订单上下文**（如果对话涉及具体订单，动态加载该订单详情）；
5. **产品知识检索**（动态，RAG）：根据当前对话内容检索相关的产品文档/FAQ片段（k=3-5）；
6. **对话历史**（最近 10 轮，超出部分滚动摘要）；
7. **当前用户消息**。
    设计要点：用户档案和订单历史不应一次性全部加载，而是按需检索（"用户提到订单号XXX时才加载该订单详情"）；产品知识库通过 RAG 按需检索而非全量预加载。

</details>

**7. 在一个代码助手应用中（类似 Claude Code），上下文中应该包含哪些信息？这些信息应该如何组织和更新？**

<details>
<summary>💡 查看答案</summary>

**核心上下文组成**：\begin{enumerate}
- **项目结构概览**：目录树（精简，可能只展示关键目录和文件，避免完整树占用过多空间）；\item  **当前正在编辑的文件内容**：完整内容，因为这是当前任务的核心；\item  **相关文件片段**：与当前任务相关的其他文件的关键部分（函数签名、接口定义），通过代码搜索/语义检索获取；\item  **最近的命令执行结果**：测试输出、构建日志（通常需要压缩，只保留错误和关键信息）；\item  **任务历史**：用户的指令序列和已完成的修改记录；\item  **System Prompt**：编码规范、工具使用说明（固定，可缓存）。**组织和更新策略**：
- 项目结构和工具定义放在最前（可缓存）；\item  当前文件内容随编辑实时更新；\item  命令输出超过一定长度自动截断+摘要（保留错误堆栈的关键行）；\item  已完成且不再相关的旧文件内容应从上下文中移除，避免累积。

</details>

**8. 在一个多步骤的"研究报告生成"Agent 中（搜索资料→分析→撰写报告），不同阶段的上下文需求有何不同？应该如何设计阶段间的上下文传递？**

<details>
<summary>💡 查看答案</summary>

**阶段一：搜索资料**——上下文需求：研究主题、已确定的子主题列表、已检索到的来源摘要列表（避免重复搜索）。这个阶段上下文相对简洁，主要追踪"已经搜索过什么"。**阶段二：分析**——上下文需求：所有收集到的资料的关键内容（可能需要分批处理，因为资料量可能超出单次窗口）。这个阶段是上下文最"重"的阶段，可能需要 Map-Reduce：每批资料单独分析提炼要点，再汇总。**阶段三：撰写报告**——上下文需求：报告大纲、各部分的关键论点和数据（来自阶段二的提炼结果），而不是阶段一收集的原始资料全文。**阶段间传递**：\begin{enumerate}
- 不直接传递全部历史，而是传递"该阶段的产出"（结构化的资料摘要、分析结论）；\item  每个阶段结束时进行"提炼"，把该阶段的工作压缩为下一阶段需要的精简输入；\item  原始资料可以存储在外部（如临时文件），各阶段通过引用按需访问。

</details>

**9. 假设你正在优化一个上下文窗口经常溢出的 Agent 系统，你会按照怎样的优先级顺序进行排查和优化？**

<details>
<summary>💡 查看答案</summary>

**排查优化顺序**：\begin{enumerate}
- **测量先行**：先统计当前系统中各上下文组件的 token 占比分布，找出占比最大的1-2个组件（通常是工具调用历史或检索结果）；\item  **去除明显冗余**：检查是否存在重复内容（同一信息被多次注入）、未经处理的原始大段数据（API 原始 JSON 响应未提取关键字段）——这类问题修复成本低、收益高，优先处理；\item  **优化高占比组件**：针对占比最大的组件，引入针对性的压缩策略（工具历史→结构化状态；检索结果→Contextual Compression）；\item  **预算重分配**：根据各组件对任务质量的实际贡献（消融实验），重新分配预算上限；\item  **引入分层管理**：如果以上措施仍不够，引入上下文分区和滚动摘要机制；\item  **架构调整**：如果单一 Agent 的上下文持续超标，考虑拆分为 Multi-Agent 架构，将大型子任务委托给独立上下文的 Subagent；\item  **验证**：每一步优化后，在测试集上验证任务质量没有下降，避免"为了省 token 而牺牲效果"。

</details>

**10. 上下文工程与 RAG、Fine-tuning、Agent 设计之间是什么关系？请阐述你的整体理解框架。**

<details>
<summary>💡 查看答案</summary>

**整体框架**：上下文工程是一个"贯穿性"的工程层，连接和协调其他技术组件：\begin{enumerate}
- **与 RAG 的关系**：RAG 解决"从哪里获取信息"的问题，上下文工程解决"获取的信息如何组织、压缩、定位在 prompt 中"的问题——RAG 是信息来源之一，上下文工程是信息的"管理者"；\item  **与 Fine-tuning 的关系**：Fine-tuning 改变模型的"内在知识和行为模式"，上下文工程改变模型"看到的输入"——两者是互补的，好的上下文工程可以降低对 Fine-tuning 的依赖（用更少的微调实现相同效果），而 Fine-tuning 也可以让模型对特定上下文格式的利用更高效；\item  **与 Agent 设计的关系**：Agent 的核心挑战之一就是"如何在多步骤执行中管理不断增长的上下文"，因此上下文工程是 Agent 工程的核心组成部分，决定了 Agent 能否可靠完成长任务；\item  **统一视角**：可以将整个 LLM 应用系统看作一个"信息处理管道"——RAG/工具/记忆是信息生产者，上下文工程是信息的编排和调度层，Fine-tuning 是消费者（模型）的能力基础，三者共同决定最终输出质量。在设计系统时，应该自顶向下思考"模型在每一步真正需要看到什么"，再倒推需要哪些信息源、如何组织。

</details>

**11. 如何评估"为某个任务增加更多上下文信息"是否值得（即边际收益分析）？**

<details>
<summary>💡 查看答案</summary>

1. **建立基线**：用当前的上下文配置在测试集上评估任务质量；\item  **候选信息识别**：列出可以增加但目前未包含的信息源（如增加检索数量、加入用户历史偏好、加入更多工具）；\item  **逐项添加测试**：分别测试加入每个候选信息后的质量变化，计算"质量提升 / 新增 token 数"的比值；\item  **优先级排序**：按边际收益比值排序，优先采纳收益高的；\item  **饱和点识别**：对于可调节数量的信息（如检索数量 k），逐步增加 k 值，绘制"k vs. 质量"曲线，找到收益递减的拐点；\item  **场景区分**：边际收益可能因任务类型而异，简单任务可能收益很快饱和，复杂任务可能持续受益于更多上下文；\item  **成本约束**：在确定"值得"的基础上，还要结合实际的成本预算和延迟要求做最终决策——理论上有收益但成本超出预算的，仍不应采纳。

</details>

**12. 在一个支持"插件/工具市场"的 Agent 平台中（用户可以动态添加第三方工具），上下文工程面临哪些独特挑战？如何应对？**

<details>
<summary>💡 查看答案</summary>

**独特挑战**：\begin{enumerate}
- **工具数量不可控**：用户可能添加大量工具，工具定义本身就可能占用大量 token；\item  **工具质量参差**：第三方工具的 description 质量不可控，可能冗长或不清晰；\item  **动态变化**：工具集随用户配置变化，无法像固定 System Prompt 一样长期缓存；\item  **安全风险**：第三方工具的描述可能包含 Prompt Injection 风险。**应对方案**：
- **工具检索而非全量加载**：不是把用户的所有工具都注册给 Agent，而是根据当前任务语义，从用户的工具集中检索最相关的少数几个（类似 RAG 的思路应用于工具）；\item  **工具描述标准化**：对第三方工具描述进行预处理和精简，统一格式，去除冗余；\item  **分层缓存**：将"用户常用工具集"作为相对稳定的缓存层，长尾工具按需加载；\item  **安全沙箱**：第三方工具描述在注入上下文前，经过安全扫描，过滤可疑指令模式；\item  **使用频率统计**：基于历史使用数据，预测当前任务最可能用到的工具，优先加载。

</details>

**13. 如何为一个"协作编辑"场景（多用户同时与 AI 交互编辑同一文档）设计上下文管理方案？**

<details>
<summary>💡 查看答案</summary>

1. **共享状态层**：文档当前内容作为共享上下文的核心，存储在中心化存储中，所有用户的请求都基于最新版本；\item  **用户特定上下文**：每个用户的对话历史、个人指令偏好独立维护，不混入共享文档上下文；\item  **变更追踪**：记录"自上次该用户交互以来，文档发生了哪些变化"，在该用户下次请求时，将这些变化摘要注入上下文（"其他用户对文档做了以下修改：..."）；\item  **冲突上下文**：如果多个用户的指令可能产生冲突（同时编辑同一段落），上下文中需要包含冲突检测信息；\item  **版本化引用**：上下文中引用文档时附带版本号，确保 AI 基于的是正确版本，避免基于过时版本生成的修改与最新版本冲突；\item  **实时性与一致性权衡**：对于高频协作场景，可能需要在"每次都获取最新文档"（高一致性、高延迟）和"使用稍微过时的缓存版本"（低延迟、可能冲突）之间做权衡，根据冲突频率动态调整。

</details>

**14. 长上下文模型（200K+ token）的出现是否意味着上下文工程会变得不那么重要？请说明你的观点。**

<details>
<summary>💡 查看答案</summary>

不会，反而更重要，但侧重点会转移。\begin{enumerate}
- **成本维度依然存在**：即使模型支持 200K，传入 200K token 的成本是传入 4K 的 50 倍，对于高频应用，盲目"塞满"context 在经济上不可持续；\item  **质量维度的挑战不变**：Lost in the Middle 等问题在长上下文中依然存在，甚至因为内容更多而更突出，"如何组织信息使其被有效利用"这一核心问题没有改变；\item  **新的设计空间**：长上下文使得"一次性传入大量原始材料"成为可能，但这要求上下文工程在更大的尺度上做信息筛选和组织（从"必须精简到4K"变成"在200K中如何安排100K的有效内容"）；\item  **延迟维度**：长上下文显著增加 TTFT，对实时性要求高的应用，仍需要克制上下文长度；\item  **结论**：长上下文模型扩展了"可以做什么"的边界，但"应该做什么"——即如何设计高效、高质量、可控成本的上下文——这一工程问题的重要性不会降低，反而因为可能性空间的扩大而需要更系统的方法论来指导决策。

</details>

**15. 你认为上下文工程未来的发展方向是什么？**

<details>
<summary>💡 查看答案</summary>

（开放题，参考方向）\begin{enumerate}
- **自动化上下文管理**：目前大部分压缩、预算分配策略依赖人工设计规则，未来可能出现能根据任务实时学习最优上下文组织策略的自适应系统（类似强化学习优化上下文调度）；\item  **模型原生的上下文管理能力**：类似 MemGPT 的思路，未来模型可能内置"主动管理自己上下文"的能力（自主决定保留什么、压缩什么），而不完全依赖外部框架；\item  **结构化上下文协议标准化**：随着 Agent 生态发展（MCP 等协议的出现），上下文的组织方式可能走向标准化，类似 API 设计有最佳实践规范；\item  **上下文质量的自动评估**：发展专门的工具自动检测"上下文中哪些内容真正被模型利用了"，指导精简；\item  **跨会话/跨任务的上下文复用**：更智能的长期记忆系统，能够跨任务积累和复用经验性上下文，减少每次从零构建的成本；\item  **多模态上下文管理**：随着多模态应用增加，如何在上下文预算中权衡文本、图像、音频等不同模态内容的"性价比"将成为新课题。

</details>
