# 11.7 Agent Harness 与 Loop Engineering — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 11 章：前沿话题与综合设计 · 共 15 题

**1. 什么是 Agent Harness？它与模型本身的职责边界如何划分？**

<details>
<summary>💡 查看答案</summary>

Agent Harness（智能体运行时）指包裹在大模型外部的一层**确定性运行时**，负责校验、授权、执行、记录模型提出的每一个动作。

**职责划分：**
- **模型（Model）负责"提议"**：基于当前上下文推理、决定下一步该调用哪个工具、传入什么参数、判断任务是否完成；
- **Harness 负责"执行与把关"**：对模型提出的动作做 schema 校验、权限检查、预算控制（token/费用/步数上限）、安全规则拦截，只有通过校验的动作才会被实际执行，并将执行结果、日志、可观测性数据反馈给模型。
**意义：** 没有合格 harness 的 Agent 容易变成"黑箱"——token 泄露、无限循环调用、执行危险指令而无人知晓；有了 harness，Agent 才具备可预测性、安全性和可观测性，这也是 2026 年被广泛认可的 Agent 工程术语（"Agent Harness"）背后的核心动机。行业共识是：харness 设计对最终 Agent 表现的影响，往往和底层模型能力同等重要甚至更大。

</details>

**2. 什么是 Loop Engineering？它试图解决什么问题？**

<details>
<summary>💡 查看答案</summary>

Loop Engineering（循环工程）是 2026 年才被明确命名的概念，核心主张是：**Agent 工程的瓶颈已经从"提示词怎么写"转移到"控制循环怎么设计"**。

**核心要素：**
1. **触发器（Trigger）**：什么条件下启动一次 Agent 循环（用户消息、定时任务、外部事件、其他 Agent 的调用）；
2. **拓扑（Topology）**：循环的执行结构是简单的单线程 ReAct 式循环，还是多 Agent 协作的图结构；
3. **验证器（Verifier）**：每一步或每一轮结束后如何判断当前结果是否可信、是否需要重试；
4. **停止规则（Stop Rule）**：Agent 何时应该主动结束——是任务完成、达到预算上限，还是连续多次未取得进展。
**要解决的问题：** 实践中最常见的失败模式并非模型"不够聪明"，而是循环本身设计不当——比如反复调用同一个失败的工具、在没有真正验证结果的情况下宣称任务完成、遇到异常（如认证失效、依赖服务报错）后无限重试。Loop Engineering 就是要把这些"控制流"问题当作独立于模型能力之外的、需要专门工程设计的对象来对待。

</details>

**3. Agent 执行模式中，Agent Loop、事件驱动、状态机、图编排四种模式各自适合什么场景？**

<details>
<summary>💡 查看答案</summary>

基于对大量开源 Agent 项目的调研，目前主流的执行模式可以归纳为几类，它们在**可控性、表达力、实现难度**上呈现明显的权衡：

- **Agent Loop（推理-行动循环）**：模型在一个循环中自主决定每一步做什么，实现最简单、表达力最强（可以处理开放式、无法提前枚举步骤的任务），但可控性最弱，容易出现前述的循环失控问题，约六成主流开源 Agent 项目采用此模式；
- **事件驱动（Event-driven）**：Agent 的行为由外部事件触发和驱动，适合被动响应式、需要与多个外部系统解耦协作的场景（如"问题追踪器有新 issue 时自动召唤 Agent"）；
- **状态机（State Machine）**：预先定义好任务可能经历的有限状态及状态转移条件，可控性最强，适合流程相对固定、步骤可枚举的结构化任务（如客服工单处理），但表达力受限，难以应对开放式探索任务；
- **图/流程编排（Graph/Flow）**：介于 Agent Loop 与状态机之间，用显式的有向图定义任务的宏观结构（如"规划→执行→验证"三个阶段），但每个节点内部仍可以是一个自主的 Agent Loop，兼顾了结构化控制和局部灵活性，是目前较多生产系统采用的折中方案。
**选择原则：** 任务结构已知、步骤可枚举时应该把结构写成程序（状态机/图），而非把控制权完全交给模型；只有在真正开放式、探索性的任务（无既定流程的头脑风暴、开放研究）中，才更适合让模型主导执行循环。

</details>

**4. 为什么说"Harness 设计"对 Agent 性能的影响，可能比换一个更强的底层模型更大？**

<details>
<summary>💡 查看答案</summary>

有研究报告指出，同一个底层模型在不同 harness 下的任务准确率差距可以达到约六倍之多，这一发现颠覆了"只要模型足够强，Agent 自然表现好"的直觉。

**原因分析：**
- **harness 决定了模型能"看到"什么**：包括暴露给模型的工具集合、每个工具的描述质量、每一步观测（observation）中包含哪些辅助信息，这些直接决定了模型能否获得足够、恰当的上下文来做出正确决策——即使模型能力再强，如果关键信息没有被恰当地组织进上下文，也无从"推理"出正确答案；
- **harness 决定了错误能否被及时纠正**：良好的 harness 会在每一步提供结构化的反馈（如工具调用失败的具体原因、执行结果的结构化摘要），使模型能够快速定位问题并调整策略；粗糙的 harness 只给模型一堆原始日志，模型需要自己从噪声中提炼关键信息，浪费大量上下文和推理步骤；
- **harness 决定了失败模式能否被兜底**：例如认证失效、下游服务报错、模型陷入重复调用等情况，如果 harness 没有相应的检测和处理机制，模型很可能在没有察觉的情况下持续在错误路径上消耗资源。
**结论：** 这也是为什么近期出现了"Meta-Harness"（用 AI 自动搜索最优 harness 配置）这类工作——在模型能力给定的情况下，harness 本身已经成为一个值得系统性优化的独立变量。

</details>

**5. 什么是"reasoning sandwich"分层调度策略？**

<details>
<summary>💡 查看答案</summary>

"reasoning sandwich"（推理三明治）是一种在多阶段 Agent 任务中，根据阶段特性动态分配不同算力/模型档位的调度策略，形象地把整个流程比作三明治结构：

- **顶层（规划阶段）**：使用最大推理预算、能力最强（或思考档位最高）的模型，因为这一阶段的决策（如何拆解任务、选择什么整体策略）错误的代价最大，会在后续所有步骤中被放大；
- **中间层（执行阶段）**：使用中等算力/速度更快的模型完成具体的、相对机械的执行步骤（如按照既定计划调用工具、生成代码），因为这一阶段步骤数量多、单步任务相对简单明确，用最强模型性价比不高；
- **底层（验证阶段）**：同样使用较高推理预算的模型对执行结果做严格校验，因为验证环节的漏检同样会导致错误被放大传播到下游。
**价值：** 相比"从头到尾统一用同一个模型/同一档位算力"的简单方案，这种分层调度能够在保证关键决策质量的同时，显著降低整体的延迟和成本，是目前生产级 Agent 系统中较为成熟的模型路由实践之一。

</details>

**6. Agent Harness 中的权限系统与执行沙箱应该遵循什么设计原则？**

<details>
<summary>💡 查看答案</summary>

- **最小权限原则**：Agent 在执行某个具体任务时，只应被授予完成该任务所必需的最小权限集合，而非默认拥有系统级的完全访问能力，避免因模型的错误决策或被恶意提示注入操纵而造成过度破坏；
- **认证与凭证隔离在工具边界处理**：敏感凭证（如 API Key、数据库密码）的鉴权逻辑应该在 harness 的工具调用边界完成，Agent 的推理过程本身不应直接接触原始凭证，避免凭证通过模型输出意外泄露，也降低了凭证被提示注入攻击窃取的风险；
- **沙箱隔离执行环境**：涉及代码执行、文件系统操作等高风险动作，应该在隔离的沙箱环境（容器、虚拟机）中执行，即使 Agent 执行了有害指令，影响范围也被限制在沙箱内，不会波及宿主系统或其他任务；
- **审批与人工介入机制**：对于影响范围大、不可逆的操作（如删除数据、对外发送邮件、资金交易），应设计显式的审批环节（要求人工确认，或至少记录并允许事后审计/回滚），而不是让 Agent 完全自主执行。

</details>

**7. 什么是 Agent 中的上下文压缩（Context Compaction）？为什么长时程任务中需要它？**

<details>
<summary>💡 查看答案</summary>

长时程 Agent 任务（跨越数十甚至上百步工具调用）会不断累积历史对话、工具调用记录、中间结果，很快就会超出模型的上下文窗口容量，或者即使没有超出，过长且冗余的上下文也会稀释模型对关键信息的注意力、增加推理成本和延迟。

**上下文压缩的常见策略：**
- **摘要压缩**：定期将较早的历史交互总结为简短摘要，替换掉原始的详细记录，只保留结论性信息，代价是可能丢失某些后续会被证明重要的细节；
- **分级存储**：将上下文类比为"工作记忆"，设计类似虚拟内存的分页机制，把不常访问的历史信息"换出"到外部存储，需要时再"换入"，只在当前工作记忆窗口内保留最相关的活跃信息；
- **结构化持久化笔记**：让 Agent 主动维护一份结构化的进展记录（类似任务日志），在上下文被压缩后，这份持久化笔记仍能提供任务的关键脉络，支持跨会话的连续性。
**核心权衡：** 压缩越激进，上下文越精简、推理效率越高，但信息丢失风险越大；如何设计"最小保真度不变量"（保证压缩后依然保留任务正确执行所需的关键信息）是这类机制设计的核心难点。

</details>

**8. 如何检测和防止 Agent 陷入死循环（Loop Detection）？**

<details>
<summary>💡 查看答案</summary>

Agent 在生产环境中一个常见的失败模式是"卡死"在某个局部——反复调用同一个失败的工具、在两个状态之间来回摆动、或者因下游服务持续报错而无限重试。

**检测机制：**
- **行为指纹比对**：记录最近若干步的动作序列（工具名+关键参数的哈希摘要），如果检测到高度重复的模式（如连续多次调用同一工具且参数几乎相同），判定为疑似循环；
- **进展度量**：定义某种可量化的"任务进展"指标（如已完成的子任务数、状态机中的阶段推进），如果连续多轮迭代该指标都没有变化，即使动作本身不完全重复，也应触发预警；
- **熔断联动**：循环检测器应与下游的"熔断器"（circuit breaker）机制联动——如果某个工具处于"开路"（持续失败）状态，Agent 仍然反复尝试调用它，应直接被判定为循环并触发中止或降级处理，而不是让模型自己"意识到"问题。
**处理策略：** 检测到循环后，harness 层通常会强制中断当前循环，可以选择直接终止任务并上报、切换到备用策略（如换一个工具或降级到人工介入），而不是无限期地把决策权继续留给模型。

</details>

**9. Meta-Harness（自动化搜索最优 Harness）的核心思路是什么？**

<details>
<summary>💡 查看答案</summary>

Meta-Harness 是把"设计一个好的 harness"这件事本身也当作一个可以被 AI 自动化搜索优化的问题，而不是完全依赖人工经验设计。

**核心思路：**
- 将 harness 的具体配置（暴露哪些工具、工具描述怎么写、每一步提供哪些辅助观测信息）视为一个可搜索的设计空间；
- 用一个高能力的 LLM Agent 读取候选 harness 配置在一批基准任务上的表现数据，分析其中的失败模式，进而提出改进后的新 harness 配置；
- 通过多轮"提出配置→评测→分析失败→改进配置"的迭代，逐步逼近在给定任务分布下表现更优的 harness 设计，这个过程与前面提到的模型自我改进（STaR 类方法）在方法论上有相通之处，只是优化对象从"模型参数"变成了"harness 配置"。
**局限：** 即使采用了自动化搜索，单纯优化 harness 本身的收益也存在上限——当底层模型能力本身不足以完成某类任务时，无论 harness 设计得多好都无法弥补，这也是相关研究指出的"harness 设计的增益不总是令人满意"的原因，说明 harness 优化和模型能力提升（后训练）需要联合考虑，而非相互独立。

</details>

**10. 为什么说 Harness 设计与模型的后训练（Post-training）之间存在相互影响？**

<details>
<summary>💡 查看答案</summary>

早期关于 harness 的研究大多假设底层模型是固定不变的，只优化 harness 配置；但近期研究开始关注：**当模型本身也在针对特定 harness 做后训练优化时，两者会产生怎样的相互作用**。

- **harness 决定了训练数据的分布**：如果模型的强化学习训练环境使用了某种特定的 harness（提供特定的观测信息格式、特定的工具集合），模型学到的策略会天然地对这套 harness 产生依赖，切换到不同的 harness 配置时性能可能出现明显下降，即"过拟合"到了特定的 harness 假设上；
- **辅助信息的多寡影响模型学到的策略类型**：研究表明，在提供更丰富辅助信息（详细的动作描述、结构化观测）的 harness 下训练出的模型，与在信息更精简的 harness 下训练出的模型，会形成不同的决策模式，且这种差异在任务或工具环境发生变化（分布外泛化）时表现出不同的鲁棒性；
- **实践启示**：这说明"设计 harness"不应该被视为训练完成后的部署阶段工程细节，而应该在后训练阶段就作为一个需要与训练算法协同设计的变量来考虑，尤其是对于计划长期迭代、可能切换执行环境的 Agent 产品而言。

</details>

**11. 什么是 Agent-Computer Interface（ACI）？为什么它的设计会显著影响 Agent 在基准测试上的表现？**

<details>
<summary>💡 查看答案</summary>

Agent-Computer Interface 指 Agent 与计算机系统（文件系统、终端、代码仓库等）交互时所使用的具体接口形式——不是指底层操作系统调用本身，而是指**专门为大模型这种交互方式设计的、经过封装和简化的操作接口**。

**设计要点：**
- **操作粒度适配模型的认知特点**：例如把复杂的多步文件编辑操作封装成单一、语义清晰的"编辑"指令（指定文件、行号范围、新内容），而不是要求模型直接生成底层的 diff 补丁或逐行的 shell 命令，降低模型在底层操作细节上出错的概率；
- **结果反馈的可读性优化**：命令执行后返回的信息应当为模型的理解做过专门优化（如代码搜索结果按相关性排序并提供上下文片段，而非原始的、冗长的终端输出），减少模型需要自行从噪声中提炼有效信息的负担；
- **实证价值**：相关工作（如 SWE-agent）证明，在固定模型能力的前提下，仅仅通过重新设计 ACI（而非改进模型本身），就能在真实软件工程基准上带来显著的任务解决率提升，这也是"harness/接口设计与模型能力同等重要"这一行业共识的重要实证来源之一。

</details>

**12. 可观测性（Observability）在 Agent Harness 中应该覆盖哪些内容？**

<details>
<summary>💡 查看答案</summary>

在生产环境中，Agent 的行为链条比传统软件系统更难预测，完善的可观测性是发现问题、持续改进的基础。

**应覆盖的内容：**
- **完整的执行轨迹（Trace）**：记录每一步的模型输入、模型输出（包括推理过程，如果可获得）、实际调用的工具与参数、工具返回结果，形成可回放、可审计的完整链路；
- **决策点的可追溯性**：能够定位到 Agent 在哪一步做出了错误决策，是因为上下文信息不足、工具描述有歧义，还是模型本身的推理错误，将失败原因归类到具体环节而非笼统地归因为"模型不够好"；
- **资源消耗指标**：token 消耗、调用步数、延迟、成本，按任务类型、按用户维度做细分统计，用于成本控制和异常检测；
- **与循环检测/熔断机制的联动**：可观测性数据不应只用于事后分析，还应实时反馈给前述的循环检测、熔断器等控制机制，形成"观测-决策-干预"的闭环；
- **跨会话的行为模式分析**：聚合大量任务轨迹，识别出系统性的、反复出现的失败模式（而非仅关注单次任务的成败），为 harness 或模型的下一轮改进提供数据支撑，这也是 Meta-Harness 等自动化优化方法所依赖的基础数据来源。

</details>

**13. 什么是 Agent Skills（如 SKILL.md 规范）？它解决了什么问题？**

<details>
<summary>💡 查看答案</summary>

Agent Skills 指将特定领域的最佳实践、操作流程、约束规则封装成结构化的、模型可读的文档（如以 SKILL.md 为入口文件，配合详细的 references 目录），供 Agent 在执行相关任务时按需读取和遵循。

**解决的问题：**
- **避免每次都从零开始"重新发明"最佳实践**：很多领域任务存在踩过无数次坑才总结出的经验规则（如"生成 Word 文档时应该遵循哪些排版规范"），把这些经验固化为可复用的 Skill 文档，比依赖模型每次临场发挥更可靠、更一致；
- **按需加载、避免上下文膨胀**：Skill 通常设计成分层结构——入口文件简明扼要，只有当任务确实涉及该领域时才进一步加载详细的参考资料，避免把所有可能用到的知识一次性塞进系统提示词造成上下文浪费；
- **可维护性与可迭代性**：Skill 以文档形式存在，可以独立于模型本身进行迭代更新（发现新的最佳实践或修正错误认知时，直接修改文档即可），不需要重新训练模型，这也是"harness 之外的另一层可迭代资产"——把经验固化在外部可编辑的自然语言资产中，而不是模型参数里。

</details>

**14. Harness Engineering 与传统软件工程中的"契约式设计"（Design by Contract）有什么共通之处？**

<details>
<summary>💡 查看答案</summary>

契约式设计是一种传统软件工程方法论，核心思想是为每个模块/函数明确定义**前置条件（调用者必须保证什么）、后置条件（模块承诺返回什么）、不变量（过程中必须始终保持的性质）**，通过这种显式契约来保证系统各部分之间协作的可靠性。

**与 Harness Engineering 的共通之处：**
- **把不确定的部分和确定的部分显式分开**：契约式设计把"如何实现"（可能变化、可能有 bug）和"承诺提供什么保证"（相对稳定的契约）分开；Harness Engineering 同样把"模型的不确定推理"和"harness 的确定性执行保证"显式分开，两者都是通过明确的边界划分来管理复杂系统中的不确定性；
- **校验作为一等公民**：契约式设计强调在运行时主动校验前置/后置条件是否满足，一旦违反立即报错而非静默出错；Harness 对模型提出的每个动作做 schema 校验、权限校验，同样是"运行时主动校验、拒绝不合规输入"的思路；
- **对不可信来源的防御性设计**：契约式设计假设调用者可能不遵守约定，因此模块自身要做防御性检查；Harness 则更进一步——它对待模型的态度类似于对待一个**本质上不可完全信任的调用者**（模型可能产生幻觉、被提示注入操纵、犯逻辑错误），因此必须在 harness 层做独立的、不依赖模型自觉性的安全校验，这也是为什么 Harness Engineering 被认为是契约式设计思想在 Agent 时代的自然延伸和发展。

</details>

**15. Agent Harness 中的工具注册表（Tool Registry）应该如何设计？**

<details>
<summary>💡 查看答案</summary>

工具注册表是 harness 中管理"模型可以调用哪些工具"的核心组件，随着 Agent 接入的工具（尤其是通过 MCP 等协议接入的第三方工具）数量增长，其设计质量直接影响 Agent 的可靠性和效率。

**关键设计要点：**
- **清晰、消歧的工具描述**：每个工具的名称、参数说明、使用场景描述需要足够清晰且相互之间不产生歧义，模糊或重叠的工具描述是导致模型选错工具、传错参数的常见原因，这也是前述"harness 设计影响准确率数倍"的重要来源之一；
- **按需动态注册与检索**：当可用工具数量很大时（如企业级场景接入数十个 MCP Server），不宜将所有工具描述一次性塞进上下文，而应该支持按任务相关性动态检索、注册当前任务实际需要的工具子集，减少上下文膨胀和模型选择时的干扰；
- **版本管理与兼容性**：工具的接口（参数、返回格式）可能随时间演进，注册表需要维护版本信息，避免模型基于过时的工具描述生成不兼容的调用；
- **调用审计与限流**：注册表应记录每个工具的调用频次、成功率、平均延迟，并支持按工具、按任务设置调用配额，作为前述可观测性体系和成本控制体系的数据来源之一。

</details>
