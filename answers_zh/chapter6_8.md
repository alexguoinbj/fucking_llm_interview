# 6.8 Agent 系统设计综合题 — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 6 章：Agent · 共 7 题

**1. 请设计一个能自动完成"读取需求文档→生成代码→运行测试→修复 bug"全流程的 Agent，描述架构和关键设计决策。**

<details>
<summary>💡 查看答案</summary>

**架构设计：**
- **Orchestrator Agent**：负责整体规划和协调，接收需求文档，分配子任务，监控进度
- **需求分析 Agent**：解析需求文档，生成结构化需求列表和验收标准
- **代码生成 Agent**：根据需求生成代码，调用代码执行工具验证语法
- **测试执行 Agent**：运行测试套件，收集失败测试用例和错误信息
- **Debug Agent**：分析错误，生成修复方案，调用代码执行验证
**关键设计决策：**
1. 设置最大修复循环次数（如 5 次），防止无限 debug 循环；
2. 所有代码执行在沙箱中进行，防止测试代码破坏环境；
3. 每次生成代码和修复后，用 git diff 记录变更，支持回滚；
4. 测试失败超过阈值时，暂停并请求人工审查；
5. 需求文档→测试用例的映射关系全程跟踪，确保所有需求都有对应测试覆盖。

</details>

**2. 如果让你从零构建一个企业级 Agent 平台，核心模块有哪些？**

<details>
<summary>💡 查看答案</summary>

核心模块：\begin{enumerate}
- **Agent 编排引擎**：支持 Agentic Loop、Multi-Agent 协作、并行执行的核心运行时；\item  **工具注册与管理**：工具的注册、版本管理、权限控制、监控；\item  **记忆系统**：短期上下文管理 + 长期向量存储 + 情节记忆，统一接口；\item  **状态管理**：任务状态持久化、检查点、断点续跑；\item  **安全层**：Prompt Injection 检测、权限校验、操作审计；\item  **可观测性**：分布式追踪、指标采集、日志管理、实时 Dashboard；\item  **测试框架**：Mock 工具、端到端测试套件、回归测试 CI/CD；\item  **发布管理**：Agent 逻辑版本控制、灰度发布、快速回滚；\item  **计费与配额**：按 token 消耗计费、用户配额管理；\item  **开发者门户**：Agent 配置界面、工具市场、文档和示例。

</details>

**3. 如何设计一个能可靠执行长达数小时任务的 Agent？**

<details>
<summary>💡 查看答案</summary>

1. **状态持久化**：每步完成后将状态序列化到外部存储，支持任意时刻断点续跑；\item  **检查点机制**：在主要子任务完成后保存检查点，而不只是每步保存；\item  **幂等操作设计**：所有工具调用幂等，重试不产生副作用；\item  **上下文管理**：滚动摘要 + 外部记忆，防止上下文溢出；\item  **人机检查点**：每完成一个大的里程碑，向用户报告进度并确认继续；\item  **资源上限**：设置最大步骤数、最大时间、最大 token 预算的硬限制；\item  **监控告警**：长时间无进展时告警；\item  **错误预算**：允许一定比例的步骤失败和重试，但设置总体失败预算上限。

</details>

**4. Agent 的"幻觉"如何在综合系统设计中被缓解？**

<details>
<summary>💡 查看答案</summary>

从系统设计层面综合缓解幻觉：\begin{enumerate}
- 工具参数强验证（Schema 校验，拒绝不合法参数）；\item  结果 grounding（后续步骤必须引用工具返回内容，不允许无来源的"知识"）；\item  状态显式化（用结构化状态对象跟踪进度，不依赖 LLM 记忆）；\item  关键步骤验证（执行不可逆操作前，让 LLM 重述执行计划并确认）；\item  外部状态核验（定期用工具实际查询，而不是依赖 LLM 对历史的记忆）。

</details>

**5. 复杂任务的拆解（Task Decomposition）应该怎么做？**

<details>
<summary>💡 查看答案</summary>

任务分解的粒度设计是 Agent 规划质量的核心权衡——分解得太粗，单个步骤的复杂度仍然过高，模型难以一次性可靠执行；分解得太细，步骤数量爆炸式增长，协调和管理成本急剧上升。

1. **两阶段分解策略**：第一阶段生成高层次的里程碑划分（任务的几个主要阶段），这一层不需要过于精确，只要逻辑结构合理；第二阶段在即将执行某个里程碑时，才将其细化展开为具体可执行的子任务，这种"先粗后细"的方式避免了一开始就在不确定信息下追求过度精确的全量分解。
2. **粒度与可执行能力对齐**：分解的最小颗粒度应该恰好对应一个工具调用或一次明确的 LLM 推理，既不应该把"调用一个 API"再进一步拆分为更细的子步骤（过度分解），也不应该把需要多个工具协同才能完成的复杂操作打包为一个步骤（分解不足导致执行不可靠）。
3. **依赖关系的清晰表达**：分解出的子任务应明确标注彼此之间的依赖关系（哪些必须顺序执行，哪些可以并行），这种依赖结构本身就是分解质量的体现——过度细碎的分解往往伴随着复杂混乱的依赖网络，难以高效调度。
4. **动态调整分解粒度**：分解粒度不应是一成不变的，应根据执行过程中观察到的实际复杂度动态调整——如果某个子任务执行中发现比预期复杂，可以进一步拆分；如果发现几个子任务可以合并简化，也应灵活合并，而非机械遵循最初的分解方案。
5. **协调成本的显式考量**：评估分解方案时应该将协调开销（步骤间数据传递、状态同步、错误处理的复杂度）纳入考量，而不仅仅关注"逻辑上是否可以再细分"，过度分解带来的协调成本有时会超过分解本身带来的清晰度收益。

</details>

**6. Agent 如何为多个待办任务设定执行优先级？**

<details>
<summary>💡 查看答案</summary>

Multi-Agent 系统中的任务优先级排序直接影响整体吞吐量和关键任务的响应速度，需要结合任务的多维属性设计合理的调度策略。

1. **依赖约束层（优先级排序的基础约束）**：优先级排序的第一原则是不违反依赖关系——前置任务未完成的任务，无论优先级多高都不能执行。先做拓扑排序确定"当前可执行的任务集合"（所有前置任务已完成），再在这个集合内按优先级排序，保证顺序合法性。
2. **紧急程度（Deadline-Driven）**：有截止时间的任务优先，采用 EDF（Earliest Deadline First）策略——在可执行任务集合中，截止时间最近的任务优先分配 Agent 资源。对于没有显式截止时间的任务，根据任务类型预设"隐式 SLA"（如实时用户交互任务的隐式截止时间为 5 秒，批处理任务为 1 小时）。
3. **关键路径优先**：标识整体任务图的关键路径（延误会影响最终完成时间的路径），关键路径上的任务优先级高于非关键路径，因为关键路径任务的延误会直接推迟系统整体目标的完成，而非关键任务有"浮动时间"可以适当延后。
4. **资源感知调度**：不只按优先级排序，还要考虑当前资源可用性——资源需求与当前可用资源最匹配的任务优先调度，避免因为高优先级任务需要的资源暂时不足，导致低资源需求的中等优先级任务也空等（资源饥饿）。
5. **防饥饿机制**：纯优先级调度会导致低优先级任务长期得不到执行（饥饿）。引入"等待时间加权"——任务等待时间越长，有效优先级自动提升，确保所有任务最终都能被执行，避免低优先级任务被无限推迟。

</details>
