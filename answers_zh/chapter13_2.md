# 13.2 检索架构与损失函数 — 题目与答案

**1. 双编码器和交叉编码器有什么区别？假设你需要构建一个大规模语义搜索引擎，你会优先选择哪种架构？**

<details>
<summary>💡 查看答案</summary>

**双编码器（Dual Encoder / Bi-Encoder）**：

- 使用同一个（或两个独立的）编码器分别对 query 和 document 进行编码，各自得到一个固定维度的向量表征；
- 通过计算两个向量之间的相似度（如余弦相似度、点积）来衡量它们的相关性；
- query 和 document 的编码过程是**独立的、互不依赖**的——document 的向量可以**预先离线计算并建立索引**（如使用近似最近邻 ANN 索引：FAISS、HNSW 等）；
- 在线检索时只需对 query 编码一次，再通过 ANN 索引快速查找最相似的若干 document 向量，检索速度极快（毫秒级，可扩展到百万/亿级文档）。
- 缺点：由于 query 和 document 是独立编码的，无法在编码阶段进行 token 级别的交叉注意力，对细粒度的语义匹配（如多跳推理、精确措辞匹配）建模能力较弱，相关性判断的精度通常不如交叉编码器。

 **交叉编码器（Cross-Encoder）**：

- 将 query 和 document 拼接成一个输入序列，一起送入同一个 Transformer 模型，通过自注意力机制让 query 和 document 的 token 之间充分交互；
- 模型输出一个标量分数（如经过一个分类头），直接表示该 query-document 对的相关性得分；
- 由于每次推理都需要对 query 和某个具体的 document 同时编码，**无法预先计算和缓存 document 表征**，每来一个新的 (query, document) 对都需要重新跑一遍完整的 Transformer 前向，计算成本远高于双编码器；
- 优点：由于有充分的 token 级交互，相关性判断的精度通常显著高于双编码器。

 **大规模语义搜索引擎的架构选择**：  对于需要在海量文档（百万到亿级）中进行实时检索的场景，**应优先选择双编码器作为第一阶段（召回阶段）**，原因是：

- 双编码器可以离线对所有文档预计算向量并建立 ANN 索引，在线检索时延迟低、可扩展性强；
- 交叉编码器由于无法预计算，若直接对全量文档逐一计算相关性得分，计算量是不可接受的（O(N) 次完整 Transformer 前向，N 为文档总数）。

 实践中通常采用**两阶段架构（Retrieve-and-Rerank）**：

1. **第一阶段（召回，Retrieval）**：用双编码器从海量文档中快速召回 top-k（如 k=100）个候选；
2. **第二阶段（精排，Reranking）**：用交叉编码器对这 k 个候选与 query 逐一计算更精确的相关性得分，重新排序，输出最终结果。

 这种组合既利用了双编码器的高效可扩展性，又利用了交叉编码器的高精度，是大规模语义搜索引擎的标准设计模式。

</details>

**2. 除了双编码器和交叉编码器，还有哪些检索架构？多向量（Multi-vector）表征（如 ColBERT）是如何工作的，相比单向量双编码器有什么优劣？**

<details>
<summary>💡 查看答案</summary>

除了单向量的双编码器（Bi-Encoder）和需要联合编码的交叉编码器（Cross-Encoder），还存在介于两者之间的**多向量（后期交互，Late Interaction）架构**，代表工作是 ColBERT。

**1. 核心思路**

- 双编码器将整个 query 和整个 document 分别压缩成**一个**固定长度向量，再计算两个向量的相似度（如余弦相似度），压缩过程会丢失细粒度的词级别信息；
- ColBERT 这类多向量方法则保留 query 和 document 中**每个 token** 编码后的向量（而不是池化成一个向量），检索时对 query 的每个 token 向量，在 document 的所有 token 向量中找到最相似的那个（MaxSim 操作），再对 query 所有 token 的最大相似度求和，作为整个 query-document 对的相关性分数；
- 这种\"先分别编码、后进行细粒度交互\"的方式被称为**后期交互**，介于双编码器（完全不交互，早期即压缩成单向量）和交叉编码器（从输入层就开始交互）之间。

**2. 相比双编码器的优势**

- 保留了词级别的匹配信息，对于关键词高度敏感的场景（如包含专有名词、代码片段、罕见实体的查询）通常比单向量双编码器有更高的检索精度，因为单一向量很容易在压缩过程中\"平均掉\"这些关键细节；
- 相比交叉编码器，document 侧的 token 向量仍然可以离线预先计算并建立索引，在线阶段只需要编码 query 并做向量间的 MaxSim 计算，因此在效果和效率之间取得了比交叉编码器更好的平衡，仍然支持大规模检索（配合专门的近似检索索引，如 PLAID）。

**3. 相比双编码器的代价**

- 存储成本显著更高：需要为 document 的每个 token 都存储一个向量（而不是一个句子只存一个向量），索引体积可能是单向量方法的数十倍；
- 检索时的计算和工程复杂度更高：需要专门设计的近似最近邻检索和后处理流程（如先用轻量方法召回候选，再对候选做精确的 MaxSim 重排序），不能直接复用标准的单向量 ANN（近似最近邻）检索库。

总结来说，双编码器、多向量（ColBERT 式后期交互）、交叉编码器三者构成了一个\"效率-精度\"的连续谱：双编码器最快但信息损失最大，交叉编码器最准但无法离线预计算、成本最高，多向量方案通过保留 token 级别向量在两者之间取得折中，通常用于对检索精度要求较高、且能承受更高存储成本的场景，实践中也常作为双编码器初筛之后的第二阶段重排序方案之一。

</details>

**3. 稀疏检索（如 BM25/SPLADE）与稠密检索（Dense Retrieval，即嵌入模型检索）各有什么优劣？**

<details>
<summary>💡 查看答案</summary>

稀疏检索和稠密检索是文本检索领域两条并行发展的技术路线，理解两者的本质差异是设计检索系统的基础：

- **稀疏检索**：以 BM25 为代表，本质是基于词汇精确匹配（结合词频、逆文档频率等统计信息）打分，向量表示是高维稀疏的（维度等于词表大小，绝大多数维度为零），优点是对关键词、专有名词、精确术语的匹配非常可靠（不会因为语义相近但用词不同而漏检），可解释性强，且不需要训练即可使用，长期作为工业级搜索引擎的基础组件；缺点是无法处理语义层面的同义词、改写、跨语言等情况（用户查询和文档措辞不同则难以匹配）；
- **稠密检索**：即基于嵌入模型的语义检索，将 query 和 document 编码为低维稠密向量，通过向量相似度检索，优点是能够捕捉语义层面的相关性，对同义改写、跨语言等场景有较好的泛化能力；缺点是对精确的关键词/术语匹配可能不够可靠（例如产品型号、专有名词等精确匹配需求，稠密向量有时会因为过度关注整体语义而"模糊"掉这些关键细节），且需要训练数据和算力支持；
- **两者的互补性**：稀疏检索擅长精确匹配、稠密检索擅长语义泛化，两者在失效场景上往往具有一定互补性，这也是后续混合检索方案被广泛采用的原因。

总结来说，稀疏检索和稠密检索分别代表了"精确词汇匹配"和"语义相似度匹配"两种不同的检索范式，各有各的适用场景和局限性，实际生产系统中很少单独依赖其中一种，而是倾向于将两者结合使用以取长补短。

</details>

**4. SPLADE 等\"学习型稀疏表示\"方法是如何训练的？相比传统 BM25 有什么改进？**

<details>
<summary>💡 查看答案</summary>

SPLADE（Sparse Lexical and Expansion Model）代表了介于传统稀疏检索和稠密检索之间的一类方法：用神经网络学习出的稀疏向量表示，而不是像 BM25 那样基于固定的统计公式：

- **核心思路**：仍然沿用稀疏向量的形式（向量维度等于词表大小），但每个维度的权重不再由词频统计公式计算，而是通过一个类似掩码语言模型的神经网络头，为输入文本中每个位置预测其对词表中各个词的"重要性得分"，再通过某种池化（如取最大值）汇总成整个文本的稀疏权重向量；
- **词项扩展（Term Expansion）能力**：与 BM25 只能匹配文本中**实际出现**的词不同，SPLADE 的神经网络头可以为文本中原本没有出现、但语义相关的词也赋予非零权重（例如输入"汽车"，模型可能给"车辆"、"轿车"等相关词也分配一定权重），这相当于隐式地做了查询/文档扩展，缓解了传统稀疏检索无法处理同义词的问题；
- **训练方式**：与稠密检索类似，SPLADE 也使用对比学习（如 InfoNCE）训练，只是相似度计算基于稀疏向量的点积，同时通常会加入一个正则化项（如 FLOPS 正则化）鼓励向量保持一定的稀疏性，避免退化成稠密向量（否则会失去稀疏检索在存储和检索效率上的优势）；
- **相比 BM25 的改进**：由于引入了神经网络学到的语义信息，SPLADE 在保留稀疏检索精确匹配优势和高效倒排索引检索能力的同时，具备了一定的语义泛化能力，在多个检索评测基准上effect通常优于传统 BM25，也优于纯稠密检索在某些精确匹配场景下的表现，是近年来学界和工业界都比较关注的"第三条路线"。

总结来说，SPLADE 通过用神经网络替代传统统计公式来学习稀疏向量权重，兼具了稀疏检索的高效倒排索引能力和一定的语义泛化能力（词项扩展），是稀疏检索和稠密检索之间一条值得关注的技术路线，尤其适合对精确匹配和语义泛化都有较高要求、且希望复用现有稀疏检索基础设施（倒排索引）的场景。

</details>

**5. 什么是混合检索（Hybrid Search）？如何将稀疏检索和稠密检索的结果融合排序（如 RRF）？**

<details>
<summary>💡 查看答案</summary>

混合检索是指同时使用稀疏检索（如 BM25）和稠密检索（嵌入模型）分别召回候选结果，再将两路结果融合成最终排序的检索架构，是当前生产级检索系统中非常常见的实践：

- **为什么需要混合**：如前所述，稀疏检索和稠密检索在失效场景上具有互补性——稀疏检索擅长精确匹配（关键词、术语、编号等），稠密检索擅长语义泛化（同义改写、跨语言、模糊查询），混合使用能同时兼顾两方面的检索质量；
- **融合方式一：分数加权融合**：将两路检索结果的相关性得分（需要先做归一化，因为 BM25 分数和向量相似度分数的量纲/分布完全不同）按一定权重加权求和，得到融合后的最终得分，权重可以是固定的经验值，也可以通过验证集调优或用一个轻量级模型学习得到；
- **融合方式二：Reciprocal Rank Fusion（RRF，倒数排名融合）**：不直接使用原始分数（避免不同检索方式分数量纲不一致的问题），而是仅利用每个文档在各自检索结果中的**排名**，融合得分计算为 $\sum_i \frac{1}{k + rank_i(d)}$（$k$ 是一个平滑常数，通常取 60），对每一路检索结果中排名靠前的文档赋予更高的融合得分，最后按融合得分重新排序；RRF 的优点是不需要对原始分数做任何归一化处理，实现简单、鲁棒性好，在实践中被广泛采用；
- **融合方式三：使用重排序模型**：将两路检索结果合并去重后的候选集合，交给一个独立的重排序模型（如交叉编码器）统一打分排序，不依赖任何显式的分数融合规则，效果通常更好但计算成本更高，一般用于候选数量已经通过前两路检索大幅缩减之后的最终精排阶段。

总结来说，混合检索通过并行运行稀疏和稠密两种检索方式并融合结果，能够同时获得关键词精确匹配和语义泛化两方面的优势，RRF 因其简单、无需处理分数量纲问题而成为最常用的融合方法之一，在对检索质量要求更高的场景下，也可以在融合后再叠加一层重排序模型进一步提升精度。



![工业级双塔向量检索 + BM25 稀疏检索 + 交叉编码器重排的混合检索架构图](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter13/fig_hybrid_search_rerank.png)

</details>

**6. 在完整的检索系统中，为什么通常采用\"召回-粗排-精排\"的多阶段（Multi-stage）架构，而不是直接用一个模型完成所有工作？**

<details>
<summary>💡 查看答案</summary>

现代大规模检索系统（尤其是 RAG、搜索引擎场景）几乎都采用分阶段的漏斗型架构，而不是用单一模型端到端解决，主要出于效果和效率的权衡：

- **第一阶段：召回（Recall/Retrieval）**：从海量候选（可能是数百万到数十亿级别的文档）中，用计算效率最高的方法（通常是双编码器的向量检索，或稀疏检索/混合检索）快速筛选出一个规模大幅缩小（如几百到几千个）的候选集合，这一阶段追求**高召回率**（尽量不漏掉真正相关的文档），对精度要求相对较低，因为后续阶段还会进一步精炼排序；
- **第二阶段：粗排（Pre-ranking，可选）**：对于候选集合规模仍然较大的场景（如电商搜索候选可能仍有数千个），会插入一个中间的粗排阶段，用比精排更轻量、但比召回阶段更精细的模型（如轻量级的双塔模型或简化版交叉编码器）进一步缩小候选集合规模；
- **第三阶段：精排（Re-ranking）**：对经过前几阶段筛选后规模已经很小的候选集合（如几十到一百个），使用计算成本最高但精度也最高的模型（通常是交叉编码器，或结合多种特征的复杂排序模型）做最终的精细排序，直接决定展示给用户的最终结果顺序；
- **为什么不能只用一个模型**：如果直接用交叉编码器这类精度最高的模型对全量候选做检索，计算成本是不可接受的（需要对每个候选都和 query 一起过一遍模型，无法预先索引、无法利用向量检索的高效近似最近邻算法）；而如果只用最高效的双编码器做到最后一步，由于双编码器在精细排序上的精度通常不及交叉编码器（如前面提到的架构对比），最终排序质量会有损失；多阶段架构本质上是在效率和精度之间做梯次权衡，让计算成本随着候选集合规模的缩小而逐步增加。

总结来说，多阶段检索架构通过"用最高效的方法快速缩小候选范围，再用逐渐更精细但更昂贵的方法层层筛选"的漏斗式设计，在保证最终排序精度的同时，将整体检索延迟和计算成本控制在可接受范围内，是处理大规模检索场景的标准工程实践。

</details>

**7. 在训练交叉编码器作为重排序（Reranker）模型时，Pointwise、Pairwise、Listwise 三种训练目标各有什么特点？**

<details>
<summary>💡 查看答案</summary>

交叉编码器常被用作检索 pipeline 中的重排序模型，训练目标的设计（即如何定义损失函数）有三种主流范式，源自传统的学习排序（Learning to Rank）领域：

- **Pointwise（点式）**：将排序问题转化为独立的回归或分类问题，对每个 (query, document) 对单独打一个相关性得分（如二分类：相关/不相关，或多级评分：0-4 分的相关性等级），训练时每个样本独立计算损失（如交叉熵或均方误差），不考虑同一 query 下不同候选之间的相对关系；优点是实现简单、训练稳定；缺点是没有显式建模"排序"这一目标本身，模型学到的是绝对相关性判断，而实际业务关心的往往是候选之间的**相对顺序**，两者不完全等价；
- **Pairwise（对式）**：每次取同一个 query 下的两个候选文档（一个相关性更高、一个相关性更低），训练模型学会正确判断"哪个候选排在前面"，损失函数通常要求相关性更高候选的打分显著超过相关性更低的候选（类似前面提到的 Triplet Loss 思路，但这里比较的是同一 query 下的两个候选而非跨样本的正负例），相比 pointwise 更直接地建模了排序关系，是三者中最常见的训练方式之一；
- **Listwise（列式）**：直接以整个候选列表的排序质量作为优化目标，损失函数考虑同一 query 下**所有**候选文档之间的相对顺序关系（而不仅仅是两两比较），通常直接优化与 nDCG 等排序评估指标更接近的目标（如 ListNet 通过 softmax 建模整个候选列表的排列概率分布，LambdaRank 直接将 nDCG 的变化量作为梯度权重），理论上与最终的排序评估指标（nDCG 等）对齐度最高，但实现和训练相对更复杂，对每个 query 需要同时处理多个候选。

总结来说，三种训练目标在\"建模复杂度\"和\"与最终排序目标的对齐程度\"上依次递进：pointwise 最简单但与排序目标对齐度最低，pairwise 是效果和实现复杂度之间较为均衡的常用选择，listwise 理论上最优但工程实现和调参更复杂，实践中很多重排序模型（包括开源的交叉编码器 reranker）采用 pairwise 或结合多种目标的混合训练方式。

</details>

**8. 为什么交叉编码器（Cross-Encoder）计算成本很高，无法直接用于大规模候选的召回阶段？**

<details>
<summary>💡 查看答案</summary>

理解交叉编码器的计算复杂度瓶颈，是理解为什么检索系统需要多阶段架构、为什么双编码器和交叉编码器要分工协作的关键：

- **计算方式的本质差异**：双编码器分别独立地对 query 和 document 编码，document 侧的向量可以**提前离线计算好并建立索引**，在线阶段只需要编码一次 query，再通过高效的近似最近邻检索算法在预建索引中查找，检索一次的计算复杂度与候选文档总数基本无关（得益于 ANN 索引的对数级或次线性复杂度）；交叉编码器则需要将 query 和**每一个**候选 document 拼接在一起，作为一个整体输入模型做联合编码，这意味着 document 侧的表示**无法**脱离具体的 query 提前计算和缓存——每来一个新 query，都需要对候选集合中的每一个文档重新做一次完整的前向传播；
- **复杂度对比**：假设候选文档总数为 $N$，双编码器检索的在线计算复杂度大致是 $O(\log N)$（借助 ANN 索引）；而交叉编码器需要对每个候选都做一次完整的 Transformer 前向计算，复杂度是 $O(N)$，且每次前向计算本身的开销（尤其是拼接后的序列长度更长）也远高于双编码器单独编码一个较短的 query；
- **实际影响**：如果候选文档规模是百万甚至更大级别，用交叉编码器对全量候选做打分，单次查询的延迟和计算成本是完全不可接受的（可能需要数分钟甚至更长，而实际检索场景通常要求毫秒到百毫秒级的响应速度）；这正是为什么交叉编码器只能被用在候选集合已经被大幅缩小之后的精排阶段（如前面提到的几十到几百个候选），而不能承担全量候选的召回工作。

总结来说，交叉编码器由于必须对 query 和每个候选文档联合编码、无法像双编码器那样预先离线计算候选表示并建立高效索引，计算复杂度随候选规模线性增长，因此只适合在候选数量已经被前序阶段大幅压缩之后承担精细排序工作，而无法直接应用于面对海量候选的召回阶段，这也是多阶段检索架构存在的核心工程原因之一。

</details>

**9. 能否将交叉编码器和双编码器联合训练（例如共享部分底层参数或用交叉编码器指导双编码器训练），以提升双编码器的效果？**

<details>
<summary>💡 查看答案</summary>

除了前面提到的知识蒸馏思路（用交叉编码器蒸馏双编码器学习相似度/排序关系），交叉编码器和双编码器之间还存在其他可能的联合训练/协同优化方式：

- **共享底层编码器参数**：让双编码器和交叉编码器共享同一个底层预训练模型的部分层（如共享前若干层 Transformer 层，仅在顶层分叉出双编码器分支和交叉编码器分支各自独立的层），在多任务框架下联合训练两个分支的损失，这样底层的语言理解能力可以在两种架构之间共享，理论上双编码器能间接受益于交叉编码器训练信号带来的更精细的语义理解能力；
- **交叉编码器打分作为难负例挖掘的辅助工具**：如前面提到的难负例挖掘方法之一，用训练好的（或联合训练过程中的）交叉编码器为双编码器挖掘更精准的难负例，这是一种间接的\"协同\"，交叉编码器本身不直接参与双编码器的梯度更新，但为双编码器提供了更高质量的训练数据；
- **迭代式协同训练（类似自蒸馏循环）**：先训练一个交叉编码器（通常用高质量标注数据），用它蒸馏/指导双编码器训练；训练好的双编码器再用于挖掘新一轮的难负例，重新训练/微调交叉编码器；如此循环迭代，两个模型互相促进，这种"生成器-判别器"式的迭代训练思路在多个检索相关工作中都有体现；
- **代价与工程复杂度**：联合训练相比独立训练两个模型引入了更高的工程复杂度（需要设计合理的多任务损失权重、共享层的梯度可能互相干扰导致训练不稳定），实践中是否采用联合训练需要权衡额外的效果收益是否能覆盖工程复杂度的增加，很多场景下"先训练强交叉编码器，再单向蒸馏双编码器"这种更简单的流程已经能取得不错的效果，不一定需要更复杂的联合/迭代训练。

总结来说，交叉编码器和双编码器可以通过共享底层参数、蒸馏、难负例挖掘、迭代式协同训练等多种方式产生联系并互相提升，核心思路都是让计算成本较高但判断更精确的交叉编码器，以某种方式将其"精确判断力"传递给计算高效但精度略逊的双编码器，具体采用哪种联合方式需要结合工程复杂度和实际效果收益权衡。

</details>

**10. 将 Transformer 输出转换为单个句子向量时，常见的池化（Pooling）策略有哪些？各自的优缺点是什么？**

<details>
<summary>💡 查看答案</summary>

Transformer 编码器对输入的每个 token 都会输出一个向量，要得到一个代表整句话的固定长度嵌入，需要通过某种池化策略将这些 token 级别的向量聚合成一个句子向量，常见策略包括：

**1. [CLS] / 特殊词元池化**

- 直接取序列开头特殊词元（如 BERT 的 [CLS]）对应位置的输出向量作为句子表征；
- 优点：实现简单，且如果模型经过针对该词元的专门训练（如下一句预测、对比学习目标直接监督该位置），该词元可以学到较强的整句语义汇聚能力；
- 缺点：如果模型没有专门针对该词元做训练（如仅使用掩码语言模型预训练的原始 BERT），[CLS] 位置的向量往往质量较差，直接用于相似度计算效果不佳。

**2. 平均池化（Mean Pooling）**

- 对序列中所有（非 padding）token 的输出向量取平均，作为句子表征；
- 优点：不依赖某一个特定位置，充分利用了序列中每个 token 的信息，在 Sentence-BERT 等大量实践中被验证为效果通常优于原始 [CLS]，是目前最常用的默认策略之一；
- 缺点：对所有 token 一视同仁，可能被句子中不重要的词（如虚词、停用词）稀释关键信息，长句子中真正关键的少数词可能被平均掉。

**3. 最后一个 token 池化（Last-token Pooling）**

- 取序列最后一个 token（对于自回归/因果注意力模型，如基于 GPT 架构的嵌入模型）的输出向量作为句子表征，因为在因果注意力机制下，最后一个 token 是唯一能看到全部前文信息的位置；
- 优点：与因果语言模型的架构天然契合（双向注意力模型的 mean pooling 不完全适用于纯因果模型），近年基于大模型（如 LLM 转嵌入模型）的方案多采用这种策略；
- 缺点：仅依赖单一位置，对该位置的表征质量高度敏感，通常需要额外的对比学习微调才能让该位置学到高质量的整句语义（预训练阶段该位置主要用于预测下一个词，不天然适合语义汇聚）。

**4. 最大池化（Max Pooling）**

- 对每个维度取所有 token 上的最大值，实践中效果通常不如平均池化稳定，在句子嵌入任务中使用较少，更多见于早期的 CNN/词向量时代。

总结来说，池化策略的选择需要结合模型架构（双向 vs 因果）和训练方式（是否有专门针对某个位置的监督信号）：双向编码器在有对比学习微调的情况下平均池化通常是稳健的默认选择；基于因果架构的大模型嵌入方案多采用最后一个 token 池化；[CLS] 池化则高度依赖预训练/微调阶段是否专门优化了该位置，不能想当然地直接使用未经微调的 [CLS] 向量。

</details>

**11. 为什么很多嵌入模型会在 Transformer 编码器输出（池化后）再接一层线性投影（Projection Head）？这一层的作用是什么？**

<details>
<summary>💡 查看答案</summary>

观察很多嵌入模型（包括图像领域的 SimCLR 以及不少文本嵌入模型）的架构设计，会发现在编码器主干输出经过池化得到句子向量后，通常还会额外接一个小型的投影头（通常是一到两层线性变换，或加非线性激活），这一设计有其特定考量：

- **分离"通用语言表征"和"对比学习专用表征"**：编码器主干（如 BERT）的深层参数中蕴含了丰富的通用语言理解能力，这些能力不一定完全适合直接用于计算相似度这一特定任务；投影头的作用是在编码器主干输出之上，学习一个专门针对对比学习目标优化的映射，让最终用于计算相似度的向量空间与编码器内部原始的表征空间适度解耦；
- **图像领域的经验（SimCLR 的发现）**：在图像对比学习的开创性工作 SimCLR 中，实验发现如果直接在编码器主干的原始输出上计算对比损失，效果不如\"编码器主干输出 → 投影头 → 计算对比损失\"这一设计；更重要的是，在下游任务中使用向量时，直接使用**编码器主干的输出**（而不是投影头之后的输出）效果反而更好，这说明投影头在训练阶段承担了一部分"为了满足对比学习目标而不得不做的、可能对通用表征有一定损伤的变换"，将这种变换隔离在投影头中，可以保护主干网络输出的表征质量不被对比学习目标过度"扭曲"；
- **文本嵌入模型中的实践差异**：不同于图像领域，很多文本嵌入模型（尤其是 Sentence-BERT 一脉的工作）实际使用时就是直接用池化后（可能经过投影头）的向量作为最终的句子表征，是否使用投影头、使用后是否仍取投影头输出作为最终向量，在不同工作中的具体设计有所差异，需要结合具体模型的技术报告确认；
- **额外的实用价值**：投影头也常被用来将编码器主干原始的高维输出（如 1024 维或更高）压缩到期望的最终嵌入维度，起到降维和适配下游存储/检索系统维度要求的作用。

总结来说，投影头的核心价值在于将"为满足对比学习损失而进行的变换"与"编码器主干学到的通用语言表征"适度解耦，避免对比学习目标过度扭曲主干网络的表征质量，同时也可以承担维度适配的实用功能，是否使用、如何使用需要结合具体模型设计和下游使用方式确定。

</details>

**12. 双编码器架构中，query 编码器和 document 编码器是否应该使用同一个共享参数的模型？什么情况下应该使用非对称（参数不共享）的双编码器？**

<details>
<summary>💡 查看答案</summary>

双编码器架构存在\"对称\"（query 和 document 共享同一套编码器参数）和\"非对称\"（query 和 document 分别使用独立参数的编码器）两种设计选择，如何取舍取决于具体应用场景：

- **对称双编码器（Siamese/Tied Weights）**：query 和 document 通过**同一个**编码器（共享全部参数）分别独立编码，这种设计的假设是 query 和 document 的**文本分布/长度/风格相对接近**（例如语义相似度任务中比较的两个句子往往长度和风格类似），共享参数意味着模型参数量更少、更容易训练（相当于两侧的梯度更新会互相促进同一套参数的优化），是很多语义相似度（STS）任务和释义检索场景中的常见选择；
- **非对称双编码器（Untied Weights）**：query 和 document 分别使用两个**独立的**编码器（参数不共享，甚至可以使用不同规模、不同结构的模型），适合 query 和 document 在**文本特性上差异明显**的场景，例如典型的检索场景中 query 通常很短（几个词到一句话），document 可能是很长的段落甚至整篇文章，两者的语言分布、所需的表征侧重点存在明显差异，用同一套参数编码可能难以同时兼顾"理解简短模糊的查询意图"和"压缩长文档的丰富信息"这两个不同的子任务；
- **非对称设计的具体实现**：可以是完全独立训练的两个模型，也可以是共享底层若干层（如共享词嵌入层和前几层 Transformer，捕捉通用语言特征）、但顶层分叉为两个独立分支的"部分共享"设计，在参数效率和适应两侧差异之间取一个折中；
- **实践选择依据**：如果任务中两侧文本的长度、风格、来源高度相似（如复述检测、句子相似度），倾向于用对称设计（参数量更省、训练更稳定）；如果任务中两侧文本存在明显的不对称性（如典型的 query-document 检索场景），倾向于考虑非对称设计，但也需要权衡额外的参数量和训练成本，很多实际系统即便面对不对称场景，出于工程简洁性考虑仍然选择共享参数的对称设计，实践中效果差异需要通过实验验证。

总结来说，是否共享 query 和 document 编码器的参数，核心取决于两侧文本在长度、风格、语义颗粒度上的相似程度：越相似越适合共享参数（对称设计），差异越大越有必要考虑非对称设计以更好地适应各自的表征需求，实践中需要结合具体任务通过实验验证两种设计的效果差异是否值得额外的参数和训练成本。

</details>

**13. 双编码器架构与经典的 Siamese Network（孪生网络）之间是什么关系？**

<details>
<summary>💡 查看答案</summary>

Siamese Network（孪生网络）是一个更早、更通用的深度学习架构概念，双编码器可以看作是 Siamese Network 思想在文本嵌入领域的具体应用：

- **Siamese Network 的核心思想**：用**同一个**编码器网络（共享权重）分别处理两个（或多个）输入，将它们映射到同一个向量空间中，再通过某种距离度量（如欧氏距离、余弦相似度）比较这些向量，最早被提出用于人脸验证（判断两张人脸照片是否属于同一个人）等度量学习（Metric Learning）任务；
- **与双编码器的关系**：前面提到的"对称双编码器"（query 和 document 共享同一套编码器参数）本质上就是 Siamese Network 思想在文本领域的直接应用——用同一个 Transformer 编码器分别编码两段文本，再计算相似度；Sentence-BERT 这一开创性工作的论文标题就明确使用了"Siamese"这个词（Sentence-BERT: Sentence Embeddings using Siamese BERT-Networks），直接借鉴了这一经典架构思想；
- **"非对称双编码器"与经典 Siamese Network 的区别**：严格意义上的 Siamese Network 要求权重共享，而前面提到的非对称双编码器（参数不共享）更接近另一个相关但不完全相同的概念——**Pseudo-Siamese Network**（伪孪生网络），即两个结构类似但参数独立的编码器分别处理不同类型的输入，这一区分在学术文献中有时会被明确提及，但在工业实践和更通俗的技术交流中，\"双编码器（Bi-Encoder）\"这个术语常常被用来泛指所有"两路独立编码再比较相似度"的架构，不严格区分是否共享权重；
- **历史脉络**：理解这一渊源有助于认识到双编码器架构并非文本嵌入领域的全新发明，而是度量学习这一更宽泛研究领域中的经典思想在 Transformer 时代的自然延续和迁移应用。

总结来说，双编码器架构在思想上直接继承自更早、更通用的 Siamese Network（孪生网络）度量学习框架，"对称双编码器"对应严格意义上权重共享的 Siamese Network，"非对称双编码器"则更接近权重独立的 Pseudo-Siamese Network，了解这一历史脉络有助于将文本嵌入模型的架构设计放在更广阔的深度学习度量学习研究背景下理解。

</details>

**14. 在向量检索中，余弦相似度、点积（内积）、欧氏距离三种相似度/距离度量应该如何选择？**

<details>
<summary>💡 查看答案</summary>

计算两个嵌入向量之间"有多相似"，常见的度量方式有余弦相似度、点积和欧氏距离，三者之间既有联系又有区别，选择时需要考虑以下因素：

- **余弦相似度（Cosine Similarity）**：衡量两个向量**方向**上的相似程度，与向量的模长无关，取值范围 $[-1, 1]$，是文本嵌入领域最常用的度量方式，因为语义相似度通常被认为应该只与向量的方向（代表语义内容）相关，而不应该受向量模长（可能受训练过程中一些无关因素影响）的干扰；
- **点积（内积，Dot Product）**：如前面提到的，如果向量已经做过 L2 归一化，点积在数值上就等价于余弦相似度，但如果向量没有归一化，点积的结果会同时受方向和模长共同影响，此时点积相似度实际上隐含了"模长也代表某种重要性/置信度"的假设（例如某些推荐系统场景中会有意保留未归一化的模长信息，用来编码额外的置信度或热度信息）；
- **欧氏距离（Euclidean Distance）**：衡量两个向量在空间中的**绝对距离**，同时受方向和模长影响，数值越小表示越相似（这与余弦相似度"数值越大越相似"的方向相反，需要注意在具体实现中不要弄反），如果向量已经归一化到单位长度，欧氏距离和余弦相似度之间存在一个简单的单调变换关系（$d^2 = 2 - 2\cdot cos_sim$），此时两者在排序结果上是完全等价的；
- **实践中的选择**：在向量已经做 L2 归一化的前提下（这是现代嵌入模型的标准做法），三种度量在排序意义上基本等价（点积和余弦相似度数值相同，欧氏距离与之单调对应），选择哪种更多是工程效率上的考量——点积计算最简单、在很多向量数据库和 ANN 索引库中有专门的优化实现（如 FAISS 的内积索引），因此在归一化向量的场景下通常优先选择点积计算相似度，直接复用高效的索引实现。

总结来说，在向量已归一化的标准做法下，余弦相似度、点积、欧氏距离三者在检索排序结果上是等价的，实践中的选择更多是出于计算效率和现有工程基础设施（向量数据库/ANN 索引库的原生支持）的考量，点积因其计算简单、索引库优化成熟，通常是归一化向量场景下的默认选择。

</details>

**15. 选择相似度度量方式时，需要与底层使用的近似最近邻（ANN）索引类型做怎样的匹配？**

<details>
<summary>💡 查看答案</summary>

前面提到相似度度量的选择需要与向量检索系统所使用的 ANN（Approximate Nearest Neighbor，近似最近邻）索引类型相匹配，这是一个容易被忽视但影响检索正确性和效率的工程细节：

- **索引库对度量方式的原生支持**：不同的 ANN 索引算法/库（如 FAISS、HNSWlib、Milvus 等）通常会针对特定的相似度度量（内积、L2 欧氏距离、余弦相似度）做专门的底层优化，选用与索引原生支持一致的度量方式，才能获得最佳的检索性能，如果度量方式不匹配（例如索引针对 L2 距离优化，但业务逻辑需要余弦相似度排序），可能需要额外的转换步骤（如前面提到的归一化后 L2 距离与余弦相似度的等价关系），增加了工程复杂度和潜在的实现错误风险；
- **向量归一化与索引选择的联动**：如果嵌入模型输出的向量已经做了 L2 归一化（现代嵌入模型的标准做法），通常直接使用支持内积（点积）计算的索引类型即可（因为归一化后点积等价于余弦相似度），无需额外处理；如果出于某些特殊原因向量没有归一化（如前面提到的保留模长代表某种置信度的场景），则需要根据具体业务逻辑决定使用哪种索引和度量方式，并确保训练阶段优化的目标（如训练时用余弦相似度还是点积计算损失）与推理阶段检索时使用的度量方式保持一致，否则可能出现训练和推理阶段"度量不一致"导致效果下降的问题；
- **常见的坑**：一个实际工程中常见的错误是训练阶段用归一化向量计算余弦相似度损失，但部署到向量数据库时忘记对向量做归一化（或者索引配置的度量方式与预期不符），导致检索结果与预期出现偏差，这类问题往往不会直接报错，而是悄悄降低检索效果，需要在上线前的评估流程中仔细核对训练和推理阶段度量方式的一致性。

总结来说，相似度度量的选择不是一个孤立的决策，需要与底层 ANN 索引库的原生支持能力、向量是否归一化、以及训练阶段使用的度量方式保持一致，任何环节的不匹配都可能导致检索效果的隐性下降，是向量检索系统工程落地时需要仔细核查的一个细节。

</details>

**16. 常见的近似最近邻（ANN）索引算法（如 HNSW、IVF、LSH）分别是什么原理？实践中如何选择？**

<details>
<summary>💡 查看答案</summary>

当向量库规模较大时，精确计算 query 与所有候选向量的相似度（暴力搜索）计算成本过高，需要借助近似最近邻算法在牺牲少量精度的前提下大幅提升检索速度，常见算法包括：

- **HNSW（Hierarchical Navigable Small World，分层可导航小世界图）**：构建一个多层图结构，每一层都是向量之间的近邻连接图，上层节点稀疏、用于快速定位大致区域，下层节点密集、用于精细搜索，检索时从顶层开始逐层向下"导航"，逐步逼近目标区域；优点是检索速度快、召回率高（在精度和速度的权衡上通常表现优异），是目前工业界最常用的 ANN 算法之一；缺点是索引构建时间较长、内存占用相对较高（需要存储图结构）；
- **IVF（Inverted File Index，倒排文件索引）**：先用聚类算法（如 K-means）将向量空间划分为若干个"桶"（cluster），每个向量归属于离它最近的聚类中心所在的桶，检索时先快速定位到 query 向量最可能所在的若干个桶（而不是全库搜索），再只在这些桶内做精细的相似度计算；优点是内存效率较高、索引构建相对较快；缺点是精度依赖于聚类的质量，且需要根据数据分布调整聚类桶的数量等超参数，常与量化技术（如前面提到的乘积量化 PQ）结合使用（IVF-PQ）以进一步压缩存储；
- **LSH（Locality-Sensitive Hashing，局部敏感哈希）**：使用特殊设计的哈希函数，让相似的向量以较高概率被映射到相同的哈希桶中，检索时只需要比较落入同一（或相邻）哈希桶中的候选向量；优点是理论基础扎实、适合超高维稀疏向量场景；缺点是在稠密向量、中等维度场景下的实际效果和效率通常不如 HNSW 等更现代的图索引方法，目前在文本嵌入检索场景中的使用相对较少；
- **实践选择建议**：在向量规模适中（百万到千万级别）、对检索精度要求较高的场景，HNSW 通常是综合表现最好的默认选择；在向量规模极大（十亿级以上）、内存资源受限、可以接受略低精度换取更低内存占用的场景，IVF（尤其结合量化技术的 IVF-PQ）更具优势；LSH 在文本嵌入检索的主流场景中使用相对较少，更多见于特定的稀疏向量或超高维场景。

总结来说，HNSW 通过分层图结构提供了当前综合表现最优的检索速度和精度平衡，是大多数中等规模场景的首选；IVF（结合量化）在超大规模、内存受限场景下更具优势；LSH 则在特定场景下仍有其理论和应用价值，实践中的选择需要结合向量库规模、内存预算、精度要求等因素综合权衡。

</details>

**17. 使用近似最近邻（ANN）检索相比精确的暴力搜索，会带来怎样的精度损失？如何在效果和效率之间权衡？**

<details>
<summary>💡 查看答案</summary>

ANN 算法之所以能够大幅提升检索速度，本质上是牺牲了一定的检索精度（即可能漏掉真正最相似的少数几个结果）来换取效率，理解并管理这种权衡是向量检索系统设计的重要一环：

- **精度损失的来源**：ANN 算法（无论是基于图的 HNSW 还是基于聚类的 IVF）本质上都是通过某种"启发式"的方式快速缩小搜索范围，而不是穷举比较所有候选，这意味着某些真正最相似的向量可能因为恰好没有被启发式搜索路径覆盖到而被遗漏，具体表现为"召回率"（Recall，即 ANN 检索结果与暴力搜索的真实 top-k 结果的重合程度）不是 100%；
- **影响召回率的关键参数**：几乎所有 ANN 算法都提供了可调节的参数来控制\"搜索范围的广度\"，从而权衡精度和速度，例如 HNSW 中的 ef_search（搜索时探索的候选数量，越大精度越高但速度越慢）、IVF 中的 nprobe（检索时实际搜索的聚类桶数量，越大精度越高但速度越慢），这些参数通常需要通过实验，在目标召回率（如相对暴力搜索 95%以上的一致性）和可接受的延迟预算之间找到合适的平衡点；
- **如何评估和监控**：在正式上线 ANN 检索系统前，通常需要在验证集上对比 ANN 检索结果与暴力精确搜索结果的召回率差异（Recall@k 一致性），确保精度损失在业务可接受范围内；上线后也可以定期抽样监控，因为随着数据量增长或分布变化，同样的 ANN 参数配置可能导致召回率发生变化，需要动态调整；
- **分层策略缓解精度损失**：与前面提到的向量量化类似的思路，可以采用"ANN 快速召回候选（追求高召回率而非精确排序）+ 精确重排序（对少量候选做精确相似度计算或使用更强的排序模型）"的两阶段策略，即使 ANN 阶段引入了一定的近似误差，只要真正相关的文档大概率被包含在召回的候选集合中，后续精排阶段仍然可以纠正 ANN 阶段可能引入的排序误差。

总结来说，ANN 检索通过启发式搜索策略换取速度提升，必然引入一定程度的召回率损失，实践中需要通过调节算法的搜索广度参数在精度和效率之间找到平衡点，并结合"ANN 召回 + 精确重排序"的分层策略，将 ANN 引入的近似误差控制在对最终业务效果影响可接受的范围内。

</details>

**18. 多负例排序损失（MNR）、余弦相似度损失和 softmax 损失在训练嵌入模型时有哪些优缺点？**

<details>
<summary>💡 查看答案</summary>

**1. 多负例排序损失（Multiple Negatives Ranking Loss, MNR，也称 InfoNCE）**  原理：对于每个正样本对 (query, positive)，将 batch 内其他样本的 positive（或额外提供的负例）作为负例，计算 query 与所有候选（1 个正例 + N-1 个负例）的相似度，通过 softmax + 交叉熵的形式，最大化正例相似度相对于所有候选的占比。  优点：

- 隐式地利用了 batch 内的大量负例，负例数量随 batch size 增长，训练效率高；
- 直接优化"区分正例和负例"的排序目标，与下游检索/排序任务高度一致，通常在语义检索任务上效果最好；
- 不需要显式的标签（相似度数值），只需要正样本对即可训练。

 缺点：

- 训练效果依赖于 batch size（更大的 batch 提供更多负例，但显存开销也更大）；
- 假负例问题（batch 内某个"负例"实际上也与 query 相关）会引入噪声；
- 需要精心设计采样策略（如难负例挖掘）才能进一步提升效果。

 **2. 余弦相似度损失（Cosine Similarity Loss）**  原理：给定带有相似度标签（如 0~1 之间的连续值，表示两段文本的语义相似程度）的样本对，直接让模型输出的余弦相似度去回归（如用 MSE）这个标签值。  优点：

- 可以利用细粒度的相似度标注（不仅是"相似/不相似"二元标签，还可以是连续的相似度分数，如 STS 数据集）；
- 实现简单直观，损失与最终使用的相似度度量（余弦相似度）直接对应。

 缺点：

- 需要高质量的、带有连续相似度分数的标注数据，这类数据获取成本较高；
- 余弦相似度的值域是 [-1, 1]，但实际的语义相似度标签往往集中在某个较窄的范围内，回归目标的数值分布可能不够"展开"，优化信号不如对比学习中的排序目标强；
- 不直接利用负例之间的相对排序信息，对检索任务的针对性不如 MNR。

 **3. Softmax 损失（分类式损失，如 Softmax Cross-Entropy over Classes）**  原理：将每个样本（如句子对）的关系视为一个分类问题（如 NLI 任务中的"蕴含/中立/矛盾"三分类），模型输出经过一个分类头后用 softmax 计算各类别概率，与真实类别标签计算交叉熵损失。  优点：

- 可以利用现成的分类标注数据（如 NLI 数据集），训练信号明确；
- 对于有明确类别区分（而非连续相似度）的任务效果较好，能学习到更细致的语义关系类型（如"蕴含"和"矛盾"的区别，而不仅仅是"相似"和"不相似"）。

 缺点：

- 训练得到的表征空间是为分类任务优化的，可能不直接对应于"向量距离=语义相似度"这一目标，迁移到检索任务时效果可能不如直接用排序损失训练的表征；
- 同样依赖于有明确类别标注的数据集，构建成本较高；
- 类别数固定，难以表达细粒度的相似度梯度。

 **总结**：

- 在数据形式上，MNR 适合"正样本对"形式的数据（最容易获取、最常用），余弦相似度损失适合带连续相似度标注的数据，softmax 损失适合带离散类别标注（如 NLI）的数据；
- 在效果上，对于面向检索/语义搜索的嵌入模型训练，**MNR（及其变体 InfoNCE）通常是当前最主流且效果最好的选择**，常作为预训练阶段的主损失；余弦相似度损失和 softmax 损失（尤其基于 NLI 数据）常用于早期阶段或作为辅助/微调损失，帮助模型学习更细粒度的语义关系。

</details>

**19. Pairwise 排序损失和 Listwise 排序损失在嵌入模型训练中分别是如何应用的？相比标准的 InfoNCE 损失有什么联系与区别？**

<details>
<summary>💡 查看答案</summary>

前面在对比学习基础部分讨论过 Triplet Loss 与 InfoNCE 的区别，这里进一步从学习排序（Learning to Rank）的经典分类视角，理解 pairwise 和 listwise 损失与嵌入模型训练中常用损失函数之间的关系：

- **InfoNCE/MNR 本质上已经带有 Listwise 的特征**：仔细分析 InfoNCE 损失的形式会发现，它同时考虑了一个正例和一组负例，通过 softmax 对整个候选集合（1 个正例 + n 个负例）做归一化，这实际上已经是在对一个"列表"（候选集合）做排序建模，而不是单纯的两两比较，因此可以认为 InfoNCE/MNR 损失本质上属于（简化版的）listwise 排序损失，只是列表中只有一个"正确答案"（相关性标签是二元的：正例 vs 负例），而不是像传统 listwise 排序损失那样处理多级相关性标注；
- **Triplet Loss 是经典的 Pairwise 形式**：如前所述，Triplet Loss 每次比较一个正例和一个负例相对于锚点的距离关系，是标准的成对（pairwise）比较范式；
- **更严格意义上的 Listwise 排序损失**：如果训练数据提供的不是简单的"正例/负例"二元标签，而是对同一个 query 下多个候选给出**细粒度的相关性等级**（如 0-4 分），则可以使用更严格意义上的 listwise 排序损失（如前面提到的 ListNet、LambdaRank），直接优化整个候选列表的排序质量，与 nDCG 等评估指标的对齐程度更高；这类训练目标在训练交叉编码器 reranker 时相对更常见（因为 reranker 通常需要处理这种细粒度相关性标注数据），在双编码器的预训练/微调阶段，由于数据规模巨大、标注通常只有二元的正负例信息，更常使用前述的 InfoNCE/MNR（简化版 listwise）损失；
- **选择依据**：如果训练数据只有二元相关性标签（大规模弱监督场景的常态），InfoNCE/MNR 是自然且高效的选择；如果训练数据提供了细粒度的多级相关性标注（通常规模较小、成本较高的高质量标注场景），可以考虑使用更严格的 listwise 排序损失以更充分利用这些细粒度信息。

总结来说，InfoNCE/MNR 损失可以被理解为一种简化版的 listwise 排序损失（列表中只有二元相关性标签），Triplet Loss 是经典的 pairwise 范式，更严格意义上考虑多级相关性的 listwise 排序损失（ListNet、LambdaRank 等）则更多用于拥有细粒度相关性标注数据的场景（如 reranker 训练），三者在\"是否利用列表整体信息\"和\"标签的精细程度\"上有所区别，选择需要结合具体训练数据的标注形式。

</details>

**20. 传统学习排序（Learning to Rank）中的经典方法，如 ListNet、LambdaRank，能否直接应用于训练嵌入模型？**

<details>
<summary>💡 查看答案</summary>

ListNet、LambdaRank 等方法是搜索排序领域历史更悠久的经典学习排序算法，最初主要设计用于**基于特征**的排序模型（如输入是人工设计的一系列相关性特征，输出是排序得分），将它们迁移到基于深度学习的嵌入模型训练中需要考虑一些适配问题：

- **ListNet 的核心思路**：将排序问题转化为一个概率分布的比较问题——给定一组候选文档的真实相关性得分和模型预测得分，分别通过 softmax 转化为两个概率分布（表示每个文档排在第一位的概率），损失函数是这两个概率分布之间的交叉熵（或 KL 散度），这一思路可以直接迁移到嵌入模型训练中：将模型计算出的候选相似度得分经过 softmax，与理想情况下的目标分布（如只有真正相关文档概率为 1，其余为 0，退化为标准的 InfoNCE 形式；或者如果有细粒度相关性标注，可以构造更平滑的目标分布）计算交叉熵；
- **LambdaRank 的核心思路**：不显式定义一个损失函数，而是直接定义梯度——对每一对候选文档比较其排序是否正确，如果错误，梯度大小由交换这两个文档位置后 nDCG 指标的变化量决定（$\Delta nDCG$），这样可以让训练直接朝着优化 nDCG 这类不可导排序指标的方向前进，是一种"用可导的梯度近似不可导的排序指标优化"的技巧，将其应用于嵌入模型训练时，需要在双编码器/交叉编码器计算出的相似度得分基础上，按照 LambdaRank 的梯度加权规则调整反向传播中每一对样本的梯度权重；
- **迁移应用的挑战**：这些经典方法在提出时主要针对候选数量相对有限（同一 query 下几十个候选）、且拥有较为丰富细粒度相关性标注的场景（如传统的网页搜索排序数据集），迁移到嵌入模型训练时，如果训练数据规模巨大但主要是二元弱监督标签（而非细粒度相关性），这些方法相对标准 InfoNCE 损失的额外收益可能有限，工程实现也更复杂（需要维护 pairwise 比较和 $\Delta nDCG$ 计算的额外逻辑）；
- **实践中的定位**：这类方法更常见于拥有高质量细粒度相关性标注数据的**精排/reranker**模型训练阶段（此时候选数量有限、标注质量高，能充分发挥 listwise 方法的优势），而不是大规模弱监督预训练阶段。

总结来说，ListNet、LambdaRank 等经典学习排序方法的核心思想可以迁移应用到嵌入模型（尤其是 reranker）的训练中，能够更直接地优化与 nDCG 等排序指标对齐的目标，但由于其对细粒度相关性标注和相对有限候选规模的依赖，更适合应用在数据质量高、候选数量可控的精排阶段，而非依赖海量二元弱监督数据的大规模预训练阶段。

</details>

**21. 用于训练嵌入模型的分类式 Softmax 损失（如将检索视为多分类问题）与标准对比学习损失（InfoNCE）有什么关系与区别？**

<details>
<summary>💡 查看答案</summary>

在一些嵌入模型/检索模型的训练实践中，也会见到将问题直接建模为传统多分类问题、使用标准 Softmax 交叉熵损失训练的方案，理解它与对比学习损失的关系有助于全面把握训练目标的设计空间：

- **分类式 Softmax 损失的具体形式**：如果候选类别（如文档、标签）的数量是**固定且有限**的（例如一个固定的商品类目体系，或固定规模的知识库），可以将检索/匹配问题直接建模为标准的多分类任务——为每个候选类别学习一个固定的输出层权重向量，模型对 query 编码后，直接计算其与每个类别权重向量的相似度并做 softmax 分类，用标准交叉熵损失训练；
- **与 InfoNCE 的相似之处**：数学形式上，标准 softmax 交叉熵损失与 InfoNCE 损失高度相似（都是对相似度得分做 softmax 归一化后计算负对数似然），可以认为 InfoNCE 是一种"候选集合在每个训练步骤中动态变化（由当前 batch 决定）"的 softmax 分类，而传统分类式 softmax 损失的候选集合（类别权重）是**固定**的、跨所有训练步骤共享的；
- **关键区别：候选集合是否固定**：这是两者最核心的区别——分类式损失要求候选类别的数量和身份提前确定并固定（每个类别对应一个可学习的权重向量，权重向量数量等于类别数），无法处理"候选集合会随着数据增长而动态扩展"的场景（如通用检索场景中，候选文档库可能持续新增文档，无法为每个新文档都训练一个固定的类别权重向量）；而 InfoNCE 中的"候选"是通过**编码器实时编码**得到的（即另一个样本的嵌入向量本身就是候选，而不是一个独立学习的固定类别权重），因此可以自然地泛化到开放式、持续增长的候选库场景，这也是为什么对比学习损失而非传统分类损失，成为现代开放域检索嵌入模型训练的主流选择；
- **适用场景**：分类式 softmax 损失更适合候选类别数量有限且相对固定的场景（如固定的意图分类、有限类目的商品匹配），而 InfoNCE/对比学习损失更适合候选是开放式文本、需要泛化到训练时未见过的新文档/新查询的通用检索场景。

总结来说，分类式 Softmax 损失和 InfoNCE 损失在数学形式上一脉相承，核心区别在于分类损失依赖于固定数量的可学习类别权重、无法自然扩展到开放式候选集合，而 InfoNCE 通过将候选表示为编码器实时编码的结果，天然支持候选库的开放式扩展，这也是为什么通用检索场景的嵌入模型几乎都采用对比学习损失而非传统分类损失训练的核心原因。

</details>

**22. Encoder-only（如 BERT 类）架构与 Decoder-only（如基于 GPT/LLM 转换而来）架构在训练嵌入模型时有什么区别？**

<details>
<summary>💡 查看答案</summary>

嵌入模型的底座架构存在 Encoder-only（如 BERT、RoBERTa）和 Decoder-only（基于因果语言模型，如 GPT 系列、LLaMA 系列等大语言模型转换而来）两条主要路线，两者各有特点：

- **Encoder-only 架构特点**：使用双向注意力机制（每个 token 可以同时看到其前后所有位置的上下文），天然更适合需要理解整句话完整语境的任务，历史上是文本嵌入模型的主流底座（BERT、Sentence-BERT 及其后续工作），配合前面提到的平均池化等策略，能够较为直接地得到较高质量的句子级表征；
- **Decoder-only 架构特点**：使用因果（单向）注意力机制（每个 token 只能看到它之前的上下文，不能看到后面的内容），最初主要为文本生成任务设计，近年来随着大语言模型（LLM）能力的飞速提升，越来越多工作探索直接基于这些强大的 LLM 底座训练嵌入模型（如前面提到的最后一个 token 池化策略就是为适配这类架构设计的），这类模型通常参数量远大于传统 Encoder-only 嵌入模型；
- **效果对比**：得益于 LLM 底座在预训练阶段吸收的海量知识和更强的语言理解/推理能力，基于 Decoder-only LLM 训练的嵌入模型在多个评测基准（如 MTEB）上近年来屡创新高，尤其在需要复杂语义理解、指令遵循能力的任务上表现突出；但 Decoder-only 架构原生的单向注意力机制在直接用于句子表征上存在一定的"先天限制"（后面的 token 无法影响前面 token 的表征），需要通过合适的池化策略（如最后一个 token 池化，因为该位置能看到全部上文）或额外的微调来弥补；
- **推理成本的权衡**：基于大语言模型的嵌入模型通常参数量远大于传统 BERT 类模型，推理成本（延迟、显存占用）显著更高，在对延迟极度敏感或需要大规模部署的场景，传统轻量级 Encoder-only 嵌入模型仍然具有明显的成本优势；实践中需要结合业务对效果和成本的具体要求权衡选择底座架构。

总结来说，Encoder-only 架构凭借原生的双向注意力机制，在文本嵌入任务上有天然的架构优势且推理成本较低，长期是主流选择；Decoder-only（LLM 转嵌入）架构凭借更大规模预训练带来的更强语言理解能力，近年来在效果上逐渐取得领先，但推理成本显著更高，两条路线的选择本质上是在效果上限和部署成本之间做权衡。

</details>

**23. 用大语言模型（LLM）作为嵌入模型的底座训练，近年来出现了哪些代表性思路（如 GritLM）？**

<details>
<summary>💡 查看答案</summary>

随着 LLM 能力的快速发展，如何充分利用其强大的语言理解能力来训练更好的嵌入模型，成为近年来的一个热门研究方向，涌现出一些代表性思路：

- **直接微调 LLM 作为嵌入模型**：在预训练好的 LLM 基础上，使用前面提到的对比学习框架（InfoNCE 等）和合适的池化策略（如最后一个 token 池化）进行微调，使其输出适合用于相似度计算和检索的向量表征，这是最直接的思路，代表工作包括基于 Mistral、LLaMA 等开源 LLM 微调得到的嵌入模型，往往能在评测基准上取得显著优于传统 BERT 类模型的效果；
- **生成与嵌入能力统一的模型（如 GritLM）**：更进一步的思路是训练一个**同时**具备文本生成能力和嵌入表征能力的统一模型，通过在同一个模型上，用不同的输入格式/指令区分"当前是要做生成任务"还是"要做嵌入表征任务"（类似前面提到的指令感知设计思路），并针对两类任务分别使用各自合适的训练目标（生成任务用标准的语言建模损失，嵌入任务用对比学习损失）联合训练，这样一个模型可以同时承担 RAG 系统中"检索相关文档"（嵌入能力）和"基于检索结果生成回答"（生成能力）两个环节的工作，避免部署和维护两个独立的模型；
- **这类统一模型的优势**：除了简化部署（一个模型服务两种能力），理论上生成能力和表征能力之间也可能存在正向的知识迁移——模型在生成任务中学到的深层语义理解能力，可能有助于提升其嵌入表征的质量，反之亦然；
- **面临的挑战**：联合训练生成和嵌入两种性质差异较大的任务目标，需要精心设计的多任务训练策略（如何平衡两类损失的权重，如何设计合适的输入格式区分任务类型），且这类统一模型的参数量通常较大，推理成本相应也较高，在对成本敏感、只需要单一嵌入能力的场景下，专门训练的轻量级嵌入模型可能仍然是更合适的选择。

总结来说，从直接微调 LLM 作为专用嵌入模型，到像 GritLM 这样训练同时具备生成和嵌入能力的统一模型，是近年来利用 LLM 强大语言理解能力提升嵌入模型效果的重要探索方向，这类思路在效果上具有明显优势，但也带来了更高的训练和推理成本，是否采用需要结合具体业务对效果、部署简洁性和成本的综合权衡。

</details>

**24. 设计嵌入模型时，输出向量的维度应该如何选择？维度过高或过低分别会带来什么问题？**

<details>
<summary>💡 查看答案</summary>

嵌入向量的维度是一个需要在效果、存储成本、检索效率之间权衡的重要设计参数：

- **维度过低的问题**：向量维度过低（如几十维）意味着能够编码的信息容量有限，难以充分表达复杂文本的丰富语义，尤其是在需要区分大量细粒度语义差异的场景下，低维向量可能因为表征能力不足而导致检索精度下降（不同语义的文本被迫挤压到同一个较小的空间中，容易产生混淆）；
- **维度过高的问题**：向量维度过高（如数千维甚至更高）虽然理论上表征能力更强，但会带来几方面的实际问题：存储成本随维度线性增长（在大规模向量库场景下可能是巨大的成本负担，如前面提到的量化/降维技术正是为了应对这一问题）；检索计算成本（无论是精确暴力搜索还是 ANN 索引中每次向量比较的计算量）也随维度增加而增长；此外，过高的维度在训练数据量不足时也更容易导致过拟合（维度灾难的一种体现），实际效果不一定随维度单调提升；
- **行业经验值**：目前主流开源嵌入模型的输出维度大多集中在 384、768、1024 这几个区间，是在表征能力和成本之间经过大量实践验证的相对均衡的选择；一些追求极致效果、可以承受更高成本的场景（如部分商用 API 提供的嵌入模型）会提供更高维度（如 3072 维）的选项；
- **结合 Matryoshka 表征学习的现代实践**：如前面提到的 MRL（Matryoshka Representation Learning）技术，让模型在训练阶段就同时优化多个不同截断维度下的表征质量，使得同一个模型可以根据实际场景灵活选择较低维度（换取更低的存储/计算成本）或较高维度（换取更高精度），一定程度上缓解了"必须在训练前就一次性确定唯一维度"这一传统限制，是目前设计新嵌入模型时值得考虑的一种方案。

总结来说，嵌入向量维度的选择本质上是在表征能力（维度越高理论上限越高）和成本（存储、计算、过拟合风险随维度增加而上升）之间寻找平衡点，行业内已经形成了 384-1024 维左右的经验取值范围，而 Matryoshka 表征学习等现代技术则为这一选择提供了更大的灵活性，允许在部署时动态权衡精度和成本，而不必在训练阶段就做出不可逆的维度决策。

</details>

**25. Transformer 编码器通常有固定的最大输入长度限制（如 512 个 token），如何扩展嵌入模型使其能够处理更长的文档？**

<details>
<summary>💡 查看答案</summary>

绝大多数基于 BERT 等架构的嵌入模型都存在最大输入长度限制（常见如 512 个 token），超出这一长度的文本需要截断或采用特殊处理，扩展这一限制的常见技术路线包括：

- **位置编码的外推/插值技术**：Transformer 模型对输入长度的限制很大程度上来自其位置编码机制在训练时只见过特定长度范围内的位置信息，超出训练时见过的长度后效果会明显下降，近年来发展出的一些位置编码改进方案（如 RoPE，旋转位置编码，以及针对 RoPE 的长度外推改进技术如 NTK-aware 插值、YaRN 等），使得模型能够通过对位置编码做特定的数学变换，在不重新训练（或只需少量继续训练）的情况下，将有效上下文长度从训练时的规模扩展数倍甚至更多；
- **直接在更长序列上继续预训练/微调**：另一种更直接的方式是在包含更长文本的语料上对模型做继续预训练或微调，让模型\"见过\"更长的输入序列，从而学习到处理长距离依赖关系的能力，这种方式效果通常更可靠，但需要额外的算力和长文本训练数据；
- **层级式/分段编码策略**：对于超出模型硬性长度限制的极长文档，一种工程上常用的折中方案是将文档切分成若干个符合长度限制的片段，分别编码后再通过某种聚合方式（如对各片段向量取平均，或用一个额外的轻量级聚合模型）得到整篇文档的表征，这一思路与前面提到的分块（chunking）策略有相通之处，但这里更强调是在**模型架构和推理流程层面**对长文档做处理，而分块更偏向于 RAG 场景中面向检索粒度的数据预处理策略，两者可以结合使用；
- **近期长上下文嵌入模型的进展**：一些近期发布的嵌入模型（尤其是基于长上下文 LLM 转换而来的嵌入模型）已经原生支持数千甚至数万 token 的输入长度，减少了对分段编码等折中方案的依赖，这也是嵌入模型架构演进的一个值得关注的方向。

总结来说，扩展嵌入模型处理长文档的能力，既可以通过位置编码层面的技术改进（RoPE 外推等）和针对性的长文本继续训练来提升模型原生支持的最大长度，也可以通过分段编码再聚合等工程手段在应用层面绕开模型的硬性长度限制，近期基于长上下文 LLM 的嵌入模型也在原生层面上不断突破传统的长度限制，是选择嵌入模型底座时值得关注的一个能力维度。

</details>

**26. 嵌入向量之间的相似度度量是否满足严格的距离公理（如三角不等式）？这对检索系统设计有什么实际影响？**

<details>
<summary>💡 查看答案</summary>

从更理论的角度审视嵌入向量的相似度度量，有一个值得关注的细节：并非所有常用的相似度度量都严格满足数学意义上"距离"所要求的公理，这一点对某些依赖距离性质的检索算法设计有实际影响：

- **距离公理简述**：一个严格的距离度量需要满足非负性、同一性（自身距离为零）、对称性、以及**三角不等式**（$d(a,c) \le d(a,b) + d(b,c)$，即经过第三点中转的距离不会比直接距离更短）；
- **余弦相似度/距离的情况**：余弦**相似度**本身不是距离（数值越大越相似，与距离"数值越小越相似"的直觉相反），但可以转化为余弦**距离**（$1 - cos_sim$），转化后的余弦距离在数学上是可以证明满足三角不等式的（在向量已归一化的前提下），因此基于余弦距离的检索系统在理论性质上是有保障的；
- **为什么这一点重要**：很多高效的 ANN 索引算法（尤其是一些较早期的基于树结构或基于距离筛选剪枝的算法）在设计时依赖于三角不等式这一性质来实现搜索剪枝（例如"如果 A 到 B 的距离已知很远，且 B 到查询点很近，可以用三角不等式快速排除 A 不可能是最近邻，无需精确计算 A 到查询点的距离"），如果实际使用的度量不满足三角不等式，这类基于距离性质的剪枝优化可能会给出错误的结果（错误地剪掉本应保留的候选）；
- **实际影响与工程选择**：值得庆幸的是，前面讨论过的主流选择（在向量归一化前提下使用点积/余弦相似度对应的余弦距离）本身满足距离公理，因此现代主流的 ANN 索引算法（如 HNSW 等基于图结构、不严格依赖三角不等式剪枝的方法）通常不会受此影响；但如果设计者尝试使用一些非标准的、自定义的\"相似度\"打分函数（例如结合了额外业务规则的加权组合打分），则需要额外审视这类自定义度量是否仍然满足检索系统所依赖的数学性质，避免出现难以察觉的检索错误。

总结来说，主流的余弦相似度/距离在数学上是良态的（满足距离公理），可以放心地与依赖这一性质的检索算法配合使用；但当业务需求要求引入更复杂的、非标准的自定义打分函数时，需要留意其是否仍然满足距离公理，尤其是三角不等式，避免因为不满足理论假设而导致某些依赖该性质进行加速剪枝的检索算法给出错误结果，这是一个容易被忽视但对检索系统正确性有实际影响的理论细节。

</details>

**27. 在训练检索场景的嵌入模型时，用于难负例挖掘的候选应该来自 ANN 索引召回的结果，还是可以随机采样？两者各有什么问题？**

<details>
<summary>💡 查看答案</summary>

前面讨论过难负例挖掘的多种算法（如 ANCE），这里更深入地探讨一个具体的工程问题：挖掘难负例时使用的候选来源（ANN 索引召回 vs 全库随机采样）会带来不同的效果和工程权衡：

- **使用 ANN 索引召回结果作为难负例来源**：用当前模型（或其早期版本）建立的 ANN 索引，对每个 query 检索出排名靠前但标注为不相关的文档作为难负例，这种方式能够高效地定位到模型当前认为"相似"的候选（不需要遍历全部文档库计算相似度），是 ANCE 等方法实践中的标准做法；
- **索引滞后性问题（Staleness）**：由于模型参数在训练过程中持续更新，而重新构建整个 ANN 索引（对全库文档重新编码并建立索引结构）通常计算成本较高、耗时较长，无法在每个训练 step 之后都重新构建索引，因此实践中索引通常是"周期性"更新的（如每隔若干个训练 epoch 或固定步数重建一次），这意味着挖掘难负例时使用的索引，其对应的模型参数版本可能已经与**当前**正在训练的模型参数存在一定差距（索引是"过时"的），挖掘出来的"难负例"的难度可能与模型当前真实的判别边界不完全匹配；
- **全库随机采样**：不依赖模型当前的判断能力，直接从整个文档库中随机采样负例，实现简单、不存在索引滞后问题，但如前面反复提到的，随机负例大多是"简单负例"，对提升模型精细判别能力的训练信号价值有限；
- **工程权衡与折中方案**：实践中通常采用"索引周期性重建 + 训练过程中混合使用随机负例和索引挖掘的难负例"的折中策略——既通过周期性重建索引跟踪模型能力的提升（尽管有一定滞后），又通过混合随机负例保证训练信号的多样性、降低索引滞后带来的负面影响；索引重建的频率需要结合训练总步数、索引重建的计算成本、以及难负例质量对最终效果的敏感程度综合确定，是一个需要通过实验调优的工程超参数。

总结来说，使用 ANN 索引召回挖掘难负例能提供更有针对性、更贴近模型当前能力边界的训练信号，但受限于索引重建成本，不可避免地存在一定的滞后性问题；全库随机采样简单可靠但信号价值有限；实践中通常结合两者，并通过合理设置索引重建频率来管理滞后性问题对训练效果的影响，是难负例挖掘工程落地时需要仔细考量的细节。

</details>

**28. 在生产环境中，应该如何设计决策框架来选择检索架构（双编码器、多向量、交叉编码器组合）？**

<details>
<summary>💡 查看答案</summary>

结合前面讨论过的各种检索架构（双编码器、ColBERT 式多向量、交叉编码器）及其优劣，在实际业务落地时，可以从以下几个维度构建一个系统性的选型决策框架：

- **候选规模**：候选文档库规模是决定架构选型的首要因素——候选规模达到百万级以上时，必须有一个能够支持高效离线索引和快速在线检索的召回层（双编码器或稀疏检索是必选项，交叉编码器不能承担这一角色）；候选规模较小（如几千到几万）时，甚至可以考虑对全量候选直接使用交叉编码器做穷举打分，省去复杂的多阶段架构；
- **延迟预算**：业务对检索响应延迟的容忍度直接决定了在召回之后能承担多重的后续处理——延迟要求极为严苛（如毫秒级）的场景可能只能依赖纯双编码器检索，不引入额外的精排环节；延迟要求相对宽松（如可以接受数百毫秒）的场景则可以在双编码器召回后叠加交叉编码器精排，甚至引入 ColBERT 式多向量方案作为召回和精排之间的过渡层；
- **精度要求与业务价值**：对检索精度极为敏感、错误排序会造成明显业务损失的场景（如医疗、法律等专业检索场景），即使增加一定的延迟和成本，也值得引入交叉编码器精排环节以确保排序质量；对精度要求相对宽松的场景（如内部知识库的辅助检索），纯双编码器方案可能已经足够；
- **存储与成本预算**：如前面讨论的，多向量（ColBERT）方案存储成本显著高于单向量双编码器，如果向量存储和索引维护是明显的成本瓶颈，需要谨慎评估是否值得为精度提升承担这部分额外成本，或考虑用双编码器+更强的精排模型组合来替代；
- **数据与迭代能力**：是否有能力持续积累高质量的相关性标注数据、进行难负例挖掘和模型迭代，也会影响架构选型——引入更复杂的多阶段架构（尤其是精排环节）通常需要相应的高质量训练数据支持才能发挥其潜力，如果数据积累和迭代能力有限，简单可靠的架构可能是更务实的起点，可以先上线简单方案积累业务数据和反馈，再逐步演进架构。

总结来说，检索架构的选型没有放之四海而皆准的最优答案，需要围绕候选规模、延迟预算、精度要求、成本约束、以及团队的数据和迭代能力这几个核心维度做系统性评估，实践中比较务实的路径通常是从简单架构（如纯双编码器）起步快速上线，再根据实际业务反馈和积累的数据，逐步向更复杂的多阶段架构（引入精排、混合检索等）演进，而不是一开始就追求架构上的\"大而全\"。

</details>
