# 7.5 检索策略（混合检索、Rerank、MMR） — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 7 章：RAG（检索增强生成） · 共 22 题

**1. RAG 中常用哪些检索技术？**

<details>
<summary>💡 查看答案</summary>

RAG 的检索技术经历了从稀疏到稠密、从单一到混合的演进，现代生产系统通常组合多种技术：

**一、稀疏检索（Sparse Retrieval）**
- **BM25**：基于词频（TF）和逆文档频率（IDF）的经典算法，对精确关键词匹配效果极佳，速度快，无需训练，是 Elasticsearch 的默认排序算法；
- **TF-IDF**：BM25 的前身，同样基于词频统计，但对文档长度归一化处理不如 BM25 完善，现代系统已基本被 BM25 替代；
- **SPLADE**：通过神经网络学习稀疏 Embedding，结合了稀疏检索的效率和神经检索的语义理解能力。

**二、稠密检索（Dense Retrieval）**
- **双编码器（Bi-Encoder）**：query 和文档分别独立编码为稠密向量，通过余弦相似度或内积计算相关性，支持离线预计算文档向量，检索速度快；代表模型：DPR、BGE、E5；
- **Late Interaction（ColBERT）**：保留 token 级向量交互，精度高于单向量 Bi-Encoder，但存储成本更高；
- **ANN 加速**：使用 FAISS（IVF-PQ、HNSW）、ScaNN 等近似最近邻算法加速稠密向量检索，将百万级向量的搜索降低到毫秒级。

**三、混合检索（Hybrid Retrieval）**
- 同时使用 BM25 和稠密检索，用 RRF（Reciprocal Rank Fusion）融合两路结果；
- 综合了稀疏检索的关键词精确匹配和稠密检索的语义理解，是当前效果最稳定的检索方案。

**四、精排模型（Reranker）**
- **Cross-Encoder**：将 query 和候选文档拼接后联合编码，精度高但无法离线预计算，用于召回后的精排阶段（top-50 → top-5）；
- **代表模型**：BGE-Reranker、ms-marco-MiniLM、Cohere Rerank API。

**五、图检索（Graph-based Retrieval）**
- 基于知识图谱的实体关系遍历，适合需要多跳推理和实体关联查询的场景，如 GraphRAG。

</details>

**2. 检索模型在 RAG 系统中为何重要？**

<details>
<summary>💡 查看答案</summary>

检索模型是 RAG 系统的关键瓶颈——生成模型只能基于被检索到的内容生成答案，检索不到的信息永远无法出现在答案中。检索模型的重要性体现在以下几个维度：

1. **决定系统效果上限**：RAG 的核心假设是"正确答案在知识库中存在且可被检索到"，检索模型的质量决定了这一假设能在多大程度上成立。检索召回率每提升 10%，端到端答案质量通常提升 5--8%。
2. **信息准入的守门者**：检索模型决定哪些信息被允许进入 LLM 的上下文窗口，它既是信息的"引路人"（召回相关内容），也是噪声的"过滤器"（排除无关内容），这一双重角色对最终答案质量至关重要。
3. **知识更新的桥梁**：RAG 比微调更具实用价值的核心原因，是知识更新只需更新知识库，而检索模型负责将更新后的知识准确地"找出来"供 LLM 使用。检索模型的稳定性保证了知识更新的可靠传导。
4. **语义理解的核心**：好的检索模型能理解"苹果手机"和"iPhone"语义相同、能跨语言检索（中文 query 检索英文文档）、能理解专业术语，这些能力远超简单的关键词匹配，是 RAG 系统区别于传统搜索的关键。
5. **系统可扩展性的基石**：随着知识库规模增长（从万级到亿级文档），检索模型的效率（ANN 算法、索引结构）直接决定系统是否能在可接受的延迟内完成检索，影响整个 RAG 系统的可扩展性。

简言之：**检索模型找到什么，LLM 就只能基于什么生成**，没有高质量的检索，再强大的 LLM 也无法给出正确答案。

</details>

**3. 什么是混合检索（Hybrid Search）？向量检索和关键词检索如何融合？**

<details>
<summary>💡 查看答案</summary>

![混合检索与重排序架构](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter7/fig_hybrid_search_rerank.png)

混合检索：同时使用向量检索（捕捉语义相似）和关键词检索（BM25，捕捉精确词汇匹配），将两路结果融合，取长补短。融合方法：
1. **RRF（Reciprocal Rank Fusion）**：将两路检索结果按排名倒数加权求和，重新排序，简单有效，无需调参；
2. **加权融合**：向量得分×α + BM25 得分×(1-α)，α 为超参数；
3. **级联**：先用一路检索粗过滤，再用另一路精排。
使用场景：文档包含专业术语、产品编号等需要精确匹配的内容；用户查询包含精确关键词（"iPhone 15 Pro"）时，BM25 比向量检索更准确。混合检索通常比单一方法提升 5–15% 检索质量。

</details>

**4. 为什么 Hybrid Search（混合检索）越来越受欢迎？**

<details>
<summary>💡 查看答案</summary>

它结合了语义检索（处理同义/近义表达）和关键词检索（处理精确匹配，如专有名词、编号）的优势，弥补了单一检索方式的短板，在多数场景下综合效果更稳定。具体原因如下：

1. **两种检索方式互补**：
    - 向量检索（Dense Retrieval）：善于处理同义词、近义表达、语义相近的问题，但对精确关键词、特殊编号、专业术语的匹配能力弱；
    - BM25（Sparse Retrieval）：对精确关键词匹配极为敏感，但无法理解语义，"汽车"和"车辆"视为完全不同的词；
    - 混合检索取两者之长，规避各自短板。
2. **企业知识库的现实需求**：企业文档往往混合了大量专业术语、产品型号、内部编码等精确词汇（适合 BM25），同时也需要语义理解（适合向量检索）。单一向量检索在这类混合场景下表现不稳定。
3. **实证效果提升显著**：大量研究和工程实践表明，混合检索相比单一向量检索，在通用基准上平均提升 5--15% 的检索质量，且几乎在任何场景下都不会比单一方法差。
4. **RRF 融合简单有效**：Reciprocal Rank Fusion（RRF）算法可以无参数地融合两路检索结果，工程实现简单，无需额外训练和调参，使得混合检索的落地成本很低。
5. **向量数据库原生支持**：Weaviate、Qdrant、Elasticsearch 等主流向量数据库都已原生支持混合检索，进一步降低了使用门槛。
6. **LLM 时代专有名词激增**：随着 RAG 应用于越来越多的垂直领域，包含模型名称（如"GPT-4o"）、版本号（"v2.1.3"）、药品名称等精确关键词的 query 越来越普遍，BM25 的价值被重新重视。

</details>

**5. 什么是 BM25？它与向量检索相比有什么优势和劣势？**

<details>
<summary>💡 查看答案</summary>

**BM25**（Best Match 25）：经典关键词检索算法，基于词频（TF）和逆文档频率（IDF）计算相关性，并对长文档做归一化，是 Elasticsearch 的默认排序算法。

**优势**：
1. 对精确词汇匹配效果极好（产品编号、人名、专有名词）；
2. 速度快，无需 GPU，资源消耗低；
3. 无需训练，开箱即用；
4. 对罕见词汇（低频术语）检索敏感度高。

**劣势**：
1. 无法处理同义词（"汽车"和"车"视为不同词）；
2. 无语义理解，措辞不同的相似问题可能匹配不到；
3. 多语言支持差（需要分词器适配）。
向量检索优势正好弥补 BM25 的劣势，两者互补。

</details>

**6. 什么是 Reranking（精排）？常用的 Reranking 模型有哪些？**

<details>
<summary>💡 查看答案</summary>

Reranking 是对向量检索初始召回的 top-k 结果进行第二轮精确排序，使最相关的文档排在前面。工作原理：使用 Cross-Encoder（交叉编码器）将 query 和每个候选文档拼接后一起输入模型，得到精确的相关性分数。常用模型：
1. **开源**：BGE-Reranker（中英双语，bge-reranker-large 效果最好）、ms-marco-MiniLM（英文，速度快）；
2. **商业 API**：Cohere Rerank（无需本地部署，API 调用简单）；
3. **ColBERT**：延迟交互模型，介于双塔和交叉编码器之间，精度和速度均衡。
典型流程：向量检索召回 top-50 → Reranker 精排 → 取 top-5 传给 LLM。

</details>

**7. Rerank 步骤是否是 RAG 流程中必须的？**

<details>
<summary>💡 查看答案</summary>

不是绝对必须，但在召回结果质量参差不齐、Top K 较大的场景下，Rerank 能显著提升最终送入模型的上下文质量，通常被认为是高质量 RAG 系统的标配。详细分析：

**不需要 Rerank 的场景**：
- 知识库规模小（$<$1 万 chunk），向量检索精度本身已经很高；
- k 值很小（top-3），召回结果质量足够好；
- 对延迟极度敏感，Reranker 的 50--200ms 延迟无法接受；
- 快速原型阶段，尚不需要精细优化。

**强烈建议使用 Rerank 的场景**：
- 知识库规模大（$>$10 万 chunk），向量检索召回的 top-k 中相关性参差不齐；
- 用户查询多样化，包含专业术语和口语化表达混合；
- 文档内容高度相关但细节差异大，需要精确排序；
- 对答案质量要求高的生产系统（如法律、医疗、金融场景）；
- 使用混合检索（向量 + BM25），两路结果分数量纲不一致，需要 Reranker 统一精排。

**Rerank 的收益**：实践数据表明，在大规模知识库场景下，加入 BGE-Reranker 后，端到端答案质量（Faithfulness + Relevancy）平均提升 10%--20%，是 RAG 优化中 ROI 最高的单项改进之一。

**轻量化方案**：如果完整 Reranker 延迟太高，可以使用 MiniLM-based 轻量 Reranker（延迟约 20ms），在速度和质量之间取得平衡。

</details>

**8. Cross-Encoder 和 Bi-Encoder 在检索中各自扮演什么角色？**

<details>
<summary>💡 查看答案</summary>

**Bi-Encoder（双塔编码器）**：query 和文档分别编码为独立向量，相似度用向量点积/余弦计算，速度极快，支持预计算文档向量，适合大规模召回阶段。缺点：query 和文档独立编码，无法捕捉细粒度的词级交互，精度有上限。

**Cross-Encoder（交叉编码器）**：将 query 和文档拼接后一起编码，模型可以在内部做全量 attention，捕捉细粒度交互，精度高。缺点：无法预计算，每次都要对每个候选对重新推理，速度慢，不适合大规模召回。

**协作关系**：Bi-Encoder 负责快速召回（top-100），Cross-Encoder 负责精确精排（top-5），两阶段组合兼顾效率和精度。

</details>

**9. 什么是 Maximal Marginal Relevance（MMR）？它解决了什么问题？**

<details>
<summary>💡 查看答案</summary>

MMR（Carbonell & Goldstein 1998）：一种同时考虑相关性和多样性的检索排序算法。计算公式：`MMR = argmax[λ·Sim(doc, query) - (1-λ)·max Sim(doc, selected)]`，每次选择的文档既要与 query 相关，又要与已选文档尽量不同。解决的问题：普通向量检索返回的 top-k 文档往往高度相似（来自同一段落的相邻 chunk），提供了冗余信息，而真正相关但措辞不同的文档排名靠后。MMR 确保选入的 chunk 覆盖不同方面，提供更完整的信息。λ 参数控制相关性和多样性的权重（λ=1 退化为纯相关性排序）。

</details>

**10. 如何处理检索结果中的重复内容？**

<details>
<summary>💡 查看答案</summary>

1. **基于 chunk_id 去重**：合并多路检索结果时，相同 chunk_id 的文档只保留排名最高的一条；
2. **语义去重**：对返回的 chunk 做互相似度计算，相似度超过阈值的 chunk 只保留相关性最高的一条（使用 MMR 算法）；
3. **文档级去重**：来自同一文档的多个高度相似 chunk，保留最相关的，其余合并为一条；
4. **模板化内容过滤**：知识库中存在大量重复的模板性内容（免责声明、页眉），在预处理阶段就去除；
5. **多样性约束**：使用 MMR 在保证相关性的同时最大化结果多样性，自然减少重复。

</details>

**11. 如何利用元数据过滤（Metadata Filtering）提升检索精度？**

<details>
<summary>💡 查看答案</summary>

元数据过滤：在向量检索时，同时附加结构化过滤条件，只在满足条件的 chunk 子集中做相似度搜索。应用场景：
1. **时间过滤**：只检索最近 6 个月的文档；
2. **类型过滤**：只检索 FAQ 类型的文档；
3. **权限过滤**：根据用户角色过滤可访问文档；
4. **来源过滤**：只检索特定产品线的文档；
5. **语言过滤**：只检索与用户语言一致的文档。
元数据过滤将大向量库拆分为多个子集，既提升精度又减少候选集大小，提升检索速度。

</details>

**12. 什么是 Contextual Compression（上下文压缩）？它有什么作用？**

<details>
<summary>💡 查看答案</summary>

Contextual Compression：在将检索到的 chunk 传给 LLM 之前，先用一个轻量模型或 LLM 从每个 chunk 中提取与当前 query 最相关的句子，只传入提取后的精华内容，而不是整个 chunk。作用：
1. **减少 token 消耗**：只传入相关句子，而不是整个 chunk，节省 LLM 推理成本；
2. **减少噪声**：过滤掉 chunk 中与问题无关的内容，提升生成质量；
3. **允许更高 k 值**：每个 chunk 压缩后更小，可以传入更多候选 chunk，提升召回率；
4. **缓解 Lost in the Middle**：更少的内容意味着 LLM 更容易关注到所有相关信息。
代价：多一次 LLM 调用，增加延迟。

</details>

**13. 什么是多路召回（Multi-Source Retrieval）？如何合并多路结果？**

<details>
<summary>💡 查看答案</summary>

多路召回：同时从多个数据源或使用多种检索方法召回候选文档，再合并排序。来源：
1. 不同向量数据库（不同知识库分别存储）；
2. 不同检索方法（向量检索 + BM25 + 图检索）；
3. 不同 Embedding 模型（不同模型对同一查询召回不同文档）。
合并方法：
- **RRF（Reciprocal Rank Fusion）**：各路排名倒数加权求和，重排序，无需调参，鲁棒性强；
- **加权合并**：根据各路检索的历史表现设置权重；
- **去重合并**：合并前去除相同 chunk_id 的重复结果；
- **Reranker 统一精排**：合并后用 Cross-Encoder 统一精排，消除不同路的分数量纲不一致问题。

</details>

**14. 为什么提高了召回率（Recall），最终答案质量反而下降？**

<details>
<summary>💡 查看答案</summary>

召回更多内容的同时也引入了更多无关或弱相关信息，增加了模型在生成阶段的干扰和噪声，模型可能被误导性内容带偏，导致"信息多了但信噪比下降"。具体机制如下：

1. **信噪比下降**：Top-k 中排名靠后的文档相关性越来越低，当 k 增大时，新增加的文档大多是弱相关甚至不相关的内容，这些噪声与真正有用的内容一起传给 LLM，稀释了高质量信息的权重。
2. **Lost in the Middle 效应加重**：上下文越长，LLM 对中间位置内容的注意力越弱。将 k 从 5 增大到 20，真正重要的 chunk 很可能被淹没在大量边缘内容中，反而更容易被忽略。
3. **矛盾信息增多**：检索范围扩大后，召回内容中出现相互矛盾的陈述的概率增大，LLM 在矛盾内容面前更容易产生错误或不一致的答案。
4. **LLM 上下文窗口饱和**：k 过大可能超出 LLM 的上下文窗口限制，导致部分内容被截断，或者 LLM 为了"消化"大量内容而降低了对每个 chunk 的精细处理质量。
5. **成本与质量的反直觉权衡**：更高的 k 意味着更高的 token 成本，而质量反而下降，造成双重损失。

**正确做法**：不应简单地增大 k 来提升召回率，而应通过 Reranking 精排来提升 top-k 的质量，或使用 Contextual Compression 压缩每个 chunk 的冗余内容，在控制传给 LLM 的内容总量的前提下提升信息密度。

</details>

**15. RAG 系统中真正的核心问题只是"召回"吗？**

<details>
<summary>💡 查看答案</summary>

不是。召回只是第一步，生成阶段如何利用检索内容（过滤噪声、判断相关性、整合多个片段）同样关键，很多失败案例其实是召回正确但生成阶段未能正确利用。RAG 系统的核心问题应从三个层次理解：

**第一层：召回质量**
- 能否检索到包含正确答案的文档？（召回率）
- 检索到的文档是否都是相关的？（精确率）
- 这是 RAG 的必要条件，但不是充分条件。

**第二层：上下文质量**（常被忽视）
- 传给 LLM 的 chunk 信噪比是否足够高？噪声 chunk 会干扰 LLM 的判断；
- chunk 的顺序是否合理？（Lost in the Middle 问题）
- 多个 chunk 之间是否有矛盾信息？如何让 LLM 正确处理矛盾？
- 单个 chunk 的上下文是否完整，LLM 能否读懂孤立的片段？

**第三层：生成忠实度**（同样关键）
- LLM 是否真正基于检索内容回答，还是忽略了检索内容？
- LLM 是否在检索内容之外"添加"了幻觉内容？
- LLM 是否正确整合了多个 chunk 的信息？

实践经验表明，约 70% 的 RAG 失败案例并非"没有检索到"，而是"检索到了但没有用好"。因此，上下文压缩、Reranking、忠实度 prompt 设计等后处理技术与召回质量同等重要。

</details>

**16. RAG 中真正困难的部分是检索还是后续的过滤/整合？**

<details>
<summary>💡 查看答案</summary>

随着检索技术（向量库、混合检索）日趋成熟，"如何从召回结果中筛选、去噪、整合出对生成最有用的上下文"逐渐成为更突出的难点。详细分析如下：

**检索侧的进步**：向量数据库、混合检索、Reranker 等技术已相对成熟，在标准场景下的召回率已经较高。但检索仍有其固有难点：同义词和术语变体问题、多跳推理需要多轮检索、罕见领域查询的语义理解。

**过滤/整合侧的难点（日益突出）**：
1. **噪声过滤**：即使是高召回率的检索，top-k 结果中往往混有相关但不精确、甚至具有误导性的 chunk，如何让 LLM 准确识别并忽略这些噪声是核心难题；
2. **矛盾信息处理**：多个 chunk 之间可能存在相互矛盾的信息，LLM 需要判断以哪个为准，但目前 LLM 对矛盾信息的处理能力有限；
3. **多 chunk 信息整合**：答案需要综合 3--5 个 chunk 的信息时，LLM 需要完成跨段落的推理和整合，这对模型的长文本理解和推理能力有较高要求；
4. **忠实度控制**：强迫 LLM 只基于检索内容回答、不使用内置知识"补充"，是持续的工程挑战；
5. **Lost in the Middle**：检索到了正确内容，但因为其位置在上下文中间而被 LLM 忽略。

**结论**：实践中约 30% 的 RAG 失败案例源于检索不到正确内容，约 70% 的失败案例是检索到了相关内容，但 LLM 未能正确利用。因此，后续的过滤与整合正在成为更关键的瓶颈。

</details>

**17. RAG 为什么容易给生成过程引入噪声？**

<details>
<summary>💡 查看答案</summary>

检索是基于相似度而非"正确性"，相似但不相关或部分相关的内容会被一并召回，这些内容会干扰模型的判断，尤其在 Top K 较大时更明显。噪声的来源与影响机制如下：

1. **相似度 $\neq$ 相关性**：向量检索基于语义相似度，"主题相关但不能回答当前问题"的 chunk 得分可能很高。例如问"苹果手机的价格"，可能召回"苹果公司的历史"这类相关但无用的内容。
2. **知识库的噪声传播**：知识库中的低质量文档（格式混乱、内容过时、重复冗余）经过 Embedding 后同样被索引，在相关 query 下会被召回，将源数据的质量问题传播到生成阶段。
3. **Top-k 尾部内容质量下降**：相似度排名越靠后的 chunk，与 query 的相关性越弱；当 k 较大时，大量弱相关 chunk 进入上下文，信噪比显著下降。
4. **Cross-Chunk 矛盾**：来自不同文档或不同版本的 chunk 可能包含相互矛盾的信息，LLM 难以判断以哪个为准，容易生成混合或错误的答案。
5. **LLM 对噪声的敏感性**：研究表明，即使只有 1--2 个高度相关但不正确的 chunk 混入上下文，LLM 生成错误答案的概率就会显著上升，"污染性"噪声比纯无关噪声危害更大。

**降噪手段**：Reranking（过滤低相关 chunk）、Contextual Compression（从 chunk 中提取与 query 最相关的句子）、知识库质量管理（预处理阶段去除低质量文档）、设置相似度阈值（低于阈值的 chunk 不传入，即使在 top-k 内）。

</details>

**18. 请解释"Lost in the Middle"问题。它描述了 RAG 中的什么现象？有什么方法可以缓解这个问题？**

<details>
<summary>💡 查看答案</summary>

![上下文“迷失在中间 (Lost in the Middle)”现象](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter7/fig_lost_in_the_middle.png)

"Lost in the Middle"是指 LLM 在处理一个长上下文时，倾向于更好地回忆和利用位于上下文开头和结尾的信息，而忽略或遗忘位于中间部分的信息的一种现象。

在 RAG 中，我们通常会将检索到的 Top-K 个文档块与用户的原始问题拼接起来形成一个长 prompt。如果 LLM 存在"Lost in the Middle"的问题，那么文档 1 和文档 K 的内容会得到 LLM 的充分关注，而位于中间的文档，即使包含了关键信息，也有很大概率被忽略。

缓解方法：
1. **文档重排序（Document Re-ordering）**：将最相关的文档放置在上下文的开头和结尾，而将次要相关的文档放在中间，确保关键信息处于 LLM 的"注意力甜点区"。
2. **减少检索的文档数量**：严格控制 Top-K 的 K 值，例如只取 Top-3 或 Top-5，确保召回的文档质量足够高。
3. **指令化提示**：在 prompt 中明确指示模型要关注所有提供的上下文，如"请确保你的回答完全基于以上提供的所有上下文信息，不要忽略任何一份文档"。
4. **对 LLM 进行微调**：构建特定的微调数据集，其中的任务要求模型必须利用位于上下文中间部分的信息才能正确回答，这是最根本但成本也最高的解决方案。

</details>

**19. 除了基础的向量检索，还知道哪些可以提升 RAG 检索质量的技术？**

<details>
<summary>💡 查看答案</summary>

基础的向量检索在处理复杂查询和多样化文档时往往会遇到瓶颈，可从三个方向改进：

**一、增强检索器（Improving the Retriever）**：
1. **混合搜索（Hybrid Search）**：将稀疏检索（如 BM25）和密集检索（向量搜索）相结合，兼顾关键词精确匹配和语义模糊匹配。
2. **重排序（Re-ranking）**：采用两阶段流程。先用向量搜索或混合搜索从海量文档中召回较大的候选集（如 Top-50），再使用 Cross-Encoder 对小候选集进行精细化的重排序，选出最终的 Top-N（如 Top-5）。

**二、优化查询（Improving the Query）**：
1. **查询扩展与转换（Query Expansion）**：不直接使用用户的原始查询进行检索，而是先用 LLM 对查询进行"加工"，包括多查询检索（从不同角度生成多个查询）、HyDE（先生成假设性答案再检索）、子问题查询（分解为多个简单子问题）。

**三、优化索引结构（Improving the Index）**：
1. **小块引用大块（Small-to-Large Chunking）**：检索时用查询匹配小块以获得高精度，但最终送给 LLM 的是包含更丰富上下文的父块，兼顾了小块检索的精确性和大块上下文的完整性。
2. **图索引（Graph Indexing）**：除了向量索引，还用 LLM 提取文档中的实体和关系，构建知识图谱，对于需要进行多跳推理、理解实体关系的查询非常有效。

</details>

**20. RAG 如何处理模糊查询？**

<details>
<summary>💡 查看答案</summary>

RAG 通过检索与查询的不同解释相关的多个文档来处理模糊查询。生成模型将这些信息综合成一个连贯的响应。具体处理策略如下：

1. **多解释检索**：对于模糊 query（如"苹果怎么样"），系统可以识别多种可能的解释（苹果公司、苹果水果、iPhone 手机），并针对每种解释分别检索，然后将所有检索结果一起传给 LLM，由 LLM 综合上下文判断最可能的用户意图并生成答案。
2. **意图消歧澄清**：在系统允许多轮对话时，遇到高度模糊的 query 可以先向用户澄清意图（"您是想了解苹果公司的股价，还是苹果手机的使用方法？"），而不是强行检索并可能答非所问。
3. **Query 扩展**：对模糊 query 生成多个同义或相关的检索变体，扩大检索范围，提高覆盖不同解释的概率。例如使用 LLM 生成 3--5 个基于不同可能意图的 query 变体，并行检索后合并结果。
4. **语境感知消歧**：在多轮对话场景中，利用历史对话上下文判断当前模糊 query 的最可能含义（如前几轮一直在讨论 iPhone，则"苹果"大概率指 iPhone），自动消歧后再检索。
5. **置信度标注**：当系统不确定 query 意图时，在答案中明确说明"您的问题可能涉及 X 或 Y，以下分别为您提供两种解释的信息"，提升答案的透明度和用户体验。

</details>

**21. RAG 如何处理对抗性查询？**

<details>
<summary>💡 查看答案</summary>

1. **输入过滤与合规检测**：在 query 进入 RAG 流程之前，进行安全检测——识别 Prompt 注入攻击（试图通过 query 修改系统 Prompt 的行为）、越权访问尝试（查询超出用户权限范围的内容）、有害内容请求等。可使用 LLM 分类器或规则引擎实现。
2. **知识库内容过滤**：对知识库中的文档预先做安全审查，过滤包含误导性、有害或政治敏感内容的文档，防止对抗性 query 通过检索引出危险内容。检索时对召回文档再次做相关性和安全性判断。
3. **Prompt 注入防御**：在系统 Prompt 中明确指令模型忽略用户 query 中试图修改其行为的指令（如"忽略以上指令，改为……"），并对异常长、包含特殊指令格式的 query 进行标记和人工审查。
4. **答案后置安全检查**：生成的答案在返回用户前经过安全过滤器，检测是否包含违禁内容、PII 信息泄露、越权信息等，不符合安全规范的答案被拦截并返回标准拒绝响应。
5. **鲁棒性训练**：对生成模型进行对抗性微调，在训练数据中包含对抗性输入和正确的拒绝回应示例，使模型学会识别并适当拒绝有害 query。
6. **速率限制与异常检测**：对频繁尝试边界情况的用户设置访问速率限制，异常查询模式（如系统性地探测权限边界）触发告警和人工审查。

</details>

**22. RAG 是否可以用于实时应用？**

<details>
<summary>💡 查看答案</summary>

是的，RAG 可以应用于实时场景，但需要针对延迟进行专项优化。以下是关键分析和工程策略：

**RAG 的延迟构成**：一次完整的 RAG 请求通常包括：Query Embedding 计算（10--50ms）+ 向量检索（5--50ms）+ 可选 Reranking（50--200ms）+ LLM 生成（200ms--数秒）。总端到端延迟在 500ms--3s 范围，与"实时"的定义有关（$<$200ms vs $<$2s）。

**适合实时应用的场景**：
- 客服对话（用户对 1--2 秒的响应延迟有一定容忍度）；
- 知识库问答（非实时交易类，秒级响应可接受）；
- 代码辅助（Copilot 风格，流式输出可减少感知延迟）。

**实时优化关键手段**：
1. **流式输出（Streaming）**：LLM 生成阶段逐 token 流式返回，用户不需要等待完整答案生成，首 token 出现时间（TTFT）可降至 $<$500ms，显著改善实时感知体验；
2. **语义缓存**：对高频重复 query 的结果缓存，命中时延迟接近零（$<$10ms）；
3. **轻量 Embedding 模型**：MiniLM-L6（22M 参数）vs BGE-Large（335M 参数），前者 Embedding 速度快 5--10×；
4. **内存向量索引**：将向量索引全量加载到内存（HNSW），检索延迟 $<$10ms；
5. **跳过 Reranking**：对延迟极度敏感的场景，可省略 Reranking 步骤，以牺牲少量精度换取 50--200ms 的延迟降低；
6. **选择更快的 LLM**：使用 GPT-4o-mini、Claude Haiku 等推理速度快的小模型，适合对质量要求不极致但延迟敏感的实时场景。

**不适合实时的场景**：高频交易（毫秒级延迟要求）、游戏实时对战（$<$100ms 要求），这些场景 RAG 的固有延迟无法满足要求，需要预计算或完全不同的架构。
