# 4.3 指令微调（SFT）与数据构建 — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 4 章：微调（Fine-Tuning） · 共 13 题

**1. 预训练和 SFT 操作有什么不同？**

<details>
<summary>💡 查看答案</summary>

- **目标**：预训练通过无监督学习从大规模文本语料库中学习通用的语言表示和语言知识；SFT 在特定任务上进一步优化模型性能。
- **数据**：预训练使用大规模的无标签文本数据；SFT 使用带有标签的任务相关数据。
- **训练方式**：预训练采用无监督学习方式；SFT 采用有监督学习方式。
- **模型调整**：预训练从随机初始化的参数开始训练；SFT 通常以预训练模型的参数作为初始化。

</details>

**2. 大模型 LLM 进行 SFT 时在学习什么？**

<details>
<summary>💡 查看答案</summary>

在大语言模型进行有监督微调（SFT）时，模型主要学习以下内容：
1. **任务特定的标签预测**：模型学习根据输入文本预测正确的标签或目标输出。
2. **上下文理解和语言模式**：模型利用预训练阶段学到的语言知识，进一步理解任务相关的上下文信息。
3. **特征提取和表示学习**：模型通过任务数据学习更有效的特征表示，以便更好地区分不同类别或完成任务目标。
4. **任务相关的优化**：模型通过反向传播和优化算法调整参数，以最小化任务相关的损失函数。
5. **适应特定领域或风格**：如果任务数据来自特定领域或具有特定风格，模型学习适应这些领域或风格的语言表达方式。

</details>

**3. SFT 阶段能学习到新的知识吗？**

<details>
<summary>💡 查看答案</summary>

在 SFT 阶段，模型可以在一定程度上学习新知识，但这种学习是基于预训练知识的优化和扩展，而非完全从零开始。

**可以学习新知识的情况**：如果 SFT 阶段的数据包含与预训练阶段不同的模式、规律或特征，模型可以通过学习这些数据来获取新知识。例如，通过领域特定的数据微调，模型可以学习到该领域的专业术语和逻辑关系。

**学习能力有限的情况**：如果新知识与预训练阶段的知识完全无关，或者超出了模型的理解范围，模型很难真正学会这些新知识。SFT 阶段的训练是基于预训练模型的参数进行微调，模型的学习能力受到预训练参数的约束。

</details>

**4. 指令微调的好处是什么？**

<details>
<summary>💡 查看答案</summary>

在大模型训练中进行指令微调（Instruction Fine-tuning）的好处包括：
1. **个性化适应**：通过指令微调，可以使用特定任务或领域的数据对模型进行优化，使其更好地适应任务需求。
2. **性能提升**：通过指令微调，可以调整模型参数和结构，提升任务性能。
3. **控制模型行为**：通过指令微调，可以引入特定指令或约束，使模型行为更符合任务需求。
4. **数据效率**：通过指令微调，可以利用通用数据上的预训练知识，结合少量特定任务数据进行微调，节省数据资源。
5. **提高训练效率**：通过指令微调，可以在预训练模型基础上进行微调，避免从头开始训练，节省时间和资源。

</details>

**5. 如何构建 SFT 的微调数据？**

<details>
<summary>💡 查看答案</summary>

构建监督微调（SFT）数据集需要以下步骤：
1. **收集原始数据**：首先收集与目标任务相关的数据，如对话数据、分类数据等，确保数据具有代表性和多样性。
2. **标注数据**：为每个样本提供正确的标签或目标输出，确保标注的准确性和一致性。
3. **划分数据集**：将数据划分为训练集、验证集和测试集，分别用于模型训练、超参数调整和最终评估。
4. **数据预处理**：根据任务需求，对数据进行清洗、分词、去除停用词等处理，使其适合模型输入。
5. **格式转换**：将数据转换为适合模型训练的格式，如文本文件、JSON 格式等。
6. **模型微调**：使用处理后的数据对基础模型进行微调，选择合适的微调方法和超参数。
7. **模型评估**：使用测试集评估微调后的模型性能，根据结果进一步优化模型。

</details>

**6. 微调数据集应该如何构建？**

<details>
<summary>💡 查看答案</summary>

构建高质量微调数据集需要关注数据来源、数据质量、数据多样性和数据格式等多个方面：

**1. 数据来源**

- **人工标注**：质量可控但成本较高，适合关键场景或种子数据；
- **现有公开数据集**：利用与任务相关的开源数据集；
- **业务日志/历史数据**：从实际业务系统中收集的真实用户输入和理想输出，贴近真实分布；
- **LLM 生成数据（合成数据）**：用更强的模型生成大量训练样本，需要后续质量过滤；
- **数据增强**：对已有数据进行改写、扩充。

**2. 数据质量控制**

- **去重**：避免数据集中存在大量近似重复的样本；
- **去噪/过滤低质量样本**：过滤格式错误、内容空洞、答案明显错误的样本；
- **去除敏感/有害内容**；
- **答案准确性核验**：对于事实性任务，需要确保标注答案本身是正确的。

**3. 数据多样性**

- 覆盖任务的各种子场景/边缘情况；
- 指令表达方式的多样性，提升模型对不同表达方式的泛化能力；
- 包含简单到复杂的不同难度样本。

**总结**：数据质量和多样性往往比单纯的数据数量对最终效果的影响更大，"少而精"通常优于"多而杂"。

</details>

**7. 指令微调的数据格式一般怎么设计？**

<details>
<summary>💡 查看答案</summary>

**1. 基础三元组格式**

最经典的格式（如 Alpaca 格式）包含三个字段：instruction（任务指令）、input（可选具体输入）、output（期望的模型输出）。

**2. 对话格式（Multi-turn / Chat Format）**

对于对话模型，通常采用"消息列表"的格式，每条消息包含角色（role）和内容（content），包括 system/user/assistant 三种角色。

**3. 损失计算范围（Loss Masking）**

在指令微调中，**通常只对 assistant（模型回复）部分的 token 计算损失**，对 instruction/input/system/user 部分的 token 不计算损失（label 设为 -100）。

**4. 特殊 token 与结束符**

每轮对话之间通常用特殊的角色标记 token 和结束符分隔，确保模型在推理时能正确判断"何时该结束当前轮的生成"。

</details>

**8. 如果微调数据模板中缺少了结束标记 `</s>会产生什么影响？`**

<details>
<summary>💡 查看答案</summary>

结束标记（EOS, End-of-Sequence token）用于标示一段生成内容的结束，如果微调数据模板中缺少这个标记，会产生以下影响：

**1. 模型无法学会"何时停止生成"**

模型在该位置上没有学到"应该输出 EOS"的信号，导致推理时模型可能无法正确地自然停止生成，而是持续生成内容直到达到最大长度限制才被强制截断。

**2. 生成内容"停不下来"/出现冗余内容**

模型在给出本应是完整的回答之后，继续生成额外的、不相关甚至重复的内容，出现"一直说下去"的现象。

**3. 多轮对话场景下轮次边界混乱**

模型可能在多轮对话推理时无法正确区分轮次边界，造成对话流程混乱。

**解决方法**：检查并修正训练数据的模板，确保每个训练样本中 assistant 回复的末尾正确附加了 EOS token，且该位置的 EOS token 也参与损失计算。

</details>

**9. 在微调过程中，损失函数应该仅计算输出部分，还是同时计算输入和输出部分？**

<details>
<summary>💡 查看答案</summary>

**方案一：仅计算输出（assistant 回复）部分的损失（loss masking）**

这是目前主流的指令微调标准做法。

优点：
- 训练目标与实际使用场景一致；
- 避免模型学习"复述输入"的不必要倾向；
- 是绝大多数开源指令微调数据集和训练框架的默认/推荐做法。

**方案二：同时计算输入和输出部分的损失**

即对整个序列都进行语言建模损失计算，类似纯粹的"继续预训练"。

缺点：
- 训练目标与推理任务不一致；
- 如果输入部分远长于输出部分，损失中绝大部分的梯度来自于"预测输入"，对真正期望优化的"生成输出能力"的贡献占比反而被压低。

**总结**：仅计算输出部分的损失（loss masking）是绝大多数指令微调场景下的正确做法。

</details>

**10. 如何提升模型的指令跟随能力？**

<details>
<summary>💡 查看答案</summary>

提升模型指令跟随（Instruction Following）能力的常见方法：

1. **高质量、多样化的指令微调数据**：覆盖广泛的任务类型、指令措辞方式、复杂度层次。
2. **严格遵循格式/约束类指令的专项数据**：大量构造"带有明确约束条件的指令及完全符合约束的回复"，强化模型对约束条件的敏感性。
3. **复杂指令的分解与多步推理训练**：训练数据中应包含多子任务组合指令及对应的完整覆盖所有子要求的回复。
4. **RLHF / DPO 等偏好优化**：通过人类对模型输出的偏好标注，进一步优化模型在"是否精确满足指令"维度上的表现。
5. **评估与迭代**：建立专门评估"指令遵循度"的评测集，针对薄弱环节补充对应的训练数据，形成迭代循环。

</details>

**11. 现有一个若干篇文章组成的企业知识库，希望通过 SFT 方法让模型记住，如何将其转换成适合 SFT 的数据集？如何确定 SFT 所需数据集的大小？**

<details>
<summary>💡 查看答案</summary>

**将知识库转换为 SFT 数据集的方法**：

**1. 生成问答对（QA Pair Generation）**
- 对知识库中的每篇文章，使用 LLM 自动生成多个相关的问题及对应的标准答案，形成 (question, answer) 形式的 SFT 样本；
- 问题应多样化，同一个知识点可以从不同角度、不同措辞方式提问，增加模型对该知识点的"记忆冗余度"。

**2. 文章摘要与改写**：让模型学习对文章内容进行摘要、改写、不同风格的复述。

**3. 填空/补全类任务**：构造"给定文章的一部分，补全/续写剩余部分"的训练样本。

**4. 多轮对话形式**：将知识包装成"用户咨询-模型解答"的多轮对话场景。

**重要的权衡考虑**：SFT（参数内记忆）并不是存储和更新知识库内容最理想的方式。在实践中，**RAG（检索增强生成）通常是比纯 SFT 更适合"让模型利用企业知识库回答问题"的方案**——"SFT 负责能力，RAG 负责知识"。

**确定 SFT 数据集大小的考虑因素**：知识库的规模与知识点数量、每个知识点的"曝光"次数、基座模型规模、以及过拟合与遗忘的平衡。

</details>

**12. 微调后的模型上线后发现一些反复出错的用例，应当怎样修改 SFT 数据集？**

<details>
<summary>💡 查看答案</summary>

针对上线后发现的反复出错用例，修改流程通常包括：

1. **错误案例的收集与分类**：系统化收集线上反馈的错误用例，对错误进行分类归因，识别错误模式的共性。
2. **针对性补充训练样本**：构造对应的"正确示范"训练样本，且应围绕该错误模式构造一批"举一反三"的变体样本，让模型学习的是"该类问题的正确处理方式"而非"特定输入的特定答案"。
3. **反例/对比样本（可选，用于偏好优化阶段）**：将"模型当前的错误输出"作为负例，"修正后的正确输出"作为正例，构造偏好对用于 DPO/RLHF。
4. **避免引入新的不平衡/遗忘**：新增数据应与原有数据集混合进行增量微调，并监控原有评测集的指标是否保持稳定。
5. **回归测试集的建设**：将已发现的错误用例整理为回归测试集，每次模型迭代后都在该测试集上验证。

</details>

**13. 模型对话轮次较多后，出现模型重复用户的提问或者之前轮次的回答等"复读机"问题，应该怎样通过微调方法解决？**

<details>
<summary>💡 查看答案</summary>

"复读机"问题的微调解决方法：

1. **检查并修正训练数据中的多轮对话样本**：排查训练数据本身是否存在"assistant 回复中包含对用户提问的复述"等样本，清洗/过滤或改写这类样本。
2. **增加"长对话、低重复"的正例数据**：专门构造长度较长（多轮）、且 assistant 回复始终简洁、不重复历史内容的高质量多轮对话样本。
3. **构造针对性的负例/偏好对（DPO）**：收集模型当前产生的"复读"输出作为负例，人工编写简洁、不重复的版本作为正例，通过 DPO 直接训练模型"避免复读"这一具体行为模式。
4. **检查上下文长度与位置编码问题**：若复读主要出现在对话轮次较多时，可能与位置编码的外推问题有关，需要检查长文本/长对话相关的训练数据是否充足。
5. **System Prompt 的强化**：在训练数据的 system prompt 中加入"不要重复用户的问题"等明确指令，并确保训练数据中的 assistant 回复确实符合这一指令。
