# 8.4 Agent 与 RAG 评估专题 — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 8 章：评估与 Benchmark · 共 41 题

**1. 评估一个 Agent 为什么比评估一个基础 LLM 更加困难和复杂？评估的维度有哪些不同？**

<details>
<summary>💡 查看答案</summary>

评估一个Agent比评估一个基础LLM更加困难和复杂，因为评估的对象从一个静态的、单轮的“文本生成器”，转变为一个动态的、多轮的、与环境交互的“决策者”。


困难和复杂性的根源：


1. 交互性与状态空间： 基础LLM是无状态的（stateless），其评估是“输入->输出”的简单模式。而Agent是有状态的（stateful），它与环境进行多步交互，每一步的行动都会改变环境和自身的内部状态。这导致其可能的行为轨迹（trajectory）数量是天文数字，难以完全覆盖。
2. 环境的动态性与不确定性： LLM的评估环境是确定的（相同的输入总是有相同的期望输出范围）。Agent的评估环境（如真实的网页、API）是动态变化的、不可预测的。一个今天还能用的API明天可能就失效了，一个网页的结构可能随时改变，这使得评估结果难以复现。
3. 非确定性（Non-determinism）： 由于LLM本身的采样随机性和环境的动态性，同一个Agent在完全相同的初始任务下，两次执行的结果和路径可能完全不同。
4. 任务的开放性： Agent处理的任务往往是开放式的、没有唯一正确答案的（例如，“帮我预订一张去新加坡的性价比最高的机票”），这使得定义一个简单的“正确/错误”指标变得不可能。

评估维度的不同：


| 评估维度       | 基础 LLM                                                                                           | Agent                                                                                                                                                                                                                             | | :----------------- | :----------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | | 核心评估对象   | 单个回答的质量 (Quality of a single response)                                                      | 整个任务完成过程 (The entire task completion process)                                                                                                                                                                             | | 主要维度       | - 准确性 (Accuracy)<br>- 流畅性 (Fluency)<br>- 相关性 (Relevance)<br>- 安全性 (Safety) | - 任务成功率 (Task Success Rate): 能否最终完成目标？<br>- 效率 (Efficiency): 完成任务花了多少资源？（见下文）<br>- 鲁棒性 (Robustness): 能否处理异常和错误？<br>- 自主性 (Autonomy): 在没有人类干预的情况下能走多远？ | | 新增的过程维度 | (无)                                                                                                   | - 成本 (Cost): LLM调用次数、API费用、Token消耗。<br>- 延迟 (Latency): 完成任务的总时间。<br>- 步骤数 (Number of Steps): 任务分解和执行的步数。<br>- 纠错能力 (Error Recovery): 从工具报错或错误状态中恢复的能力。     | | 评估方法       | 静态数据集上的基准测试 (MMLU, HumanEval)                                                               | 交互式环境中的基准测试 (WebArena, AgentBench)                                                                                                                                                                                     |


总结来说，对LLM的评估更像是“产品质量检测”，而对Agent的评估更像是“路况复杂的真实驾驶测试”，不仅要看是否到达终点，更要看驾驶过程中的效率、安全性和应对突发状况的能力。

</details>

**2. 为什么 Agent 系统的评测特别困难？**

<details>
<summary>💡 查看答案</summary>

Agent 任务往往是开放式、多步骤的，"正确答案"可能不唯一，过程是否合理与最终结果是否正确并不完全等价，且涉及工具调用等外部副作用，难以用简单的字符串匹配评估。

</details>

**3. Agent 的"成功率"应该如何定义？**

<details>
<summary>💡 查看答案</summary>

通常基于明确的任务完成标准（如最终状态是否达到预期、关键产物是否生成且正确），可以是二元的（成功/失败）也可以是分级的（部分完成度打分），需要针对具体任务场景制定标准。

</details>

**4. Agent 评测常用的指标有哪些？**

<details>
<summary>💡 查看答案</summary>

包括任务成功率、平均执行步数、Token/成本消耗、执行延迟、工具调用准确率、错误恢复率，以及针对特定能力的细分指标（如规划合理性、记忆使用有效性）。

</details>

**5. 在评估一个 Agent 的任务完成情况时，除了最终结果的正确性，还有哪些过程指标是值得关注的？（例如：效率、成本、鲁棒性）**

<details>
<summary>💡 查看答案</summary>

在评估Agent时，只看最终结果的正确性（Task Success）是远远不够的。一个优秀的Agent不仅要能“做对事”，还要“聪明地、高效地、可靠地做事”。因此，关注过程指标至关重要，它们能更全面地反映Agent的智能水平。


值得关注的关键过程指标包括：


1. 效率 (Efficiency):

- 定义： 衡量Agent完成任务所消耗的资源。效率是决定Agent在现实世界中是否可用的关键因素。
- 具体指标：
- 成本 (Cost):
- Token消耗量： Agent在所有思考和生成步骤中消耗的总Token数。
- API调用费用： 如果使用了付费的LLM或工具API，完成一次任务的总花费。
- 延迟 (Latency):
- 总耗时 (Wall-clock Time): 从任务开始到结束所经过的真实时间。
- 计算时间 (CPU/GPU Time): Agent自身运行所占用的计算时间。
- 步骤数 (Number of Steps / Turns): Agent执行“思考-行动”循环的总次数。通常，能用更少步骤完成任务的Agent被认为规划能力更强。

1. 鲁棒性 (Robustness):

- 定义： 衡量Agent在面对非理想、非预期情况时的表现。
- 具体指标：
- 错误处理能力 (Error Handling Capability): 当工具返回错误、网页加载失败或遇到预期外的环境状态时，Agent能否识别问题并采取纠正措施（例如，尝试不同的工具、修正输入参数、重新规划）。
- 抗干扰能力 (Disturbance Resistance): 在环境中加入一些噪声或误导性信息，评估Agent的成功率下降了多少。

1. 自主性与对齐 (Autonomy & Alignment):

- 定义： 衡量Agent在多大程度上能够独立完成任务，以及其行为是否符合人类的意图。
- 具体指标：
- 需要人类干预的次数 (Number of Human Interventions): 在一个需要人类协助的系统中，一个更自主的Agent需要人类帮助的次数更少。
- 行为可解释性 (Interpretability): Agent的“思考”过程是否清晰、合乎逻辑，是否能让人类理解其决策依据。
- 计划遵循度 (Plan Adherence): 如果Agent预先生成了一个计划，它在多大程度上遵循了自己的计划。

通过综合评估这些过程指标，我们不仅能知道Agent“是否能行”，还能深入了解它“行不行得好”，并找到针对性的优化方向。

</details>

**6. Agent 的成本应该如何评测？**

<details>
<summary>💡 查看答案</summary>

统计完成单个任务消耗的总 Token 数、调用的模型/工具次数及对应费用，结合任务成功率计算"单位成功任务成本"等综合指标。

</details>

**7. Agent 的延迟应该如何评测？**

<details>
<summary>💡 查看答案</summary>

统计端到端完成任务所需的总耗时，并拆解各环节（模型推理、工具调用、等待）的耗时占比，定位延迟瓶颈所在。

</details>

**8. Agent 如何进行离线评测？**

<details>
<summary>💡 查看答案</summary>

基于预先构建的标准化任务集（含输入和评判标准），在隔离环境中批量运行 Agent，自动或半自动评判结果，适合用于版本迭代前的回归验证。

</details>

**9. Agent 如何进行在线评测？**

<details>
<summary>💡 查看答案</summary>

在真实流量中通过埋点收集 Agent 的实际表现数据（成功率、用户反馈、人工抽样审核结果），用于发现离线评测未覆盖的真实场景问题。

</details>

**10. Agent 如何进行 A/B 测试？**

<details>
<summary>💡 查看答案</summary>

将真实流量按比例分配给不同版本的 Agent（不同 Prompt/模型/工具配置），对比关键业务指标（任务完成率、用户满意度、成本）的差异，验证改动效果。

</details>

**11. Agent 如何进行回归测试？**

<details>
<summary>💡 查看答案</summary>

维护一组覆盖核心场景和历史问题 Case 的标准任务集，每次系统改动后重新运行该测试集，确保新改动没有引入对已有能力的退化。

</details>

**12. Agent 评测如何实现自动化？**

<details>
<summary>💡 查看答案</summary>

对于有明确判定标准的任务（如代码是否通过测试、数值计算是否正确）可以用程序自动判定；对于开放式输出，可以引入"裁判模型"（LLM-as-Judge）按预定标准打分，并辅以人工抽检校准裁判模型的可靠性。

</details>

**13. Agent 如何进行任务级（Task-Level）评测？**

<details>
<summary>💡 查看答案</summary>

关注端到端的最终结果是否达成任务目标，不关心中间过程，适合衡量"对用户而言是否解决了问题"。

</details>

**14. Agent 如何进行步骤级（Step-Level）评测？**

<details>
<summary>💡 查看答案</summary>

对每个中间步骤（如某次工具调用、某次规划决策）单独评判其合理性和正确性，适合定位是哪个具体环节出了问题，是任务级评测的细化补充。

</details>

**15. Agent 的工具调用能力应该如何单独评测？**

<details>
<summary>💡 查看答案</summary>

构建专门的工具调用测试集，评估"是否选择了正确的工具""参数是否填写正确""调用时机是否合理"等指标，与最终任务结果解耦评估。

</details>

**16. 什么是评估中的"工具使用 Benchmark"（如 ToolBench、Berkeley Function-Calling Leaderboard）？关注哪些方面？**

<details>
<summary>💡 查看答案</summary>

此类 Benchmark 专门评估模型的 Function Calling/工具调用能力，关注维度包括：是否能根据任务正确选择需要调用的工具（单工具/多工具场景）、是否能正确生成符合 Schema 的调用参数、是否能正确处理工具返回结果并生成最终回答，以及在工具数量较多时的选择准确率等。

</details>

**17. 什么是 Berkeley Function-Calling Leaderboard 中的"AST 评估"和"执行评估"两种评判方式？**

<details>
<summary>💡 查看答案</summary>

AST（抽象语法树）评估是将模型生成的函数调用解析为结构化表示，与标准答案在结构和参数层面进行比对（检查函数名、参数名、参数值是否匹配，允许一定的等价形式）；执行评估则是实际执行模型生成的函数调用（在真实或模拟环境中），检查执行结果是否符合预期。AST 评估速度快、不需要真实执行环境，但可能对一些"形式不同但语义等价"的有效调用产生误判；执行评估更接近真实场景但实现成本和复杂度更高。

</details>

**18. 如何评估一个支持工具调用的 Agent 在"工具选择正确性"和"最终任务完成度"之间可能出现的分歧？**

<details>
<summary>💡 查看答案</summary>

可以分别构建两套评测：（1）工具调用轨迹评测——独立检查每一步是否选择了合理的工具及参数（即使最终任务可能因为其他原因未完成）；（2）任务结果评测——只关注最终状态是否达成目标（即使中间过程不是"标准"路径，但通过其他合理路径也达成了目标）。两者的分歧（如工具选择"不标准"但任务依然完成）本身也是有价值的分析信息，可能反映出标准路径定义过于狭窄或模型找到了更优路径。

</details>

**19. Agent 的 RAG 能力应该如何评测？**

<details>
<summary>💡 查看答案</summary>

分别评估检索环节（是否召回了正确文档/片段）和生成环节（是否基于检索内容给出准确、忠实的答案），可参考 RAG 评测中提到的分层评测方法。

</details>

**20. 如何评估一个 RAG 系统中"检索内容是否被模型正确利用"（即生成内容是否忠实于检索结果）？**

<details>
<summary>💡 查看答案</summary>

可以采用：（1）基于 NLI（自然语言推理）模型，判断生成的每个陈述是否能从检索内容中被"蕴含"（Entailment）；（2）LLM-as-Judge，给定检索内容和生成回答，判断回答中的每个事实陈述是否有据可查；（3）人工标注样本中"幻觉率"（生成内容中无法从检索内容中找到依据的陈述比例）作为校准基准。

</details>

**21. Agent 的 Memory 能力应该如何评测？**

<details>
<summary>💡 查看答案</summary>

设计需要跨多轮/跨会话才能正确回答的测试场景，评估 Agent 是否正确存储、检索并利用了相关历史信息，以及是否避免了无关记忆的干扰。

</details>

**22. Agent 的规划（Planning）能力应该如何评测？**

<details>
<summary>💡 查看答案</summary>

评估生成的计划是否覆盖了任务所需的关键步骤、步骤顺序是否合理、是否存在冗余或遗漏步骤，可以与人工专家方案或参考方案做对比。

</details>

**23. 什么是评估"长程规划"（Long-Horizon Planning）能力的 Benchmark 设计难点？**

<details>
<summary>💡 查看答案</summary>

难点包括：（1）任务本身需要足够长的步骤序列才能体现"长程"特性，但步骤越多，评测的执行成本（时间、Token消耗）越高；（2）需要设计明确的、可自动判定的"中间里程碑"和"最终成功"标准，否则难以区分"模型整体方向正确但某个中间步骤出错"和"模型完全偏离目标"两种情况；（3）由于步骤间存在依赖关系，某一步的微小错误可能在后续步骤中被放大，导致最终成功率对早期步骤的正确性高度敏感，使得评测结果的方差可能较大，需要多次运行取统计结果。

</details>

**24. Agent 的安全性应该如何评测？**

<details>
<summary>💡 查看答案</summary>

构建包含越权操作尝试、敏感信息泄露诱导、恶意指令注入等场景的测试集，验证 Agent 是否能正确识别并拒绝/规避这些风险操作。

</details>

**25. Agent 的鲁棒性应该如何评测？**

<details>
<summary>💡 查看答案</summary>

对输入做扰动测试（如错别字、不完整信息、非常规表达方式），观察 Agent 在这些扰动下的表现是否稳定，识别对特定输入格式过度敏感的问题。

</details>

**26. Agent 的稳定性应该如何评测？**

<details>
<summary>💡 查看答案</summary>

对相同或相似输入多次运行，统计输出结果（或任务成功与否）的一致性/方差，评估系统在多次运行中的可重复性。

</details>

**27. Agent 的可解释性应该如何评测？**

<details>
<summary>💡 查看答案</summary>

检查 Agent 是否能为其决策和行动提供清晰、与实际执行过程一致的理由说明，可通过人工审核 Trace 与解释的吻合程度来评估。

</details>

**28. 为什么 Agent 在 Benchmark 上得分很高，但线上实际表现却经常翻车？**

<details>
<summary>💡 查看答案</summary>

Benchmark 任务通常分布相对集中、输入格式规范，而线上面对的是更广泛、更"脏"的真实分布；此外 Benchmark 评判标准可能与真实业务的成功标准存在差异（即"刷分"和"解决实际问题"并不完全等价）。

</details>

**29. 当前的 Agent 真的具备"推理"能力吗？**

<details>
<summary>💡 查看答案</summary>

模型展现出的推理能力本质上是基于大规模数据训练得到的模式延展和概率组合，能在很多任务上产生类似推理的效果，但与人类基于因果理解的推理在机制上并不相同，对超出训练分布的全新逻辑结构泛化能力有限。

</details>

**30. 当前的 Agent 真的具备"规划"能力吗？**

<details>
<summary>💡 查看答案</summary>

Agent 能够生成结构合理的计划文本，在很多场景下表现接近"规划"，但其规划过程缺乏对真实世界状态的持续建模和反馈闭环，更像是基于经验模式生成"看起来合理"的步骤序列，而非严格意义上的（如经典 AI 规划算法那样的）状态空间搜索。

</details>

**31. 当前的 Agent 真的具备"学习"能力吗？**

<details>
<summary>💡 查看答案</summary>

单次对话/任务内的"学习"主要体现为利用上下文中的新信息调整后续行为（即 In-Context Learning），并不会改变模型本身的参数；要实现持久化的能力提升，仍需依赖外部记忆机制或对模型进行微调。

</details>

**32. Agent 的泛化能力应该如何评测？**

<details>
<summary>💡 查看答案</summary>

设计与训练/调优数据分布不同的测试场景（不同领域、不同任务结构），观察 Agent 在这些"分布外"场景中的表现衰减程度。

</details>

**33. Agent 的长期任务能力应该如何评测？**

<details>
<summary>💡 查看答案</summary>

设计需要持续多步、跨较长时间跨度（甚至跨会话）才能完成的任务，评估其在整个过程中是否能保持目标一致性、状态正确性。

</details>

**34. 如何设计针对"长期任务"（如需要持续多天/多会话完成的任务）的评估方法？**

<details>
<summary>💡 查看答案</summary>

需要构建支持跨会话状态保持的评测环境（模拟系统能够在任务执行间隙保存和恢复状态），评测指标除了最终任务是否完成外，还应关注：任务进度的正确追踪、是否出现目标遗忘或偏离、中断后能否正确恢复，以及整个过程中的资源消耗（成本、时间）是否在合理范围内；由于此类评测耗时较长，通常需要在自动化评测框架中支持并行运行大量长期任务实例。

</details>

**35. Agent 的复杂任务处理能力应该如何评测？**

<details>
<summary>💡 查看答案</summary>

设计涉及多个子目标、多种工具、存在依赖关系的综合任务，观察 Agent 是否能正确拆解并协调完成各部分。

</details>

**36. Agent 的协作能力应该如何评测（Multi-Agent场景）？**

<details>
<summary>💡 查看答案</summary>

评估多个 Agent 在协作任务中通信是否高效、是否出现重复劳动或遗漏、最终融合结果是否优于任一单独 Agent 的产出。

</details>

**37. Agent 的自主性应该如何评测？**

<details>
<summary>💡 查看答案</summary>

评估在缺少明确分步指导、仅给出高层目标的情况下，Agent 能否自主完成合理的任务拆解、决策和执行，以及在遇到意外情况时的自主应对能力。

</details>

**38. 你了解哪些专门用于评估 Agent 能力的基准测试？这些基准通常如何构建测试环境和任务？**

<details>
<summary>💡 查看答案</summary>

是的，随着Agent研究的兴起，一系列专门用于评估Agent能力的基准测试被开发出来，它们的核心特点是提供可控的、可复现的交互式环境。


几个知名的Agent能力基准测试：


1. WebArena:

- 专注领域： 网页浏览与操作。
- 简介： 一个高度逼真的、独立的网页环境模拟器。它复刻了多个真实网站（如电商、论坛、软件开发协作工具）的功能，让Agent在其中完成真实世界的复杂任务。
- 任务举例： 在电商网站上找到一个满足特定要求（如价格、评分）的商品并加入购物车；在论坛上预订一个会议室。
- 评估方式： 基于最终网页状态的程序化判断（例如，购物车里是否有正确的商品）。

1. AgentBench:

- 专注领域： 通用Agent能力的综合评估。
- 简介： 一个全面的基准，包含了8个不同环境来评估Agent在不同场景下的能力。
- 任务举例：
- 操作系统环境： 在一个Linux终端中操作文件、执行命令。
- 数据库环境： 根据自然语言问题，对一个SQL数据库进行查询。
- 知识图谱环境： 在知识图谱中进行多跳推理。
- 游戏环境： 玩一些简单的文字冒险游戏。

1. GAIA (General AI Assistants):

- 专注领域： 模拟人类使用真实工具完成复杂任务。
- 简介： 一个极具挑战性的基准，其问题通常需要Agent进行多步推理，并组合使用多种工具（如网页浏览器、代码解释器、文件操作）才能解决。这些问题被设计得对人类来说很简单，但对AI来说却很困难。
- 任务举例： “找出引用了论文A和论文B的所有论文中，被引用次数最高的那篇的第三位作者是谁？”

这些基准通常如何构建测试环境和任务？


1. 环境构建 -> 沙箱化与可复现性（Sandboxing & Reproducibility）：

- 为了安全和可复现，基准测试通常不会让Agent直接访问真实的互联网，而是创建一个受控的、隔离的环境。
- 方法：
- 使用 Docker 容器来封装一个包含浏览器、终端、文件系统的独立环境。
- 对于网页浏览，通常会本地托管一个网站的静态副本，或使用Web后台模拟器来响应Agent的请求。
- 对API的调用会被重定向到一个模拟（mock）的API服务器上。

1. 任务构建 -> 目标导向（Goal-Oriented）：

- 任务通常以一个 高层次的目标（high-level goal） 的形式给出，而不是具体的步骤指令。
- 任务的设计会尽量覆盖多种需要Agent展示的能力，如信息检索、工具使用、推理规划、记忆等。
- 任务通常附带一个明确的、可程序化验证的成功标准。

1. 评估构建 -> 程序化验证（Programmatic Validation）：

- 评估的核心是自动判断任务是否成功。
- 方法： 在Agent完成任务后，一个 评估脚本（evaluator script） 会自动检查环境的 最终状态（final state） 是否满足成功条件。
- 举例：
- 检查磁盘上是否创建了内容正确的文件。
- 检查购物车的最终状态是否包含了正确的商品和数量。
- 检查Agent提交的最终答案字符串是否与标准答案匹配。

</details>

**39. 什么是"Agentic Benchmark"（智能体类 Benchmark）？与传统的单轮问答 Benchmark 有什么本质区别？**

<details>
<summary>💡 查看答案</summary>

Agentic Benchmark（如 SWE-bench、WebArena、AgentBench 等）评估的是模型在多步骤、需要与环境（如代码仓库、网页、操作系统）交互、调用工具完成复杂任务的能力，关注的是端到端的"任务完成度"而非单次问答的正确性；与传统单轮问答 Benchmark 相比，其评测过程更复杂（需要搭建可交互的环境、定义任务成功的判定标准），评测成本和耗时也显著更高，但更接近真实世界中 Agent 应用的实际场景。

</details>

**40. 为什么评估 Agentic Benchmark（如 SWE-bench）时，"环境的可复现性"是一个特别突出的挑战？**

<details>
<summary>💡 查看答案</summary>

Agentic Benchmark 通常需要在一个完整的、可交互的环境（如包含特定依赖版本的代码仓库、可运行的容器）中评估模型的多步操作；环境本身的微小差异（如依赖库版本不同、网络访问导致的不确定性、容器初始状态的随机性）都可能影响任务能否成功完成，与单纯的文本输入输出评估相比，环境层面的不确定性引入了额外的"噪声"，使得评测结果的可复现性和跨团队复现的一致性更难保证，需要严格的环境镜像/容器化和版本固定来缓解。

</details>

**41. Agent 评测中最大的难点是什么？**

<details>
<summary>💡 查看答案</summary>

是缺乏统一、可规模化、又能真实反映线上效果的评判标准——人工评估成本高且主观，自动化指标（如裁判模型打分）又存在自身的偏差和不可靠性，如何在评测成本、规模和准确性之间找到平衡是核心难点。

</details>
