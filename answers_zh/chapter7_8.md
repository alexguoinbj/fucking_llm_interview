# 7.8 知识库管理与工程实践 — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 7 章：RAG（检索增强生成） · 共 22 题

**1. 什么是知识库（Knowledge Base）？它在 RAG 中扮演什么角色？**

<details>
<summary>💡 查看答案</summary>

知识库是经过处理和索引的外部信息集合，是 RAG 的核心数据源。在 RAG 中的角色：
1. **信息来源**：提供 LLM 训练数据中没有的知识（私有文档、实时信息、专业领域知识）；
2. **检索目标**：向量数据库中存储的正是知识库文档的 embedding；
3. **准确性保障**：LLM 的答案锚定于知识库内容，减少幻觉；
4. **可更新性**：知识库可以独立于模型更新，使系统保持最新；
5. **来源溯源**：每个 chunk 关联原始文档信息，答案可以引用来源。
知识库质量是 RAG 系统质量的天花板。

</details>

**2. RAG 知识库的增量更新策略有哪些？**

<details>
<summary>💡 查看答案</summary>

![知识库文档增量更新与生命周期管理流程](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter7/fig_incremental_update.png)

1. **全量重建**：定期清空向量库重新索引所有文档，实现简单、无碎片，但耗时长，适合数据量小或更新频率低的场景；
2. **增量 Upsert**：检测到文档新增/修改时，只处理变更文档——删除旧 chunk，重新 embedding 并插入新 chunk；使用文档 ID + hash 检测变更；
3. **事件驱动更新**：文档管理系统发布变更事件，RAG 系统订阅并实时处理；
4. **软删除**：过期文档不立即删除，标记为"archived"，检索时默认过滤，保留回滚能力；
5. **版本化更新**：为每个文档版本保留向量，支持按版本检索；
6. 关键挑战：保证更新期间系统的检索一致性，避免"旧文档未删除+新文档已插入"的状态混乱。

</details>

**3. RAG 如何支持实时更新的数据？**

<details>
<summary>💡 查看答案</summary>

需要建立增量索引更新机制，数据变更时及时更新向量库和元数据；对时效性要求极高的数据，也可以结合实时查询接口（而非纯检索）作为补充。具体实现方案如下：

1. **事件驱动的增量更新**：文档管理系统（CMS、数据库）在文档新增、修改或删除时发布变更事件（通过 Kafka、SQS 等消息队列），RAG 系统订阅这些事件，自动触发对应 chunk 的重新 Embedding 和向量库更新，目标端到端延迟 $<$ 1 分钟。
2. **定时批量同步**：对实时性要求不那么高的场景（如每日更新的报告），设置定时任务（如每小时或每天），扫描数据源中的变更文档，批量重新索引。
3. **实时查询接口兜底**：对于实时性要求极高（秒级）的数据（如股价、库存量），不适合走向量检索，而应直接调用外部 API 或结构化数据库查询，将查询结果作为上下文传给 LLM，与向量检索结果合并使用。
4. **软删除机制**：删除或过期的文档不立即从向量库中移除，先标记为"archived"状态，检索时默认过滤，定期清理，防止在更新过程中出现数据空窗。
5. **版本一致性保证**：更新期间采用"先写新、后删旧"的顺序，确保任何时刻检索都能返回有效结果，避免查询命中已被删除的旧 chunk。

核心挑战在于：高频更新与索引重建的计算成本之间的权衡，以及更新期间系统的检索一致性保证。

</details>

**4. RAG 索引如何实现增量更新？**

<details>
<summary>💡 查看答案</summary>

新增/修改文档时只对变更部分重新切片、生成 Embedding 并更新索引，而非全量重建；需要维护文档版本和索引的映射关系以支持准确的增删改。具体实现步骤：

1. **变更检测**：计算每个文档的内容哈希（MD5/SHA256），与上次入库时的哈希值比较。哈希变化的文档视为已修改，需要重新处理；哈希未变化的文档跳过，避免不必要的重新 Embedding。
2. **文档-Chunk 映射维护**：在元数据中记录每个文档 ID 对应的所有 chunk ID，当文档发生变更时，通过 document_id 快速找到并删除所有旧 chunk，再插入重新生成的新 chunk。
3. **原子性保证**：采用"先插入新 chunk，再删除旧 chunk"的顺序，确保在更新过程中系统始终有有效的 chunk 可供检索，避免更新期间出现数据空窗。
4. **软删除机制**：删除的 chunk 先标记为 `status=deleted`，不立即从索引中物理删除，定期清理，防止并发更新时出现不一致。
5. **版本号管理**：为每次批量更新分配版本号，允许按版本回滚（将 chunk 的 status 从 deleted 恢复为 active）。
6. **批量处理优化**：将多个文档的更新合并为批次处理，减少向量数据库的写入次数，提升吞吐量；Embedding 计算使用 GPU 批量推理（batch_size=128+），最大化利用率。
7. **监控指标**：追踪增量更新的端到端延迟（从文档变更到向量库生效）、成功率、重试次数，设置超时告警。

</details>

**5. 如何设计一个支持实时更新的 RAG 系统（文档修改后立即生效）？**

<details>
<summary>💡 查看答案</summary>

1. **事件驱动架构**：文档管理系统发布变更事件（Kafka/SQS），RAG 系统订阅并实时处理；
2. **异步处理流水线**：收到事件→分块→Embedding 计算→更新向量库，全程异步，目标延迟 <30 秒；
3. **读写分离**：写入新向量时不影响正在进行的检索，向量数据库支持并发读写；
4. **软删除+延迟清理**：旧 chunk 先标记为"待删除"，等新 chunk 写入成功后再删除；
5. **幂等性**：同一文档的更新事件可能重复投递，处理逻辑必须幂等（通过文档 ID + 版本号去重）；
6. **实时性 SLA**：监控从文档更新到向量库生效的端到端延迟，设置告警阈值。

</details>

**6. 如何处理知识库中的时效性问题（过期文档）？**

<details>
<summary>💡 查看答案</summary>

1. **时间戳元数据**：每个文档记录创建时间和最后更新时间，检索时可附加时间过滤条件；
2. **有效期标注**：对明确有有效期的内容标注过期时间，检索时自动排除；
3. **定期审查机制**：为不同类型文档设置审查周期，到期由人工或自动化任务核实内容是否仍有效；
4. **来源监控**：对来自外部网站的文档，监控源页面变化，自动触发重新爬取和更新；
5. **用户反馈信号**：用户标记"信息过期"时，触发对应文档的人工核查；
6. **时效性降权**：在检索排序中，对较旧的文档给予时间衰减惩罚（decay factor），让新文档自然排名更高。

</details>

**7. 如何处理知识库中的矛盾信息（不同文档对同一问题有不同表述）？**

<details>
<summary>💡 查看答案</summary>

1. **来源权威性排序**：为不同来源文档设置权威性评分（官方文档 > 博客 > 论坛），检索时权威性高的文档排名靠前；
2. **时间优先**：同等权威性时，最新文档优先；
3. **在 prompt 中声明处理策略**：告知 LLM "如果检索到的文档有矛盾，以[来源A]为准，并说明存在不同观点"；
4. **矛盾检测**：在生成答案时让 LLM 检测传入文档中是否存在矛盾，并在答案中明确说明；
5. **知识库质量审查**：定期识别并处理知识库中的矛盾内容，从源头解决；
6. **版本控制**：矛盾来源于文档版本不同时，只保留最新版本。

</details>

**8. 如何为 RAG 系统设计文档权限控制（不同用户可访问不同文档）？**

<details>
<summary>💡 查看答案</summary>

1. **文档权限元数据**：每个 chunk 附加权限标签（`accessible_roles: ["admin", "sales"]`）；
2. **查询时权限注入**：用户发起查询时，系统将用户的角色/权限注入检索过滤条件，只检索有权访问的 chunk；
3. **向量数据库原生过滤**：大多数向量数据库支持元数据过滤，在向量检索同时做权限过滤；
4. **行级安全**：类似数据库的 Row-Level Security，在向量数据库层强制实施，无法被绕过；
5. **用户上下文隔离**：缓存的检索结果必须与用户权限绑定，不允许不同权限的用户共享检索缓存；
6. **权限变更传播**：文档权限变更时，更新对应 chunk 的权限元数据，确保实时生效。

</details>

**9. RAG 系统如何做权限控制？**

<details>
<summary>💡 查看答案</summary>

在检索阶段就按用户权限过滤可访问的文档/片段（而非检索后再过滤），权限信息应作为索引元数据的一部分参与检索过滤。完整的权限控制方案如下：

1. **权限元数据注入**：文档入库时，将其访问权限（可访问的角色列表、部门、用户 ID 等）作为结构化元数据与 chunk 向量一同存储，例如 `accessible_roles: ["admin", "finance"]`。
2. **检索时权限过滤**：用户发起查询时，系统从认证层获取当前用户的角色/权限信息，并将其转换为向量数据库的过滤条件，在向量检索的同时执行权限过滤，确保只返回用户有权访问的 chunk。
3. **过滤时机的重要性**：权限过滤必须在检索阶段完成，而非检索后再过滤。后者虽然实现简单，但存在安全隐患——已经检索到的无权限内容可能通过 LLM 生成被间接泄露。
4. **行级安全（Row-Level Security）**：在向量数据库层强制实施访问控制，使权限过滤不可被应用层绕过，类似关系型数据库的 RLS 机制。
5. **缓存隔离**：对检索结果或生成结果做缓存时，必须将用户权限作为缓存 key 的一部分，防止高权限用户的缓存结果被低权限用户命中。
6. **权限变更实时同步**：当文档权限调整时，必须同步更新对应 chunk 在向量库中的权限元数据，防止"已撤销权限但仍可检索"的安全漏洞。
7. **审计日志**：记录每次查询涉及的文档访问记录，支持合规审计。

最佳实践：权限控制应作为 RAG 系统的一等公民在架构设计阶段就规划好，而非事后添加的补丁。

</details>

**10. 多租户 RAG 系统中如何实现知识库的隔离？**

<details>
<summary>💡 查看答案</summary>

1. **独立向量数据库**：每个租户拥有独立的向量数据库实例，完全物理隔离，安全性最高，成本也最高；
2. **共享数据库+命名空间**：同一向量数据库，每个租户分配独立的 collection/namespace，逻辑隔离，成本低但需确保查询不会跨命名空间；
3. **元数据过滤隔离**：所有文档存在同一 collection，每个 chunk 附加租户 ID 元数据，查询时强制附加 `tenant_id = xxx` 过滤条件；
4. **权限双重验证**：在 API 层和向量数据库层分别做租户验证，防止单点失效；
5. **数据加密**：不同租户的向量分别用不同密钥加密存储；
6. **审计日志**：记录每次跨租户操作的日志，便于安全审计。

</details>

**11. 知识库中文档版本管理的最佳实践是什么？**

<details>
<summary>💡 查看答案</summary>

1. **版本号标注**：每个文档有版本号和版本创建时间，chunk 继承父文档的版本信息；
2. **版本并存**：新版本发布后，旧版本不立即删除，保留一段时间（如 30 天），用于回滚或版本对比查询；
3. **默认最新版本**：检索时默认只返回最新版本的文档；
4. **历史版本按需检索**：允许指定版本号查询历史版本（用于审计、对比）；
5. **变更日志**：记录每次版本更新的内容摘要，便于追溯；
6. **自动清理**：超过保留期的旧版本自动归档或删除，防止索引膨胀；
7. **原子更新**：新版本 chunk 插入和旧版本 chunk 删除在事务内完成，防止状态不一致。

</details>

**12. 如何检测和清理知识库中的低质量文档？**

<details>
<summary>💡 查看答案</summary>

检测方法：
1. **规则过滤**：文本过短（<50 字）、过长（>10 万字）、特殊字符比例过高、停用词比例异常；
2. **重复检测**：MinHash LSH 检测语义重复文档（>90% 相似度）；
3. **信息密度评分**：用语言模型评估文档的信息密度；
4. **检索频率分析**：长期未被任何查询检索到的文档可能质量低或已过期；
5. **用户反馈**：被用户标记为"无用"的来源文档。
清理策略：自动清理规则触发的明显低质量文档；人工审查边界情况；建立文档质量评分，定期对低分文档做批量清理；清理前备份，防止误删。

</details>

**13. 如何评估知识库的覆盖率（能回答多少比例的目标问题）？**

<details>
<summary>💡 查看答案</summary>

1. **构建目标问题集**：收集目标用户最常提问的 N 个问题（用户日志分析 + 业务专家出题）；
2. **人工标注**：人工判断知识库中是否包含回答每个问题所需的文档；
3. **自动化覆盖率评估**：用 RAG 系统回答每个问题，用 LLM-as-judge 判断答案是否有充分的知识支持；
4. **覆盖率 = 有充分知识支持的问题数 / 总问题数**；
5. **缺口分析**：对未覆盖的问题分类，指导知识库补充方向；
6. **持续监控**：线上系统检测"知识库未找到相关内容"的比例，作为覆盖率的代理指标；
7. 目标覆盖率取决于场景（客服问答通常要求 >90%）。

</details>

**14. 如何构建一个支持多模态（文本+图片+表格）的知识库？**

<details>
<summary>💡 查看答案</summary>

![多模态知识库构建与解析提取流程](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter7/fig_multimodal_ingestion.png)

1. **文本内容**：标准 Embedding 流程，分块后向量化存入向量库；
2. **图片处理**：方案 A：用多模态模型（GPT-4V、LLaVA）生成图片的详细描述，对描述做文本 Embedding；方案 B：用多模态 Embedding 模型（CLIP、ImageBind）直接对图片生成向量；方案 C：混合，同时存图片描述和图片向量；
3. **表格处理**：转为 Markdown 或 CSV 格式后做文本 Embedding；复杂表格可生成自然语言摘要；
4. **统一检索接口**：对不同模态的内容使用统一的检索 API，内部路由到不同的 Embedding 和索引；
5. **元数据记录内容类型**：每个 chunk 标注 `content_type: image/table/text`，便于按类型过滤；
6. **多模态 Reranker**：召回后用多模态模型对混合内容精排。

</details>

**15. RAG 系统如何设计缓存策略？**

<details>
<summary>💡 查看答案</summary>

可以对常见查询的检索结果和最终生成结果做缓存（注意结合数据更新频率设置失效策略），减少重复计算和成本。完整的多层缓存方案如下：

1. **Embedding 缓存**：相同的文本 embedding 计算结果可以缓存（按文本内容哈希为 key）。在 query 预处理、文档更新时，避免对未变更内容重复调用 Embedding API，尤其对于大量重复处理的批量场景成本节省显著。
2. **检索结果缓存（Semantic Cache）**：对 query 的向量检索结果做缓存，key 为 query embedding 向量（通过近似最近邻匹配，语义相似的 query 可命中同一缓存）。适合高频重复性问题（如 FAQ 场景），命中率可达 30%--60%。注意：知识库更新时需要使对应缓存失效。
3. **生成结果缓存（Response Cache）**：对完整的"query → 最终答案"做缓存，适合完全相同或高度相似的问题。失效策略：绑定知识库版本，知识库更新时对应缓存失效；设置 TTL（如 24 小时）。
4. **分层 TTL 策略**：根据数据更新频率设置不同缓存时长——实时数据（不缓存或 TTL=5 分钟）；日更数据（TTL=1 小时）；静态知识库（TTL=24 小时或按版本失效）。
5. **权限隔离**：缓存 key 必须包含用户权限标识，防止不同权限级别的用户共享缓存导致数据泄露。
6. **缓存预热**：识别高频 query（从历史日志中提取），系统启动或知识库更新后提前预热这些 query 的缓存，避免冷启动时的高延迟。
7. **成本收益评估**：Embedding 缓存和检索缓存 ROI 较高（计算成本节省明显）；生成结果缓存需要权衡缓存一致性和成本节省，对于个性化程度高的问答不适合缓存。

</details>

**16. RAG 如何处理长文档？**

<details>
<summary>💡 查看答案</summary>

对长文档需要先做合理切片并保留层级结构信息（如所属章节），检索时可以采用"先检索章节摘要、再检索章节内细粒度片段"的多级检索策略。完整方案如下：

1. **结构感知分块**：利用长文档自身的结构（目录、章节标题、段落标记）进行语义分块，而不是简单按字符数切断。每个 chunk 保留"文档名→章节名→段落"的层级路径作为元数据前缀，使独立的 chunk 仍具备上下文定位信息。
2. **多粒度索引（层级摘要）**：对长文档生成多个粒度的索引：
    - 全文摘要（1 个向量）：用于宏观匹配，判断该文档是否与 query 相关；
    - 章节摘要（若干向量）：用于确定答案所在章节；
    - 细粒度 chunk（大量向量）：用于精确定位具体段落。
3. **两阶段检索**：先用章节摘要向量做粗粒度检索，缩小候选范围；再在候选章节内做细粒度 chunk 检索，精确找到相关段落。
4. **Parent-Child Chunk 策略**：小 chunk（约 200 token）用于精确匹配检索，检索命中后向上查找对应的父 chunk（约 800 token）传给 LLM，兼顾检索精度和上下文完整性。
5. **跨页连续性处理**：PDF 等格式在分页处可能切断语义，预处理时检测跨页段落（通过页面文本末尾是否以完整句子结束来判断），将跨页内容拼接后再分块。
6. **Map-Reduce 生成**：当问题需要综合整篇长文档（如"总结全文要点"）时，对每个 chunk 分别生成局部答案（Map），再将所有局部答案汇总生成最终答案（Reduce），而非试图将整篇文档塞入单次 LLM 调用。

</details>

**17. RAG 可以使用哪些类型的数据源？**

<details>
<summary>💡 查看答案</summary>

RAG 系统的知识库几乎可以接入任何类型的数据源，不同类型的数据源有不同的处理策略：

**一、非结构化文本文档**（最常见）
- **文档文件**：PDF、Word（.docx）、PowerPoint（.pptx）、Markdown、纯文本（.txt）；
- **网页内容**：通过爬虫或 URL 列表抓取，处理 HTML 并剥离无关内容（导航栏、广告）；
- **电子书**：EPUB、MOBI 格式。

**二、结构化与半结构化数据**
- **数据库**：SQL 数据库（MySQL、PostgreSQL）通过 Text-to-SQL 支持自然语言查询；
- **电子表格**：CSV、Excel，可将每行/每列转为自然语言描述后索引；
- **JSON/XML**：配置文件、API 响应数据，需要预处理展平为文本；
- **知识图谱**：Neo4j、RDF 三元组数据库，支持结构化的实体关系检索。

**三、协作与生产力工具**
- **Wiki 与文档平台**：Confluence、Notion、SharePoint、MediaWiki；
- **代码仓库**：GitHub、GitLab，代码文件、README、Issue、PR 描述；
- **即时通讯**：Slack、Teams 的历史消息记录（适合企业内部知识沉淀）；
- **邮件**：历史邮件线程（需要隐私处理）。

**四、实时与流式数据源**
- **新闻 API**：实时新闻流（NewsAPI、路透社数据服务）；
- **搜索引擎 API**：Bing Search API、SerpAPI，提供实时网络搜索结果；
- **金融数据 API**：股价、财报、宏观经济数据；
- **物联网数据**：传感器读数、设备状态（通常需要流式处理后索引）。

**五、多媒体内容**（需要额外处理）
- **图片**：通过多模态模型（GPT-4V）生成描述后索引，或使用 CLIP 等多模态 Embedding；
- **音频/视频**：通过语音转文字（Whisper）生成字幕/文稿后索引；
- **扫描 PDF**：通过 OCR 提取文字后索引。

</details>

**18. RAG 如何处理结构化数据（如表格、数据库记录）？**

<details>
<summary>💡 查看答案</summary>

对结构化数据通常不适合直接做向量检索，可以将其转换为自然语言描述后索引，或者采用"Text-to-SQL"等方式让模型直接查询结构化数据源，再将结果与非结构化检索结果结合。具体方案如下：

1. **自然语言化后向量索引**：将表格、数据库记录转换为自然语言描述（如将一行记录转为"产品 X 的价格为 Y 元，库存为 Z 件"），再对这些描述做 Embedding 存入向量库，支持模糊语义检索。适合数据量不太大、内容相对固定的场景。
2. **Text-to-SQL**：对于结构化数据库，让 LLM 将用户的自然语言问题转换为 SQL 查询，直接执行查询并将精确结果返回。适合需要精确数值、聚合统计、过滤筛选的问题（如"去年销售额最高的前 5 个产品"）。
3. **Markdown 表格嵌入上下文**：对于文档中嵌入的小型表格，将其转换为 Markdown 格式直接包含在 chunk 文本中，LLM 可以直接解读 Markdown 表格，适合表格规模小（$<$20 行）的情况。
4. **表格摘要生成**：对于大型表格，用 LLM 预先生成表格的文字摘要（描述表格结构、关键数据分布、重要统计值），将摘要向量化存储。检索到表格时，将摘要和原始表格一起传给 LLM。
5. **混合路由**：构建路由层，识别 query 是否涉及结构化数据，是则走 Text-to-SQL 路径，否则走向量检索路径，最后将两路结果合并。
6. **挑战**：Text-to-SQL 的准确率在复杂 schema 和多表 join 场景下仍然有限；自然语言化的结构化数据可能丢失精确数值信息，需要根据场景选择合适方案。

</details>

**19. RAG 如何支持图结构数据？**

<details>
<summary>💡 查看答案</summary>

可以构建图数据库并支持基于实体关系的图检索（GraphRAG），通过图遍历找到与查询相关的实体及其关联信息，弥补纯向量检索难以表达多跳关系的不足。具体实现如下：

1. **知识图谱构建**：使用 NLP 技术（NER + 关系抽取）从文档中提取实体和关系，构建知识图谱存入图数据库（Neo4j、Amazon Neptune 等）。节点代表实体（人、地点、概念），边代表关系（属于、创建于、竞争关系等）。
2. **实体链接**：将向量库中的 chunk 与知识图谱中的实体节点关联，使得每个 chunk 既有语义向量，又有图谱中的结构化位置。
3. **图检索路径**：
    - 从 query 中识别核心实体（如"OpenAI"）；
    - 在图谱中定位该实体节点，执行图遍历（广度优先/深度优先），找到 N 跳以内的相关节点和关系；
    - 以这些相关节点为锚点，在向量库中检索对应的文本 chunk；
    - 将图谱结构化信息和向量检索文本合并传给 LLM。
4. **社区检测与全局搜索**：对于需要全局视角的问题，利用图谱的社区结构（Louvain 算法等）将图谱分割为主题社区，对每个社区生成摘要，支持"这些文档的主要主题是什么"类型的宏观问答。
5. **GraphRAG 框架**：微软开源的 GraphRAG 提供了完整的从文档到图谱再到问答的流水线，是当前最成熟的图结构 RAG 实现方案。
6. **适用场景**：高度关联的知识（医疗药物-疾病-基因关系、企业股权关系、科技文献引用网络）；需要多跳推理的复杂问答；需要理解实体间关系的场景。

</details>

**20. RAG 如何应用于代码库场景？**

<details>
<summary>💡 查看答案</summary>

需要针对代码特点设计切片策略（按函数/类/模块切分而非固定长度），结合代码语义 Embedding 和符号级索引（如调用关系、定义引用），支持跨文件的依赖检索。完整方案如下：

1. **代码感知分块**：使用 AST（抽象语法树）解析代码，按函数、类、方法为单位切分，而不是按行数切断。每个 chunk 包含完整的函数签名、函数体和文档注释（Docstring），确保语义完整性。
2. **代码专用 Embedding 模型**：使用针对代码预训练的 Embedding 模型（如 CodeBERT、UniXcoder、StarEncoder），这类模型理解代码语义的能力显著优于通用文本 Embedding 模型。
3. **元数据丰富化**：每个 chunk 附加丰富的元数据——文件路径、所属类名、函数签名、编程语言、导入依赖、被哪些函数调用等，支持基于符号的精确过滤。
4. **符号索引（Symbol Index）**：建立独立的符号索引（函数名 → 定义位置、类名 → 方法列表），支持精确的符号查询（"找到 DataLoader 类的定义"），与语义检索互补。
5. **依赖图增强**：构建代码调用关系图，当检索到某函数时，自动关联其直接依赖的函数和类，一起传给 LLM，使其理解完整的调用上下文。
6. **自然语言+代码混合检索**：开发者的 query 通常是自然语言（"如何初始化数据库连接"），需要将自然语言 query 映射到代码语义空间，使用支持自然语言到代码跨模态检索的模型（如 CodeT5+）。
7. **典型应用**：代码问答（"这个函数的作用是什么"）、代码生成辅助（"如何在现有代码库中添加 X 功能"）、Bug 定位（"哪段代码可能导致这个错误"）。

</details>

**21. RAG 如何与知识图谱结合？**

<details>
<summary>💡 查看答案</summary>

知识图谱可以提供结构化的实体关系信息，用于增强检索的精确性（基于实体关联做检索扩展）和生成的准确性（提供结构化事实约束模型输出）。具体结合方式如下：

1. **实体识别增强检索**：在 query 中识别出实体（人名、地名、产品名等），先在知识图谱中查找该实体的相关节点和关系，将图谱查询结果（结构化事实）和向量检索结果（非结构化文本）合并，一起作为 LLM 的上下文。
2. **关系扩展召回**：当 query 涉及实体关系时（"A 公司的竞争对手有哪些"），在知识图谱中沿边扩展，找到所有相关联的实体，再以这些实体为锚点去向量库中检索相关文本片段，实现"图谱引导的 RAG"。
3. **多跳推理支持**：对于需要多步关联的问题（"X 的母公司的 CEO 毕业于哪所大学"），知识图谱可以完成第一步（X → 母公司 → CEO 是谁），向量检索完成第二步（CEO 的教育背景），两者串联完成多跳推理。
4. **事实验证与约束**：生成答案后，用知识图谱中的结构化事实对答案中的实体关系进行验证，检测明显的事实错误（如"A 的 CEO 是 B"与图谱中的记录不符），提升事实准确性。
5. **GraphRAG 架构**：微软的 GraphRAG 将文档中的实体和关系抽取为图谱，在图谱上构建社区摘要，支持全局性问题的回答——这是向量 RAG 难以实现的能力。
6. **挑战**：知识图谱的构建和维护成本高（需要实体抽取、关系抽取、实体链接等步骤），且图谱的覆盖率和更新频率是长期挑战。

</details>

**22. RAG 如何确保响应基于最新信息？**

<details>
<summary>💡 查看答案</summary>

确保 RAG 响应基于最新信息需要从知识库维护、检索策略和生成阶段三个层面协同设计：

**一、知识库层面（根本保障）**：
1. **增量实时更新**：建立事件驱动的自动化索引流水线，当源文档（网页、数据库、文件系统）发生变更时，自动触发重新处理和索引更新，目标端到端延迟 $<$1 分钟；
2. **时间戳元数据**：每个文档和 chunk 记录精确的创建时间和最后更新时间，为后续的时间过滤和时效性判断提供依据；
3. **定时全量审查**：对于没有主动推送变更能力的数据源（如公开网页），定期爬取并与现有内容进行哈希比对，发现变更后触发更新流程；
4. **过期文档清理**：为不同类型的文档设置有效期（如新闻稿 30 天、产品手册 1 年），过期文档自动标记为 archived，从检索结果中过滤。

**二、检索层面（时效性筛选）**：
1. **时间优先排序**：在检索结果精排时，引入时间衰减因子（Time Decay）对旧文档降权，使更新的文档在同等语义相关性下排名更靠前；
2. **时间范围过滤**：根据 query 的时效性要求附加时间过滤条件（"只检索近 6 个月的文档"），防止过期信息进入上下文；
3. **新旧版本去重**：同一文档的多个版本同时存在时，只保留最新版本参与检索（通过文档 ID + 版本号管理）。

**三、生成层面（时效性声明）**：
1. **信息日期标注**：在 Prompt 中要求 LLM 在引用信息时标注文档日期，使用户知道答案基于何时的信息；
2. **不确定性声明**：当检索到的最新文档仍超过一定时间（如 6 个月以上），主动在答案中提醒用户"此信息来自 X 年 X 月，建议核实是否有更新"；
3. **实时 API 旁路**：对于极高时效性要求（分钟级变化的数据），绕过向量检索，直接调用实时 API（天气、股价、汇率）获取最新数据。
