# 7.7 高级 RAG（GraphRAG、Self-RAG、CRAG、Agentic RAG） — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 7 章：RAG（检索增强生成） · 共 14 题

**1. Advanced RAG 相比 Naive RAG 做了哪些关键改进？**

<details>
<summary>💡 查看答案</summary>

![三种 RAG 范式对比 (经典 vs 高级 vs 模块化)](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter7/fig_rag_paradigms.png)

**Pre-retrieval 改进**：Query Rewriting（改写 query 提升检索质量）、Query Decomposition（分解复杂 query）、HyDE（生成假设文档）。

**Retrieval 改进**：混合检索（向量+关键词）、多路召回（多来源、多模型）、元数据过滤。

**Post-retrieval 改进**：Reranking（精排，提升 top-k 质量）、Contextual Compression（压缩减少噪声）、MMR（多样性优化）。

**整体架构改进**：Parent-Child Chunk（小 chunk 检索大 chunk 传入）、层级索引、迭代检索。

这些改进分别针对 Naive RAG 的不同失效模式，实际系统中通常组合使用 3–5 种改进，而不是全部叠加（过多改进增加复杂度和延迟）。

</details>

**2. 什么是 Modular RAG？它的核心思想是什么？**

<details>
<summary>💡 查看答案</summary>

Modular RAG（Gao et al. 2023）：将 RAG 流程拆解为独立的功能模块，每个模块可以独立替换、组合和配置，打破固定的"检索-生成"流水线。核心模块：路由（根据 query 类型选择检索策略）、检索（向量/关键词/混合）、精排、压缩、融合、生成。核心思想：
1. 模块化使得每个环节可以独立优化；
2. 不同 query 类型可以走不同的模块组合；
3. 支持动态流程：根据中间结果调整后续模块选择；
4. 便于 A/B 测试：替换单个模块对比效果，而不是整体对比。
与固定流水线 RAG 相比，更灵活、可扩展，是当前 Advanced RAG 的发展方向。

</details>

**3. 什么是 GraphRAG？它与传统向量 RAG 有什么区别？**

<details>
<summary>💡 查看答案</summary>

GraphRAG（Microsoft Research 2024）：将文档中的实体和关系提取为知识图谱，检索时结合向量相似度和图遍历，支持需要跨实体关联的复杂问答。与传统向量 RAG 的区别：
1. **数据结构**：向量 RAG 存储文本 chunk 的向量；GraphRAG 额外存储实体（节点）和关系（边）的知识图谱；
2. **检索方式**：向量 RAG 做相似度检索；GraphRAG 在相似度检索基础上做图遍历（找到相关实体后沿关系边扩展）；
3. **适合问题类型**：向量 RAG 适合直接问答；GraphRAG 适合多跳推理和全局性问题；
4. **构建成本**：GraphRAG 需要额外的实体抽取和关系抽取，成本高，适合知识密集型静态知识库。

</details>

**4. GraphRAG 的全局搜索（Global Search）和局部搜索（Local Search）有什么区别？**

<details>
<summary>💡 查看答案</summary>

**Local Search（局部搜索）**：从与 query 最相关的实体出发，沿知识图谱的关系边扩展到相关实体和文本，类似有图引导的向量检索。适合：针对特定实体或具体事实的问答（"X 公司的 CEO 是谁"）。

**Global Search（全局搜索）**：利用图谱的社区结构，对整个图谱或大子图生成层级摘要，回答需要全局视角的问题。适合：需要跨多个实体/文档的综合性问题（"这些文档的主要主题是什么"）。

两者互补，实际系统中根据 query 类型（具体 vs. 综合）自动选择或组合使用。

</details>

**5. 在什么场景下，你会选择使用图数据库或知识图谱来增强或替代传统的向量数据库检索？**

<details>
<summary>💡 查看答案</summary>

我会选择使用图数据库或知识图谱，主要在处理高度关联、结构化的数据以及需要进行复杂关系推理的场景下。

核心应用场景：
1. **需要多跳推理（Multi-hop Reasoning）的复杂问题**：例如"`Llama 2` 的作者所在的公司的 CEO 是谁？"需要沿关系链进行多次跳转，向量检索几乎无法完成，但对于知识图谱来说就是几次简单的图遍历查询。
2. **当数据本身具有强结构和关联性时**：金融领域的公司股权结构、欺诈检测中的资金流动网络、医疗领域的药物-基因-疾病关系网络。
3. **需要提供高度可解释性的答案时**：知识图谱的查询路径本身就是一种非常直观、可解释的证据链，如"为什么将这个交易标记为高风险？"

增强或替代：在大多数情况下，知识图谱和向量数据库是互补增强的关系。一个常见的先进 RAG 模式是：如果问题涉及复杂关系，先查询知识图谱找到核心实体和事实，再将这些结构化信息作为上下文，去向量数据库中检索相关的非结构化文本，最后汇总给 LLM 生成答案。

</details>

**6. 什么是 Self-RAG？它如何让模型自主决定是否需要检索？**

<details>
<summary>💡 查看答案</summary>

Self-RAG（Asai et al. 2023）：训练一个特殊的 LLM，能够在生成过程中自主输出"反思 token"（Reflection Tokens），决定是否需要检索、评估检索结果的相关性和忠实度。反思 token 类型：
1. `[Retrieve]`：决定是否触发检索；
2. `[Relevant]`：评估检索到的文档是否与 query 相关；
3. `[Supported]`：评估生成的句子是否有检索内容支持；
4. `[Utility]`：评估整体答案的有用程度。
优势：按需检索（减少不必要的检索调用），更精确的相关性判断，生成时的忠实度自我评估。缺点：需要专门训练，使用现有通用 LLM 无法直接应用。

</details>

**7. 什么是 Corrective RAG（CRAG）？它如何处理低质量的检索结果？**

<details>
<summary>💡 查看答案</summary>

![CRAG与Self-RAG自适应检索流程对比](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter7/fig_adaptive_rag.png)

CRAG（Yan et al. 2024）：在标准 RAG 之上增加一个检索质量评估和纠正机制。工作流程：
1. 标准检索后，用评估器（轻量 LLM）对检索结果的相关性打分；
2. 如果相关性分数高 → 正常使用检索结果生成；
3. 如果相关性分数中等 → 对检索结果做知识提炼（只保留相关部分）；
4. 如果相关性分数低 → 判定检索失败，触发网络搜索（Bing/Google）作为补充来源。
优势：自动识别和纠正检索质量差的情况，不依赖原始知识库给出兜底答案；适合知识库覆盖不完整或用户 query 多样化的场景。

</details>

**8. 什么是 Agentic RAG？它相比标准 RAG 有哪些能力扩展？**

<details>
<summary>💡 查看答案</summary>

Agentic RAG：将 Agent 的规划、工具调用和自主决策能力与 RAG 的知识检索能力结合，使系统能够主动、灵活地完成复杂的信息获取和问答任务。相比标准 RAG 的能力扩展：
1. **按需检索**：不是每次都检索，Agent 判断是否需要；
2. **多轮迭代检索**：一次任务可以多次检索，逐步补充信息；
3. **跨知识库协作**：同时使用多个工具（知识库A + 知识库B + 网络搜索）；
4. **推理与检索交织**：先推理需要什么信息，再检索，再推理，形成思维链；
5. **任务规划**：将复杂问题分解为多个子问题，分别检索再综合；
6. **结果验证**：检索到信息后自主验证其准确性（多源交叉验证）；
7. 适合：复杂多步骤信息综合任务，标准 RAG 单次检索无法完成的场景。

</details>

**9. 如何将 RAG 与 Agent 结合，构建能主动决策检索策略的系统？**

<details>
<summary>💡 查看答案</summary>

Agentic RAG 的核心：让 Agent 自主决定何时检索、检索什么、检索多少次。实现方式：
1. **检索工具化**：将 RAG 检索封装为 Agent 的工具之一（`search_knowledge_base(query)`），Agent 自主决定是否调用；
2. **多检索工具**：提供多个检索工具（向量检索/关键词检索/图检索/网络搜索），Agent 根据场景选择；
3. **迭代检索**：Agent 在得到初步检索结果后，分析是否足够，不足则再次检索（不同 query 或不同知识库）；
4. **检索策略推理**：在 Thought 中让 Agent 明确说明"我需要检索 X 来获取 Y 信息"；
5. **检索结果评估**：Agent 对检索结果做相关性判断，低质量结果触发重新检索或替代方案；
6. **上下文管理**：多轮检索结果合理整合进上下文，避免重复和冗余。

</details>

**10. 如何设计一个支持"多知识库动态路由"的 RAG 系统？**

<details>
<summary>💡 查看答案</summary>

1. **Query 分类路由**：用分类器（LLM 或轻量分类模型）判断 query 属于哪个知识库的范畴，路由到对应知识库检索；
2. **元数据过滤路由**：在统一向量库中，通过元数据过滤实现逻辑路由；
3. **并行多库检索**：不确定属于哪个知识库时，同时向多个库发起检索，合并结果后精排；
4. **路由置信度**：路由器输出置信度，低于阈值时触发多库并行检索；
5. **动态扩展**：新增知识库时，只需注册新库的元数据和描述，路由层零改动；
6. **路由性能监控**：追踪每个路由决策的最终检索质量，识别路由错误模式并优化分类器。

</details>

**11. 传统的 RAG 流程是"先检索后生成"，你是否了解一些更复杂的 RAG 范式？**

<details>
<summary>💡 查看答案</summary>

是的，传统的"先检索后生成"范式虽然经典，但比较刻板。为了应对更复杂的问题，研究界已经提出了多种更动态、更智能的 RAG 范式：

**1. 迭代式检索（Iterative Retrieval）—— 例如 Self-RAG、Corrective-RAG**：将 RAG 从一个单向的流水线，变成一个循环、自我修正的过程。首次检索与生成后，LLM 会对初步生成的答案和检索到的上下文进行"反思"，评估当前的信息是否足够；如果认为信息不足，LLM 会主动生成一个新的、更具针对性的查询，进行新一轮的检索；最后整合新旧检索到的所有信息，生成更完善的最终答案。

**2. 自适应检索（Adaptive Retrieval）—— 例如 FLARE、Self-Ask**：不在生成前一次性检索所有信息，而是在生成过程中"按需"检索，实现"即时"（just-in-time）的信息获取。LLM 在生成的同时预测不确定性，当预测到即将生成一个不确定的事实性信息时，暂停生成并插入一个特殊的占位符，主动提出一个需要查询的问题，获取信息后继续生成。

**3. 多源数据 RAG（Multi-Source RAG）**：让 Agent 能够智能地从多种不同类型的数据源中进行检索和整合。Agent 首先对问题进行分解，可能会从向量数据库检索非结构化文档、从知识图谱查询结构化实体关系、调用 SQL 数据库获取精确统计数据，甚至调用搜索引擎 API 获取实时信息，最后将所有信息综合生成全面的答案。

</details>

**12. 什么是混合 RAG 系统？**

<details>
<summary>💡 查看答案</summary>

混合 RAG 系统结合了传统检索方法（例如 BM25/TF-IDF 等稀疏检索）与神经向量检索模型（稠密检索），以平衡速度和准确性。各组件的角色与融合机制：

1. **稀疏检索（BM25/TF-IDF）**：基于关键词的词频统计，对精确词汇匹配（专有名词、产品编号、人名）非常有效，速度快，无需 GPU，无需训练，是工程上成熟的可靠基线。
2. **稠密检索（向量搜索）**：基于 Embedding 模型的语义向量相似度，能理解同义词、近义表达和语义关联，弥补 BM25 对词汇变体的不敏感。
3. **融合方式**：
    - **RRF（Reciprocal Rank Fusion）**：将两路检索结果的排名倒数加权求和重新排序，无需调参，鲁棒性强，是最常用的融合方法；
    - **加权线性融合**：`score = α × dense_score + (1-α) × sparse_score`，需要调优 α；
    - **级联融合**：先用一路粗过滤（如 BM25 召回 1000），再用另一路精排（向量重排）。
4. **实际收益**：混合检索相比单一向量检索，在综合基准上平均提升 5--15% 的检索质量，且在包含专业术语的企业文档场景下收益更显著。
5. **工程实现**：Elasticsearch（BM25 + 向量搜索）、Weaviate、Qdrant 等均原生支持混合检索，无需额外部署两套独立系统。

</details>

**13. RAG 如何适应动态数据源？**

<details>
<summary>💡 查看答案</summary>

动态数据源是指内容频繁变化的数据，包括新闻、实时数据库、频繁修订的文档等。RAG 通过以下机制适应动态数据源：

1. **事件驱动的增量索引**：数据源（数据库、CMS、文件系统）在内容变更时发布事件，RAG 系统订阅这些事件，自动对变更内容重新 Embedding 并更新向量库，而不是等待定时批量同步，实现近实时的知识更新。
2. **定时批量同步**：对于无法提供变更事件的数据源，设置定时爬取任务（如每小时），全量扫描数据源并与现有索引做差异对比，只对新增或修改的内容重新索引，降低计算成本。
3. **实时 API 查询旁路**：对于变化极频繁的数据（股价、库存、天气），向量检索的时效性无法满足需求，可以绕过向量检索，直接在生成时调用实时 API 获取最新数据，将 API 结果作为上下文传给 LLM。
4. **文档版本管理与过期处理**：每个索引文档附带更新时间戳和可选的过期时间，检索时自动过滤超过有效期的文档，防止过时内容影响答案质量。
5. **定期重新训练检索器**：对于基于学习的检索模型（如微调的 Embedding 模型），定期在最新数据上重新微调，使其适应新领域术语和表达方式的变化，保持检索质量不随时间退化。
6. **数据源健康监控**：监控各数据源的更新频率和质量，对长期未更新的数据源发出警告，避免知识库悄然"过时"而用户无感知。

</details>

**14. 知道或者使用过哪些开源 RAG 框架比如 RAGFlow？如何选择合适场景？**

<details>
<summary>💡 查看答案</summary>

除了最广为人知的 LangChain 和 LlamaIndex 之外，还涌现出了一批更专注于提供端到端 RAG 解决方案的平台，其中 RAGFlow 就是一个很有代表性的例子，其他类似的框架还包括 Haystack、DSPy 等。

**对 RAGFlow 的理解**：RAGFlow 与 LangChain/LlamaIndex 这类"代码库"形态的框架不同，它更像一个"开箱即用"的、对业务人员更友好的 RAG 应用平台。它的特点是：自动化与可视化（提供基于深度学习的"智能"文本分块方法）；端到端整合（从数据接入、处理、索引到最终的应用接口）；为非专家设计（目标用户不仅是开发者，也包括业务分析师或产品经理）。

**如何选择合适场景**：

选择 LangChain / LlamaIndex 的场景：高度定制化需求（需要对 RAG 流水线的每一个环节进行深度控制和定制）；作为底层库集成到更大的软件系统中；开发者为核心的团队。一句话总结：选择它们是为了"灵活性"和"控制力"。

选择 RAGFlow / Haystack 这类平台的场景：快速原型验证（几天内快速搭建 RAG 原型）；追求最佳实践（直接利用领域内已经验证过的最佳实践）；技术团队规模有限或业务人员主导。一句话总结：选择它们是为了"效率"和"易用性"。

我的选择策略：在项目初期，使用 RAGFlow 这样的平台搭建一个基线（Baseline）。在验证了业务价值后，如果发现平台的标准化流程无法满足更深度的性能优化或业务逻辑定制需求，再考虑使用 LangChain 或 LlamaIndex 进行更精细化的重构和实现。
