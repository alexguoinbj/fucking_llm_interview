# 7.6 查询优化（改写、HyDE、分解） — 题目与答案

**1. 什么是 Query Rewriting（查询改写）？有哪些常见的改写策略？**

<details>
<summary>💡 查看答案</summary>

![三种典型查询优化 (Query Optimization) 策略](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter7/fig_query_optimization.png)

Query Rewriting：在检索前对用户原始 query 进行改写或扩展，提升检索效果。常见策略：
1. **意图明确化**：将模糊 query 改写为更明确的描述（"它是什么" → "Python 中的列表推导式是什么"）；
2. **同义词扩展**：生成同义表达，增加检索覆盖（"费用" → "费用、价格、收费标准"）；
3. **上下文补充**：多轮对话中，将历史上下文融入当前 query（"它有什么优势" → "Python 相比 Java 有什么优势"）；
4. **子问题分解**（Query Decomposition）：将复杂问题分解为多个简单子问题；
5. **Step-Back Prompting**：将具体问题抽象为更高层次的通用问题。

</details>

**2. Query Rewrite（查询改写）真的有价值吗？**

<details>
<summary>💡 查看答案</summary>

有价值，尤其对于口语化、指代不清或信息不全的用户提问，改写后的查询能更准确地匹配知识库中的表达方式，提升检索召回质量。具体来说：

**Query Rewrite 的核心价值**：
1. **弥合表达鸿沟**：用户输入的 query 往往是口语化、省略式的（如"它怎么用"），而知识库中的文档是正式的陈述语言。改写将用户表达转换为与文档风格更接近的形式，显著提升语义匹配度。
2. **解决多轮对话的指代问题**：在多轮对话中，"它"、"这个"等代词无法单独检索。改写将代词还原为具体实体（"GPT-4 的价格是多少"），使检索系统能够独立理解当前 query。
3. **扩展查询覆盖面**：通过生成同义改写或多个 query 变体（Multi-Query），可以从不同角度检索，减少因单一措辞导致的漏检。
4. **明确模糊意图**：用户提问有时意图模糊，改写步骤可以让 LLM 先对 query 做意图分类和明确化，再针对明确的意图检索。

**适用场景与局限**：
- 对于表达清晰、措辞专业的 query，改写收益有限，且引入额外的 LLM 调用会增加延迟和成本；
- 改写质量依赖 LLM 能力，低质量改写可能将原本正确的检索方向带偏；
- 实践中建议在 query 质量评估后有条件地触发改写，而非对所有 query 无差别应用。

总体评价：在面向普通用户（非专家用户）的 RAG 系统中，Query Rewrite 通常能带来 5%--15% 的检索质量提升，ROI 较高。

</details>

**3. 什么是 HyDE（Hypothetical Document Embeddings）？它的核心思路是什么？**

<details>
<summary>💡 查看答案</summary>

HyDE（Gao et al. 2022）：先让 LLM 根据用户 query 生成一段"假设的答案文档"，再对这段假设文档做 embedding 去检索，而不是直接对 query 做 embedding。

核心思路：解决 query-document embedding 空间不对齐问题——用户 query 通常是问句风格，而知识库文档是陈述性风格，两者在向量空间中可能距离较远。假设文档的语言风格更接近真实文档，embedding 更接近目标文档的向量，检索召回率更高。

缺点：
1. 每次检索多一次 LLM 调用，增加延迟和成本；
2. 如果 LLM 生成的假设文档质量差，检索效果反而更差。
适合知识密集型问答场景。

</details>

**4. 什么是 Query Decomposition（查询分解）？在什么场景下使用？**

<details>
<summary>💡 查看答案</summary>

Query Decomposition：将复杂的多部分 query 拆解为多个简单的子 query，分别检索后合并结果。使用场景：
1. **多跳问题**：回答需要多步关联（"A 公司 CEO 的母校在哪个城市" → 先查 CEO 是谁，再查其学历背景）；
2. **比较性问题**：需要分别检索多个对象（"X 和 Y 有什么区别" → 分别检索 X 和 Y 的信息）；
3. **聚合性问题**：答案需要汇总多个维度（"2024 年的主要 AI 进展" → 分别检索各领域进展）；
4. **时序问题**：涉及多个时间点的信息。
实现：让 LLM 先将 query 分解为 N 个子 query，并行或串行检索，最后综合生成答案。

</details>

**5. 什么是 Step-Back Prompting？它如何提升检索效果？**

<details>
<summary>💡 查看答案</summary>

Step-Back Prompting：先让 LLM 将具体问题"抽象化"为更通用的高层次问题，再用这个高层次问题做检索，同时也检索原始问题，合并两路结果。

例子："如何配置 Kubernetes 中的 CPU 限制" → 抽象为"Kubernetes 资源管理的原理和最佳实践"。

提升效果的原因：
1. 高层次问题能检索到包含原理和背景知识的文档，这些文档对回答具体问题有帮助；
2. 原始问题的检索保证了具体细节；
3. 两路结合使 LLM 既有背景知识又有具体信息，生成质量更高。
适合专业领域的深度问答场景。

</details>

**6. 什么是 RAG Fusion？它的核心机制是什么？**

<details>
<summary>💡 查看答案</summary>

RAG Fusion：将单一 query 改写为多个相关 query（通常 4–5 个），分别检索，再用 RRF（Reciprocal Rank Fusion）合并多路结果，最后用全部结果生成答案。核心机制：
1. **Multi-Query Generation**：用 LLM 对原始 query 生成变体（同义改写、不同角度、不同详细程度）；
2. **并行检索**：对每个 query 变体独立检索；
3. **RRF 融合**：对所有检索结果按 RRF 算法合并排序：`score = Σ 1/(k + rank_i)`；
4. **综合生成**：用合并后的检索结果（多样性更好）生成答案。
优点：覆盖了原始 query 的多种语义变体，提升召回率；减少因单一 query 措辞而导致的检索失败。

</details>

**7. 什么是 FLARE（Forward-Looking Active Retrieval）？它与标准 RAG 有什么不同？**

<details>
<summary>💡 查看答案</summary>

FLARE（Jiang et al. 2023）：一种主动检索方法，让 LLM 在生成答案的过程中，主动判断何时需要检索、检索什么。与标准 RAG 的不同：
1. **检索时机不同**：标准 RAG 在生成前一次性检索；FLARE 在生成过程中动态决定是否需要额外检索；
2. **检索内容动态**：FLARE 根据已生成的内容预测接下来需要什么信息，用预测生成的句子作为检索 query；
3. **多轮检索**：FLARE 可能触发多次检索，直到 LLM 对当前生成有足够置信度；
4. **适合场景**：需要多跳推理、答案需要整合多个知识点的复杂问答；标准 RAG 适合简单的单次检索问答。

</details>

**8. 什么是迭代检索（Iterative Retrieval）？在哪些场景下有明显收益？**

<details>
<summary>💡 查看答案</summary>

迭代检索：多轮检索，每轮检索的 query 基于上一轮的检索结果和已生成的部分答案动态调整，逐步收敛到最相关的文档。工作流程：
1. 初始 query 做第一轮检索，获取初步信息；
2. 基于第一轮结果，LLM 识别信息缺口，生成新的检索 query；
3. 第二轮检索补充缺失信息；
4. 重复直到信息足够或达到轮数上限。

有明显收益的场景：多跳推理问题（需要串联多个知识点）；开放性问题（无法事先确定需要哪些信息）；探索性查询（答案范围不明确，需要逐步缩小）；知识库覆盖不均匀（部分知识需要特定措辞才能找到）。

</details>

**9. RAG 如何处理复杂的多跳查询？**

<details>
<summary>💡 查看答案</summary>

RAG 执行迭代检索来处理多跳查询：先检索初始相关数据，利用这些数据进一步细化查询以进行进一步检索，这种迭代过程使其能够从多个来源综合和合并信息。具体的多跳处理策略：

1. **查询分解（Decomposition）**：使用 LLM 将复杂的多跳问题拆解为若干简单的子问题，分别独立检索，最后将各子问题的检索结果综合传给 LLM 进行最终推理。例如："谁是特斯拉 CEO 的母校所在城市的市长？"可分解为：①特斯拉 CEO 是谁 → ②他的母校是哪里 → ③该城市现任市长是谁。
2. **迭代检索（Iterative Retrieval）**：第一轮检索获取初步信息后，LLM 分析这些信息并识别"还缺什么"，动态生成第二轮的检索 query，补充缺失的知识链，循环直到信息充足或达到最大轮次（通常 2--4 轮）。
3. **ReAct 推理框架**：将 Thought（推理）-Action（检索）-Observation（观察结果）循环融入 RAG，LLM 在 Thought 中明确说明需要什么信息，在 Action 中执行检索，在 Observation 中消化结果并决策下一步，形成透明的多跳推理链。
4. **知识图谱辅助（GraphRAG）**：利用知识图谱的实体关系网络，通过图遍历直接连接多跳实体关系，是解决多跳问题最自然的方法——向量检索找不到的"A→B→C"关系链，图遍历可以直接走通。
5. **挑战与注意事项**：多跳错误会叠加（第一跳错误导致整个推理链方向偏差）；迭代检索增加延迟（每次检索约增加 200--500ms）；需要合理设置最大迭代轮次，防止无限循环。

</details>

**10. RAG 如何支持多跳（Multi-Hop）检索？**

<details>
<summary>💡 查看答案</summary>

对于需要综合多个信息源才能回答的问题，可以采用迭代检索策略：先检索初步信息，基于初步结果生成新的检索查询，逐步逼近完整答案。具体实现方案：

1. **查询分解（Query Decomposition）**：将复杂的多跳问题分解为若干简单的子问题，分别检索，最后将各子问题的检索结果合并传给 LLM 进行综合推理。例如："A 公司 CEO 的母校在哪个城市？" → 子问题1："A 公司的 CEO 是谁？" → 子问题2："[CEO 姓名] 在哪所大学就读？"
2. **迭代检索（Iterative Retrieval）**：第一轮检索获取初步信息，LLM 基于初步信息识别信息缺口并生成新的 query，第二轮检索补充缺失信息，如此循环直到 LLM 判断信息足够或达到最大轮次上限（通常 2--4 轮）。
3. **ReAct 范式**：将多跳检索融入 Agent 的 Thought-Action-Observation 循环，LLM 在 Thought 中规划下一步检索内容，在 Action 中执行检索，在 Observation 中分析结果并决定是否继续检索。
4. **图检索（GraphRAG）**：利用知识图谱的图结构，通过实体关系的多跳遍历（如 A → B → C）直接找到跨实体的关联信息，是多跳检索最自然的实现方式。
5. **挑战**：多跳检索的错误会叠加（第一跳错误导致第二跳方向偏差），且延迟随跳数线性增加；复杂问题需要合理控制最大跳数，避免过度检索。

</details>

**11. RAG 如何处理实体消歧？**

<details>
<summary>💡 查看答案</summary>

实体消歧（Entity Disambiguation）是指当 query 中的实体名称有多种含义时（如"苹果"既可指苹果公司也可指水果），准确识别用户意图所指实体的过程。RAG 中的处理方法：

1. **上下文感知检索**：向量检索本身具备一定的上下文消歧能力——当 query 包含足够的上下文信息时（如"苹果公司的市值"），Embedding 模型能够区分不同含义并检索到对应的正确文档。但对于上下文稀疏的短 query，这种能力有限。
2. **命名实体识别（NER）+ 实体链接**：在 query 预处理阶段，使用 NER 模型识别 query 中的实体，再通过实体链接将实体名称映射到知识图谱中的唯一实体 ID（如"苹果" → Apple Inc. [Q312]），使用 ID 而非名称进行后续检索，彻底消除歧义。
3. **知识图谱辅助消歧**：在知识图谱中，同名实体会有不同的节点 ID 和关联属性，通过查询图谱并结合上下文选择最合适的实体节点，再以该节点为锚点进行向量检索扩展。
4. **多解释并行检索**：对于高度模糊的实体，并行检索多种可能的解释，将所有结果传给 LLM，由 LLM 根据完整 query 和检索内容判断最可能的用户意图，并在答案中明确说明所选择的解释。
5. **多轮对话中的消歧**：在多轮对话中，利用历史对话上下文判断当前 query 中模糊实体的指向（如前一轮提到了 iPhone，则当前轮"苹果"大概率指 Apple Inc.），将上下文信息注入检索以提升消歧准确性。
6. **主动澄清**：当系统对实体含义无法确定且不同解释对答案影响显著时，主动向用户提问澄清（"您提到的'苹果'是指苹果公司还是苹果产品？"），避免基于错误假设检索并给出误导性答案。
