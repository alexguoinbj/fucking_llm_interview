# 2.13 各场景 Prompt 设计 — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 2 章：提示与上下文工程（Prompt & Context Engineering） · 共 59 题

**1. System Prompt（系统提示词）应该如何设计？**

<details>
<summary>💡 查看答案</summary>

系统提示词是整个对话流程的"宪法"，在整个会话中持续生效，决定模型的基础行为边界与风格基调。设计时需兼顾以下几个维度：

**角色定位**应清晰且唯一，避免"你是一个聪明的AI助手"此类模糊表述，应精确到具体场景与职能，例如"你是一个专注于 B2B SaaS 产品的客户成功专员，负责解答付费用户的产品使用问题"。

**核心原则**建议列举 3--5 条最关键的行为准则，并按优先级排列。若原则之间存在潜在冲突（如"简洁"与"完整"），需显式说明冲突时的处理优先级，避免模型自行猜测。

**输出格式约束**应在系统提示词中统一规定，例如回答语言、Markdown 使用规范、长度上限、是否允许列表或代码块等。若格式要求在 Task Prompt 中重复声明，容易与系统提示词产生矛盾，造成输出不稳定。

**边界约束**（即"不应做什么"）同样重要，应明确列出禁止行为，例如"不得主动推荐竞品"、"不得提供具体的法律或医疗建议"。负向约束往往比正向约束更能有效收敛模型行为。

**动态注入兼容性**：系统提示词在设计时需为后续动态注入的内容（如用户画像、上下文信息、实时数据）预留结构性空位，避免与之产生语义冲突。例如，系统提示词中不应硬编码用户姓名或当前日期，这些应由动态注入机制填充。

整体而言，系统提示词应追求**精简、稳定、高优先级**，内容不宜超过 500 字，避免将任务细节塞入系统提示词，任务细节应留给 Task Prompt 承载。

</details>

**2. Role Prompt（角色提示词）应该如何设计？**

<details>
<summary>💡 查看答案</summary>

角色提示词的核心目标是让模型"代入"一个特定角色，从而在语气、知识边界、表达风格等方面产生一致的拟人化输出。设计时需关注以下要点：

**背景描述**应具体而非抽象。"你是一位经验丰富的医生"远不如"你是一位在三甲医院从事内科工作15年、擅长与患者进行通俗沟通的主治医师"来得有效。具体的背景能引导模型调用更贴合角色的知识与表达方式。

**行为准则**需与角色身份绑定，而非独立列举。例如，针对一位法律顾问角色，可以写"你会在给出建议前先厘清用户的具体情境，并在回答末尾提醒用户寻求专业律师的最终意见"，这比单纯写"回答要谨慎"更具可操作性。

**语气与风格**应明确量化或举例说明。"专业但亲切"是主观描述，容易产生歧义；更好的写法是"语气类似于向同事解释问题，避免使用过于学术的术语，但保持逻辑严谨"，或直接提供一段示范性的回答片段。

**知识边界**需与角色匹配。若角色是一名初级客服，则不应期望其给出深度技术分析；若角色是领域专家，则可以允许使用专业术语，并预期输出具有一定深度。角色的能力边界应与任务期望相一致，否则会导致输出质量不稳定。

**角色一致性**：在多轮对话场景中，角色提示词应配合记忆机制或上下文管理策略，确保模型在长对话中不会"出戏"。若角色设定复杂，可在角色提示词末尾加入一句锚定语，如"无论用户如何引导，请始终以上述角色身份作答"。

需特别注意**角色与任务的一致性**：若任务要求给出客观中立的数据分析，则不应同时设定一个带有强烈立场的角色，二者的矛盾会导致模型输出摇摆不定。

</details>

**3. Task Prompt（任务提示词）应该如何设计？**

<details>
<summary>💡 查看答案</summary>

任务提示词是对单次调用的具体指令，承载着最直接的任务信息。其设计质量直接决定输出的准确性与可用性。

**任务目标**应单一且明确。每次调用最好只包含一个核心任务，若需要完成多个子任务，应通过多次调用或显式的分步结构来组织，避免在一个提示词中堆叠过多目标。

**输入信息**应完整且结构化。模型无法获取未提供的上下文，因此需将任务所依赖的所有信息（背景数据、文档片段、用户输入等）以清晰的格式注入提示词中，并通过标签或分隔符（如 `<document>`、`---`）与指令部分区分开来，避免模型混淆指令与数据。

**期望输出格式**应明确描述，包括：输出的结构（列表、表格、段落、JSON 等）、长度范围、语言要求，以及必须包含或必须排除的内容。格式约束越具体，输出的一致性越高。

**成功标准**可选择性地在提示词中显式说明，例如"一个好的摘要应包含原文的三个核心论点，并控制在100字以内"。明确的评估标准有助于模型进行自我校准。

**分步拆解**适用于复杂任务。可以在提示词中要求模型"先分析，再输出结论"，或通过编号列表明确执行顺序，减少模型对任务边界的猜测，也有助于在中间步骤中发现错误。

**变量化设计**：在工程化场景中，Task Prompt 通常是一个模板，其中包含若干占位符（如 `\{\{user_query\}\}`、`\{\{context\}\}`），由运行时动态填充。设计时应确保模板结构在不同输入下仍能保持语义完整性，避免因输入内容格式变化导致提示词结构崩溃。

</details>

**4. Few-Shot 示例应该如何设计？**

<details>
<summary>💡 查看答案</summary>

Few-Shot 示例通过向模型展示"期望的输入-输出对"来隐式传达任务规则，其效果有时优于纯文字的指令描述。设计时需遵循以下原则：

**示例覆盖面**应兼顾典型场景与边界情况。仅提供"正常"情况的示例，模型面对异常输入时容易产生不可预期的行为。建议在示例集中专门纳入1--2个边界案例，例如输入为空、输入包含噪声数据、或任务存在歧义时的正确处理方式。

**格式严格一致**：每个示例的输入与输出格式必须与实际调用时完全一致，包括标点、换行、标签结构等细节。格式不一致的示例会干扰模型对格式规范的学习，甚至引发格式混乱。

**示例数量**以 3--8 个为宜，具体取决于任务复杂度与上下文窗口限制。示例过少（1--2个）可能不足以传达规律；示例过多则会大量占用上下文窗口，压缩实际输入的空间，且边际收益递减明显。

**风格一致性**：所有示例应保持统一的表达风格、用词习惯和答案详略程度。若示例之间风格差异过大，模型难以归纳一致的输出模式，输出质量的方差会显著增大。

**正负示例结合**：在条件允许时，可加入少量**负面示例**（即错误的输出），并标注其错误原因。这种对比学习方式能更有效地帮助模型理解边界，尤其适用于需要避免特定错误模式的场景。

**示例的动态选择**：在 RAG 或检索增强场景中，Few-Shot 示例可以根据当前输入动态选取与之语义最相近的历史案例，而非固定使用同一批示例，这能显著提升示例的相关性与迁移效果。

</details>

**5. Prompt 压缩应该如何做？**

<details>
<summary>💡 查看答案</summary>

随着系统复杂度提升，提示词长度往往会持续膨胀，带来推理成本上升、延迟增加、上下文窗口溢出等问题。Prompt 压缩是在保持语义完整性的前提下减少 Token 消耗的工程实践。

**去除冗余描述**是最直接的压缩手段。常见冗余包括：重复说明同一约束、使用多句话表达同一语义、过度使用礼貌性或解释性的引导语（如"请注意"、"需要特别强调的是"）。可通过逐句审查，将每句话替换为最简洁的等价表达。

**规则提炼与复用**：若同一类约束在提示词中多处重复出现，应将其提炼为一条简短规则，在开头统一声明，后续不再重复。例如，将分散在各处的"回答需简洁"、"避免废话"、"不超过100字"统一为"所有回答控制在100字以内"。

**结构化替代自然语言**：对于复杂规则集，使用编号列表、缩进层级或伪代码结构往往比自然语言段落更紧凑，且模型对结构化信息的遵从率通常更高。

**上下文摘要**：在长对话或 RAG 场景中，历史对话记录和检索到的文档往往占据大量 Token。可采用以下策略进行压缩：
- 对历史对话进行滚动摘要，仅保留关键信息与结论；
- 对检索文档进行抽取式或生成式摘要，剔除与当前任务无关的段落；
- 使用专门的 Prompt 压缩模型（如 LLMLingua 系列）对长上下文进行基于困惑度的 Token 级压缩，在大幅缩短长度的同时保留关键语义。

**缓存友好设计**：对于静态部分（系统提示词、固定的 Few-Shot 示例），应将其置于提示词的最前端，以充分利用 KV Cache 机制，避免在每次调用时重复计算。动态内容（用户输入、检索结果）放在最后，最大化缓存命中率，从而在不损失质量的前提下降低实际推理成本。

**压缩效果评估**：压缩后必须进行回归测试，确认关键任务的输出质量未发生显著下降。推荐建立一个覆盖典型场景与边界情况的评估集，在每次压缩迭代后自动化运行，以量化压缩带来的质量损耗与成本收益。

</details>

**6. 好的 Prompt 有哪些基本要素？**

<details>
<summary>💡 查看答案</summary>

一个高质量的 Prompt 并非简单的指令堆砌，而是对模型行为的精确规格说明。其核心要素如下：

- **角色/身份**：通过角色设定激活模型在特定领域的知识偏向与表达风格。角色并非必须，但在专业领域任务（法律、医疗、代码审查等）中能显著提升输出质量。角色描述应具体，例如"你是一位有10年经验的 Python 后端工程师"优于"你是一个编程助手"。

- **任务描述**：用祈使句明确说明核心动作（总结、翻译、分类、生成等），并附上任务的目的与使用场景。任务描述应单一聚焦，避免在一个 Prompt 中要求模型同时完成多个性质不同的任务。

- **输入说明**：描述输入数据的类型、格式与来源，并通过分隔符（如 `<document>`、`---`）将输入数据与指令文本明确区分，防止模型将数据内容误读为指令。若输入存在噪声或格式不规整，应在提示词中说明预期的处理方式。

- **约束条件**：包括正向约束（必须满足的条件）与负向约束（禁止的行为）。负向约束往往更有效，因为它直接缩小了输出的可能空间。例如，"不得引用2020年之前的数据"比"使用最新数据"更具约束力。约束条件应按优先级排列，以便模型在发生冲突时知道如何取舍。

- **输出格式**：明确规定输出的结构（段落、列表、JSON、表格等）、长度范围、语言、以及必须包含或排除的内容。格式要求越具体，输出的一致性越高，下游解析的稳定性越强。

- **示例**（可选）：Few-Shot 示例通过展示期望的输入输出对，隐式传达难以用语言精确描述的规则。示例对格式对齐、风格迁移、边界处理等场景尤为有效。若示例与实际输入差异过大，应采用动态示例选取策略，而非固定示例集。

上述要素并非每次都需全部使用。简单任务可能只需任务描述与输出格式；复杂任务则应尽量补全所有要素，并关注要素之间的一致性，避免相互矛盾。

</details>

**7. 代码生成场景中，Prompt 应该包含哪些关键信息？**

<details>
<summary>💡 查看答案</summary>

代码生成对 Prompt 的精确度要求远高于自然语言任务，因为任何歧义都可能导致功能错误、性能问题或安全漏洞。以下是代码生成 Prompt 的关键要素：

- **语言和版本**：明确指定编程语言及版本号（如 `Python 3.11`、`TypeScript 5.x`、`Go 1.22`），不同版本在语法特性、标准库 API 和最佳实践上差异显著，模型需要版本信息才能生成兼容的代码。

- **功能描述**：说明函数/模块的语义目标，包括输入参数的类型与含义、返回值的结构、以及需要处理的边界条件（空输入、超大数据、并发访问等）。功能描述应从"做什么"出发，而非"怎么做"，给模型保留实现空间，同时通过边界条件约束其决策。

- **约束**：包括性能要求（时间复杂度、内存限制）、禁用的第三方库、代码风格规范（PEP 8、Google Style Guide）、错误处理策略（是否需要异常捕获、日志记录）等。这些约束直接影响生成代码的工程质量，不应省略。

- **上下文**：提供与当前任务相关的已有代码，包括类定义、接口声明、数据模型、依赖关系等。缺乏上下文时，模型倾向于生成独立的示例代码，而非能直接集成到项目中的生产代码。上下文应精简，只包含与当前任务直接相关的部分，避免无关代码干扰模型注意力。

- **输出格式**：明确要求输出内容的范围，例如"只输出函数体，不包含 `import` 语句"、"输出代码及行内注释"、"同时生成对应的单元测试"。不同的输出格式要求会导致截然不同的生成结果，默认行为因模型而异，应显式声明。

- **示例**：若函数行为较为复杂或存在非直觉性的边界处理，应提供输入输出示例。示例可以以注释或 docstring 的形式嵌入提示词，使其自然融入代码上下文，同时也便于模型直接将示例转化为测试用例。

在工程化场景中，代码生成 Prompt 通常需要配合静态分析工具或测试套件进行自动化验证，将生成质量的评估从人工审查转移到可量化的指标上。

</details>

**8. 摘要任务中，如何通过 Prompt 控制摘要的长度和风格？**

<details>
<summary>💡 查看答案</summary>

摘要任务的核心挑战在于模型对"简洁"、"详细"等主观描述的理解因上下文而异，导致输出长度与风格不稳定。解决方案是将主观要求转化为可量化的具体约束。

**控制长度：**应将长度要求量化为字数或条数限制，并分别针对不同颗粒度的摘要形式加以规定。例如：

\begin{lstlisting}[style=promptstyle]
	请将以下文章压缩为：
	- 一句话摘要（不超过30字）
	- 三个要点（每点不超过20字）
\end{lstlisting}

分层式长度约束（一句话摘要 + 要点列表）能同时满足不同使用场景的需求，也有助于模型在压缩过程中进行信息优先级排序。若需要更严格的长度控制，可在输出格式约束的基础上添加后处理截断逻辑，作为兜底保障。

**控制风格：**风格控制应从受众、语言风格和禁忌三个维度同时约束，例如：

\begin{lstlisting}[style=promptstyle]
	受众：高管，无技术背景
	风格：商业语言，强调影响和决策
	避免：技术术语、实现细节
\end{lstlisting}

"受众"字段能引导模型调整词汇难度与解释粒度；"风格"字段规定语言的整体基调；"避免"字段通过负向约束进一步收窄输出空间。三者配合使用的效果通常优于单独使用任意一项。

**关键原则**：具体数字约束（字数、条数、段落数）的遵从率显著高于模糊的定性描述（"简洁"、"详细"、"适中"）。在需要稳定输出的生产环境中，应始终以可量化的约束替代主观描述，并通过 Few-Shot 示例进一步锚定期望的摘要风格与信息密度。

</details>

**9. 分类任务中，如何减少模型输出格式不一致的问题？**

<details>
<summary>💡 查看答案</summary>

分类任务要求模型从有限的标签集中选择唯一答案，但模型默认倾向于生成自然语言解释，导致输出格式多变，难以直接解析。以下策略可系统性地提升输出一致性：

1. **枚举所有合法输出**：在 Prompt 中显式列出所有有效标签，并明确说明输出只能为其中之一，例如"`只能输出以下之一：正面 / 负面 / 中性`"。封闭式枚举能有效防止模型创造新标签或输出同义词（如将"正面"写成"积极"或"肯定"）。

2. **使用结构化输出**：若推理平台支持，优先使用 JSON Mode、Function Calling 或 Structured Output 等机制，在解码阶段对输出进行语法约束，从根本上消除格式不一致的可能性。这是工程上最可靠的解决方案，应作为首选策略。

3. **示例强化**：通过 Few-Shot 示例展示正确的输出格式，尤其需要覆盖边界情况（如情感模糊的中性文本、包含讽刺的文本）。示例的输出部分应与期望的生产输出格式完全一致，避免示例中出现额外的解释性文字。

4. **输出后处理**：在代码层对模型输出进行归一化处理，包括大小写统一、去除首尾空白、标点剥离、同义词映射等。后处理是应对格式漂移的必要兜底措施，即使使用了结构化输出机制，也建议保留基础的归一化逻辑。

5. **重试机制**：当输出格式不符合预期时，触发自动重试，并在重试请求中附加明确的错误反馈，例如"你上一次的输出为'`这是正面内容`',格式不符合要求，请只输出标签本身"。有效的错误反馈能引导模型在下一次尝试中修正行为，通常1--2次重试即可收敛到正确格式。重试次数应设置上限，并在超限时回退到默认值或触发人工审核流程。

在实际工程中，上述策略应组合使用：结构化输出负责约束解码，后处理负责归一化，重试机制负责异常兜底，共同构建一个对格式问题具有鲁棒性的分类推理管道。

</details>

**12. Few-Shot 示例应该如何选择？数量多少合适？**

<details>
<summary>💡 查看答案</summary>

Few-Shot 示例的质量对模型输出的影响往往大于数量。选择不当的示例不仅无法提升性能，还可能引入偏差或误导模型对任务边界的理解。

**选择原则：**

- **代表性**：示例应覆盖任务中最常见的输入模式，确保模型能从示例中归纳出适用于主流场景的规律。若任务存在若干典型子类型（如情感分析中的强烈正面、弱正面、中性等），每种子类型至少应有一个示例加以覆盖。

- **多样性**：避免选取语义或结构过于相似的示例，否则模型容易过拟合到示例的表面特征而非任务规律本身。多样性不仅指输入内容的差异，也包括输入长度、句式结构、领域词汇等维度的变化。

- **正确性**：示例中的输出必须完全准确，不存在任何歧义。错误的示例会以极高的权重误导模型的输出行为，且这种影响难以通过指令文字加以纠正。在生成示例时，应经过人工审核或自动化验证，确保答案的准确性。

- **难易结合**：示例集应同时包含直接明了的典型案例与具有一定难度的边界案例。简单示例帮助模型快速对齐任务格式，边界示例则传达任务在模糊情况下的处理规则，二者缺一不可。

- **与实际输入的分布匹配**：在生产环境中，示例应尽可能与实际用户输入的分布相近。若任务输入分布随时间变化，应定期更新示例集，避免示例与实际输入产生分布偏移，导致性能下降。在检索增强场景中，可根据当前输入动态检索最相近的历史示例，而非使用固定的静态示例集。

**数量建议：**

- **简单分类任务**：每个类别 1--2 个示例，总计 3--6 个。过多示例对简单任务的收益边际递减明显，且会无谓占用上下文窗口。
- **复杂推理任务**：3--8 个示例通常已足够。需注意，在某些推理任务中，示例数量超过一定阈值后性能反而下降，原因是过长的示例序列会稀释任务指令的注意力权重，建议通过实验确定最优数量。
- **代码生成**：1--3 个示例为宜。代码示例通常较长，过多示例会大量消耗上下文窗口，挤压实际任务输入的空间，得不偿失。

研究表明，Few-Shot 示例的**格式一致性**对输出稳定性的影响大于示例数量本身。所有示例的输入输出格式应严格统一，包括标点、换行、标签写法等细节，任何格式上的不一致都会增加模型输出的方差。

</details>

**13. Chain-of-Thought（CoT）Prompt 如何设计？适合哪些任务？**

<details>
<summary>💡 查看答案</summary>

Chain-of-Thought（CoT）通过在示例中展示完整的推理过程，引导模型在生成最终答案之前逐步分解问题。其核心机制是将"直接输出答案"转变为"先推理、再结论"，从而显著降低复杂任务中的错误率。

**基本结构示例：**

\begin{lstlisting}[style=promptstyle]
	问题：一列火车以60km/h行驶，需要2.5小时到达目的地。距离是多少？

	思考：
	- 已知速度 = 60 km/h
	- 已知时间 = 2.5 小时
	- 距离 = 速度 × 时间
	- 距离 = 60 × 2.5 = 150 km

	答案：150公里
\end{lstlisting}

**设计要点：**

CoT 的触发方式分为两类：**Few-Shot CoT** 通过在示例中展示推理链来隐式引导模型，适用于对推理格式有严格要求的场景；**Zero-Shot CoT** 则直接在提示词末尾添加"让我们一步一步思考"等触发语句，无需提供示例，适用于快速原型验证。在生产环境中，Few-Shot CoT 的稳定性通常优于 Zero-Shot CoT。

推理链的设计应遵循**最小化原则**：每一步只引入一个推断，避免在单步中进行多个跳跃。推理步骤的粒度应与任务复杂度匹配，过细的拆分（如对简单加法进行多步推导）会引入不必要的出错机会，过粗的拆分则失去 CoT 的意义。

对于需要精确控制输出格式的场景，可在推理链末尾设置固定的输出标记（如"`最终答案：`"），并在后处理阶段通过正则表达式提取标记后的内容，从而将自由格式的 CoT 输出转化为结构化的可解析结果。

**适合任务：**

- **数学推理与计算**：需要多步运算、单位换算或代数求解的问题，CoT 能显著降低中间步骤的计算错误率。
- **多步逻辑推理**：需要从前提逐步推导结论的任务，如演绎推理、因果分析、条件判断链等。
- **复杂问题分解**：面对结构复杂的综合性问题，CoT 能引导模型将其拆解为若干可独立处理的子问题，降低整体求解难度。
- **代码调试与分析**：需要逐行追踪执行逻辑、定位错误根因的场景，CoT 能有效模拟人工 Debug 的思维过程。

**不适合场景：**

- **简单事实问答**：对于直接检索型问题（如"法国的首都是哪里"），强制触发 CoT 不仅不会提升准确性，反而增加了在无关推理步骤中引入错误的概率。
- **对延迟敏感的场景**：CoT 会成倍增加输出 Token 数量，从而显著提升推理延迟与成本，不适用于实时性要求高的应用（如流式对话、高频 API 调用）。在此类场景中，可考虑将 CoT 推理结果缓存，或采用 CoT 蒸馏技术将推理能力迁移至更小的直接输出模型。

</details>

- 收集失败案例，定期迭代

</details>

**26. 什么是 Prompt Engineering？它的核心目标是什么？**

<details>
<summary>💡 查看答案</summary>

Prompt Engineering 是通过设计和优化输入给 LLM 的文本（prompt），来引导模型产出更准确、更相关、更符合预期的输出的工程实践。核心目标：\begin{enumerate}
- 最大化模型在特定任务上的输出质量；\item  提升输出的一致性和可靠性；\item  控制输出格式、风格和长度；\item  减少幻觉和有害输出；\item  在不修改模型参数的前提下，通过 prompt 实现对模型行为的精确控制。

</details>

**27. 一个完整的 Prompt 通常包含哪些组成部分？**

<details>
<summary>💡 查看答案</summary>

完整 prompt 的六个组成部分：\begin{enumerate}
- **角色设定（Role）**：定义 AI 的身份和专业背景（"你是一位资深数据分析师"）；\item  **任务指令（Instruction）**：明确需要完成的具体任务；\item  **上下文（Context）**：提供背景信息、约束条件、相关知识；\item  **示例（Examples）**：展示期望的输入输出格式（few-shot）；\item  **输入数据（Input）**：当前需要处理的具体内容；\item  **输出格式（Output Format）**：指定回答的格式、长度、结构要求。并非所有部分都必须，根据任务复杂度按需组合，简单任务只需指令+输入即可。

</details>

**28. Prompt 中的"示例"（examples）有什么作用？**

<details>
<summary>💡 查看答案</summary>

1. **格式示范**：展示期望的输入输出结构，消除格式歧义；\item  **任务引导**：通过示例让模型理解任务的性质和边界；\item  **质量标准设定**：示例的详细程度和风格成为模型输出的参考标杆；\item  **边界定义**：不同类型的示例帮助模型了解任务的处理范围；\item  **减少幻觉**：结构化示例（JSON 格式示例）显著降低输出格式错误；\item  **任务激活**：对于模型已有能力的任务，示例帮助激活对应能力，而不是教会新知识。

</details>

**29. Prompt 的长度和质量之间有什么关系？**

<details>
<summary>💡 查看答案</summary>

长度与质量不成正比。核心关系：\begin{enumerate}
- **内容密度**：有效信息才有价值，冗余说明不提升质量反而增加 token 成本；\item  **过短的问题**：任务描述过于简略，模型可能理解偏差；\item  **过长的问题**：关键指令被稀释，模型注意力分散，可能出现"指令遗忘"（instruction following 失效）；\item  **最优长度**：覆盖所有必要约束即可，不需要为"看起来更完整"而填充；\item  原则：每增加一句话，都应该有明确的目的（澄清、约束、示例）；没有目的的内容应删除。

</details>

**30. 什么是 Temperature 和 Top-p？它们如何影响输出？**

<details>
<summary>💡 查看答案</summary>

**Temperature（T）**：控制生成随机性的缩放系数。T→0：输出趋于确定性（贪心解码），适合代码/逻辑任务；T=1：标准分布；T>1：输出更随机多样，适合创意任务。**Top-p（Nucleus Sampling）**：动态选取累积概率达到 p 的最小 token 集，自适应候选数量。p=0.9 是常用值。两者的组合：\begin{enumerate}
- 代码生成：Temperature=0.2, Top-p=0.95（高确定性）；\item  创意写作：Temperature=0.8–1.0, Top-p=0.9（适度多样）；\item  事实问答：Temperature=0（最确定性输出）；\item  两者叠加使用时，先用 Top-p 缩小候选集，再用 Temperature 从候选集中采样。

</details>

**31. 如何通过 Prompt 减少幻觉？**

<details>
<summary>💡 查看答案</summary>

1. **RAG 结合**：在 prompt 中提供相关文档，要求模型只基于提供的内容回答；\item  **不知道选项**：明确告知"如果不确定，请说'我不知道'，不要猜测"；\item  **来源引用要求**：要求模型标注信息来源，无来源的内容不输出；\item  **降低 Temperature**：减少随机性，模型更倾向高概率（通常更确定）的输出；\item  **范围限定**：明确限制回答范围（"只根据以下文档回答"）；\item  **自我验证**：要求模型在给出答案前先说"我确信这一点，因为……"；\item  **简化问题**：将复杂问题拆分，减少每步的不确定性；\item  **Self-Consistency**：多次采样取一致的答案。

</details>

**32. 什么是上下文（Context）在 Prompt 中的作用？**

<details>
<summary>💡 查看答案</summary>

上下文是提供给模型的背景信息，帮助模型理解当前任务的具体场景。作用：\begin{enumerate}
- **消除歧义**：相同问题在不同上下文下有不同正确答案（"如何处理这个问题"——什么行业？什么场景？）；\item  **知识补充**：提供模型可能没有的专业知识、最新信息或私有数据；\item  **范围限定**：限制模型回答的范围（"基于以下合同条款……"）；\item  **个性化**：提供用户信息，使回答更有针对性（"用户是一位初学者……"）；\item  **减少幻觉**：将答案锚定在具体上下文，减少模型凭空推断；\item  注意：上下文过长会引发 lost in the middle 问题，关键信息应放在开头或结尾。

</details>

**33. 什么样的任务最适合 Prompt Engineering 而不是 Fine-tuning？**

<details>
<summary>💡 查看答案</summary>

最适合纯 Prompt Engineering 的任务：\begin{enumerate}
- **通用推理**：数学解题、逻辑分析、代码调试，模型已有能力，prompt 只需激活；\item  **格式转换**：结构化信息提取、翻译、摘要，通过示例即可精确指定格式；\item  **多任务场景**：产品需要同时支持多种任务，不能为每个任务单独微调；\item  **快速验证**：新功能的 PoC 阶段，需要快速测试可行性；\item  **频繁变化的任务**：业务规则经常更新，微调跟不上变化节奏；\item  **数据不足**：标注数据 <100 条，无法支撑微调；\item  **隐私限制**：数据不能发送到训练平台。

</details>

**34. 如何通过 Prompt 让模型输出结构化的 JSON 格式？**

<details>
<summary>💡 查看答案</summary>

1. **在指令中明确要求**："请以 JSON 格式输出，不要包含任何解释文字"；\item  **提供 JSON Schema 或示例**：在 prompt 中给出期望的 JSON 结构示例（含所有字段名和值类型）；\item  **使用 Structured Outputs API**：OpenAI/Anthropic 提供强制 JSON 输出的 API 参数（`response_format: json_object`），从根本上保证格式；\item  **加强约束**："只输出合法 JSON，不加 markdown 代码块包裹"；\item  **程序层兜底**：解析前剥离可能的 markdown 代码块（““json ... ““）；\item  **复杂 Schema**：对复杂嵌套结构，先让模型"思考"再输出 JSON（CoT + 结构化输出分离），减少格式错误。

</details>

**35. 什么是 Prompt Chaining（提示链）？它适合解决什么类型的问题？**

<details>
<summary>💡 查看答案</summary>

Prompt Chaining 是将复杂任务分解为多个步骤，每个步骤是一次独立的 LLM 调用，前一步的输出作为后一步的输入，形成处理流水线。适合的问题类型：\begin{enumerate}
- **超出单次 context window 限制的任务**（如长文档处理→分段摘要→整体摘要）；\item  **需要中间验证的任务**（生成→审查→修改）；\item  **不同步骤需要不同专业知识的任务**（先提取信息，再法律分析，再生成建议）；\item  **有条件分支的流程**（根据第一步判断结果决定后续路径）；\item  优势：每步可以独立优化和测试；便于追踪中间结果；错误更容易定位。代价：增加延迟和 API 调用次数。

</details>

**36. 什么是 Meta Prompting？如何让模型自己优化 Prompt？**

<details>
<summary>💡 查看答案</summary>

Meta Prompting 是让 LLM 自己生成、评估或优化 prompt，而不是人工手写。实现方式：\begin{enumerate}
- **Prompt 生成**：`"设计一个 prompt，让 LLM 完成以下任务：[任务描述]"`；\item  **Prompt 优化**：`"以下 prompt 在这些案例上失败了：[失败案例]。请分析原因并改进 prompt"`；\item  **Prompt 评估**：`"评估以下两个 prompt 的优劣，说明哪个更适合任务 X"`；\item  **迭代优化（OPRO）**：每轮将历史 prompt 版本和对应效果提供给优化器 LLM，让它生成更好的版本。优势：减少人工试错，加速迭代。局限：LLM 生成的 prompt 仍需人工验证；存在"AI 自说自话"的风险，需要用真实评估集验证效果。

</details>

**37. 如何设计 Prompt 使模型在不确定时主动说"我不知道"而不是胡乱编造？**

<details>
<summary>💡 查看答案</summary>

1. **明确授权**："如果你不确定答案，请直接说'我不确定'或'我没有这方面的信息'，不要猜测"；\item  **置信度要求**："只有在你有很高确信度时才给出具体答案，否则说明你的局限"；\item  **来源要求**："回答时说明信息来源，如果无法确认来源，请说明"；\item  **范围限定**："只基于以下文档回答，文档中没有的信息不要推断"；\item  **示例强化**：提供一个"模型正确说不知道"的示例，作为 few-shot；\item  **降低 Temperature**：减少随机性，模型更倾向于保守输出；\item  **避免追问陷阱**：prompt 中不要说"你必须给出答案"，这会逼模型编造。

</details>

**38. 如何通过 Prompt 设计减少模型的"过度道歉"和"过度谨慎"？**

<details>
<summary>💡 查看答案</summary>

1. **直接指令**："直接回答问题，不要以道歉开头"、"不要说'作为一个 AI……'"；\item  **角色设定**："你是一位直接、自信的专家，直接给出建议而不是询问更多信息"；\item  **格式约束**："回答格式：[直接答案] → [解释]，不需要前置礼貌语"；\item  **示例对比**：提供"过度道歉版本"标注为错误，"直接版本"标注为正确；\item  **温度调整**：适当提高 Temperature 减少过于保守的倾向；\item  **减少安全提示堆叠**：过多的安全约束会让模型"什么都不敢说"，精简 system prompt 中不必要的安全警告；\item  **任务驱动**：明确说明这是一个专业的业务工具，用户是专业人士，不需要基础免责声明。

</details>

**39. 什么是"思维链"在 Prompt 中的激活方式？"Let's think step by step"为什么有效？**

<details>
<summary>💡 查看答案</summary>

"Let's think step by step"（Kojima et al. 2022）是最简单的 Zero-shot CoT 触发词。有效原因：\begin{enumerate}
- **激活逐步推理模式**：这个短语在预训练数据中与高质量的逐步推理内容高度相关（教程、解题过程），使用它相当于告知模型"进入推理模式"；\item  **分配更多计算**：让模型生成更多中间 token，相当于增加了"思考时间"；\item  **错误可见化**：显式推理步骤使中间错误暴露，有机会在后续步骤中修正；\item  **格式先例**：这个短语成为 LLM 使用中的"元语言"，大量微调数据中都与高质量 CoT 关联。其他有效触发词："Let's work through this carefully"、"Think step by step"、"First, let's understand the problem"。

</details>

**40. 什么是"角色扮演"Prompt？它有哪些实际应用场景？**

<details>
<summary>💡 查看答案</summary>

角色扮演 Prompt 是让模型扮演特定角色（人物、系统、实体），以该角色的视角和能力参与对话。实际应用场景：\begin{enumerate}
- **客服助手**：扮演特定品牌的客服，使用品牌语气和知识库；\item  **教育辅导**：扮演耐心的老师，用适合学生水平的语言解释；\item  **代码审查员**：扮演严格的高级工程师，指出代码问题；\item  **面试模拟**：扮演面试官，提供模拟面试体验；\item  **文档助手**：扮演特定技术领域的专家，解答专业问题；\item  **创意写作**：扮演特定历史人物或虚拟角色参与创作；\item  **压力测试**：扮演挑剔的用户，对产品设计提出批评。注意：角色扮演不应用于绕过安全约束。

</details>

**41. 如何设计 Prompt 让模型给出置信度或不确定性说明？**

<details>
<summary>💡 查看答案</summary>

1. **显式要求置信度**："在每个回答的末尾，用[高/中/低]标注你的置信度"；\item  **百分比置信度**："如果你对某个陈述不确定，请标注 (置信度约 X%)"；\item  **不确定语言要求**："对不确定的陈述使用'可能'、'据我所知'等限定词"；\item  **来源追溯**："每个陈述说明其依据（训练知识/推断/不确定）"；\item  **结构化输出**：`{"answer": "...", "confidence": "high", "caveat": "..."}` ；\item  注意局限：LLM 的自我置信度评估不总是准确（过度自信问题普遍存在），应与外部验证结合使用；\item  **示例强化**：提供模型正确表达不确定性的示例，比纯文字要求更有效。

</details>

**42. 如何通过 Prompt 引导模型进行对比分析？**

<details>
<summary>💡 查看答案</summary>

1. **显式对比框架**："对比 X 和 Y，从以下维度分析：[维度1]、[维度2]、[维度3]"；\item  **表格格式**："用 Markdown 表格对比，行为维度，列为选项"；\item  **分别分析再综合**："先分别分析 X 的优缺点，再分析 Y 的优缺点，最后给出综合比较结论"；\item  **受众导向**："如果你是一个[角色]，在[场景]下，X 和 Y 哪个更适合"；\item  **中立性要求**："客观分析，不倾向任何一方，列出各自的优势和局限"；\item  **证据要求**："每个比较点都说明依据"；\item  示例辅助：提供对比格式的示例，引导一致的输出结构。

</details>

**43. 如何设计 Prompt 使模型能够处理边界情况（edge case）？**

<details>
<summary>💡 查看答案</summary>

1. **在 prompt 中枚举边界情况**："如果输入为空/格式错误/超出范围，请[处理方式]"；\item  **默认值定义**："当信息缺失时，使用[默认值]并说明"；\item  **边界示例**：在 few-shot 示例中包含 1–2 个边界情况的处理示例；\item  **明确拒绝条件**："如果输入不属于[合法范围]，拒绝处理并说明原因"；\item  **降级策略**："当无法完全满足要求时，尽力完成可以完成的部分，并说明哪部分无法完成"；\item  **程序层兜底**：对于关键边界（空输入、极长输入），在 prompt 之外用程序预处理，不完全依赖 LLM 处理边界。

</details>

**44. 如何为代码生成任务设计高质量的 Prompt？**

<details>
<summary>💡 查看答案</summary>

1. **语言和版本明确**："使用 Python 3.10，不使用任何第三方库"；\item  **功能描述精确**：清晰描述函数的输入、输出、边界条件；\item  **代码风格约束**："遵循 PEP8，添加 docstring，函数命名使用 snake_case"；\item  **示例驱动**：提供 1–2 个函数签名和使用示例（few-shot）；\item  **测试用例**："同时提供 3 个测试用例，覆盖正常情况和边界情况"；\item  **错误处理**："添加适当的 try-except，对无效输入抛出有意义的异常"；\item  **CoT 引导**："先描述实现思路，再给出代码"；\item  **避免过度工程**："使用最简洁的实现，不要过度设计"；\item  **分步生成**：复杂功能先生成框架，再逐步填充细节。

</details>

**45. 如何为文档摘要任务设计 Prompt？有哪些常见陷阱？**

<details>
<summary>💡 查看答案</summary>

设计要点：\begin{enumerate}
- **摘要类型**：抽取式 vs. 生成式；面向专家 vs. 面向大众；关键点列表 vs. 连贯段落；\item  **长度约束**："用不超过 200 字概括……"；\item  **内容重点**："重点关注[主题]，忽略[不相关内容]"；\item  **格式**："输出：[1–3 句话执行摘要] + [关键点列表]"；\item  **保真度要求**："只总结文档中明确提到的内容，不要添加推断"。常见陷阱：\item  模型过于简化，丢失关键信息→加"必须包含[关键字段]"；\item  模型添加文档中没有的内容（幻觉）→加"只基于文档内容"；\item  摘要太长（与文档差不多）→加字数限制；\item  长文档的中间部分被忽略（Lost in the Middle）→先分段摘要，再汇总摘要（Map-Reduce）；\item  技术文档被过度简化→指定目标受众是专业人士。

</details>

**46. 如何为数据抽取（信息提取）任务设计 Prompt？**

<details>
<summary>💡 查看答案</summary>

1. **明确抽取字段**：列出所有需要抽取的字段名称和数据类型；\item  **JSON 输出格式**：指定 schema，包括必填字段和可选字段；\item  **空值处理**："如果某字段在文本中未提及，输出 null"；\item  **多值处理**："如果某字段有多个值，输出数组"；\item  **示例驱动**：提供 2–3 个完整的抽取示例；\item  **保真要求**："只抽取文本中明确陈述的信息，不要推断或补全"；\item  **格式约束**："只输出 JSON，不要加任何解释"；\item  **模糊性处理**："如果文本表述模糊，在抽取字段旁加 confidence 字段（high/medium/low）"；\item  程序层：解析前清理可能的 markdown 包裹，用 Pydantic 做 schema 验证。

</details>

**47. 如何为分类任务设计 Prompt？标签描述应该如何写？**

<details>
<summary>💡 查看答案</summary>

**54. Agent 的 Prompt 应该如何设计？**

<details>
<summary>💡 查看答案</summary>

Agent Prompt 的核心目标是让模型清晰理解自身角色、可用能力与决策框架。设计时应涵盖以下维度：

#### 角色与目标定义
在 System Prompt 开头明确 Agent 的身份与任务边界，例如：
\begin{lstlisting}[style=promptstyle]
	你是一个代码审查 Agent，负责分析用户提交的代码并给出改进建议。
	你只处理编程相关问题，不回答其他类型的问题。
\end{lstlisting}

#### 可用工具的声明
以结构化方式列出所有可用工具的名称与简介（详细说明见工具 Prompt），使模型形成工具全局视图：
\begin{lstlisting}[style=promptstyle]
	## 可用工具
	- search_web: 搜索互联网上的最新信息
	- run_code: 在沙箱中执行 Python 代码
	- read_file: 读取指定路径的文件内容
\end{lstlisting}

#### 决策逻辑
明确告知模型如何在"思考、行动、观察"三个阶段之间切换，以及何时调用工具、何时直接回答：
\begin{lstlisting}[style=promptstyle]
	决策流程：
	1. 分析用户意图，判断是否需要调用工具
	2. 若需要工具，选择最匹配的一个并构造调用参数
	3. 获取工具返回结果后，评估是否需要继续调用或直接总结
	4. 若不需要工具，直接给出回答
\end{lstlisting}

#### 输出格式规范
为便于程序解析，应严格规定思考过程与行动指令的分隔格式，常见方案如 ReAct 格式：
\begin{lstlisting}[style=promptstyle]
	Thought: <你的思考过程>
	Action: <工具名称>
	Action Input: <JSON 格式的参数>
	Observation: <工具返回结果，由系统填入>
	... （可循环多次）
	Final Answer: <最终回答>
\end{lstlisting}

#### 约束与终止条件
明确最大迭代次数、禁止行为及终止信号，防止 Agent 陷入死循环：
\begin{lstlisting}[style=promptstyle]
	- 最多调用工具 5 次，超出后必须输出 Final Answer
	- 禁止伪造工具返回结果
	- 若无法完成任务，诚实说明原因而非猜测
\end{lstlisting}

</details>

**55. Tool 相关的 Prompt（工具说明）应该如何设计？**

<details>
<summary>💡 查看答案</summary>

工具说明 Prompt 是 Agent 正确调用工具的基础，每条工具描述应做到精准、完整、无歧义。

#### 标准描述模板
每个工具应包含以下字段：

\begin{lstlisting}[style=promptstyle]
	工具名称: search_web
	功能描述: 通过关键词在互联网上搜索信息，返回相关网页的摘要列表。
	适用于需要最新数据、事实核查或未知领域知识的场景。
	参数说明:
	- query (string, 必填): 搜索关键词，建议简洁精准，不超过 20 个词
	- max_results (int, 可选, 默认 5): 返回结果的最大数量，范围 1-10
	返回格式: JSON 数组，每项包含 title、url、snippet 字段
	使用示例:
	输入: {"query": "2024年全球AI芯片市场规模", "max_results": 3}
	输出: [{"title": "...", "url": "...", "snippet": "..."}]
	注意事项: 不适用于需要登录才能访问的内容；结果可能存在时效性问题
\end{lstlisting}

#### 避免语义重叠
当多个工具功能相近时，应在描述中明确区分使用场景：
\begin{lstlisting}[style=promptstyle]
	search_web: 用于搜索公开互联网信息（实时性强，覆盖广）
	search_docs: 用于搜索企业内部文档库（权威性高，限内部知识）
	// 并在每个工具中注明："如需搜索内部文档，请使用 search_docs"
\end{lstlisting}

#### 动态加载策略
当工具数量超过 10 个时，全量罗列会稀释注意力并增加误调用概率。建议：
- 按任务类型分组，仅在对应任务阶段注入相关工具描述
- 使用工具检索机制：先让模型描述需要的能力，再匹配并注入对应工具
- 将高频工具固定加载，低频工具按需追加

#### 参数约束的明确性
对参数的类型、范围、格式要求应尽量量化，避免模糊描述：
\begin{lstlisting}[style=promptstyle]
	// 差：path 参数是文件路径
	// 好：path 参数为绝对路径字符串，格式如 /home/user/file.txt，
	//     不支持相对路径和通配符
\end{lstlisting}

</details>

**56. Memory 相关的 Prompt 应该如何设计？**

<details>
<summary>💡 查看答案</summary>

Memory Prompt 的关键挑战是让模型正确区分"注入的历史记忆"与"当前对话"，并合理评估记忆的可信度。

#### 明确标注记忆来源
在注入记忆内容时，用清晰的标签将其与当前对话隔离：
\begin{lstlisting}[style=promptstyle]
	## 历史记忆（来自过去对话，供参考）
	[记忆片段 1 - 2024-11-03]
	用户曾提到其技术栈为 Python + FastAPI，偏好异步编程风格。

	[记忆片段 2 - 2024-10-15]
	用户的项目名称为 "DataPilot"，目标用户是数据分析师。

	## 当前对话
	用户: 帮我写一个数据导出接口
\end{lstlisting}

#### 标注时效性与相关性
对记忆内容附加元数据，引导模型判断其可靠程度：
\begin{lstlisting}[style=promptstyle]
	[记忆片段 - 距今 180 天，相关性：中]
	注意：此条记忆距今较久，若与当前对话存在冲突，
	请优先以用户当前表述为准。
\end{lstlisting}

#### 防止记忆污染的指令
在 System Prompt 中加入明确的使用规则：
\begin{lstlisting}[style=promptstyle]
	使用历史记忆的原则：
	1. 历史记忆仅作为背景参考，不作为事实断言
	2. 若当前对话中用户提供了与记忆矛盾的信息，以当前信息为准
	3. 使用记忆中的信息时，应向用户确认其是否仍然有效
	4. 不得将记忆中的内容直接作为"用户刚刚说的"来引用
\end{lstlisting}

#### 记忆分层设计
根据记忆类型采用不同的注入策略：
- **核心档案（长期有效）**：用户基本偏好、项目元信息，每次对话固定注入
- **情景记忆（中期有效）**：近期任务状态、未完成事项，按相关性筛选注入
- **工作记忆（短期有效）**：本次对话的上下文摘要，动态维护

</details>

**57. Planning 相关的 Prompt 应该如何设计？**

<details>
<summary>💡 查看答案</summary>

Planning Prompt 的目标是引导模型将复杂任务拆解为可执行的步骤序列，并在执行过程中保持对计划的追踪与修正。

#### 两阶段分离：先规划后执行
明确要求模型在行动前输出完整计划，避免边想边做导致的路径混乱：
\begin{lstlisting}[style=promptstyle]
	请按照以下两个阶段处理用户任务：

	【阶段一：制定计划】
	在执行任何操作前，先输出完整的执行计划，格式如下：
	## 执行计划
	- [ ] 步骤 1: <具体描述>
	- [ ] 步骤 2: <具体描述>
	- [ ] 步骤 3: <具体描述>
	预期最终结果: <描述>

	【阶段二：逐步执行】
	按计划依次执行，每步完成后更新状态。
\end{lstlisting}

#### 进度追踪机制
每个步骤执行后，要求模型显式对照计划检查进度：
\begin{lstlisting}[style=promptstyle]
	执行步骤 N 后，输出：
	## 进度更新
	- [x] 步骤 1: 已完成 - <简要结果>
	- [x] 步骤 2: 已完成 - <简要结果>
	- [ ] 步骤 3: 进行中
	剩余步骤: 2 步
\end{lstlisting}

#### 计划调整的触发与规范
允许模型在遇到意外情况时修改计划，但需说明原因：
\begin{lstlisting}[style=promptstyle]
	若执行过程中发现原计划不可行或需要调整，请：
	1. 明确说明需要调整的原因
	2. 输出修订后的计划（标注哪些步骤发生了变化）
	3. 从调整点继续执行，无需重新执行已完成的步骤
\end{lstlisting}

#### 计划粒度的控制
提示模型控制计划步骤的合理粒度，避免过于宏观或过于琐碎：
\begin{lstlisting}[style=promptstyle]
	制定计划时注意：
	- 每个步骤应对应一个可验证的具体产出
	- 步骤数量建议在 3-7 步之间
	- 避免将"思考"作为独立步骤，计划中只包含有实际产出的行动
\end{lstlisting}

</details>

**58. Reflection（反思）相关的 Prompt 应该如何设计？**

<details>
<summary>💡 查看答案</summary>

Reflection Prompt 的关键在于将反思聚焦于具体的执行结果，而非引导模型进行泛化的自我审视，从而避免无意义的循环。

#### 锚定具体对象
反思应始终针对具体的执行结果或错误信息，而非抽象地"检查自己"：
\begin{lstlisting}[style=promptstyle]
	// 差：请反思你的回答是否正确
	// 好：
	针对上述代码执行后出现的错误信息：
	"TypeError: unsupported operand type(s) for +: 'int' and 'str'"
	请分析：
	1. 错误发生在哪一行？原因是什么？
	2. 你在生成代码时做了哪个错误的假设？
	3. 修正方案是什么？
\end{lstlisting}

#### 明确反思维度与范围
给出结构化的反思框架，防止模型漫无目的地发散：
\begin{lstlisting}[style=promptstyle]
	请对本步骤的执行结果进行反思，只需回答以下问题：
	1. 预期产出是什么？（来自计划）
	2. 实际产出是什么？
	3. 两者是否一致？若不一致，差距在哪里？
	4. 差距的根本原因是什么？（限定在本步骤内，不追溯更早的步骤）
	5. 下一步如何调整？
\end{lstlisting}

#### 设置反思终止条件
避免模型在无问题时也进行无意义的反思，或陷入反思循环：
\begin{lstlisting}[style=promptstyle]
	反思规则：
	- 若执行结果符合预期，输出"✓ 本步骤达成预期，继续执行"后直接进入下一步
	- 若发现问题，完成一次有针对性的反思后即给出修正方案
	- 同一问题最多反思 2 次，若仍无法解决，升级为任务失败并说明原因
\end{lstlisting}

#### 区分反思层级
根据任务阶段设计不同深度的反思：
- **步骤级反思**：每步执行后快速检查（是否达成该步骤的小目标）
- **阶段级反思**：完成一个子任务后检查（是否推进了整体计划）
- **任务级反思**：任务结束后进行全局总结（最终结果是否满足用户需求）

</details>

**59. Evaluation（评估）相关的 Prompt 应该如何设计？**

<details>
<summary>💡 查看答案</summary>

Evaluation Prompt 的目标是将主观的质量判断转化为可量化、可复现的结构化评分，减少评估结果的随机波动。

#### 明确评分维度与权重
预先定义评分维度，避免模型自行决定评估标准：
\begin{lstlisting}[style=promptstyle]
	请从以下 4 个维度对输出内容进行评估，每项满分 10 分：

	1. 准确性（权重 40%）：内容是否事实正确、逻辑自洽，无明显错误
	2. 完整性（权重 30%）：是否覆盖了用户需求的所有要点，无遗漏
	3. 格式合规性（权重 20%）：是否符合指定的输出格式要求
	4. 简洁性（权重 10%）：是否避免了不必要的冗余内容
\end{lstlisting}

#### 提供评分标准锚点
为每个维度提供不同分数段的描述，减少边界模糊：
\begin{lstlisting}[style=promptstyle]
	准确性评分标准：
	- 9-10分: 完全正确，无任何事实或逻辑错误
	- 7-8分:  基本正确，存在 1-2 处小瑕疵但不影响结论
	- 5-6分:  部分正确，存在明显错误但核心逻辑成立
	- 3-4分:  错误较多，核心结论存疑
	- 1-2分:  严重错误，结论与事实相悖
\end{lstlisting}

#### 要求结构化输出
强制要求分项输出，避免仅给出一个总分：
\begin{lstlisting}[style=promptstyle]
	请按以下格式输出评估结果：

	## 评估报告
	| 维度     | 得分 | 权重  | 加权分 | 主要依据（一句话）         |
	|----------|------|-------|--------|--------------------------|
	| 准确性   | X/10 | 40%   | X.X    | <具体说明>               |
	| 完整性   | X/10 | 30%   | X.X    | <具体说明>               |
	| 格式合规 | X/10 | 20%   | X.X    | <具体说明>               |
	| 简洁性   | X/10 | 10%   | X.X    | <具体说明>               |

	**加权总分**: X.X / 10
	**总体结论**: 通过 / 需要修改 / 不通过
	**最需改进的一点**: <具体建议>
\end{lstlisting}

#### 分离评估与生成
将评估任务与内容生成任务分配给独立的调用，避免模型"既当运动员又当裁判"导致的自我美化偏差。在实现上，可使用独立的 Evaluator Agent，输入为原始任务要求与待评估内容，输出为结构化评分报告，其 System Prompt 中不包含任何生成内容的上下文。
