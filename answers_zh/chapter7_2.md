# 7.2 文档处理与分块策略 — 题目与答案
> [⬅ 返回目录](../README_ZH.md) · 第 7 章：RAG（检索增强生成） · 共 21 题

**1. 什么是文档分块（Chunking）？为什么不能直接把整篇文档作为一个单元？**

<details>
<summary>💡 查看答案</summary>

Chunking 是将文档切分为更小的片段（chunk）的过程。不能用整篇文档的原因：
1. **超出上下文窗口**：长文档超过 LLM 的 context window，无法传入；
2. **检索精度差**：整篇文档的 embedding 是所有内容的平均表示，语义太模糊，无法精确匹配具体问题；
3. **token 浪费**：传入整篇文档时大部分内容与当前问题无关，浪费 token 并引入噪声；
4. **降低相关性评分**：在相似度计算中，包含大量无关内容的长文档得分会被摊薄。
合理的 chunk 大小使得每个 chunk 语义集中，与特定问题的匹配精度更高。

</details>

**2. 文本数据分块有哪些不同的方法？**

<details>
<summary>💡 查看答案</summary>

以下是几种不同的文本数据分块方法：
- **基于句子的解析**：将文本文档分解为完整的句子块。实现简单且处理成本低，但可能无法捕捉完整的思想上下文。
- **固定大小解析（带重叠）**：根据固定数量的字符或标记将文档分解为块，并在块之间设置一定的重叠。可以捕捉跨越多个句子的语义信息，但需要选择合适的块大小和重叠量。
- **自定义代码**：使用自定义代码根据文档结构中的模式创建块。适用于具有已知或可推断结构的文档。
- **大型语言模型增强**：利用大型语言模型创建块，例如生成图像的文本表示或表格的摘要。适用于非文本数据，但处理成本较高。
- **文档布局分析**：使用库和服务提取文档的结构和文本。为内容提供了更好的语义信息。

</details>

**3. 固定大小分块和语义分块各有什么优缺点？**

<details>
<summary>💡 查看答案</summary>

**固定大小分块**：按字符数或 token 数切分，实现简单、速度快。优点：无需理解文档结构，适合任何格式。缺点：可能截断句子中间或段落中间，破坏语义完整性；相邻 chunk 的上下文连贯性差。

**语义分块**：按语义边界切分（段落、标题、句子），保留语义完整性。优点：每个 chunk 内容完整，检索质量更高。缺点：需要理解文档结构（难以通用化），chunk 大小不一致（难以预测 token 消耗）。

实践建议：优先语义分块（段落级），辅以大小上限约束，超过上限时再做固定大小二次切分。

</details>

**4. 什么是递归字符分块（Recursive Character Splitting）？**

<details>
<summary>💡 查看答案</summary>

递归字符分块（LangChain 的 RecursiveCharacterTextSplitter）：按优先级从高到低尝试不同分隔符切分，只有当切分后的片段仍超过大小上限时，才使用更细粒度的分隔符。分隔符优先级（通常）：
1. 双换行（段落边界）→
2. 单换行 →
3. 句号/问号/叹号 →
4. 逗号 →
5. 空格 →
6. 单字符。
优点：尽量在语义边界处切分，保留语义完整性；自动适应不同文档格式；只在必要时使用更细粒度的分割，避免过度切碎。是一种兼顾实用性和语义完整性的通用分块方案。

</details>

**5. 在构建知识库时，如何选择合适的切块大小和重叠长度？背后有哪些权衡？**

<details>
<summary>💡 查看答案</summary>

文本切块是 RAG 流程中最关键且最需要经验的步骤之一，它直接影响检索的召回率和精确度。

**如何选择合适的切块大小（Chunk Size）**：
1. **依据嵌入模型的能力**：嵌入模型有其输入的最大 Token 数限制。切块大小应小于这个限制，且很多嵌入模型在处理中等长度（如 256–512 个 token）的文本时效果最好。
2. **依据数据的类型和结构**：结构化文档（如论文、报告）可以采用语义切块，即按段落、标题来切分；非结构化长文本更多依赖固定长度切块；代码应该按函数或类来切块，而不是简单地按行数。
3. **依据预期的查询类型**：如果用户的问题通常很具体，需要精确定位，那么较小的切块更有效；如果用户的问题很宽泛，需要综合多个段落的信息，那么较大的切块会更好。

**如何选择合适的重叠长度（Overlap）**：重叠的作用是防止语义信息在切块边界被硬生生地切断。一个常见的经验法则是设置重叠长度为切块大小的 10%–20%。例如，对于 1024 个 token 的切块，可以设置 128 或 256 个 token 的重叠。重叠并非越大越好，过大的重叠会增加数据冗余和存储成本。

**背后的权衡（Trade-offs）**：
- 大块的优点：包含更丰富的上下文；缺点：噪声增加、检索精度下降、成本更高、容易触发 Lost in the Middle 问题。
- 小块的优点：信息密度高，与具体问题的相关性强；缺点：上下文不足，需要检索并拼接多个小块；容易造成语义割裂。

实践中，通常会从一个合理的基线（如 `chunk_size=512`，`overlap=64`）开始，通过评估检索质量，针对具体的文档类型和查询场景进行迭代优化。

</details>

**6. 文档分块大小（chunk size）如何影响检索效果？太大或太小分别有什么问题？**

<details>
<summary>💡 查看答案</summary>

**太小（<100 token）**：
1. 语义不完整，单个 chunk 无法表达完整思想；
2. Embedding 向量语义太局部，相似度计算不稳定；
3. 索引体积大，检索成本高；
4. 传给 LLM 的信息碎片化，需要更多 chunk 才能覆盖答案。

**太大（>1000 token）**：
1. 语义分散，一个 chunk 涵盖多个主题，检索时被"摊薄"；
2. 精确问题的相关 chunk 包含大量不相关内容；
3. 传入 LLM 消耗更多 token。

经验值：通用文本 512–1024 token；问答型文档（FAQ）200–500 token；代码文件按函数/类切分。最佳 chunk size 依赖具体文档类型和问题模式，需实验确定。

</details>

**7. 为什么 Chunk（文本切片）不能切得太细？**

<details>
<summary>💡 查看答案</summary>

切得过细会破坏语义完整性，导致检索到的片段缺乏上下文，模型难以理解其含义；同时过细的切片数量庞大，增加索引和检索成本。详细分析如下：

1. **语义完整性破坏**：一个完整的语义单元（如一个论点及其支撑句）被拆分为多个 chunk 后，每个 chunk 单独看都语义不完整，LLM 接收到这样的片段难以理解其真实含义，更难据此生成准确答案。
2. **Embedding 质量下降**：Embedding 模型对过短文本（如 1--2 句话）的语义表达能力有限，向量无法充分捕捉语义信息，导致相似度计算不稳定，容易出现"语义相似但内容无关"的错误匹配。
3. **缺乏上下文造成歧义**：同一句话在不同上下文中含义可能截然不同。切得过细后，chunk 失去了上下文依托，检索时可能将词义相近但语境完全不同的 chunk 混淆。
4. **索引膨胀**：切片越细，chunk 数量越多，向量数据库的存储成本和 ANN 检索的计算成本线性增长，同时增加了检索到噪声 chunk 的概率。
5. **需要传入更多 chunk**：由于每个 chunk 信息量不足，需要传给 LLM 更多 chunk 才能覆盖完整答案，导致 token 消耗增加，且更容易触发 Lost in the Middle 问题。
6. **经验规则**：一般建议最小 chunk 不低于 100 token，通用场景推荐 256--512 token，保证每个 chunk 至少包含一个完整的语义段落。

</details>

**8. Chunk Size 应该如何选择？**

<details>
<summary>💡 查看答案</summary>

需要在"语义完整性"和"检索精度"之间权衡：过大会导致一个片段包含多个主题、降低检索精度；过小会丢失上下文。通常根据文档结构（段落/章节）自然切分，并结合实验调优，常见范围在几百 Token 量级。具体选择策略：

1. **参考文档结构**：
    - 有清晰段落结构的文档（学术论文、产品文档）→ 按段落切分，自然段落通常在 200--500 token；
    - 长篇叙述性文档 → 按章节切分，每章可能 500--1500 token；
    - FAQ 类文档 → 按问答对切分，通常 100--300 token。
2. **参考 Embedding 模型限制**：Embedding 模型有最大输入长度（如 BERT 系列通常 512 token，BGE-M3 支持 8192 token），chunk 大小不应超过模型最优处理长度，否则超出部分会被截断或语义质量下降。
3. **参考问题类型**：精确事实型问题（"X 的价格是多少"）→ 小 chunk（100--300 token），提升精确匹配度；综合分析型问题（"请总结 X 的优缺点"）→ 大 chunk（500--1000 token），保留更多上下文。
4. **实验优先**：chunk size 是超参数，最佳值取决于具体文档类型和 query 分布。建议先从 512 token 开始，在评估集上对比 256/512/1024 三个候选值的 Hit Rate@k，选择最优值。
5. **动态分块作为进阶方案**：不同类型文档使用不同 chunk size（代码按函数切，论文按段落切，FAQ 按问答对切），比统一固定大小效果更好。

</details>

**9. 什么是重叠分块（Overlap Chunking）？重叠大小如何设置？**

<details>
<summary>💡 查看答案</summary>

重叠分块：相邻 chunk 之间有一定数量的重叠 token，防止关键信息恰好落在两个 chunk 的边界处而被截断。工作原理：chunk_1 覆盖 token 1–500，chunk_2 覆盖 token 401–900（重叠 100 token），如此确保跨边界的连续信息至少在一个完整 chunk 中出现。重叠大小设置建议：
1. 通常为 chunk 大小的 10–20%（如 chunk=512 token，overlap=50–100 token）；
2. 重叠太小：边界信息仍可能丢失；
3. 重叠太大：索引体积增大，检索到的重复内容增多；
4. 不同文档类型调整：结构化文档（代码）重叠可小，叙述性文档（论文）重叠应大些。

</details>

**10. Chunk 之间设置 Overlap（重叠）有必要吗？**

<details>
<summary>💡 查看答案</summary>

有一定必要，可以避免关键信息恰好被切分点截断；但 Overlap 过大会增加索引冗余和存储成本，需要适度设置。详细分析如下：

**Overlap 的必要性**：
1. **防止关键信息被截断**：如果没有 Overlap，一段重要的论述恰好横跨两个 chunk 的分界线，被分成了前半句和后半句，任何一个 chunk 都无法完整表达这段信息，导致检索时无论命中哪个 chunk，LLM 得到的都是不完整的内容；
2. **保留上下文连贯性**：相邻 chunk 之间有重叠，使得每个 chunk 自身更具语义完整性，减少了因为切分点位置而导致的语义割裂；
3. **提升边界信息的检索概率**：恰好在边界处的关键信息会同时出现在两个 chunk 中，任意一个 chunk 被检索到都能提供该信息。

**Overlap 的代价**：
1. **索引膨胀**：Overlap 越大，chunk 数量越多，向量数据库存储成本和检索延迟线性增加；
2. **重复内容**：top-k 检索结果中可能出现内容高度重复的 chunk（来自相邻 chunk 的重叠部分），需要去重处理；
3. **Embedding 计算成本增加**：重叠内容需要被重复 Embedding，增加索引构建时间。

**建议**：通常设置 Overlap 为 chunk size 的 10%--20%（如 chunk=512 token，overlap=50--100 token）；对于结构化文档（代码、表格），边界清晰，Overlap 可以设置为 0 或很小值；对于叙述性文档（论文、报告），Overlap 建议适当增大。

</details>

**11. 什么是 Parent-Child Chunk 策略？它解决了什么问题？**

<details>
<summary>💡 查看答案</summary>

Parent-Child Chunk：将文档切分为两个粒度——小 chunk（Child，约 100–200 token）用于精确检索，大 chunk（Parent，约 500–1000 token）用于传给 LLM 生成。流程：
1. 检索时用小 chunk 做相似度匹配（小 chunk 语义集中，匹配精度高）；
2. 检索到小 chunk 后，找到它对应的父 chunk，将父 chunk 传给 LLM；
3. LLM 获得更完整的上下文信息，生成质量更高。
解决的问题：小 chunk 检索精度高，但上下文信息不完整；大 chunk 上下文完整，但检索精度差（语义太分散）；Parent-Child 结合两者优点，实现精确检索 + 完整上下文。

![双粒度分块 (Parent-Child Chunking) 检索机制](https://img.pricenode.uk/llm_interview_questions/zhongw/chapter7/fig_parent_child_chunking.png)

</details>

**12. 如何针对 PDF、HTML、Markdown 等不同格式设计分块策略？**

<details>
<summary>💡 查看答案</summary>

**PDF**：
1. 用 PyMuPDF/pdfplumber 提取文本时保留页码和段落结构；
2. 按段落切分，保留页码作为元数据；
3. 表格单独处理（转为 Markdown 表格格式）；
4. 注意多栏 PDF 的文本提取顺序问题。

**HTML**：
1. 解析 DOM 结构，按语义标签切分（`<p>`、`<section>`、`<article>`）；
2. 剥离导航栏、广告等无关内容；
3. 保留标题层级作为上下文前缀。

**Markdown**：
1. 按标题层级（`#`、`##`）切分，形成层级化的 chunk；
2. 代码块保持完整，不在代码块中间切分；
3. 表格保持完整。

通用原则：利用文档自身的结构信息做语义切分，优于盲目按字符数切分。

</details>

**13. 如何处理包含表格、代码块、图片的文档的分块？**

<details>
<summary>💡 查看答案</summary>

**表格**：
1. 保持表格完整性，不在表格内部切分；
2. 将表格转为 Markdown 格式或 CSV，便于 LLM 理解；
3. 为表格添加标题和描述作为上下文前缀；
4. 复杂表格可用 LLM 生成文字摘要代替原始表格。

**代码块**：
1. 按函数/类/方法为单位切分，不在代码块内部切分；
2. 保留语言标识和函数签名；
3. 为每个代码块添加所属文件路径、类名等元数据。

**图片**：
1. 无法直接向量化（文本 Embedding 模型无法处理图片）；
2. 方案一：用多模态模型（GPT-4V、LLaVA）生成图片描述，对描述做 Embedding；
3. 方案二：提取图片标题/说明文字作为代理；
4. 方案三：使用多模态 Embedding 模型（CLIP）。

</details>

**14. 如何为分块添加元数据（metadata）？元数据有哪些常见用途？**

<details>
<summary>💡 查看答案</summary>

**元数据添加方式**：在向量数据库存储 chunk 时，同时存储结构化的元数据字段，与向量关联。**常见元数据字段**：文档来源（URL/文件路径）、文档标题、作者、创建/更新时间、所在页码、所属章节/标题层级、文档类型、语言、版本号、权限标签。

**用途**：
1. **元数据过滤**：检索时附加过滤条件（"只检索 2024 年之后的文档"、"只检索 marketing 类型"），提升精度；
2. **答案溯源**：输出答案时引用原始文档来源；
3. **权限控制**：根据用户权限过滤可访问的 chunk；
4. **时效性管理**：按更新时间过滤，排除过期内容；
5. **调试分析**：追踪哪些文档被频繁检索。

</details>

**15. 如何处理跨页或跨段落的语义连续性问题？**

<details>
<summary>💡 查看答案</summary>

1. **重叠分块**：相邻 chunk 之间保留 50–100 token 的重叠，确保跨边界信息在某个完整 chunk 中出现；
2. **Parent-Child 策略**：小 chunk 检索后传入更大的父 chunk，自然包含了跨段落的上下文；
3. **标题前缀注入**：每个 chunk 前缀所属章节/标题信息，让独立的 chunk 也有文档结构上下文；
4. **跨页拼接**：PDF 处理时先检测跨页段落（下一页开头没有新段落标识），拼接后再分块；
5. **层级摘要**：对长文档生成多级摘要（段落→章节→全文），不同粒度的摘要也加入索引，用于需要跨段落理解的问题。

</details>

**16. 文档预处理（清洗、去噪）对 RAG 效果有多大影响？**

<details>
<summary>💡 查看答案</summary>

影响非常大，垃圾进垃圾出（GIGO）。预处理的主要步骤和影响：
1. **去除无关内容**（页眉页脚、广告、导航栏）：减少噪声 chunk，提升检索精度；
2. **编码问题修复**（乱码、特殊字符）：防止 Embedding 模型对异常字符编码失败；
3. **格式标准化**（统一标点、去除多余空白）：使同类文档风格一致；
4. **重复内容去除**（文档库中相同或高度相似的内容）：减少索引冗余，防止同一内容被多次检索；
5. **PII 去除**（个人信息）：合规要求，防止知识库暴露敏感信息。
经验表明，高质量预处理可使 RAG 的检索精度提升 15–30%。

</details>

**17. 检索组件需要哪些预处理步骤？**

<details>
<summary>💡 查看答案</summary>

1. **文档加载与格式解析**：从各类数据源（PDF、Word、HTML、Markdown、数据库）加载文档，提取纯文本内容，处理特殊格式（表格转 Markdown、图片生成描述文字），保留文档结构信息（标题层级、段落边界）。
2. **文本清洗**：去除无关内容（页眉页脚、广告导航栏、重复的免责声明）；修复编码问题（乱码、特殊字符）；标准化文本格式（统一标点符号、去除多余空白行、规范化数字格式）；检测并去除重复文档（MinHash LSH 相似度去重）。
3. **分块（Chunking）**：按照适合当前文档类型的策略将长文档切分为合适大小的 chunk（通常 200--1000 token），保留语义完整性，设置适当的 Overlap，记录每个 chunk 的来源信息（文档 ID、页码、章节）。
4. **元数据提取与标注**：为每个 chunk 标注结构化元数据（来源 URL/文件路径、文档标题、创建/更新时间、作者、文档类型、语言、权限标签等），这些元数据后续用于过滤检索和答案溯源。
5. **向量化（Embedding）**：调用 Embedding 模型将每个 chunk 转换为高维向量，注意使用与在线检索阶段相同的模型和参数；批量处理以提升效率（batch_size=128--256）；对超长 chunk 做截断或分段处理。
6. **索引构建与写入**：将向量和对应的元数据、原始文本写入向量数据库，构建 ANN 索引（HNSW、IVF 等），对于混合检索还需同步构建 BM25 倒排索引。
7. **质量验证**：对索引结果做抽样验证（随机抽取 chunk 检索，确认能找回自身），并在评估集上做端到端质量检测，确保预处理流程没有引入错误。

</details>

**18. 如何对超长文档（如几百页的报告）进行分层索引？**

<details>
<summary>💡 查看答案</summary>

1. **层级摘要索引**：为文档生成多层摘要（章节摘要→全文摘要），摘要和原始 chunk 都加入索引；根据问题复杂度选择层级（宏观问题用摘要层，细节问题用原始 chunk 层）；
2. **稀疏索引+密集检索**：先用文档级摘要做粗粒度过滤，缩小候选文档范围，再在候选文档内做精细检索；
3. **目录驱动分块**：利用文档目录结构，按章节边界切分，每章作为独立的检索单元，章节内再做细粒度分块；
4. **滑动窗口检索**：对超长文档维护多粒度的分块版本（小/中/大），根据问题类型选择合适粒度；
5. **图索引**：抽取文档中的实体和关系构建知识图谱，支持跨章节的关联检索。

</details>

**19. 如何设计一个自适应分块策略，根据文档类型动态调整分块大小？**

<details>
<summary>💡 查看答案</summary>

1. **文档类型分类**：先对文档做类型分类（FAQ、学术论文、代码、新闻、法律文档等），可用规则或分类器；
2. **类型-策略映射**：为每种文档类型预配置最优分块策略：FAQ → 按问答对切分；学术论文 → 按章节切分（摘要/引言/方法/结论独立）；代码 → 按函数/类切分；法律文档 → 按条款切分；
3. **动态大小调整**：同类型文档根据密度动态调整（信息密度高的段落 chunk 更小）；
4. **评估反馈**：收集检索效果数据，对检索质量差的文档类型调整策略；
5. **元数据记录**：chunk 的分块策略记录在元数据中，便于追溯和调试。

</details>

**20. 如何评估分块策略的质量？有哪些指标？**

<details>
<summary>💡 查看答案</summary>

1. **检索精度指标**：在标注好"正确答案所在 chunk"的测试集上，计算 top-k 中包含正确 chunk 的比例（Hit Rate@k）；
2. **MRR（Mean Reciprocal Rank）**：正确 chunk 在检索结果中排名的倒数均值，衡量精确排名质量；
3. **端到端答案质量**：用固定的 LLM 生成阶段，对比不同分块策略下的最终答案质量（RAGAS 评分）；
4. **上下文精确率（Context Precision）**：传给 LLM 的 chunk 中，真正有用的比例；
5. **Chunk 大小分布**：过大/过小 chunk 的比例，理想分布应集中在目标大小范围内；
6. **A/B 测试**：在生产环境对比两种分块策略，直接比较用户满意度。

</details>

**21. 如何处理多语言文档的分块？**

<details>
<summary>💡 查看答案</summary>

1. **语言检测**：预处理时检测每个文档的语言，记录为元数据；
2. **分块策略适配**：不同语言可能需要不同的分隔符（中文无明显词边界，需用句号/换行分割；英文可按词边界）；
3. **多语言 Embedding 模型**：使用支持多语言的 Embedding 模型（mE5、multilingual-e5-large），确保不同语言的 chunk 在同一向量空间可比；
4. **语言过滤**：检索时可按语言过滤，或允许跨语言检索（中文 query 检索英文文档）；
5. **翻译策略**：如果文档量大、语言多样，可考虑在索引前将所有文档翻译为统一语言；但翻译会引入误差，需权衡。
