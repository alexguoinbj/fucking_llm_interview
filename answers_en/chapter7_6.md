# 7.6 Query Optimization (Rewriting, HyDE, Decomposition) — Questions & Answers

**1. What Is Query Rewriting? What Are Common Rewriting Strategies?**

<details>
<summary>💡 Show Answer</summary>

Query Rewriting: Rewriting or expanding the user's original query before retrieval to enhance retrieval effectiveness. Common strategies:
1. **Intent Clarification**: Rewrite ambiguous queries into clearer descriptions ("What is it?" $\rightarrow$ "What is a list comprehension in Python?");
2. **Synonym Expansion**: Generate synonymous expressions to increase retrieval coverage ("cost" $\rightarrow$ "cost, price, fee structure");
3. **Context Supplementation**: In multi-turn dialogues, integrate historical context into the current query ("What are its advantages?" $\rightarrow$ "What are the advantages of Python compared to Java?");
4. **Query Decomposition**: Decompose complex questions into multiple simple sub-questions;
5. **Step-Back Prompting**: Abstract specific questions into higher-level general questions.

</details>

**2. Is Query Rewrite Truly Valuable?**

<details>
<summary>💡 Show Answer</summary>

Yes, it is valuable. Especially for colloquial, anaphoric (unclear coreference), or incomplete user queries, the rewritten query can match expressions in the knowledge base more accurately, enhancing retrieval recall quality. Specifically:

**Core Value of Query Rewrite**:
1. **Bridging the Expression Gap**: User-input queries are often colloquial and elliptical (e.g., "How to use it?"), whereas documents in the knowledge base are in formal declarative language. Rewriting converts user expressions into forms closer to document style, significantly boosting semantic match quality.
2. **Resolving Anaphora in Multi-Turn Dialogues**: In multi-turn conversations, pronouns like "it" or "this" cannot be retrieved independently. Rewriting resolves pronouns back to concrete entities (e.g., "What is the price of GPT-4?"), allowing the retrieval system to understand the current query independently.
3. **Expanding Query Coverage**: By generating synonymous rewrites or multiple query variants (Multi-Query), retrieval can be performed from different angles, reducing missed retrievals caused by a single phrasing.
4. **Clarifying Ambiguous Intent**: User questions sometimes have ambiguous intent. The rewriting step allows an LLM to classify and clarify query intent before searching for specific intents.

**Applicable Scenarios and Limitations**:
- For queries that are clearly phrased and professionally articulated, the benefit of rewriting is limited, while introducing an additional LLM call increases latency and cost;
- Rewriting quality depends on LLM capability; low-quality rewrites may derail an originally correct retrieval direction;
- In practice, it is recommended to conditionally trigger rewriting after query quality evaluation, rather than applying it indiscriminately to all queries.

Overall Evaluation: In RAG systems targeting general users (non-experts), Query Rewrite typically brings a 5%--15% improvement in retrieval quality, yielding a high ROI.

</details>

**3. What Is HyDE (Hypothetical Document Embeddings)? What Is Its Core Idea?**

<details>
<summary>💡 Show Answer</summary>

HyDE (Gao et al. 2022): First ask an LLM to generate a "hypothetical answer document" based on the user query, and then embed this hypothetical document for retrieval, rather than embedding the query directly.

Core idea: Resolve the query-document embedding space misalignment problem—user queries are typically interrogative, whereas knowledge base documents are declarative, so they may be distant from each other in vector space. The language style of hypothetical documents is closer to real documents, making their embeddings closer to target document vectors and achieving higher retrieval recall.

Disadvantages:
1. An extra LLM call is required for each retrieval, increasing latency and cost;
2. If the hypothetical document generated by the LLM is of poor quality, retrieval effectiveness will deteriorate.
Suitable for knowledge-intensive Q&A scenarios.

**4. What Is Query Decomposition? In What Scenarios Is It Used?**

<details>
<summary>💡 Show Answer</summary>

Query Decomposition: Decomposing a complex, multi-part query into multiple simple sub-queries, retrieving results for each separately, and then merging the results. Scenarios of use:
1. **Multi-Hop Questions**: Answers require multi-step associations ("In which city is the alma mater of Company A's CEO?" $\rightarrow$ first query who the CEO is, then query their educational background);
2. **Comparative Questions**: Need to retrieve multiple objects separately ("What is the difference between X and Y?" $\rightarrow$ retrieve information for X and Y separately);
3. **Aggregative Questions**: Answers require summarizing multiple dimensions ("Major AI advances in 2024" $\rightarrow$ retrieve advances across various fields separately);
4. **Sequential / Temporal Questions**: Involve information across multiple time points.
Implementation: Have an LLM decompose the query into N sub-queries first, retrieve in parallel or sequentially, and finally synthesize the results to generate an answer.

</details>

**5. What Is Step-Back Prompting? How Does It Improve Retrieval Performance?**

<details>
<summary>💡 Show Answer</summary>

Step-Back Prompting: First prompt the LLM to "abstract" a specific question into a more general, high-level question, then use this high-level question for retrieval while also retrieving with the original question, merging both sets of results.

Example: "How to configure CPU limits in Kubernetes" $\rightarrow$ abstracted to "Principles and best practices of Kubernetes resource management."

Reasons for performance improvement:
1. High-level questions can retrieve documents containing principles and background knowledge, which are helpful for answering specific questions;
2. Retrieval with the original question ensures specific details;
3. Combining both routes provides the LLM with both background knowledge and specific details, leading to higher generation quality.
Suitable for deep Q&A scenarios in specialized domains.

</details>

**6. What Is RAG Fusion? What Is Its Core Mechanism?**

<details>
<summary>💡 Show Answer</summary>

RAG Fusion: Rewriting a single query into multiple related queries (typically 4--5), performing separate retrievals, merging multi-path results using RRF (Reciprocal Rank Fusion), and finally generating the answer using all results. Core mechanism:
1. **Multi-Query Generation**: Use an LLM to generate variants of the original query (synonymous rewrites, different angles, varying levels of detail);
2. **Parallel Retrieval**: Retrieve independently for each query variant;
3. **RRF Fusion**: Merge and rank all retrieved results using the RRF algorithm: `score = Σ 1/(k + rank_i)`;
4. **Comprehensive Generation**: Generate the answer using the merged retrieval results (with better diversity).
Advantages: Covers multiple semantic variants of the original query, improving recall; reduces retrieval failures caused by single-query phrasing.

</details>

**7. What Is FLARE (Forward-Looking Active Retrieval)? How Does It Differ from Standard RAG?**

<details>
<summary>💡 Show Answer</summary>

FLARE (Jiang et al. 2023): An active retrieval method that allows an LLM to actively decide when retrieval is needed and what to retrieve during the answer generation process. Differences from standard RAG:
1. **Different Retrieval Timing**: Standard RAG performs retrieval once prior to generation; FLARE dynamically decides during the generation process whether additional retrieval is needed;
2. **Dynamic Retrieval Content**: FLARE predicts what information is needed next based on already generated content, using predicted sentences as retrieval queries;
3. **Multi-Round Retrieval**: FLARE may trigger multiple retrievals until the LLM has sufficient confidence in the current generation;
4. **Suitable Scenarios**: Complex Q&A requiring multi-hop reasoning and synthesizing multiple knowledge points; standard RAG is suitable for simple single-retrieval Q&A.

**8. What is Iterative Retrieval? In Which Scenarios Does It Yield Significant Benefits?**

<details>
<summary>💡 Show Answer</summary>

Iterative retrieval: Multi-round retrieval where the query for each round is dynamically adjusted based on the retrieval results of the previous round and the partially generated answer, gradually converging to the most relevant documents. Workflow:
1. The initial query performs the first round of retrieval to obtain preliminary information;
2. Based on the first-round results, the LLM identifies information gaps and generates a new retrieval query;
3. The second round of retrieval supplements the missing information;
4. Repeat until sufficient information is acquired or the maximum number of rounds is reached.

Scenarios with significant benefits: Multi-hop reasoning problems (requiring the chaining of multiple knowledge points); open-ended questions (where required information cannot be predetermined); exploratory queries (where the answer scope is unclear and needs to be narrowed down step-by-step); uneven knowledge base coverage (where certain knowledge can only be retrieved using specific phrasing).

</details>

**9. How Does RAG Handle Complex Multi-Hop Queries?**

<details>
<summary>💡 Show Answer</summary>

RAG performs iterative retrieval to handle multi-hop queries: it first retrieves initial relevant data, then uses this data to further refine queries for subsequent retrieval. This iterative process enables it to synthesize and merge information from multiple sources. Specific multi-hop processing strategies:

1. **Query Decomposition**: Use an LLM to decompose a complex multi-hop question into several simple sub-questions, retrieve independently for each, and finally synthesize the retrieval results of all sub-questions into the LLM for final reasoning. For example: "Who is the mayor of the city where Tesla's CEO's alma mater is located?" can be decomposed into: ① Who is Tesla's CEO? $\rightarrow$ ② Where is his alma mater? $\rightarrow$ ③ Who is the current mayor of that city.
2. **Iterative Retrieval**: After obtaining preliminary information in the first round of retrieval, the LLM analyzes this information and identifies "what is still missing," dynamically generating a second-round retrieval query to supplement the missing knowledge chain. This loops until the information is sufficient or the maximum number of rounds (typically 2--4 rounds) is reached.
3. **ReAct Reasoning Framework**: Integrate the Thought (Reasoning)--Action (Retrieval)--Observation (Observation Result) loop into RAG. The LLM explicitly specifies what information is needed in Thought, executes retrieval in Action, and digests results and decides the next step in Observation, forming a transparent multi-hop reasoning chain.
4. **Knowledge Graph Assistance (GraphRAG)**: Utilize the entity-relation network of knowledge graphs to directly connect multi-hop entity relationships via graph traversal. This is the most natural method for solving multi-hop problems---the "A$\rightarrow$B$\rightarrow$C" relationship chain that vector retrieval fails to find can be directly traversed via graph traversal.
5. **Challenges and Considerations**: Multi-hop errors compound (an error in the first hop leads to a directional bias for the entire reasoning chain); iterative retrieval increases latency (each retrieval adds approximately 200--500ms); maximum iteration rounds must be set reasonably to prevent infinite loops.

</details>

**10. How Does RAG Support Multi-Hop Retrieval?**

<details>
<summary>💡 Show Answer</summary>

For questions that require synthesizing multiple information sources to answer, an iterative retrieval strategy can be adopted: retrieve preliminary information first, generate a new retrieval query based on the preliminary results, and gradually approach the complete answer. Specific implementation schemes:

1. **Query Decomposition**: Decompose complex multi-hop questions into several simple sub-questions, retrieve for each separately, and finally merge the retrieval results of all sub-questions and feed them into the LLM for synthesized reasoning. For example: "In which city is the alma mater of Company A's CEO located?" $\rightarrow$ Sub-question 1: "Who is the CEO of Company A?" $\rightarrow$ Sub-question 2: "Which university did [:CEO Name] attend?"
2. **Iterative Retrieval**: The first round of retrieval obtains preliminary information. Based on this preliminary information, the LLM identifies information gaps and generates a new query. The second round of retrieval supplements the missing information. This loops until the LLM determines that the information is sufficient or the maximum round limit (typically 2--4 rounds) is reached.
3. **ReAct Paradigm**: Integrate multi-hop retrieval into the Agent's Thought-Action-Observation loop. The LLM plans the next retrieval content in Thought, executes retrieval in Action, and analyzes results and decides whether to continue retrieval in Observation.
4. **Graph Retrieval (GraphRAG)**: Utilize the graph structure of knowledge graphs to directly find cross-entity association information through multi-hop traversal of entity relations (e.g., A $\rightarrow$ B $\rightarrow$ C), which is the most natural implementation method for multi-hop retrieval.
5. **Challenges**: Errors in multi-hop retrieval compound (a first-hop error causes directional deviation in the second hop), and latency increases linearly with the number of hops; complex questions require proper control over the maximum number of hops to avoid over-retrieval.

</details>

**11. How Does RAG Handle Entity Disambiguation?**

<details>
<summary>💡 Show Answer</summary>

Entity Disambiguation refers to the process of accurately identifying the entity intended by the user's query when an entity name in the query has multiple meanings (for example, "Apple" can refer to Apple Inc. or the fruit). Processing methods in RAG:

1. **Context-Aware Retrieval**: Vector retrieval itself possesses a certain degree of context disambiguation capability---when a query contains sufficient context information (e.g., "market capitalization of Apple Inc."), the Embedding model can distinguish different meanings and retrieve the corresponding correct documents. However, for short queries with sparse context, this capability is limited.
2. **Named Entity Recognition (NER) + Entity Linking**: During the query preprocessing stage, an NER model is used to identify entities in the query, and entity linking maps entity names to unique entity IDs in a knowledge graph (e.g., "Apple" $\rightarrow$ Apple Inc. [Q312]). Subsequent retrieval uses IDs instead of names to completely eliminate ambiguity.
3. **Knowledge Graph-Assisted Disambiguation**: In a knowledge graph, homonymous entities have different node IDs and associated properties. By querying the graph and combining context to select the most appropriate entity node, vector retrieval can then be expanded using that node as an anchor.
4. **Multi-Interpretation Parallel Retrieval**: For highly ambiguous entities, multiple possible interpretations are retrieved in parallel. All results are passed to the LLM, which determines the most likely user intent based on the full query and retrieved content, and explicitly states the chosen interpretation in the answer.
5. **Disambiguation in Multi-Turn Conversations**: In multi-turn conversations, historical conversation context is utilized to determine the referent of ambiguous entities in the current query (e.g., if iPhone was mentioned in the previous turn, "Apple" in the current turn most likely refers to Apple Inc.), injecting context information into the retrieval process to improve disambiguation accuracy.
6. **Proactive Clarification**: When the system cannot determine the entity's meaning and different interpretations significantly impact the answer, it proactively asks the user for clarification ("Does the 'Apple' you mentioned refer to Apple Inc. or Apple products?"), avoiding retrieving based on false assumptions and providing misleading answers.
